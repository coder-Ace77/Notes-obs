### Analysis and where it will broke at rest

This analysis is about where our db will breakdown at rest. We are not considering queries and updates here. 

First thing is MVCC bloat. Given the posts table will have likes_count and since it updates around 30 times on avg it means 30 versions of each row will get formed. With 40 billion posts averaging 30 likes each, that is 1.2 trillion dead row versions, or roughly 300 TB of garbage churned through a table whose live size is only 10 TB. This is the concrete reason counters are moved out of the database into Redis: it is not that the update is slow, it is that the update produces garbage the storage layer then has to clean up forever.

Not only this we will have to remove these rows as well. Vacuum works in phases: it scans the heap to collect the identifiers of dead rows, then scans **each index in full** to remove pointers to them, then returns to the heap to free the space.

For example, in our system the `likes` table is 62 TB of heap plus 74 TB of indexes. A single vacuum pass that has dead rows to clean must read essentially all 136 TB, because the index-cleaning phase is a full scan of every index. At a sustained 1 GB/s that is roughly 38 hours for one pass. If the table receives writes faster than vacuum can complete a cycle, dead tuples accumulate permanently and the table grows without bound.

Every write transaction consumes a 32-bit transaction ID (XID), and the counter is global to a cluster rather than per table. Because the counter is finite, PostgreSQL must periodically rewrite old rows to mark them as "frozen," meaning permanently visible and no longer dependent on the counter. If freezing falls behind far enough, PostgreSQL refuses to issue new XIDs and stops accepting writes entirely.

For example, in our system a single shard sustaining 1,000 write transactions per second burns through the default `autovacuum_freeze_max_age` of 200 million XIDs in about 2.3 days. That means every shard must complete a freeze pass over all of its unfrozen data roughly twice a week, indefinitely, on top of ordinary vacuum work. The failure mode is not gradual: the database performs normally right up to the point where it has about 3 million XIDs remaining, and then writes stop.

The Write-Ahead Log (WAL) is the durability mechanism: every change is written to a sequential log before the data pages themselves are written. Not only this indexes makeup has to go over too many entries backup etc will take too much. 

Another thing is that postgres extensively keeps pages in memory for faster access and its the whole reason why postgres is fast. `shared_buffers` is PostgreSQL's own page cache, typically configured at around 25% of system memory, with the operating system page cache handling the rest. The working set is the portion of data actually accessed frequently. 

For example, in our system a shard on an instance with 512 GB of RAM might allocate 128 GB to `shared_buffers` against 1.6 TB of data, caching under 10% of it. That is fine for `posts`, where recent content is read far more often than old content, and terrible for the `follows` and `likes` indexes, which are accessed by user ID in a pattern that has no locality at all. Every follow-graph lookup becomes a random storage read.

The through-line in all of this: at 320 TB the constraint is almost never how much data fits, it is how much _maintenance work per unit time_ a single PostgreSQL cluster can complete. Vacuum, freezing, WAL replay, index rebuilds, and `ANALYZE` all scale with data volume, while the machine's ability to perform them does not. Sharding is not primarily about splitting storage or spreading queries; it is about keeping each unit small enough that its housekeeping finishes.

## Sharding 

A single database server runs on a single physical (or virtual) machine. That machine has a fixed amount of CPU, a fixed amount of RAM, and a fixed amount of disk space. No matter how well you write your queries or how much you optimize your indexes, there comes a point where the data itself is simply too large to fit comfortably on one machine. This we have seen through an example. Buying a bigger single machine called **vertical scaling** has diminishing returns and a hard ceiling; at some point, there simply is no bigger machine you can buy. The alternative is **horizontal scaling**: instead of one huge machine, use many smaller, ordinary machines, and split the data across all of them. This splitting is exactly what Partitioning and Sharding are about.

 - **Partitioning** is the general concept of splitting a large dataset into smaller, more manageable pieces, called partitions. This can happen even within a _single_ database server for example, splitting one huge `orders` table into twelve smaller partitions, one per month, all still living on the same machine.
 - **Sharding** specifically means splitting data across **multiple separate machines (or database instances)**, where each machine, called a **shard**, holds only a portion of the total data and operates largely independently of the others.

In short: every shard is a partition, but not every partition is a shard. Sharding is partitioning taken one step further distributing the pieces across physically separate servers, not just separate tables on the same server.

### Vertical vs horizontal partitioning

**Vertical partitioning** splits a table by its _columns_. Imagine a `users` table with frequently accessed columns like `username` and `email`, alongside rarely accessed, heavy columns like `bio` and `profile_picture_binary`. You can split this into two tables one with the frequently accessed, lightweight columns, and one with the rarely accessed, heavy columns so that common queries (like a login check) never have to load the heavy, rarely-needed data at all.

```
-- Before: one wide table
-- users(id, username, email, password_hash, bio, profile_picture_binary)

-- After vertical partitioning: two focused tables
-- users_core(id, username, email, password_hash)
-- users_profile(id, bio, profile_picture_binary)
```

**Horizontal partitioning** splits a table by its _rows_. Instead of splitting which columns live where, you split which _rows_ live where, based on some value in each row. This is the far more common approach when the real problem is "there are simply too many rows," and it is also the foundation for almost every sharding strategy that follows.

```
-- users_shard_1: user_id 1 to 1,000,000
-- users_shard_2: user_id 1,000,001 to 2,000,000
-- users_shard_3: user_id 2,000,001 to 3,000,000
```

The best answer for horizontal sharding is `consistent hashing`. 

### How many shards?

Sharding means splitting one logical database across many independent database servers, each holding a subset of the data. There is no single formula for how many you need. Instead, several independent constraints each impose a _minimum_, and the answer is whichever minimum is largest.

Constraint 1 -  Disk size

The hard limit on how much data one cluster can hold. Aurora PostgreSQL grows automatically up to 128 TiB per cluster volume; RDS for PostgreSQL supports up to 64 TiB per instance.

```
320 TB ÷ 128 TiB (Aurora) = 2.4  →  3 shards
320 TB ÷  64 TiB (RDS)    = 4.8  →  5 shards
```

Constraint 2 - Write throughput

How many write transactions one primary can commit per second. Each write must be flushed to the write-ahead log before the transaction is acknowledged, and that flush is the bottleneck. A well-tuned primary on modern hardware sustains roughly **15,000 write transactions per second**; you can exceed this with batching and relaxed durability, but 15,000 is a safe planning number.

```
82,600 peak writes/s ÷ 15,000 per shard = 5.5  →  6 shards
```

Constraints 3 - Read throughput

How many queries one instance can execute per second. A point lookup by primary key on cached data costs roughly 50–100 microseconds of CPU, plus parsing, planning, and network protocol overhead. On a 64-vCPU instance behind a connection pooler, a realistic sustained figure for real application queries is **100,000 to 200,000 per second**.

```
2,600,000 peak reads/s ÷ 150,000 per shard = 17.3  →  18 shards
```

Constraint 4 - Memory

The working set is the portion of data actually accessed frequently. Social traffic follows a Zipfian distribution: roughly the newest 10% of content receives about 90% of reads. If the working set fits in memory, reads cost about 100 nanoseconds; if it does not, they cost about 200 microseconds a 2,000× difference. So this constraint is really asking: how many machines' worth of RAM do we need to hold the hot data?

```
hot set        = 320 TB × 10%                    =  32 TB
usable cache   = 512 GB instance, ~400 GB usable for data
shards         = 32 TB ÷ 400 GB                  =  80 shards
```

With this we have 10% of data in memory we get for the largest of the machines we will get `512Gb` RAM and thus 80 shards. 

Other factors are `RTO` The recovery time objective (RTO) is how long you are willing to have a shard unavailable after it fails. With calculation if we want our RTO to be 1hr we need aroudn 100 shards.

##### Why memcached rather than Redis here

**Redis** is single-threaded per node and offers rich data structures, durability options, and replication. **Memcached** is multi-threaded, offers only opaque key-value storage, and has no persistence at all.

For example, in our system the object cache needs to serve 4.9 million lookups per second and stores nothing but flat serialised blobs. Memcached's multi-threading turns a 32-vCPU node into 32 workers rather than one, and none of Redis's structures or durability would be used. The feed cache made the opposite trade, because `LPUSH`/`LTRIM` is exactly a Redis data structure and the feed lists are worth keeping across a restart.

### Query problems

With sizing settled, these are the failure modes that appear once real queries arrive.
#### The N+1 query problem

An **N+1 query** is when an application fetches N items with one query, then issues one additional query per item to fill in related data producing N+1 round trips where two or three would do.

For example, in our system rendering a feed screen naively looks like: fetch 25 post IDs, then fetch each post row, then fetch each author's name and avatar, then check whether the viewer liked each post. That is 1 + 25 + 25 + 25 = **76 queries per screen**.

At 104,000 feed loads per second, that is **7.9 million queries per second** for a screen that logically needs three. Each query also carries network round-trip time  typically 0.5 ms within a datacenter  so the screen takes 38 ms in round trips alone, even against an infinitely fast database.

The fix is batching: one query returning 25 posts via `WHERE post_id = ANY($1)`, one returning the distinct authors, one returning which posts the viewer liked. Three queries, three round trips.

#### Cross-shard joins do not exist

A **join** combines rows from two tables by matching a column value. PostgreSQL can only join tables inside the same instance. Once data is spread across 32 independent clusters, a join across them is not something the database can perform at all.

For example, in our system `posts` is sharded by `user_id`, so a user's posts live together. But a feed shows posts from the 200 accounts someone follows, and those are scattered across all 32 shards. "Recent posts from the people I follow, joined with author details, ordered by time" cannot be expressed as SQL. No single database can see the inputs.

The application must join for itself: read the follow list, group followed IDs by shard, issue 32 parallel queries, merge and sort in memory. This is **scatter-gather**, and it has two costs.

First, latency becomes the _slowest_ of 32 queries rather than the average. If each shard responds in 5 ms typically but one in a hundred takes 100 ms, then `1 - 0.99³²` = **27%** of scatter-gathers wait 100 ms. This is tail latency amplification, and it worsens with shard count at 200 shards it would be 87%.

#### Fanout-on-read versus fanout-on-write

**Fanout** is distributing content to the people who should see it. There are two moments to do it.

**Fanout-on-read** computes the feed when the user opens the app the scatter-gather above. Cheap writes, brutal reads.

**Fanout-on-write** computes feeds when a post is created, inserting a reference into a precomputed list for every follower. Reading becomes one lookup of an already-built list.

For example, in our system fanout-on-write turns the read path into one Redis list read per feed load — 104,000 per second against an in-memory store, trivial. The write path becomes 200 list insertions per post: at 2,500 posts per second, **500,000 feed insertions per second**. Redis handles that comfortably.

This is also what produces the 50% feed-cache absorption in Section 5. Both approaches work for the average case. Neither works for the tail.

#### The celebrity problem

A **power-law distribution** means a few items account for most activity. Social graphs have this shape: most accounts have a few hundred followers, a handful have hundreds of millions.

For example, in our system an account with 400 million followers posts once. Under fanout-on-write that single insert triggers **400 million feed insertions**. Even with a dedicated fanout tier sustaining 1,000,000 insertions per second on top of the 500,000 per second ordinary posts already consume the fanout takes about **7 minutes**, during which followers see the post at wildly different times. Ten such accounts posting in the same minute produce 4 billion pending insertions and the queue backs up for hours.

Under fanout-on-read, the same account's posts are read by 400 million people, so one shard receives an enormous share of all read traffic while its 31 peers idle. This is a **hot shard**, and adding shards does not fix it, because the imbalance is inherent to the data rather than to the partitioning.

The resolution is a **hybrid**: fanout-on-write below a follower threshold, fanout-on-read above it. Reading a feed means fetching the precomputed list, separately fetching recent posts from the few celebrities you follow, and merging by timestamp. Celebrity posts are cached once and served to everyone, so 400 million reads become one database read plus 400 million cache hits.

Sharding solves a real scaling problem, but it introduces problems that simply do not exist in a single-database system, and it is worth naming them plainly:

- **Cross-shard queries and joins become expensive.** A query that used to be one simple `JOIN` across two tables might now require querying multiple shards separately and combining the results in application code, because the two pieces of data you need happen to live on different machines.
- **Cross-shard transactions lose strong consistency**, for exactly the same reason the Saga pattern exists — there is no single database transaction spanning multiple shards, so multi-shard writes need the same compensating-transaction thinking we covered in Phase 4.
- **Choosing the shard key is a one-way door.** Pick a shard key that does not match your actual access patterns, and you end up with the exact hot-spot or scatter-query problems described above — and changing your shard key after the fact usually means physically moving enormous amounts of live data.
