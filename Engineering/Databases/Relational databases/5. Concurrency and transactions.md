Concurrency arises when multiple users or applications try to access the database at the same time.  When concurrent transactions take place without concurrency control following can happen - 

- **Dirty Reads:** Transaction A reads data that Transaction B changed but hasn't committed yet. If Transaction B rolls back, Transaction A is left with "fake" data.
- **Non-Repeatable Reads:** Transaction A reads a row. Transaction B updates that same row and commits. If Transaction A reads the row again, it sees a different value. 
- **Phantom Reads:** Transaction A queries a range of rows (e.g., "all users in NY"). Transaction B inserts a new user in NY. If Transaction A runs the same query again, a new "phantom" row appears.
- **Lost Updates:** Two transactions read the same value, modify it, and write it back. The last one to write simply overwrites the first one's changes without knowing it.

### ACID properties

One of PostgreSQL's greatest strengths is its strict adherence to ACID (Atomicity, Consistency, Isolation, and Durability) properties. If you've used databases like MongoDB or Cassandra, you're familiar with eventual consistency or relaxed transaction guarantees which are common trade-offs in NoSQL databases. PostgreSQL takes a different approach – it ensures that your data always follows all defined rules and constraints (like foreign keys, unique constraints, and custom checks), and that all transactions complete fully or not at all, even if it means sacrificing some performance.

#### Atomicity

```sql
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE account_id = 'savings';
  UPDATE accounts SET balance = balance + 100 WHERE account_id = 'checking';
COMMIT;
```

Atomicity guarantees that either both operations succeed or neither does. If the system crashes after deducting from savings but before adding to checking, PostgreSQL will roll back the entire transaction. Your money never disappears into thin air.

#### Consistency

Consistency ensures that transactions can only bring the database from one valid state to another.

```sql
CREATE TABLE accounts (
    account_id TEXT PRIMARY KEY,
    balance DECIMAL CHECK (balance >= 0),
    owner_id INTEGER REFERENCES users(id)
);
```

If a transaction would make your balance negative, PostgreSQL will reject the entire transaction.

Confusingly, consistency in ACID has a slightly different meaning than consistency in CAP Theorem. In ACID, consistency means that the database always follows all defined rules and constraints. In the CAP Theorem, consistency means that the database always returns the correct result, even if it means sacrificing availability or partition tolerance.

#### Isolation

_Isolation_ means that each transaction runs **as if it were the only transaction** executing on the system — even though many might actually run at the same time.

It prevents **interference** between concurrent transactions, so one transaction’s intermediate (uncommitted) data isn’t visible to another.

Without isolation, two transactions running together could **read or modify each other’s partial results**, leading to problems like:

- Incorrect totals
- Missing updates
- Inconsistent reads

In reality there are isolation levels which define when multiple transations run concurrently how much others are allowed to see each other transation.

When multiple transactions run **concurrently**, the database needs to decide how much they are allowed to “see” or “interfere” with each other.

**Higher isolation = safer, but slower.**
**Lower isolation = faster, but may cause inconsistent results.**

#### Serializable

Transactions are executed **as if they were completely sequential** — one after another.  
The database ensures no other transaction affects your results, even indirectly.

Prevents: Dirty reads, non-repeatable reads, phantom reads. It is like doing each transaction one by one and this is achieved by **locks** or **MVCC snapshots**.

#### Durability

Once PostgreSQL says a transaction is committed, that data is guaranteed to survive a crash, an OS restart, or a power failure even if the actual table data on disk hasn't been updated yet. This guarantee is built almost entirely on **Write-Ahead Logging (WAL)**.

##### The core idea: log before data

The rule that gives WAL its name is simple: **no change to a data page may be written to disk until the log record describing that change has been written (and flushed) to disk first.**

This is powerful because the WAL file is:
- **Append-only** – purely sequential writes, which are cheap even on spinning disks and don't require random I/O.
- **Small per-record** – you're logging "add 100 to balance", not rewriting an 8KB data page.
- **The single source of truth for recovery** – if the server dies, the data pages on disk can be stale/inconsistent, but as long as the WAL up to the commit record made it to disk, the database can reconstruct the correct state.

This is why WAL makes commits fast: PostgreSQL doesn't need to fsync the actual table/index pages on every commit (those are cached in shared buffers and flushed lazily later by the background writer/checkpointer). It only needs to fsync a small, sequential log record.

##### Step by step: what happens on `COMMIT`

```sql
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE account_id = 'savings';
  UPDATE accounts SET balance = balance + 100 WHERE account_id = 'checking';
COMMIT;
```

1. **In-memory change:** Each `UPDATE` modifies the data page in **shared buffers** (RAM), not on disk yet.
2. **WAL record generated:** For each change, a WAL record is generated describing it (e.g. "on page X, at offset Y, set new tuple version = ...") and appended to the **WAL buffer** in memory. Each record gets a monotonically increasing **LSN (Log Sequence Number)**. The data page itself is stamped with the LSN of the WAL record that last modified it.
3. **Commit record:** When `COMMIT` runs, a special WAL "commit" record is written, marking the transaction as committed.
4. **WAL flush (the durability moment):** The WAL buffer up to and including that commit record  is written to the OS and `fsync`'d to the physical WAL segment file on disk. **This fsync is the actual moment durability is achieved.** Only after this fsync returns does PostgreSQL send the "COMMIT successful" acknowledgment back to the client.
5. **Data pages flushed later, lazily:** The actual modified table pages (still just sitting in shared buffers) are **not** flushed to disk right now. That happens later, asynchronously, driven by the background writer or the next **checkpoint**. This decoupling — fast sequential log flush now, slow random data-page flush later — is the whole performance trick behind WAL.

##### Checkpoints and the REDO pointer

A **checkpoint** is the process that periodically flushes all dirty (modified) buffers to their actual data files on disk, and then records a **REDO pointer** (an LSN) in the control file (`pg_control`). This pointer means: *"everything before this LSN is guaranteed to already be safely on disk in the data files — you never need to replay WAL from before this point."*

This is what bounds how much WAL needs to be replayed after a crash and lets old WAL segments eventually be recycled/archived.

##### Recovery: what happens after a crash, scenario by scenario

When PostgreSQL restarts after an unclean shutdown, it enters **crash recovery** and replays WAL starting from the last checkpoint's REDO pointer. WAL replay is **idempotent** — reapplying an already-applied change is a no-op (checked via the LSN stamped on each page vs. the LSN of the WAL record), so recovery can safely resume even if it crashes again midway through recovery itself.

| Scenario | What happened | What survives / recovery behavior |
|---|---|---|
| **Crash after WAL commit record fsync'd, before data pages flushed** (the normal, common case) | Client got "COMMIT OK". Data pages in shared buffers were lost (RAM), but the WAL record made it to disk. | On restart, PostgreSQL replays WAL from the last checkpoint forward, **redoing** every change including this one, reconstructing the exact data pages in memory/disk as they should be. Transaction is still committed — no data loss. |
| **Crash before the WAL commit record is fsync'd** (e.g. mid-transaction, or fsync hadn't happened yet) | Client either got an error, or never got an acknowledgment at all. | On replay, no commit record exists for this transaction in WAL, so it's treated as if it never happened. Any partial WAL records for it are simply ignored/not replayed as committed — effectively an automatic rollback. This is fine because the client was never told it succeeded. |
| **Crash mid-write of a data page itself (a "torn page")** | Data pages are 8KB but disk sectors/OS writes can be smaller, so a crash mid-write can leave a page half-old, half-new garbage. | PostgreSQL protects against this with **full_page_writes**: the *first* time a page is modified after a checkpoint, the WAL record contains the **entire page image**, not just a delta. On recovery, if a page looks torn, replaying that full-page WAL record simply overwrites it wholesale, discarding the torn version rather than trying to patch it. |
| **Crash during a checkpoint** | The checkpoint hadn't finished flushing all dirty buffers before the crash. | Harmless — the *old* REDO pointer (from the previous, completed checkpoint) is still in `pg_control` until the new checkpoint fully completes. Recovery just replays a bit more WAL than strictly necessary, starting from that older, safe REDO pointer. |
| **"Crash" after commit was acknowledged but WAL wasn't actually fsync'd** — only possible if `synchronous_commit = off` (async commit) | PostgreSQL intentionally acknowledges commit to the client *before* fsync, to trade durability for latency. There's a small window (default up to `wal_writer_delay`, ~200ms) where committed data only exists in the WAL buffer in RAM. | If the crash happens inside that window, that transaction's commit record never reached disk, so on recovery it's **lost** — the client was told "committed" but after restart it's gone. This is the explicit, documented trade-off of async commit; `synchronous_commit = on` (the default) never has this gap. |
| **OS/hardware crash where fsync "lied"** (e.g. disk write-back cache reports success before data is physically persisted) | Some disks/RAID controllers acknowledge `fsync` before data is actually on stable storage, to look fast in benchmarks. | This is outside what any database's WAL logic can protect against — the durability guarantee assumes fsync is honest. Mitigated at the hardware layer via battery-backed/capacitor-backed write caches, or disabling volatile write caching. |
| **Replica crash / replication lag** (streaming replication) | WAL records are shipped to standby servers and replayed there the same way as local crash recovery. | If the primary fails, a replica that had received (and fsync'd, if using synchronous replication) the commit's WAL record can be promoted with no data loss. With asynchronous replication, a replica lagging behind may be missing the most recent commits — same trade-off as async local commit, just across the network. |

##### A note on rollback / "undo" — why there's no separate undo log

Unlike engines such as MySQL/InnoDB (which maintain a separate undo log to physically reverse uncommitted changes), PostgreSQL doesn't need an undo phase during recovery. Because of **MVCC** (see below), an uncommitted change is just a new row version tagged with the transaction's ID — nothing else has been overwritten. Visibility is decided by checking transaction status (via `pg_xact`/clog): if the transaction never got a commit record, its row versions are simply invisible to everyone and are later cleaned up by `VACUUM`. So "rollback" during recovery is really just *absence of a commit record*, not an active undo step.

### Concurrency control mechanisms 

#### Pessimistic locking

Pessimistic locking means locking the resource before hand before using it. LOcking requries multiple entries to be maanged by the database and thus is slow. In case of no contention it should not be used. 

**Shared Locks (S-Locks):** Used for reading. Multiple transactions can hold a shared lock on the same resource.

**Exclusive Locks (X-Locks):** Used for writing. Only one transaction can hold this lock, and no one else can even read the data until the lock is released.

**Two-Phase Locking (2PL):** A protocol ensuring that a transaction acquires all its locks in a "growing phase" and releases them in a "shrinking phase," preventing consistency issues.


During phase 1, the transaction is allowed to acquire as many locks as it needs.
- It can request **Shared Locks (S)** for reading.
- It can request **Exclusive Locks (X)** for writing.
- It can "upgrade" a lock (turn a Read lock into a Write lock).
- **Constraint:** It cannot release _any_ locks during this phase.


This phase 2 (shrink) begins the moment the transaction releases its first lock.
- The transaction can release locks it no longer needs.
- It can "downgrade" a lock (turn a Write lock into a Read lock).
- **Constraint:** It is strictly forbidden from acquiring any new locks or upgrading existing ones.

This is done to ensure serializability. However this can introduce dead locks. `Req1 picks AB and Req2 picks BA`. Solution is do a global ordering of resources so only both req will then have to take the requests in same order. This breaks circular wait.  

**Best for:** Environments with **high contention** (many users fighting for the same rows) where the cost of rolling back a transaction is much higher than the cost of waiting for a lock.

#### Optimisatic locking 

This technique is helpfull when the conflicts are rare. The user assumes that since conflicts are rare it first tries to do the update but before commiting it checks if the resource has changed if yes then it reverts the transaction. 

**The Three Phases:**

1. **Read Phase:** The transaction reads the data and its current version number (e.g., Version 5). It performs all calculations in a local "private workspace."
2. **Validation Phase:** When the user hits "Save," the database checks: _"Is the version in the database still Version 5?"_
3. **Write Phase:** * If **Yes**: The data is updated and the version is bumped to 6.
    - If **No**: Someone else changed it while you were working. Your transaction is **aborted**, and you have to start over.

**Best for:** **Low-contention** environments (like a CMS where two people rarely edit the same article at the exact same time). It is highly "performant" because there is zero locking overhead.

#### Multiversion concurrency control

It is technically a form of optimistic control, but it is so robust that it is treated as its own category. Its mantra is: **"Readers should never block writers, and writers should never block readers."**

**How it works:** Instead of overwriting a row, the database creates a **new version** of that row. 
- Every row has a "Valid From" and "Valid To" timestamp (or Transaction ID).
- When you start a transaction, the DB gives you a **Snapshot**. You only see versions of data that were committed _before_ your start time.

**The Workflow:**
1. User A starts reading a row (Version 1).
2. **User B** starts an update on that same row. Instead of locking User A out, User B creates **Version 2**.
3. **User A** continues reading Version 1. They are completely unaware that Version 2 is being built.
4. **User B** commits. New readers will now see Version 2.
5. **Garbage Collection:** Later, a background process (like Postgres's 

`VACUUM`) deletes Version 1 once no active transactions need it anymore.
- **Best for:** Almost everything. This is why it’s the default in **PostgreSQL, Oracle, and SQL Server** (in certain modes). It provides high concurrency by allowing reads and writes to happen simultaneously.
- **The Downside:** **Storage bloat**. Since you are keeping multiple copies of the same data, the database uses more disk space and requires background maintenance to clean up old versions.
