Kubernetes does not implement networking. It specifies three rules and delegates everything else to a plugin. Knowing the rules  and which plugin you have explains almost all networking behaviour.

The Kubernetes network model is deliberately minimal. Any conforming implementation must satisfy:

1. **Every Pod gets its own unique IP address.**
2. **Every Pod can reach every other Pod, on any node, without NAT.**
3. **Agents on a node (kubelet, system daemons) can reach all Pods on that node.**

It is often called the “flat network” or “IP-per-Pod” model. The absence of NAT between Pods is the load-bearing requirement. It means a Pod sees the same address for itself that everyone else uses to reach it.

Three consequences follow directly and surprise people:

**Pod IPs are ephemeral.** They are assigned when the sandbox is created and released when the Pod dies. A restarted container keeps the Pod’s IP. 

**You need a lot of IP addresses.** One per Pod, cluster-wide. On a 100-node cluster with 30 Pods each, that is 3,000 addresses.

Nobody in core Kubernetes actually implements this — it's a contract. The **CNI plugin** (Calico, Cilium, Flannel, AWS VPC CNI, etc.) is the thing that makes it true. It does this by:

- Giving each **node** a slice of a larger IP range (a "pod CIDR" per node).
- Creating a virtual ethernet pair (`veth`) for every pod: one end lives inside the pod's network namespace as `eth0`, the other end lives on the host, plumbed into a bridge or into routing tables.
- Setting up **routes** (or overlay tunnels — VXLAN, IP-in-IP, or eBPF-based forwarding in Cilium) so that traffic addressed to "Pod IP on Node B" gets carried from Node A to Node B, then handed to that pod's veth.

Now observe that pods get an ip, iptables and route tables are setup etc. So once CNI is done it attaches ip to all pods and packet can travell inside the network. 

So at Layer 3, a pod's IP is a first-class citizen of the cluster network. This is fundamentally different from Docker's default networking, where containers on different hosts can't talk to each other without you doing port mapping — Kubernetes assumes you _can_ reach any pod directly if you know its IP.


So the idea is that inside kubernetes a pod can connect any other pod. A Deployment’s Pods come and go constantly rollouts, scaling, node failures. Clients need a stable address that always reaches a healthy backend. A Service doesn't create connectivity — connectivity already exists. A Service exists to solve a different problem: **stability and load-balancing across a set of pods whose IPs are constantly changing.**

### How service works

A Service is **not a process, not a proxy, not a listener you can point to on the network and say "that's it."** A Service object is:

- A stable virtual IP address (the **ClusterIP**) that is _never actually assigned to any real network interface anywhere_. It's a fiction a routable-looking IP that only means something because every node's packet-filtering rules know to redirect traffic sent to it.
- A **label selector** (e.g. `app: backend`) that tells Kubernetes "the real destinations behind this virtual IP are any pod matching this selector."
- A continuously-updated list of the actual healthy pod IPs matching that selector — this list is called **Endpoints** (or, in modern Kubernetes, **EndpointSlices**). The `endpoint-controller` watches pods matching the selector and keeps this list current in real time — when a pod dies, it drops out; when a new one starts and passes its readiness probe, it's added.
- A DNS name, automatically created by **CoreDNS**, of the form `servicename.namespace.svc.cluster.local`, which resolves to the ClusterIP.

So what happens is that when the service is created this object is written to `etcd`. The `endpoint-controller` watches pods matching the selector and keeps this list current in real time. 

kube-proxy runs as a daemon on every node. It watches the API server for Services and their Endpoints/EndpointSlices, and its entire job is: **rewrite the packet-filtering rules of the node's kernel so that "ClusterIP:port" gets transparently DNAT'd (destination-NAT'd) to one of the real pod IPs.** 

kube-proxy writes a set of `iptables` rules (in the `nat` table) for every Service. Conceptually, for a Service with 3 backend pods, it writes something equivalent to - 

- "If a packet's destination is `ClusterIP:Port`, jump to a per-Service chain."
- In that chain, use **random probability matching** across multiple rules to pick one of the 3 backend pods roughly equally
- The matched rule performs a `DNAT` — it rewrites the destination IP:port of the packet from `ClusterIP:Port` to `PodIP:TargetPort`, right there in the kernel's connection tracking (`conntrack`), before routing even happens.
- Return traffic is automatically un-translated by conntrack, so the client never sees the real Pod IP.

This all happens **in-kernel, on whichever node the packet currently is on** — there's no separate load-balancer process the packet visits. iptables is evaluated as part of normal netfilter packet processing. 

So this is what happens when service of type `clusterip` is created. 

### Types

#### Clusterip - Default type

This is what you get if you create a Service and don't specify a `type`. **What it's for**: internal-only communication — pod to pod, service to service, inside the cluster.

**Request path**, say a frontend pod calling `backend-svc`:

- Frontend pod does a DNS lookup for `backend-svc.default.svc.cluster.local`. Its `/etc/resolv.conf` (injected by kubelet) points it at the **CoreDNS** service. CoreDNS returns the ClusterIP, e.g. `10.96.45.12`.
- The pod opens a connection to `10.96.45.12:80`. This packet leaves the pod's network namespace via its veth, and hits the host's network stack.
- On that node, netfilter/iptables (or IPVS, or eBPF) rules installed by kube-proxy intercept the packet _before normal routing decides where it goes_, see the destination matches a known Service ClusterIP, pick one backend pod from the current Endpoints list, and DNAT the destination to that pod's real IP (say `10.244.2.9:8080`).
- Now the packet is just a normal pod-to-pod packet with a real destination. It's routed across the flat pod network (via the CNI's routing/tunneling) to whichever node hosts `10.244.2.9`, and delivered to that pod's veth → its `eth0`.
- Response traffic comes back, and conntrack automatically reverses the DNAT so the frontend pod sees replies as if they came from `10.96.45.12`, never learning the real pod IP.

Important nuance: **the DNAT happens on the _client's_ node**, not on some central load-balancer node. This is why ClusterIP has no single point of failure and no extra network hop through a "service" process — the rewriting happens locally, then the packet is routed normally.

ClusterIP Services are **not reachable from outside the cluster** — nothing outside knows how to route to `10.96.x.x`, because that range isn't a real routed network anywhere, it only means something to iptables rules that only exist inside cluster nodes.

Lets say we have backend pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: backend-pod
  labels:
    app: backend        # ← this label is the ONLY thing a Service uses to find pods
spec:
  containers:
  - name: backend
    image: myrepo/backend:1.0
    ports:
    - containerPort: 8080   # informational only — doesn't open/restrict anything by itself
```

Two things worth noticing since they trip people up:

- `labels` is what a Service's selector actually matches against. There's no other link between a Service and a Pod — no name reference, nothing. Pure label matching.
- `containerPort` doesn't do any firewalling. It's documentation for humans and tooling (and it's what `targetPort` in a Service defaults to referencing by name if you use named ports). A container listening on 8080 is reachable on 8080 whether or not you declare `containerPort`.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-svc
spec:
  # type: ClusterIP        <- this is the default, so it's usually omitted entirely
  selector:
    app: backend            # must match the Pod label above — this is how Endpoints gets built
  ports:
  - port: 80                # the port on the ClusterIP itself (what clients connect to)
    targetPort: 8080         # the port on the actual Pod that traffic gets DNAT'd to
```

#### Nodeport

**What it's for**: crude external access — mostly a building block for LoadBalancer, or for bare-metal clusters without a cloud LB.

A NodePort Service is a **ClusterIP Service plus one more rule**: kube-proxy additionally opens a specific port (default range 30000–32767) on **every single node's** host network, regardless of whether that node is even running one of the target pods.

**Request path**, external client hitting `NodeC-IP:30080`:

1. Client sends a packet to `<any-node-ip>:30080`. It doesn't matter which node — you could hit Node A, B, or C; the pods could be running only on Node A.
2. That node's kube-proxy-installed rules catch traffic on port 30080 and DNAT it to a pod IP from the Endpoints list — exactly the same DNAT mechanism as ClusterIP, just triggered by "port 30080 on the node" instead of "ClusterIP:80."
3. If the chosen pod happens to live on a _different_ node than the one that received the request, the packet is forwarded over the pod network to that node (same flat-network routing as always) — this extra hop is sometimes called "unnecessary" traffic and is why `externalTrafficPolicy: Local` exists (it restricts routing to only pods on the node that received the request, trading even load distribution for avoiding the extra hop and preserving the real client source IP).
4. Response returns via conntrack the same way.

Notice the nodeport how are we referencing the nodePort and then putting traffic to 30080 will be transferred to port 8080 on the pod. 

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-svc-nodeport
spec:
  type: NodePort
  selector:
    app: backend
  ports:
  - port: 80              # still the ClusterIP port — this Service has one internally too
    targetPort: 8080       # still the Pod port
    nodePort: 30080         # NEW: the port opened on every node's host IP (30000-32767 range)
```

#### Loadbalancer

**What it's for**: proper external exposure on cloud providers (AWS, GCP, Azure, etc.).

A LoadBalancer Service is a **NodePort Service plus cloud automation**: when you create it, the **cloud-controller-manager** notices the new Service, and calls out to your cloud provider's API to provision an actual external load balancer (an AWS NLB/ELB, a GCP Network LB, etc.) and configures it to forward traffic to the NodePort opened on every node.

**Request path**, external client hitting the LB's public IP/DNS:

1. Client connects to the cloud load balancer's external IP.
2. The cloud LB (a real piece of infrastructure outside Kubernetes, managed by the cloud) forwards the connection to one of the cluster's node IPs, on the NodePort that was auto-assigned.
3. From here it's identical to step 2–4 of NodePort above: node's kube-proxy rules DNAT to a real pod IP, possibly forwarding cross-node if needed.

So LoadBalancer doesn't introduce a new in-cluster mechanism — it's cloud infrastructure automation sitting in front of the exact same NodePort → ClusterIP → Pod chain. The "magic" is entirely in the cloud-controller-manager talking to your cloud's API, not in any new Kubernetes networking primitive.

Headless Service (`clusterIP: None`) worth knowing even though it's a variant, not a separate "type". **What it's for**: when you want direct addressing of _individual_ pods instead of load-balanced access to "any one of them" common for StatefulSets (databases, Kafka, etc.) where clients need to talk to a _specific_ replica.

Again we will restate that loadbalancer uses nodeport internally so keep that in mind. 

### CoreDNS

It's just a DNS server. Nothing mystical — the same concept as any DNS server on the internet, just running as pods inside your own cluster, watching the Kubernetes API for Services and Pods, and auto-generating DNS records for them. So when you create a Service called `backend` in namespace `default`, CoreDNS notices this (it watches the API server continuously) and automatically starts answering: "if anyone asks for `backend.default.svc.cluster.local`, tell them the Service's virtual IP."

Say a pod's code does something like connecting to `http://backend`. Here's what happens step by step:

1. The application inside the pod calls a DNS resolution function (this happens transparently, e.g., inside your HTTP library or `getaddrinfo` at the OS level).
2. That request goes to the DNS resolver configured inside the pod's `/etc/resolv.conf` — Kubernetes automatically sets every pod's resolver to point at CoreDNS's internal Service IP.
3. CoreDNS receives the query, checks its records built from watching Services/Endpoints, and replies with the Service's cluster IP.
4. The app now connects to that Service IP directly, and kube-proxy (a separate piece — the one that actually load balances traffic to backing pods) takes it from there.

Again something important that `/etc/resolv.conf` which points to dns is not pointing to some outser router but to the internal coreDNS. 

Also each service gets DNS A record following a fixed pattern:

```
<service>.<namespace>.svc.<cluster-domain>
```

Headless Services (Chapter 20) return **all Pod IPs** instead of a ClusterIP, and StatefulSets additionally get per-Pod records. 


CoreDNS runs as a Deployment in `kube-system` (usually 2 replicas), fronted by a Service — conventionally at `172.20.0.10` — that every Pod is pointed at.

It watches Services and EndpointSlices through the API and answers from an in-memory view. It is not a zone-file server; there is nothing to reload when a Service changes.
resolv.conf is the file it injects into every pod. Which is how the pod knows how to resolve dns A records. 

### Ingress and ingress controller

A `LoadBalancer` Service gives one workload one cloud load balancer, at L4. Ten HTTP services would mean ten load balancers, ten IPs, ten certificates, and no shared routing.

What you actually want is **one** entry point that routes by hostname and path to many backends, terminates TLS once, and is configured declaratively. That is Ingress.

Example ingress

An example ingress file is this its kind is Ingress and apiVersion `networking.k8s.io/v1`. Now we also have annotations which are given for the required loadbalancer for an instance in aws we can have alb loadbalacer. 

Types of load balanvers.

|   |   |
|---|---|
|**AWS Load Balancer Controller**|Provisions an ALB (or NLB)|
|**ingress-nginx**|An nginx Deployment in-cluster, fronted by an NLB|
|**Traefik**, **HAProxy**, **Contour**|Similar in-cluster proxies|

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    kubernetes.io/ingress.class: alb
spec:
  ingressClassName: alb
  tls:
    - hosts: [app.example.com]
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 80

```

The distinction matters: the AWS controller creates AWS infrastructure _outside_ the cluster from your Ingress; ingress-nginx runs proxy Pods _inside_ the cluster and needs its own `LoadBalancer` Service to be reachable. So what happens with AWS loadbalancer is we are creating a lod balancer outside of the cluster which means its reacahble and loadbalancer acts as bridge between two. 

Now we understand that with ingress we have just one loadbalancer and every req goes through it. So we need to have the path matching since external ip is going to be same. This is why we have rules section. which specifies first host and then rules for the paths. 

```
pathType: Prefix     # /api matches /api, /api/, /api/v1 (path segments)
pathType: Exact      # /api matches ONLY /api
pathType: ImplementationSpecific   # controller-defined — avoid
```

`Prefix` matches whole **path segments**, not string prefixes. `/api` matches `/api/v1` but **not** `/apiary` — despite `/api` being a string prefix of `/apiary`.

## The AWS Load Balancer Controller

On EKS this is the standard controller. It watches Ingress objects and provisions an **Application Load Balancer**, configuring listeners, rules, and target groups from your annotations.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-2:123456789012:certificate/abc
    alb.ingress.kubernetes.io/ssl-redirect: '443'
    alb.ingress.kubernetes.io/healthcheck-path: /healthz
    alb.ingress.kubernetes.io/target-group-attributes: deregistration_delay.timeout_seconds=30
    alb.ingress.kubernetes.io/group.name: shared      # ← see below
spec:
  ingressClassName: alb
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
           service: {name: web, port: {number: 80}}
```

Two design points that matter on EKS:

**`target-type: ip`** registers Pod IPs directly as ALB targets using the VPC CNI’s real Pod addresses. The ALB talks straight to Pods, bypassing the Service/NodePort hop, with accurate per-Pod health checks. Prefer it over `instance` mode always.

**`group.name`** is the killer feature for cost. Without it, each Ingress creates its own ALB. With a shared `group.name`, **multiple Ingress objects across namespaces share one ALB** — the controller merges their rules. This is how you run dozens of services behind a single load balancer, each team owning its own Ingress object.

Without `group.name`, ten Ingress objects create ten ALBs — each with an hourly charge and its own DNS name. This is the most common source of surprise AWS bills on EKS. Set a shared `group.name` from the start; retrofitting it later means new ALB DNS names and a DNS cutover.

#### TLs mode

Two models, and on EKS you almost always want the first.

**Terminate at the ALB with an ACM certificate.** TLS ends at the load balancer; the ALB→Pod hop is plaintext inside the VPC. You reference the ACM cert ARN in an annotation, and ACM handles renewal automatically. Simplest and most common.

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: app-tls
spec:
  secretName: app-tls
  dnsNames: [app.example.com]
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
```

**Terminate in-cluster with a Kubernetes Secret.** The `tls` block references a `kubernetes.io/tls` Secret. For ingress-nginx this is normal; for the ALB controller it is unusual. **cert-manager** automates this by obtaining certificates from. 

### External dns 

The ALB gets an AWS-generated name like `k8s-shared-abc-123.us-east-2.elb.amazonaws.com`. Pointing `app.example.com` at it by hand, every time an ALB is recreated, is error-prone.

**ExternalDNS** watches Ingress (and Service) objects and manages Route 53 records automatically:

```yaml
metadata:
  annotations:
    external-dns.alpha.kubernetes.io/hostname: app.example.com
```

The `host` in the Ingress rule is enough for ExternalDNS to create and maintain the Route 53 alias record. Combined with the ALB controller and cert-manager/ACM, deploying a new public service becomes: create a Deployment, a Service, and an Ingress — and DNS, TLS, and the load balancer all appear.
