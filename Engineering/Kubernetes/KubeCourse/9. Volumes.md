A container if you recall has a writable layer on top which vanishes when pod restarts secondly its scoped to container only so sidecar can not read from it. 

A **volume** solves both. It is storage mounted into one or more containers at a path, with a lifetime independent of the writable layer.

|Storage|Survives container restart?|Survives Pod deletion?|Shared in Pod?|
|---|---|---|---|
|Writable layer|No|No|No|
|`emptyDir`|**Yes**|No|Yes|
|`emptyDir` (memory)|Yes|No|Yes|
|ConfigMap / Secret|Yes (read-only)|No|Yes|
|PersistentVolume|Yes|**Yes**|Depends on access mode|

Volumes are declared at Pod level and mounted per container. 

```yaml
spec:
  volumes:
    - name: scratch
      emptyDir: {}
  containers:
    - name: app
      volumeMounts:
        - name: scratch
          mountPath: /data
```

The `volumes` list defines what exists; `volumeMounts` places it into a container at a path. The same volume can be mounted into several containers, at different paths. 

First kind of volume is `emptyDir`

Created empty when the Pod is assigned to a node, and deleted when the Pod leaves the node. It survives container restarts (the Pod persists), which is its whole point.

```yaml
volumes:
  - name: cache
    emptyDir:
      sizeLimit: 1Gi
  - name: shm
    emptyDir:
      medium: Memory        # tmpfs — RAM-backed
      sizeLimit: 256Mi
```

**By default it lives on the node’s disk**, in the kubelet’s directory, and counts against `ephemeral-storage`. A Pod filling an `emptyDir` can trigger `DiskPressure` and get itself and its neighbours evicted. Set `sizeLimit`.

**`medium: Memory` is tmpfs** — fast, but it counts against the container’s **memory limit** (Chapter 8). A 256Mi memory-backed `emptyDir` reserves 256Mi of the Pod’s memory budget.

`emptyDir` feels persistent because it survives crashes, and people reach for it as “storage”. It is destroyed the moment the Pod is deleted — which happens on every rollout, every scale-down, every node drain, every eviction.

#### hostPath

Mounts a file or directory from the **node’s** filesystem into the Pod:

```yaml
volumes:
  - name: docker-sock
    hostPath:
      path: /var/run/containerd/containerd.sock
      type: Socket
```

`hostPath` is a security hazard and an anti-pattern for applications, for two independent reasons:

- `hostPath` is a security hazard and an anti-pattern for applications, for two independent reasons:
- **It is a privilege escalation vector.**. A Pod that can mount `hostPath` can mount `/`, the kubelet’s directory, other Pods’ secrets, or the container runtime socket — and from the runtime socket, take over the node.

#### Projected volumes

Combine several sources into one directory. The most important instance is the **ServiceAccount token projection** the kubelet mounts into every Pod. 

Note that we define projected and then sources with multiple types. 

```yaml
volumes:
  - name: kube-api-access
    projected:
      sources:
        - serviceAccountToken:
            path: token
            expirationSeconds: 3600      # short-lived, auto-rotated
            audience: sts.amazonaws.com
        - configMap:
            name: kube-root-ca.crt
            items: [{key: ca.crt, path: ca.crt}]
        - downwardAPI:
            items:
              - path: namespace
                fieldRef: {fieldPath: metadata.namespace}

```

#### Ephemeral volumes

A **generic ephemeral volume** gives Pod-lifetime storage that uses the full CSI machinery so you can get a fast provisioned SSD that is created with the Pod and deleted with it:

```yaml
volumes:
  - name: scratch
    ephemeral:
      volumeClaimTemplate:
        spec:
          accessModes: [ReadWriteOnce]
          storageClassName: gp3
          resources:
            requests:
              storage: 50Gi
```

### PVC -  PersistentVolumes and StorageClasses

A PVC (Persistant Volume Claim) is a request for storage. A StorageClass is a factory that fulfils it. A PV(Persistant volume) is the result. The separation lets applications ask for storage without knowing what provides it.

Persistent storage in Kubernetes is a claim-check system with three players:

- **PersistentVolumeClaim (PVC)** — “I need 100Gi, read-write-once.” A request, written by the application author, namespaced.
- **StorageClass** — “here is how to make storage of type X.” A factory, written by the cluster operator, cluster-scoped.
- - **PersistentVolume (PV)** — an actual piece of storage. Cluster-scoped, bound to one PVC.


The point of the split is **decoupling roles**. An application author writes a PVC asking for “100Gi, RWO, class `fast`” and never mentions EBS, IOPS, or availability zones. The cluster operator defines what `fast` means. The same PVC works on EKS (EBS), GKE (PD), or a laptop (local disk) — only the StorageClass changes. This is the same portability principle as the whole object model

What an application author writes:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
  namespace: platform
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: gp3
  resources:
    requests:
      storage: 100Gi
```

Then a Pod uses it by name:

```yaml
spec:
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: data
  containers:
    - name: db
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
```

The Pod refers only to the claim. It does not know or care which PV backs it.

### Storage class

What the operator defines. On EKS with the EBS CSI driver:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  kmsKeyId: arn:aws:kms:us-east-2:123456789012:key/abc
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
allowVolumeExpansion: true
```

### CSI in brief 

Now above `PVC` discussion just tells us what we want. However it does not mentions the details like difference in hard disks over laptop vs AWS vs GCP. So kuberntes has a interface `CSI` Container Storage Interface is an `gRPC` specification and defines how will kuberntes will ask for the stroge. Vendors can write their own `CSI` and ship it as container.

A CSI driver has two parts, deployed differently because they do different jobs.

```
┌─────────── CONTROLLER (Deployment, usually 2 replicas) ──────────┐
│  Calls the cloud API. Creates, deletes, attaches, snapshots      │
│  volumes. Runs anywhere.                                         │
│                                                                  │
│  sidecars (generic, provided by Kubernetes):                     │
│    external-provisioner  ← watches PVCs → CreateVolume           │
│    external-attacher     ← watches VolumeAttachment → attach     │
│    external-resizer      ← watches PVC size → ExpandVolume       │
│    external-snapshotter  ← watches VolumeSnapshot → snapshot     │
│  + the vendor's CSI container (ebs.csi.aws.com)                  │
└──────────────────────────────────────────────────────────────────┘

┌─────────── NODE PLUGIN (DaemonSet, one per node) ────────────────┐
│  Does the on-node work: format, mount, unmount. Runs on every    │
│  node because mounting is inherently node-local.                 │
│    node-driver-registrar  ← registers the driver with kubelet    │
│  + the vendor's CSI container                                    │
└──────────────────────────────────────────────────────────────────┘
```

The split follows the work: **provisioning and attaching call the cloud API** (do it once, from a Deployment), while **mounting manipulates the node’s filesystem** (must happen on the specific node, hence a DaemonSet).

Following a PVC to a mounted filesystem, naming the actual gRPC calls (the vocabulary of the error messages):

```
1. CreateVolume          (controller → cloud)   makes the EBS volume
2. ControllerPublishVolume (controller → cloud) attaches it to the EC2 node
3. NodeStageVolume       (node plugin)           format + mount to a staging path
4. NodePublishVolume     (node plugin)           bind-mount into the Pod
   ... Pod runs ...
5. NodeUnpublishVolume   (node plugin)           unmount from the Pod
6. NodeUnstageVolume     (node plugin)           unmount from staging
7. ControllerUnpublishVolume (controller → cloud) detach from the node
8. DeleteVolume          (controller → cloud)    destroy (if reclaimPolicy: Delete)
```

AWS CSI driver has multiple drivers underneath for each sotrage class for example `AWS EBS CSI driver` `AWS EFS CSI driver` etc.
