### Functional requirements

- Start group chats
- Send and recieve messages
- Constraints on message - Media attachments on the messages. 
- Access the messages after i go offline

Out of scope - 
- Audio and video calls
- Encryption

### Non functional requerements

- Low latency < 500ms
- Guarantee the delievery of messages.
- Scale of the system - 1billion , high throughput - 
- Messages not stored unnecessarily

Note a device can be offline but not a person. So for example a user has laptop on which it can receive messages and on phone it might be offline.

#### API design

Next, we'll want to think through the API of our system. Unlike a lot of other products where a REST API is probably appropriate, for a chat app, we're going to have high-frequency updates being both sent and received. So we will use websockets for high freq low latency working. 

However we will still have some rest api end points such as - 

- createChat
```
POST /chat
{
	participants:[]
	name:""
}

returns {
	chatId:""
}
```

- send and receive

```
// sendMessage
{
	"chatId":""
	message:""
	attachment:[] // list of urls for blob storage
}

{
	"status":"success|failure"
	messageId:""
}
```

Modify the participants

```
// -> modifyChatParticipants
{
    "chatId": "",
    "userId": "",
    "operation": "ADD" | "REMOVE"
} -> "SUCCESS" | "FAILURE"

```

Each of these commands will have parallel commands that are sent to other clients. When the command has been received by clients, they'll send an ack command back to the server letting it know the command has been received (and it doesn't have to be sent again)!

The message receipt acknowledgement is a bit non-obvious but crucial to making sure we don't lose messages. By forcing clients to ack, we can know for certain that the message has been delivered all the way to the client.

### High level design

First thing is that we should be able to start chat - createchat end point note that since we will be using the websocket for near real time updates. We can not use `L7` loadbalancer working at the application reason being we want our client to be able to connect to the same server on which it was last communicating to and that is very important. 

L4 loadbalancers work at tcp layer. So when client connects to the load balancer the lb creates a symmetric connection to the server. This is creeated at tcp level meaning the connection remains and it works like a single hop equivalent to invisible loadbalancer. 

Now we will create the db for now lets choose dynamodb. Its a great choice 

We create a chat table 
```md
Chat
- id
- name
- metadata
  
Chatpariticipant
- chatId
- participantId - unq for the user or can be client specific. 
```

To find all the people in a given chat we will Create chat participant with the chatId as the partition key and participantId as sortkey. Meaning we can easily find all the people in certain group. For the reverse finding all the chats in which a person is part of we can use GSI on pariticantId as PK and chatId as sortkey. 

With this we can easily create chats. 

Now how to send or receive messages. We will have the client get connected to the server. Now which one server a client connects to we will be using L4 loadbalancer with least configuration setup so it will get connected to the server currently having least number of connections. Now once a chat receives message meaning some user sends some message to the chat we will send out the message back to all the clients on a given chat. Now we run into a problem how will we send out message to all clinets since some client may get connected to some other server. This is problem with horizontal scaling. 

So to solve it we first observe that no matter what every client will be connected to some server via websocket. So we can use kafka partitioned on user_id meaning when a client gets connected to some server this server will subscribe to the user's topic and then another server will just have to send the message to the kafka topic itself and that's it. More importantly this is not a good design because kafka is not build for this rapid connect and disconnect and each partition is heavy around 10kbs so it will tbs of data for the billion users. Note that idea itself is not bad but kafka is not good for this task. 

Solution here is Redis `pub/sub`. So redis pub/sub creates an internal hashmap and user has to subscribe to that topic. Redis maintains internal hashmap of which topics are being subscribed by whom when the message is published to that topic redis looks into hashmap which sockets are listening on that topic and pass them message. Guarantees are preety low it guarantees atmost once delievery. However since we already have an inbox we can keep sending messages if redis was not able to send via the direct websocket later on via replay of messages. 

Another problem is what happens when a client is disconnected when websocket was sending out messages. To solve this issue we need to keep those messages. A good idea is to create an inbox table. So consider each user has a Inbox where they recieve all the messages ordered by timestamp for a chat. We should use participantId as PK for this table. Now the flow will be like this when the chat server will recieve the message it will send the message to the inbox of all chat participants. Now chat server will send out the messages to all the websockets for each client id and client in turn will return an acknowledgement. With this acknowledgement we remove the entry from Inbox. Finally when all the messages are deleted we will remove the message itself from db.

### Scaling

If there are 1billion users and say one user does 10 messages we need 10billion messages and say each message can be of size atmost `1kb` then we need =  `10*1000 billion bytes` = `10 trillion bytes` = `10tb storage per day`. However we understand that most messages are not that long 1kb is 1000 chars content and most messages are going to get delievered in a day so we will need to have storage of `10-100tbs` which is manageble by modern standards. 

Finally to have a user where it can get connected to multiple clients we just need to swap out the notion of user with the client ip and we will be done.
