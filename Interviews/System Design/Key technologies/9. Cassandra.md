
---

Cassandra is a wide-column, distributed NoSQL database.

It is designed for achieving three goals - 
- Being highly scalable -  Add nodes and both storage and throughput grow roughly linearly, with no single node acting as a bottleneck
- Highly available - There's no single primary every node can accept both reads and writes, so there's no single point of failure the way a relational primary can be. 
- Fault tolerant -  Data is replicated across multiple nodes, so losing a node, or even a whole datacenter, doesn't mean losing data. 
Those three goals come at a real cost, though mainly around consistency and query flexibility which is the recurring theme worth keeping in mind throughout everything below.

## Basics of Cassandra

### Keyspace

The top-level organizational unit in Cassandra, roughly equivalent to a "database" in relational systems like Postgres or MySQL. A keyspace is where you define the **replication strategy** (covered below) that governs how data in it gets spread and duplicated across nodes, and it also owns any user-defined types (UDTs) you create.

### Table

Lives within a keyspace and organizes data into rows. Each table has a schema defining its columns and critically, in a way that has no real relational equivalent  its **primary key structure**, which doesn't just identify rows uniquely but also determines exactly where and how that data is physically stored across the cluster (more on this below).

### Row

A single record in a table, identified by a primary key. Each row stores values across multiple columns.

### Column

The actual data storage unit: a column has a name, a type, and a value for a specific row. Not every row needs every column populated Cassandra is a *wide-column* database, meaning the set of populated columns can genuinely vary from row to row within the same table, unlike a relational table where every row has an entry for every column (even if that entry is `NULL`). Every column also carries its own timestamp metadata recording when it was written, and that timestamp is what resolves write conflicts between replicas: if two replicas end up holding different values for the same column, the one with the later timestamp simply wins  "last write wins."

At the most basic level, you can liken Cassandra's data structures to a large, sparse JSON object:

```json
{
  "keyspace1": {
    "table1": {
      "row1": {
        "col1": 1,
        "col2": "2"
      },
      "row2": {
        "col1": 10,
        "col3": 3.0
      },
      "row3": {
        "col4": {
          "company": "Hello Interview",
          "city": "Seattle",
          "state": "WA"
        }
      }
    }
  }
}
```

Cassandra columns support a wide range of types, including user-defined types and JSON-like nested values, which makes it a flexible store for both flat and nested data.

## Primary keys and data modeling

A Cassandra primary key is really two things bundled together: a **partition key** (required) and, optionally, one or more **clustering columns**.

```sql
CREATE TABLE posts_by_user (
    user_id UUID,
    created_at TIMESTAMP,
    post_id UUID,
    content TEXT,
    PRIMARY KEY ((user_id), created_at)
);
```

The partition key  `user_id` here decides which nodes physically own a given row's data (via hashing, covered next); every row sharing the same partition key value lives together, physically co-located on disk. Clustering columns `created_at` here decide the *sort order within that partition*, so rows for a given `user_id` are stored pre-sorted by `created_at`, making a query like "give me this user's most recent posts" a fast sequential read rather than a scan-and-sort.

 The practical approach when using cassandra is **query-first modeling**: you start from the specific queries your application needs to serve, and design a table (often several, deliberately denormalized copies of the same data) whose partition key and clustering columns line up exactly with each query's access pattern. It's completely normal in Cassandra to store the same logical data in multiple tables  `posts_by_user`, `posts_by_hashtag`, `posts_by_date`  each shaped around one specific query, trading storage and write amplification for read speed and horizontal scalability.

## Partitioning: how data is spread across the cluster

Cassandra distributes data using **consistent hashing**: every node in the cluster owns a range of hash values (called *tokens*) on a conceptual ring, and a row's partition key is hashed to produce a token that determines exactly where on that ring and therefore which node the row belongs. In practice, each physical node is actually assigned many smaller token ranges rather than one large contiguous range, a technique called **virtual nodes (vnodes)**; this spreads a given node's data across many smaller chunks scattered around the ring, which makes adding or removing a node from the cluster much smoother, since the resulting data rebalancing gets spread thinly across many other nodes instead of dumping a single huge contiguous range onto one neighbor.

Because all of a partition's data is physically co-located on whichever node(s) own its token, the choice of partition key has real, sometimes painful, consequences: a partition key that's too coarse — say, partitioning a global chat app by `channel_id` when a handful of channels are enormous — creates a **hot partition**, where a disproportionate share of reads and writes lands on one physical location no matter how many nodes you add to the cluster. This is one of the most common Cassandra data-modeling mistakes to flag in a system design interview: the partition key needs to be chosen so that both storage *and* traffic end up roughly evenly spread across the cluster.

## Replication

A keyspace's replication strategy determines how many copies of each partition exist, and where. The **replication factor (RF)** sets how many total copies of each partition are kept — RF=3 is a common default, meaning any single row can survive up to two node failures and still be readable. Replicas are placed by walking clockwise around the token ring from the partition's owning node and picking the next RF−1 distinct nodes (or racks/datacenters, depending on strategy).

Two replication strategies matter in practice: **SimpleStrategy**, which just walks the ring without any awareness of physical topology  fine for a single-datacenter test setup, but not something you'd run in production and **NetworkTopologyStrategy**, which is topology-aware and lets you specify a replication factor *per datacenter* (e.g., RF=3 in `us-east`, RF=3 in `eu-west`), ensuring replicas land across different racks and datacenters rather than clustering behind the same failure domain. Multi-datacenter, active-active replication like this  where every region can serve both reads and writes locally  is one of Cassandra's standout capabilities and a big part of why it gets reached for over a single-primary system like Postgres when true multi-region write availability is a hard requirement.

## Tunable consistency

Unlike a system with one fixed consistency guarantee, Cassandra lets you choose a **consistency level (CL) per query**, trading off latency and availability against how consistent the answer is guaranteed to be. Common levels include `ONE` (only one replica needs to respond fastest, weakest guarantee), `QUORUM` (a majority of replicas `⌊RF/2⌋ + 1`  must respond), `ALL` (every replica must respond  strongest, but a single down replica blocks the whole operation), and datacenter-scoped variants like `LOCAL_QUORUM` (a quorum within the local datacenter only, avoiding cross-region latency).

This is where the classic **CAP theorem** framing applies directly: Cassandra is fundamentally an **AP system** by design it prioritizes availability and partition tolerance over strict consistency, defaulting toward eventual consistency between replicas. But consistency level is genuinely tunable *per operation*: if you set both writes and reads to `QUORUM`, you get a strong consistency guarantee  because any write-quorum and any read-quorum are mathematically guaranteed to overlap on at least one replica (`W + R > RF`), a read is guaranteed to see the most recent write. Using `ONE` for both instead maximizes availability and latency at the cost of that guarantee  a read can land on a replica that hasn't yet received the latest write. This tunability, chosen per query rather than baked into the whole system, is one of Cassandra's defining characteristics and a favorite interview talking point.

## Write path

Cassandra writes are built to be extremely fast, and the write path explains why: there's no read-before-write, no row-level locking, and (for a basic write) no coordination with other replicas beyond satisfying the chosen consistency level. When a write arrives at a coordinator node, it's first appended to the **commit log** on disk a purely sequential, append-only write, similar in spirit to Postgres's WAL, which is what makes the write durable and crash-recoverable. At essentially the same time, the write is applied to an in-memory, sorted structure called the **memtable** (one per table), which is what actually serves subsequent reads of that data until it's flushed. Because there's no lookup or lock involved  a write is just an append to the log and an insert into an in-memory sorted structure  this whole path is dramatically cheaper than the read-modify-write cycle a relational database's row updates typically involve.

Once a memtable grows past a size threshold, it's flushed to disk as an immutable file called an **SSTable** (Sorted String Table) and the memtable is cleared to accept new writes. Because SSTables are immutable, an `UPDATE` to an existing row doesn't rewrite anything in place it's simply written as a new entry (with a newer timestamp) that may end up in a different SSTable entirely, to be reconciled with older versions at read time (or removed later during compaction).

## Compaction

Because every memtable flush produces a brand-new, immutable SSTable, a single partition's data can end up scattered across many SSTables over time — the latest value for a given column might be in a brand-new SSTable while older, superseded values for other columns of the same row sit in older ones. **Compaction** is the background process that periodically merges multiple SSTables into fewer, larger ones: it reconciles multiple versions of the same row (keeping only the latest, per-column, by timestamp) and physically discards data that's been overwritten or deleted, reclaiming disk space and keeping reads fast by reducing how many SSTables a single read has to consult.

Cassandra supports a few compaction strategies suited to different workloads: **Size-Tiered Compaction (STCS)**, the default, groups similarly-sized SSTables together and merges them, which is efficient for write-heavy workloads but can leave reads touching more SSTables than ideal; **Leveled Compaction (LCS)** organizes SSTables into levels with bounded overlap, giving much more predictable read latency at the cost of significantly more disk I/O from compaction itself, which suits read-heavy workloads; and **Time-Window Compaction (TWCS)** groups SSTables by time bucket, which is purpose-built for time-series or TTL'd data where whole time windows tend to expire and get dropped together.

## Read path

Because a row's current state can be spread across the active memtable and multiple SSTables on disk, a read generally has to check several places and reconcile whatever it finds — merging column values across all of them and keeping only the latest timestamp per column, the same logic compaction uses, just done on the fly at read time instead of ahead of time. To avoid this being slow, Cassandra layers a few optimizations in front of that disk work: a **bloom filter** per SSTable lets a node cheaply and probabilistically answer "does this SSTable definitely *not* contain this partition?" without touching disk at all, which lets most irrelevant SSTables be skipped instantly; a **partition index/summary** then lets the node jump close to the right location on disk for SSTables that might contain the data, rather than scanning the whole file; and an optional **row cache** or **key cache** can keep hot rows or their disk locations in memory entirely, skipping disk access for frequently-read data altogether.

## Tombstones

Deletes in Cassandra don't remove data immediately — since SSTables are immutable, a `DELETE` is implemented by writing a special marker called a **tombstone**, which just says "this data, as of this timestamp, is deleted," and the actual physical removal only happens later, during compaction. This is a fairly sharp edge worth knowing about: a workload that deletes (or overwrites with nulls) very frequently within the same partition can accumulate a huge number of tombstones that all have to be scanned through and filtered out on every read of that partition, even though none of them represent real data anymore — degrading read latency badly, and in extreme cases causing Cassandra to reject the query outright as a protective measure. This is a real, commonly-cited production gotcha, and it's part of why Cassandra is a poor fit for queue-like access patterns (write, read once, delete) that generate tombstones as fast as they generate real rows.

## Gossip, hinted handoff, and repair

Cassandra has no central coordinator tracking cluster state — nodes learn about each other and detect failures through a peer-to-peer **gossip protocol**, where each node periodically exchanges state information (which nodes are up, their token ranges, load, etc.) with a few random peers, so that knowledge of cluster state spreads across the whole ring over time without any single node being a bottleneck or single point of failure for membership itself.

Because replicas can be temporarily unreachable, Cassandra layers on a couple of mechanisms to keep replicas converged despite that. **Hinted handoff** covers short outages: if a replica is down when a write comes in but the write still satisfies its consistency level via other replicas, the coordinator stores a "hint" — essentially "replay this write once that node comes back" — and replays it once the replica rejoins, without the client needing to do anything. For longer outages, or just to catch drift generally, **anti-entropy repair** compares data between replicas using **Merkle trees** (hash trees that let two replicas efficiently identify exactly which ranges of data differ, without transferring and comparing all the data itself) and reconciles any differences found — this is typically run as a periodic maintenance job (`nodetool repair`) rather than continuously.

## Lightweight transactions

For the narrow set of cases that genuinely need linearizable, single-partition consistency — most commonly enforcing uniqueness, like "insert this username only if it doesn't already exist" — Cassandra offers **lightweight transactions (LWT)** via `INSERT ... IF NOT EXISTS` or `UPDATE ... IF <condition>`. Under the hood these use a Paxos-based consensus protocol among the replicas to guarantee the compare-and-set semantics hold even under concurrent attempts. They're meaningfully more expensive than a normal write, since they require multiple round trips of coordination rather than a fire-and-forget append, so they're meant to be used sparingly for the specific operations that need this guarantee, not as a general substitute for the tunable-consistency writes described above.

## When to use (and not use) Cassandra

Cassandra is a strong fit when write throughput needs to scale near-linearly across many nodes and, often, multiple regions simultaneously — think IoT telemetry, event/activity logging, time-series metrics, or any workload where availability during a network partition matters more than every reader seeing the absolute latest write immediately. Its architecture — no single primary, tunable consistency, natural multi-datacenter replication — is purpose-built for exactly that shape of problem, which is why it comes up as the go-to alternative when a relational database's single-node write ceiling (see [[2. Postgres and system design.md|Postgres's practical write throughput limits]]) becomes the actual bottleneck.

It's a poor fit, on the other hand, when your access patterns are still evolving or genuinely ad hoc — because the data model is physically baked around a fixed set of queries via the partition key, changing your querying needs later often means creating and backfilling entirely new tables rather than just adding an index. It's also a poor fit when you need multi-row or multi-partition transactional guarantees (joins across tables, atomic updates spanning multiple partitions), strong consistency by default rather than as an opt-in per query, or when your workload naturally involves heavy deletes within partitions (queue-like patterns), given the tombstone issues described above. In those cases, a relational database's flexibility, joins, and transactional guarantees are usually worth more than Cassandra's write-throughput ceiling.
