Spring Boot supports full-stack web development using Spring MVC, allowing you to build
RESTful APIs and web applications easily.

### Creating rest endpoints

@RestController combines @Controller and @ResponseBody, enabling RESTful endpoints.
`@ResponseBody` tells Spring that every method’s return value should be written directly to the HTTP response body (usually as JSON or XML). 
`@RequestMapping` -  The mapping defines the **URL path** and the **HTTP Method** (GET, POST, PUT, DELETE). Example -`@GetMapping` , `@PostMapping` , `@PutMapping` etc. 

```java
@RestController
@RequestMapping("/api/v1/users")
public class UserController{
	@GetMapping("/{id}")
	public User getUser(@PathVariable Long id){
		return new User(id,"John");
	}
}
```

How do we get data into the method?

- **`@PathVariable`**: For values inside the URL (e.g., `/users/5`).
- **`@RequestParam`**: For query strings (e.g., `/users?name=John`).
- **`@RequestBody`**: For JSON data sent in the body of a POST/PUT request.

```java
@RestController
@RequestMapping("/api/v1/users")
public class UserController{
	@GetMapping("/{id}")
	public User getUser(@PathVariable Long id){
		return new User(id,"John");
	}
	
	@PostMapping("/{id}")
	public Long createUser(@RequestBody User user){
		// logic
		return user.id;
	}
}
```

#### Work flow

In reality the request does not automatically gets to your controller. Rather spring acutally manages this behind the schene. 

This is what happens when request hits your end point

- A request hits the **`DispatcherServlet`** (the Front Controller).
- The `DispatcherServlet` consults the **`HandlerMapping`** to find which Controller matches the URL.
- The request is passed to your Controller method. Jackson auto converts json to java object. 
- The return value is handled by a **`HandlerAdapter`**, which uses **Message Converters** (like Jackson) to turn your Java object into JSON.

#### Handler method

To understand a `@RestController` function (often called a **Handler Method**), you have to look at it as a transformation engine: it takes an unstructured HTTP request and turns it into a structured Java response.

A standard handler method is composed of four distinct "zones."

Zone 1: Mapping & Routing (The "When")  - Annotations here tell Spring which incoming traffic should trigger this specific function.  It contains of url ,  verb mapping and production media types. 

Zone 2: Arguments & Data Binding (The "Input")

Spring uses **Argument Resolvers** to extract data from the HTTP request and inject them into your method parameters.

- **`@PathVariable`**: Extracts values from the URI (e.g., `id` from `/users/{id}`).
- **`@RequestParam`**: Extracts query parameters (e.g., `page` from `/users?page=1`).
- **`@RequestBody`**: The star of REST. It uses an `HttpMessageConverter` (usually Jackson) to turn JSON text into a Java POJO.
- **`@RequestHeader`**: Accesses specific HTTP headers like `Authorization`.

Zone 3: The Implementation (The "Process")

Zone 4: The Return Type (The "Output")
This is how you talk back to the client.
- **`ResponseEntity<T>`**: The gold standard. It wraps your data (`T`) and allows you to set the HTTP status code (e.g., `201 Created`) and custom headers.
- **Type `T`**: The object you return (List, Map, or custom DTO) which Spring automatically serializes back into JSON.

Full example of handler methods. 

```java
@PutMapping("/{id}") // 1. Mapping: Defines the "Path" and "Verb"
public ResponseEntity<UserDto> updateUser(
    @PathVariable Long id,                 // 2a. Input: From the URL
    @Valid @RequestBody UserDto userDto,   // 2b. Input: From the JSON Body (Validated)
    @RequestHeader("X-Trace-ID") String traceId // 2c. Input: From Headers
) {
    // 3. Implementation: Logic delegation
    UserDto updatedUser = userService.update(id, userDto);

    // 4. Return: Status Code (200 OK) + Body (JSON)
    return ResponseEntity.ok()
            .header("Trace-Id", traceId)
            .body(updatedUser);
}
```

```java
@GetMapping("/users")
public ResponseEntity<UserDto> getUser(
	@RequestParam String role,
	....
){
	// do something
}
```


#### Headers

Headers are metadata. They don't contain the actual data (like a User's name), but they tell the client and server **how** to handle that data. 

When a request hits your controller, you can intercept these using the `@RequestHeader` annotation. Since annotation we need to provide which header and then varaible since headers are string key value pairs we can take the value of header in a string. 

```java
@PutMapping("/{id}")
public ResponseEntitiy<User> updateUser(
	@RequestHeader("Content-Type") String contentType,
	... 
){
	// do something
}
```

Just like request header we can also have response headers. These are sent back to the client via the `ResponseEntity`.
Important response headers are - 

- **`Location`**: Used after a `201 Created` to tell the client where the new resource lives.
- **`Set-Cookie`**: Sends a session ID or cookie to the browser.
- **`Cache-Control`**: Tells the browser if it's allowed to save this response locally to save bandwidth.

In Spring, `ResponseEntity` is the "Master Container." It represents the entire HTTP response: **Status Code, Headers, and Body.**

Why use `ResponseEntity` instead of just returning a List or Object?

ResponseEntity allows customizing the response body, headers, and HTTP status.
If you return a plain `User` object, Spring assumes a `200 OK` status. If you want to return a `201 Created`, a `403 Forbidden`, or add a custom header, you **must** use `ResponseEntity`.

```java
@GetMapping("/download")
public ResponseEntity<byte[]> getFile() {
    byte[] fileData = fileService.load();
    
    return ResponseEntity.ok()
            .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"report.pdf\"")
            .contentType(MediaType.APPLICATION_PDF)
            .body(fileData);
}
```

##### Response entity 

In springboot there are many ways to create response object. 

### Builder method

This is the most modern and readable way to write controllers. Instead of a bulky constructor, you chain methods together. It reads like a sentence. Note that it is builder pattern so you need to use build in the end. 

- **`ResponseEntity.ok(body)`**: Shorthand for a `200 OK` with a body.
- **`ResponseEntity.created(uri).body(entity)`**: Returns a `201 Created`. It usually requires a URI pointing to the new resource (sent in the `Location` header).
- **`ResponseEntity.noContent().build()`**: Returns a `204 No Content`. Great for DELETE operations where there's no data to send back.
- **`ResponseEntity.badRequest().body(errors)`**: Returns a `400 Bad Request`.

Example 

```java
@GetMapping("/{id}")
public ResponseEntity<User> getUser(@PathVariable Long id){
	User user = userService.findById(id);
	if(user==null){
		return ResponseEntity.status(HttpStatus.NOT_FOUND).build();
	}
	return ResponseEntity.ok(user);	
}
```

Sometimes you need to add specific headers before you define the body. Spring provides a `BodyBuilder` interface for this.

```java
return ResponseEntity.status(HttpStatus.ACCEPTED)
        .header("Custom-Header", "Value")
        .contentType(MediaType.APPLICATION_JSON)
        .contentLength(1024)
        .body(myObject);
```

Finally there is standard way of crreating object

```java
return new ResponseEntity<>(body, status);
```

### Handle interceptors

Sometimes you need to do something **before** the request hits the `DispatcherServlet` or **after** the controller finishes (like logging the time taken or checking a custom auth header). 

In Spring Boot, "preprocessors" are the components that sit between the incoming network request and your Controller. There are three distinct layers of preprocessing: **Filters**, **Interceptors**, and **Aspects**.

### Servlet filters 

Filters are part of the standard Servlet container (Tomcat). They are the very first thing to touch a request. Because they run **outside** of Spring MVC's core, they don't know which specific Controller method is about to be called.

- **Scope:** The entire application.
- **Best For:**
    - **Security:** (Spring Security is essentially a chain of filters).
    - **Logging/Auditing:** Logging raw HTTP body or remote IP addresses.
    - **Compression:** GZipping the response.
    - **CORS:** Handling cross-origin requests.

```java
@Component
public class CustomFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) 
            throws IOException, ServletException {
        // PRE-PROCESS: Logic before the request hits anything else
        System.out.println("Filter: Request received");
        chain.doFilter(request, response); // Pass the request to the next filter/controller       
        // POST-PROCESS: Logic after the response comes back
        System.out.println("Filter: Response sent");
    }
}
```

Every filter must implement the `jakarta.servlet.Filter` interface, which contains three lifecycle methods:

- **`init()`**: Runs once when the application starts.
- **`doFilter()`**: The heart of the filter. It intercepts the `ServletRequest` and `ServletResponse`
- **`destroy()`**: Runs once when the application shuts down.

Filters work in a **Chain**. Your filter does its work and then must explicitly call `chain.doFilter(request, response)` to pass the "baton" to the next filter. If you don't call this, the request is "blocked" and will never reach your Controller.

example of cors

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE) // Ensure this runs before Security filters
public class CorsFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req,ServletResponse res,FilterChain chain) 
            throws IOException, ServletException {
        
        HttpServletResponse response = (HttpServletResponse)res;
        HttpServletRequest request = (HttpServletRequest) req;
        // 1. Set the Allow-Origin (Who can call us?)
        response.setHeader("Access-Control-Allow-Origin", "http://localhost:3000");
        // 2. Set the Allow-Methods (What can they do?)
        response.setHeader("Access-Control-Allow-Methods", "POST, GET, PUT, OPTIONS, DELETE");
        // 3. Set the Allow-Headers (What metadata can they send?)
        response.setHeader("Access-Control-Allow-Headers", "Content-Type, Authorization");
        // 4. Handle the OPTIONS request (The "Pre-flight" check)
        if ("OPTIONS".equalsIgnoreCase(request.getMethod())){
            response.setStatus(HttpServletResponse.SC_OK);
        } else {
            // 5. If it's a normal request, continue the journey to the Controller
            chain.doFilter(req, res);
        }
    }
}
```

To add the filter to the filter chain there are two options annotate using `@Component`. Another way is to use `Configuration` for more flexible logic. Note that return type of bean must be `FilterRegistrationBean` and then follwoing boiler plate. 

```java
@Configuration
public class FilterConfig {

    @Bean
    public FilterRegistrationBean<CorsFilter> loggingFilter(){
        FilterRegistrationBean<CorsFilter> registrationBean = new FilterRegistrationBean<>();
        registrationBean.setFilter(new CorsFilter());
        registrationBean.addUrlPatterns("/api/*"); // Only protect the API
        return registrationBean;
    }
}
```

### HandlerInterceptors

Interceptors are specific to Spring MVC. Unlike Filters, Interceptors are aware of the "Handler" (the Controller method). This means you can apply logic based on which specific endpoint is being hit. 

`preHandle()`: Runs before the Controller. If it returns `false`, the request stops immediately. `afterCompletion()`: Runs after everything is done (even after the response is sent).

- **Authorization:** Checking if a user has a specific role for a specific endpoint.
- **Performance Tracking:** Measuring exactly how long a specific Controller took.
- **Injecting Attributes:** Adding common data to the request.

### Asynchronous request handling

Spring Boot (via Tomcat) maintains a **Thread Pool** (usually 200 threads by default).

1. **The Request Arrives**: A request hits the server.
2. **Thread Assignment**: Tomcat grabs one idle thread (let's call it `http-nio-8080-exec-1`) from the pool and assigns it to your request.
3. **The Controller Execution**: The thread enters your `@RestController` method.
4. **The I/O Call**: You call an external API or a database that takes 5 seconds.
5. **The Block**: The thread **stops** at that line of code. It cannot do anything else. It cannot help another user. It just sits there waiting for the packets to come back over the network.

Now what happens is that even if all the threads are just waiting for i/o call all the subsequent requests will get qued up. To solve this we use deffered approach meaning having a `CompletableFuture<T>`. This is non blocking and thread will take other requests. 

When you return a `CompletableFuture<T>`, `Callable<T>`, or `DeferredResult<T>`, Spring MVC recognizes this as a signal to perform an **Async Dispatch**.

1. **Request Hits Tomcat:** A thread (`http-exec-1`) is assigned.
2. **Controller Starts:** The method is called.    
3. **The Hand-off:** The controller starts a background task (using an `AsyncTaskExecutor`) and returns a `CompletableFuture` immediately.
4. **The Exit:** The `http-exec-1` thread **exits the method and returns to the Tomcat pool**. It is now free to handle a _new_ incoming HTTP request.
5. **Background Work:** A separate "Worker Thread" handles the 5-second I/O call.
6. **The Completion:** Once the worker thread finishes, it "marks" the `CompletableFuture` as done.
7. **The Re-Dispatch:** Spring catches this, grabs _any_ available thread from the Tomcat pool, and sends the final response back to the client.

First way is to use `CompletableFuture<T>` another way is to add `@Async` annotation. However to do this we need to enable `@EnableAsync` in main config class. 

Example - 

Completable future

```java
@GetMapping("/process")
public CompletableFuture<ResponseEntity<String>> process() {
    return CompletableFuture.supplyAsync(() -> {
        // This is the "Worker Thread" zone
        String result = externalApiService.call(); 
        return ResponseEntity.ok(result);
    });
}
```

or we can call `@Async`

```java
@Service
public class EmailService {
    @Async
    public void sendEmail(String address) {
        // This runs on a separate thread; the Controller doesn't wait for this.
    }
}
```

But we should be configuring thread scheduler because by default spring uses `SimpleAsyncTaskExecutor` which creates one thread per call. We can provde a bean for executors.

```java
@Configuration
public class AsyncConfig {
    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);  // Always keep 10 threads alive
        executor.setMaxPoolSize(50);   // Scale up to 50 if busy
        executor.setQueueCapacity(100); // Wait in line if all 50 are busy
        executor.setThreadNamePrefix("AsyncThread-");
        executor.initialize();
        return executor;
    }
}
```

### Handling exceptions

Here is the anatomy of exception handling, from the basic to the advanced.

If you only want to handle an error for **one specific Controller**, you can write a method inside that controller and annotate it with `@ExceptionHandler`.

```java
@RestController
public class UserController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        if (id < 0) throw new IllegalArgumentException("ID must be positive");
        return userService.findById(id);
    }

    // Only catches errors thrown by methods in THIS class
    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<String> handleInternalError(IllegalArgumentException ex) {
        return ResponseEntity.badRequest().body(ex.getMessage());
    }
}
```

This is the **"Professional Way."** A `@RestControllerAdvice` is a global interceptor that catches exceptions thrown by **any** controller in your entire application. Here we define with annotation what this method is gonno be handling.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // Catching a custom business exception
    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleUserNotFound(UserNotFoundException ex) {
        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND, ex.getMessage());
        problemDetail.setTitle("User Not Found");
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problemDetail);
    }

    // Catching validation errors (e.g., from @Valid @RequestBody)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, String>> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(error -> 
            errors.put(error.getField(), error.getDefaultMessage()));
        return ResponseEntity.badRequest().body(errors);
    }
}
```

### Validation

Validation is the "Security Guard" of your Controller. Its job is to ensure that the data entering your system is sane, safe, and complete **before** it ever touches your database or business logic.

In Spring Boot, we use the **Jakarta Bean Validation** (formerly Hibernate Validator) to handle this declaratively using annotations.

Validation typically happens at the **DTO (Data Transfer Object)** level. You define rules on the object fields, and Spring enforces them during the "Data Binding" phase.

```java
public class UserRequest {

    @NotBlank(message = "Username is required")
    @Size(min = 3, max = 20, message = "Username must be between 3 and 20 characters")
    private String username;

    @Email(message = "Invalid email format")
    private String email;

    @Min(value = 18, message = "You must be at least 18 years old")
    private int age;

    @Pattern(regexp = "^[0-9]{10}$", message = "Phone number must be 10 digits")
    private String phoneNumber;
}
```


Now we can use it. 

```java
@PostMapping("/register")
public ResponseEntity<String> registerUser(@Valid @RequestBody UserRequest userRequest) {
    // If validation fails, this code NEVER runs.
    userService.save(userRequest);
    return ResponseEntity.ok("User registered successfully");
}
```

|**Annotation**|**Purpose**|**Example**|
|---|---|---|
|**`@NotNull`**|Field cannot be null.|`private Integer id;`|
|**`@NotEmpty`**|Not null AND size > 0 (for Collections/Strings).|`private List<String> tags;`|
|**`@NotBlank`**|Not null AND trimmed length > 0 (Strings only).|`private String name;`|
|**`@Min` / `@Max`**|Numerical boundaries.|`@Min(1) int quantity;`|
|**`@Past` / `@Future`**|Date validation.|`@Past LocalDate birthday;`|
|**`@Size`**|Length of string or size of a list.|`@Size(min=5) String pwd;`|
