### Quickly about the dependencies

They are the way to allow a function to depend on some other function. **Dependency Injection** is a fancy way of saying: "Before this function runs, I need you to go get something for me.

To use a dependency, you use the `Depends` class from `fastapi`.

```python
from fastapi import FastAPI, Depends

app = FastAPI()

# 1. Define the dependency (a simple function)
async def common_parameters(q: str | None = None, skip: int = 0, limit: int = 100):
    return {"q": q, "skip": skip, "limit": limit}

# 2. Use it in an endpoint
@app.get("/items/")
async def read_items(params: dict = Depends(common_parameters)):
    return params
```

When a request hits `/items/`, FastAPI looks at the `Depends(common_parameters)`.
They can be used to create the database connections, handle auth etc. 

### Alchemy 

It is an orm library which can convert the oops data into relational and vice versa. 

**Database Compatibility**
    - FastAPI can work with any relational database that has a compatible Python library.
    - Options include SQLite, PostgreSQL, MySQL, etc.

**Object Relational Mapping (ORM)**
    - ORM simplifies working with databases by converting Python objects into database records.
    - SQLAlchemy is commonly used ORM with FastAPI in this context.

**Data Flow for User Creation**    
    - **User Request Schema:** Collects user input such as username, email, and password.
    - **Database User Model:** Converts request data into a database-compatible format; involves security measures like password hashing.
    - **Creating Database Entry:** Uses the model to insert a new user into the database.
    - **User Response:** Confirms operation success; avoids exposing sensitive info like passwords

Now to work with databases in fastapi we first need to understand four components first one is request schema which we have studied, next comes Engine

#### Engine 

Engine is the source of connectivity and is an long lived object that application creates once. Engine uses dialect to translate the `SQLAlchemy's` command into specific sql strings so that database can understand. Note that we need to install the dialect as well for the working. 
Engine also opens the connection pools and keeps them in memory. In the fastapi model whenever we ask for a session object a connection pool is allocated to it from the backend.

To create engine we simply call the create_engine function with the following params. - 

- db_url
- echo - true/false - 
- connect_args - A dictionary which holds the configs - Notable key - `check_same_thread` 
- pool_size - Minimum number of connections
- max_overflow - Max number under load

```python
from sqlalchemy import create_engine

DATABASE_URL = "postgresql://user:password@localhost/dbname"

engine = create_engine(
    DATABASE_URL,
    echo=False,                # Set to True only for debugging
    pool_size=10,              # Keep 10 connections ready
    max_overflow=20,           # Allow up to 30 total under load
    pool_recycle=3600,         # Refresh connections every hour
    connect_args={"options": "-c timezone=utc"} # Example driver-specific arg
)
```

#### Base

Like BaseModel , in SQLAlchemy we define the base class `BASE` which acts as central registry. Everytime we create new class registry keeps track of the classes we have created. Base also has a hidden object called metadata which keeps track of table names , column types and foreign keys. 

#### Session 

Session is a single transaction with the database that happens during one http request. Note that `session`  object can be created from the engine via sessionfactory. Actually session implements what is called as the Unit of work pattern. Now once an http request comes you do the database transactions using the session object. Which actually manages the life cycle of the objects in memory and database. 

To create session object- 

```python
SessionLocal = sessionmaker(
    bind=engine,          # Which engine to use
    autoflush=True,       # Automatically push changes to DB before every query
    autocommit=False,     # ALWAYS keep this False in modern SQLAlchemy
    expire_on_commit=True # Objects become "stale" after commit; they reload on next access
)
```

Now understand that flush and commit are different - **Flush** sends SQL commands to the database (INSERT, UPDATE). The database "holds" them in a pending state. **Commit** tells the database, "Okay, we're done, make these changes permanent for everyone else to see."
Now you can get hold of the session by calling session object. Also these session objects are injected in the api's. Now the way these are injected is interesting - 

First we create from the `SessionLocal` using an database-

```python
from sqlalchemy import create_engine,sessionmaker

DATABASE_URL = "postgresql://user:password@localhost/dbname"

engine = create_engine(
    DATABASE_URL,
    echo=False,                # Set to True only for debugging
    pool_size=10,              # Keep 10 connections ready
    max_overflow=20,           # Allow up to 30 total under load
    pool_recycle=3600,         # Refresh connections every hour
    connect_args={"options": "-c timezone=utc"} # Example driver-specific arg
)

session = sessionmaker(autocommit=False, autoflush=False, bind=engine)

def get_db():
	db = session()
	try:
		yield db
	finally:
		db.close()
```


Note that this `get_db`  will be called by the fast api when injected via the dependency injection using Depend(get_db). Now first time when it is called db will be returned and the execution will stop at the `yield` and when api will finish again get_db will be called and connection will be closed. 

Now how to use it in `api`.

```python
from fastapi import FastAPI, Depends
from sqlalchemy.orm import Session
from .database import get_db

app = FastAPI()

@app.get("/users/")
def read_users(db: Session = Depends(get_db)):
    # You now have access to 'db' just like a normal SQLAlchemy session
    users = db.query(User).all()
    return users
```

Now that we have the access to the session object in call we can use it in various ways. 

### Refernece for the session object - 

- **`session.add(obj)`**: Moves a transient object to the "Pending" state.
- **`session.execute(statement)`**: The modern (2.0) way to run queries. Usually used with `select()`.
- **`session.flush()`**: This pushes all pending changes to the database (so the DB knows about them), but **does not** finalize the transaction. Useful if you need the database to generate an ID for an object so you can use it in a second step.
- **`session.commit()`**: The "Save" button. It flushes all changes and closes the transaction permanently.
- **`session.rollback()`**: The "Undo" button. If an error occurs, this reverts all changes made during that session.
- **`session.refresh(obj)`**: Re-loads the object's data from the database. Essential in FastAPI after a commit if you want to return the newly created object (with its ID and default values) to the user.
- **`session.close()`**: Releases the connection back to the Engine’s pool. In FastAPI, this is handled by the `finally` block in your dependency.

#### execute -

Earlier people used to use the query() which was used to be ORM-centric. It was there to make sql feel like python. We used to have the chain methods 

`session.query(User).filter_by(name="Alice").all()`

Now execute is the modern way to do it. It accepts the stametent using select or insert etc and then tell the session to `execute` the statement. 

Example - `session.execute(select(User).where(User.name == "Alice")).scalars().all()`

This execute returns the result object which on which we can specify how to get the data. 

General syntax - 

```python
from sqlalchemy import select, insert, update, delete

# The basic pattern
result = db.execute(statement)
```

Now the statments can be made using the sqlAlchemy expression language which is used to write the sql queries. 

#### SQLAlchemy expression language

In the ORM, you deal with **Classes** (like `User`). In the Expression Language, you deal with **Tables** and **Columns**. 

While the ORM is great for business logic, the Expression Language is much more powerful for:

- Complex reports and aggregations.
- Bulk data operations.
- Scenarios where you don't want the overhead of converting every row into a heavy Python object.

Read - 

```python
from sqlalchemy import select
from .models import User

# 1. Create the statement
stmt = select(User).where(User.email == "alex@example.com")

# 2. Execute it
result = db.execute(stmt)

# 3. Get the data
user = result.scalar_one_or_none() # Gets one object or None
# OR
users = result.scalars().all()    # Gets a list of objects
```

Create - 

```python
from sqlalchemy import insert

stmt = insert(User).values(name="John", email="john@test.com")
db.execute(stmt)
db.commit()
```

Update and delete

```python
from sqlalchemy import update

stmt = update(User).where(User.id == 5).values(name="New Name")
db.execute(stmt)
db.commit()
```

```python
from sqlalchemy import delete

stmt = delete(User).where(User.id == 5)
db.execute(stmt)
db.commit()
```

When you call db.execute(), you get a Result object back. You have several ways to extract data from it:

- all(): Returns all rows as a list of tuples.
- first(): Returns the first row and closes the result set.
- scalar(): Returns the first column of the first row (useful for count or single objects).
 - scalars(): Returns an iterator over the first column of each row (standard for getting Model objects).
 - mappings(): Returns rows as dictionaries (keys are column names).

### ORM way of handling 

ORM (Object-Relational Mapping) for CRUD is essentially a way to treat your database like a collection of Python objects. Instead of writing raw SQL strings, you interact with classes and instances.

Create - 

Here we use the `.add`. Note the object here need not be model but actual python object or pydantric object will also work. 

```python
# 1. Create the Python object
new_user = User(name="Bob", age=30)

# 2. Add it to the session "staging area"
db.add(new_user)

# 3. Save it to the database
db.commit()

# 4. Optional: Refresh to get the DB-generated ID
db.refresh(new_user)
```


Read - 

Reading data uses the `select()` statement. This is where you "ask" the database for specific rows.

```python
from sqlalchemy import select

# Fetch all users
stmt = select(User)
result = db.execute(stmt)
users = result.scalars().all()

# Fetch one specific user by ID
stmt = select(User).where(User.id == 1)
user = db.execute(stmt).scalar_one_or_none()
```

Update and delete follow the find first and then update or delete. The session object internally tracks that object is changed and then updates in db when using commit. 

```python
# 1. Get the object from the DB
user = db.execute(select(User).where(User.name == "Bob")).scalar_one()

# 2. Change an attribute
user.age = 31

# 3. Commit the change
db.commit()
```

```python
# 1. Get the object
user_to_delete = db.get(User, 1) # Short-cut for finding by Primary Key

# 2. Mark for deletion
db.delete(user_to_delete)

# 3. Commit
db.commit()
```

##### query

When you call `db.query(User)`, you are essentially telling the Session: _"Start a new search operation specifically for the User model."_
This returns a **Query Object**. Unlike the modern `select()` (which is just a static statement), a Query object is "live" and tethered to your database session.

1. **Initialization:** `db.query(User)` creates the object.    
2. **Modification:** You chain methods like `.filter()` or `.limit()`. Each one returns a _new_ Query object with that logic added.
3. **Automatic Compilation:** You never see the SQL. The Query object holds the "recipe" and waits.
4. **Implicit Execution:** The moment you call a "termination" method (like `.all()`), the Query object asks its parent Session to run the SQL and give back the results.

```python
# The "Classic" Chain
user = db.query(User)\
         .filter(User.email == "hello@example.com")\
         .order_by(User.created_at.desc())\
         .first()
```

Now note that first we need to specify the table by using the class name here User the we define the filter which is analogoues to where and then we need to define which column which we define by using `User.email` now the orm will have all the corresponding functions which can be used to track all the possibilities with sql where. Also we can chain the order etc. Note that this chain does not do anything. To notify db we need to first flush and then commit. `FLush` is just to notify the db and `commit` is used to flush data to disk. 

Now query can give us result object now we can use `db.delete(res_obj)` or do update etc. 

Note that these database requests are runned on the different threads by default by the sqlalchemy. However there are the async drivers which runs these async tasks on the single event loop this reduces the context switch time and we can effectively handle thousands of concurrent requests. 

Note that never try to mix the async with the normal synchronous sqlalchemy query. If you do that entire main event loop will be halted.
