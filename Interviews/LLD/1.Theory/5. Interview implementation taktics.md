```java
boolean inBounds(int r, int c) {

}
```

#### Ray casting technique

In low-level design (LLD) and game development, **ray casting** is a technique where you "shoot" a straight line (a ray) step-by-step from a starting position in a specific direction until it hits something like an obstacle or the edge of the board.

Niave way to track for an instance moves for a queen is to write a separate loop for every single direction inside each piece's class. For a Queen, you'd end up writing 8 different loops, duplicating a massive amount of logic. With ray casting we use starting point and the direction and move in that path until hit a blocker. 

Instead of hardcoding how a rook or bishop moves, you break their movements down into **directions** using coordinate offsets $(dx, dy)$


For any given direction, the ray-casting loop follows these simple rules:

1. **Start** at the piece's current square.
2. **Take a step** in the chosen direction (e.g., move one square right: $x + 1, y$).
3. **Check the square:**
    - **Out of bounds?** Stop ray casting in this direction (you fell off the board).
    - **Empty square?** Add it to the list of valid moves, then **keep going** in the same direction.
    - **Enemy piece?** Add it to the list of valid moves (you can capture it!), but **stop** (you can't jump over pieces).
    - **Friendly piece?** **Stop** immediately (you can't pass through or capture your own team).
4. **Repeat** for all valid directions of that piece.

This ray casting is not only usable in a good game of chess but also in other places for an example consider this 

```java
private int countInDirection(int col, int row, int dc, int dr, BoardState color) {
	int count = 0;
	int c = col + dc;
	int r = row + dr;
	while (c >= 0 && c < COLS && r >= 0 && r < ROWS && grid[c][r] == color) {
		count++;
		c += dc;
		r += dr;
	}
	return count;
}
```

Most of the times you will use some kind of while loop here. 

#### Checking for only the last move

The obvious way to check a win is to scan the whole board after every move. For Connect Four that is 42 cells times 4 directions every time, and it gets worse for bigger boards. But the board was not a win before this move, so if there is a win now it must pass through the cell we just filled. So we only check the lines through that cell. For each direction we count matching discs forward and backward and add 1 for the cell itself.

Tic tak toe game make move for an `n X n` game can be solved in `O(1)` time. We keep one counter per row, one per column, and one each for the two diagonals. Player 1 adds +1 and player 2 adds -1. A row is fully owned by one player only when its counter is n or -n , because any mix of players pulls it away from the edge.

Also while we are at remember for a diagonal of board `r==c` and for antidiagonal `r+c=n-1`

##### Validate, mutate, check and advance

When we write an action method like makeMove , bookSeat or dispense , the obvious way is to just start doing things and add checks wherever we remember them. This is how we end up with bugs like the turn changing even when the move was invalid, or money being deducted before we found out the item is out of stock.

So we fix the order once and follow it every time:
1. Validate everything that can fail, and return early. Nothing is changed yet, so failing is free.
2. Mutate the state.
3. Check consequences of the change (win, draw, low stock, booking full).
4. Advance to the next state or player

##### Modular turn rotation

With two players the obvious way is a ternary: current = (current == RED) ? BLUE : RED . This works, but the moment the interviewer says "now support 4 players" we have to rewrite it. So we keep players in a list and an index, and move the index with % . Now the number of players doesn't matter.

```java
List<Player> players;
int turn = 0;
Player current() { return players.get(turn); }
void advance() { turn = (turn + 1) % players.size(); }
```

##### Enum state machine with transition table

In a naive implementation, business rules for state transitions are scattered across multiple methods and classes:

- `cancelOrder()` checks `if (status == CREATED || status == PAID) ...`
- `shipOrder()` checks `if (status == PAID) ...`

**Why this fails:**

- **Scattered Logic:** The full lifecycle of the order is hidden across the codebase.
- **Open/Closed Principle Violation:** Adding a new state or changing a rule requires modifying multiple methods, increasing the risk of bugs.
- **Invalid States:** It’s easy to accidentally allow an illegal transition (e.g., jumping straight from `CREATED` to `SHIPPED`).

Instead of scattering rules, we consolidate everything into a **Single Source of Truth**: a **Transition Table** (implemented as a map or adjacency list) that defines precisely which states can legally transition to other states.

The Order Lifecycle Rules:

- `CREATED` $\rightarrow$ `PAID`, `CANCELLED`
- `PAID` $\rightarrow$ `SHIPPED`, `CANCELLED`
- `SHIPPED` $\rightarrow$ `DELIVERED`
- `DELIVERED` $\rightarrow$ _(Terminal State — no transitions allowed)_
- `CANCELLED` $\rightarrow$ _(Terminal State — no transitions allowed)_

A good example is 

```java
import java.util.*;

public class Order {

    public enum OrderState {
        CREATED, PAID, SHIPPED, DELIVERED, CANCELLED
    }

    // The Transition Table (Single Source of Truth)
    private static final Map<OrderState, Set<OrderState>> VALID_TRANSITIONS = new HashMap<>();

    static {
        VALID_TRANSITIONS.put(OrderState.CREATED, EnumSet.of(OrderState.PAID, OrderState.CANCELLED));
        VALID_TRANSITIONS.put(OrderState.PAID, EnumSet.of(OrderState.SHIPPED, OrderState.CANCELLED));
        VALID_TRANSITIONS.put(OrderState.SHIPPED, EnumSet.of(OrderState.DELIVERED));
        VALID_TRANSITIONS.put(OrderState.DELIVERED, EnumSet.noneOf(OrderState.class));
        VALID_TRANSITIONS.put(OrderState.CANCELLED, EnumSet.noneOf(OrderState.class));
    }

    private OrderState currentState;

    public Order() {
        this.currentState = OrderState.CREATED; // Initial state
    }

    public boolean transitionTo(OrderState nextState) {
        if (isValidTransition(nextState)) {
            this.currentState = nextState;
            // Trigger side-effects here (e.g., send email, update DB)
            return true;
        }
        throw new IllegalStateException("Invalid transition from " + currentState + " to " + nextState);
    }

    public boolean isValidTransition(OrderState nextState) {
        Set<OrderState> allowedStates = VALID_TRANSITIONS.get(currentState);
        return allowedStates != null && allowedStates.contains(nextState);
    }

    public OrderState getCurrentState() {
        return currentState;
    }
}
```

- **Declarative vs. Imperative:** Instead of writing _how_ to check rules imperative-style via messy conditions, we declare _what_ is allowed upfront in a data structure.
- **Extensibility:** If product management introduces a new state (e.g., `REFUNDED`), you only update the static map rather than hunting down `if/else` blocks across 10 different files.
- **Testability:** You can easily write unit tests that iterate over _every possible pair_ of states to verify that illegal transitions throw exceptions and legal ones succeed.

Similer to this a side pattern where we create a lookup table instead of writing if/else for rules. In gerel whenever set of if/else can be changed with lookup table do that.
