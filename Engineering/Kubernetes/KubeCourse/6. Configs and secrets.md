These are the objects which can be used to push the configurations and secrets to pods , deployments etc. Both don't have spec field instead have `data` fields as they are data objects. 

### Config maps

Comes under core `v1` . Its simply a set of key value pairs which will be taken by the kubernetes api. How will they be injected is different issue. Note that name here is important as we will be using name to refernce it. Note `|` means whole file as a value. This file is yaml file. 

To create first

```yaml
apiVersion: v1
kind: ConfigMap
data:
	LABAL_KEY: LABEL_VALUE
	....
	application.yaml: |              # a whole file as a value
	    server:
	      port: 8080
	    cache:
		ttl: 300s
binaryData:
  keystore.jks: <base64>           # for non-UTF-8 content
```

The 1 MiB size limit is a hard etcd constraint. If your configuration is approaching it, it belongs on a volume or in object storage, not in a ConfigMap.

#### Secrets 

They are structurally identical but have a type and values are base64 encoded. If you want to pass values as normal string and let the kubernetes itself parse them before storing use `stringData` field

```yaml
apiVersion: v1
kind: Secret
metadata:
	name: secret
data:
	username: adil
	password: weiocwei 
stringData:
	data: 230-9v# 
```

Common `type` values matter because consumers look for them:

|Type|Required keys|Used by|
|---|---|---|
|`Opaque`|any|general|
|`kubernetes.io/dockerconfigjson`|`.dockerconfigjson`|`imagePullSecrets`|
|`kubernetes.io/tls`|`tls.crt`, `tls.key`|Ingress, cert-manager|
|`kubernetes.io/service-account-token`|—|legacy SA tokens|
|`kubernetes.io/basic-auth`|`username`, `password`|various controllers|

What a Secret _does_ give you over a ConfigMap:

- Values are not printed by `kubectl describe`.
- It can be restricted separately by RBAC.
- It can be encrypted at rest, **if you configure that**.
- The kubelet stores it in tmpfs (memory), not on node disk.
- It is only distributed to nodes running a Pod that uses it.

### Injecting to pods

First method directly inject as env. Here we have two methods as well. First one is to inject as individual keys. Or we can pass every key at once. Note in both we reference env field of the spec.container

```
spec:
	containers:
		- name: 
		  image:
		  env:
			  - name:
			    value:
```

Look how we refernce it. First we reference the configmap by name then we reference the field and optionally change the actual field name. 

```
env:
	- name: LOG_LEVEL # Actual env name we will get
	  valueFrom:
		  configMapKeyRef:
			  name: app-config
			  key: LOG_LEVEL # key in configmap
```

Also we can get all the keys at once using `envFrom`. 

```
envFrom:
  - configMapRef:
      name: app-config
  - secretRef:
      name: db-credentials
      prefix: DB_             # optional prefix
```

### Volume mounts

Second method is to mount the secret on the pod. ConfigMap will get mounted as a readonly file system. Secrets are mapped as in memory filesystems. To do this we create configMaps and then create a volume at pod level and then at container level add a volumeMount to define the path to get mount to. 

```yaml
spec: # spec of container
	containers:
		- name:
		  image:
		  volumeMounts:
			  - name: user-config
			    mountPath: /user/data
			  - name: user-secret
			    mountPath: /user/secret
	volumes:
		- name: user-config
		  configMap:
			  name: config-map-name # actiual 
		- name: user-secret
		  secret: 
			  secretName: secret-name # secret multiple screts can be seen
```

**Environment variables are set at process start.** Linux provides no mechanism to change another process’s environment. The only way to pick up a change is to restart the container.

**Volume mounts are updated by the kubelet**, which periodically resyncs and atomically swaps a symlink so readers never see a partial file. The delay is the kubelet sync period plus cache TTL.

So although we are doing like this we can not pass these yamls to others since the secrets are present  `ExternalSecretManager` solves this **External Secrets Operator.** A controller syncs from AWS Secrets Manager, Vault, or similar into Kubernetes Secrets. Git contains only a reference:

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secret-store
    kind: ClusterSecretStore
  target:
    name: db-credentials
  data:
    - secretKey: password
      remoteRef:
        key: prod/db
        property: password

```
