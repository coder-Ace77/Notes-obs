### Functional requirements

**Core Requirements**
1. Users can upload videos.
2. Users can watch (stream) videos.

### Non functional requirements

**Core Requirements**

1. The system should be highly available (prioritizing availability over consistency).
2. The system should support uploading and streaming large videos (10s of GBs).
3. The system should allow for low latency streaming of videos, even in low bandwidth environments.
4. The system should scale to a high number of videos uploaded and watched per day (~1M videos uploaded per day, 100M videos watched per day).
5. The system should support resumable uploads.

### Core entities

- User
- Video
- Videomatadata

### API 

```
POST /upload
Request:
{
  Video,
  VideoMetadata
}

GET /videos/{videoId} -> Video & VideoMetadata
```


### High level design

First lets tackle the upload part like earlier we will be uploading the video to the s3 via multipart and resumable upload strategy with retry logic on client. Once fully uploaded we can then update the status on the db via trust but verify strategy. This handles the upload efficiently. 

To view and watch we can again get the metadata directly and then diretly get the video from s3 again. This compleses the both functional requirements.

#### Handling large video files

Current design has limitation that we need to download entire video before it can be watched which is definitely not good. We want to have better streaming latency.  So we will rechunk the video via a chunker service which will get notification that a video is uploaded and will chunk the given video into smaller portions. Now in metadata we will have s3 urls of every chunks so once client wants to watch a video we will either provide the list of all chunks or will give it to the client one by one we can try to store the remaining video in background at client so that perceived latency is reduced. 

### Handling slow connection

To handle slower connection and give it good latency we can stream them lower resolution chunks. So when chunker does chunking we can also trnascode the video into lower resolutions. and then now chunks will have Chunks resolution and that's it. 

Now the client can be adaptive and will fetch the next chunks so it will determince which kinds of chunks are needed next maybe our internet connection upgraded or maybe downgraded so we also get the better or worst quality. 

Finally we can introduce the cdn for storing chunks. 

Now this streaming is so popular that we have two streaming protocols which can do chunking, apaditve bitrate and resolutions - 

Two of them are - 
 - DASH (open source)
 - HLS (APPLE developed)

Availabilty is also done since we are stateless and the chunking etc is stateless. `S3` is infinitely scalable. 

Now the data in db  `= 1m*1kb&365 = .375TB`. We can shard based on the videoId and if decide to use relational db we can work with two tables metadata and chunks.
