Dropbox is basically drive a storage file accessible from browser. 
### Functional requirements

- Users should be able to upload files from any device. 
- Users should be able to dwonload files from any device
- Users should be able to share a file with other users and view the files shared with them
- Users can automatically sync files across devices

OOS - 
- Edit file
- View file

### Non functional requirements

-  System should be highly available(availabilty over consistency)
- Support file versioning
- Anti virus scan
- low latency uploads and downloads
- Suppose large files (<=50gb)
- Resumable upload
- high data integrety

## NFR's 

It won't work large files. We need chunking. So we will create chunks of files say may be 5mb each. Now once chunks have been introduced we need to update the status of the chunks. Each chunk is like its own file with default size say 5mb and some chunks can be smaller. This chunking helps us to upload file in smaller parts. Additionally each chunk needs to have id, a presigned url and a status.  

Chunking solves two problems at once - 

- First - We needed to support large files which is possible now very easily. Since chunking is there we will simply upload and update the status of each chunk to uploaded. 
- Second - If upload stalled at any point we will comming back online will compare both the `server` and `client` side and will be able to get to the point figuring out which chunks are not uploaded and needs to get reuploaded. 

Finally to have the `chunk_id` we can calculate the chunk id as the hash of the file content. And we will be done at this point. 
Now how do we update the status of uploaded chunk now there are two main ways -

- Either client may tell that its done. But obsere that client may lie. This is not fully secure. 
- Second - We can use the pattern called trust but verify. In this pattern the client will tell the backend that chunk has been uploaded , but now backend instead of updating will also verify this info with s3 and then update. 

Note that this chunking and validation is so popular that `s3` provides its own solution called multipart which keeps track of all this. Also S3 provides the `CDC` so when a chunk is uploaded a `s3` notification is triggered and which can also be used to update the backend and in this way we will not be relying on the backend itself. 

Additionally we can add the compression on the client side however note that compression is very great for formats like text files however formats like jpg etc are already compressed to begin with. 

For upload, chunking, beyond being useful for resumable uploads, also plays a significant role in speeding up the upload process. While bandwidth is fixed (put another way, the pipe is only so big), we can use chunking to make the most of the bandwidth we have. By sending multiple chunks in parallel, and utilizing adaptive chunk sizes based on network conditions, we can maximize the use of available bandwidth. The same chunking approach can be used for syncing files. When a file changes, we only need to sync the chunks that actually changed rather than the entire file, making syncing much faster.

One subtlety worth calling out is that if you use fixed-size chunks (e.g., every 5MB), inserting a single byte near the beginning of the file shifts all subsequent chunk boundaries, causing _every_ chunk after the edit to produce a different fingerprint. This makes delta sync nearly useless. The solution is Content-Defined Chunking (CDC), where chunk boundaries are determined by the file's content using a rolling hash (like Rabin fingerprinting). With CDC, a small edit only affects the chunks immediately surrounding the change, the vast majority of chunks remain identical. This is how systems like Dropbox actually achieve efficient delta sync in practice.

### Security

We should also encrypt the files when they are stored in S3. This is a feature of S3 and is easy to enable. When a file is uploaded to S3, we can specify that it should be encrypted. S3 will then encrypt the file using a unique key and store the key separately from the file. This way, even if someone gains access to the file, they won't be able to decrypt it without the key. You can learn more about S3 encryption. 

Our shareList or separate share table/cache is our basic ACL. As discussed earlier, we make sure that we share download links only with authorized users.

This is where those signed URLs we talked about early come back into play. When a user requests a download link, we generate a signed URL that is only valid for a short period of time (e.g. 5 minutes). This signed URL is then sent to the user, who can use it to download the file. It's worth noting that signed URLs are bearer tokens - anyone with a valid, unexpired URL can download the file. The short expiration window limits the exposure, but doesn't fully prevent sharing. For higher security scenarios, you could add additional restrictions like IP binding or require the signed URL to be used in conjunction with authentication cookies.

### Event bus architecture of dropbox

Currently our system has been using the polling so for example each 10s or so its asking the server if anything changed on server or not. 
At Dropbox's scale, this is a disaster. If 700 million users poll every 30 seconds, the servers are crushed by a "thundering herd" of requests—most of which return "No changes." To solve this, Dropbox moved toward an **event-driven architecture**. Instead of the client asking for news, the server broadcasts news the moment it happens.

Dropbox clients and servers both maintain the mutation journal. Every change—a rename, an edit, a deletion—is treated as a **mutation**. These mutations are written to a massive, distributed database (internally known as **Edgestore**). But writing to a database is a "passive" act; the database doesn't inherently tell the world it has been updated.

This is where the EventBus enters. Once a mutation is committed to the database, a service "publishes" an event to the Bus. The Bus is a high-throughput messaging queue (built on technologies like **Apache Kafka**). It doesn't contain the file itself; it contains a **notification** that something changed in a specific "Namespace" (Dropbox's term for a shared folder or account).

The true challenge of Dropbox is **fan-out**. If you edit a file in a shared folder with 50 teammates, one event must be replicated 50 times. The EventBus identifies every device currently "subscribed" to that folder and routes the message to the **Notification Server**.

The notification is a tiny, encrypted packet that essentially says: _"Hey, Folder XYZ just moved from Version 10 to Version 11."_ 1. **The Wake-up:** Your coworker’s laptop receives this poke via a long-lived connection (like a WebSocket). The laptop realizes it’s behind. It then makes a targeted request to a **Delta Server**: _"Give me the changes for Folder XYZ between Version 10 and 11."_ The Delta Server sends only the specific pieces of data (the "deltas") needed to update the file.
