## What Low Level Design actually asks of you

Low Level Design is the phase where a rough idea gets turned into classes that a computer can run. High Level Design tells you there will be a scheduler service. Low Level Design tells you what a `Node` object looks like, what a `Pod` object looks like, and what method gets called when a pod needs a home. It is the difference between drawing a box labeled scheduler on a whiteboard and actually writing the code that decides which machine a workload lands on.

Most people fail LLD interviews not because they do not know design patterns. They fail because they jump into code before they understand the problem. So before we touch the container scheduler problem let us build a small mental checklist you can carry into any LLD problem, not just this one.

### Step 1: Read the problem like a product spec, not a coding question

Every LLD prompt hides two things inside plain English. It hides the nouns, which become your classes. And it hides the verbs, which become your methods. When someone says "pods request cpu and memory and the scheduler places them on nodes that have room" you should already be underlining three nouns. Pod. Node. Scheduler. And two verbs. Request. Place.

Do this before writing a single class. Say the requirements out loud in your own words and list what nouns and verbs keep repeating.

### Step 2: Find the one hard decision the problem is testing

Almost every LLD problem has one place where two requirements pull against each other. A parking lot problem tests whether you can swap the pricing strategy without touching the parking lot class. A rate limiter problem tests whether your algorithm stays correct under concurrent hits. The interviewer already knows the entities are easy. What they want to see is whether you can spot the tension and design around it cleanly instead of patching it with more if statements.

For a container scheduler the tension is this. A pod cannot just go on any node that has room. First you eliminate nodes that genuinely cannot host the pod. Then, among the nodes that survive, you rank them and pick the best one. Two separate questions, two separate mechanisms, and both need to be pluggable because real scheduling rules change all the time.

### Step 3: Sketch entities and relationships before code

Write down each entity as a one line description of what it owns and what it knows. Do not write methods yet. Just ownership. A `Node` owns its capacity and what is currently running on it. A `Pod` owns what it needs and how important it is. A `Scheduler` owns nothing permanent, it just makes decisions using the other two.

### Step 4: Design the interfaces first

The single biggest tell of a strong LLD answer is that swappable behavior lives behind an interface, not inside a giant method full of conditionals. If a rule might change later, for example how we score nodes, that rule becomes an interface with one method, and the scheduler simply loops over a list of them. This is what lets you say during an interview "if tomorrow we want to add a new scheduling rule, we just write one new class, nothing else changes."

### Step 5: Get single threaded correctness first, then add concurrency

Many candidates panic and start adding locks before the core logic even works for one thread. Do not do that. Get the filter and score logic correct first. Only after that is solid should you reason about what happens when two requests try to bind two different pods to the same node at the same time.

### Step 6: Write code that shows the design, not code that shows off

You do not need every getter, every null check, every exception type to be production perfect. You need the reader to look at your classes and immediately understand who is responsible for what. That is the actual skill being tested.

Keep this checklist in your head. Now let us apply it to problem fifty from the platform and infra tier, the container scheduler, which is basically Kubernetes with the edges sanded off.

## Understanding the container scheduler problem

Picture a small data center. There are a handful of machines, each with a fixed amount of cpu and memory. Work arrives in units called pods. Each pod says how much cpu and memory it needs and how important it is compared to other pods. Your job is to write the piece of software that decides which machine each pod runs on.

This sounds simple until you notice the real constraints that Kubernetes actually deals with, scaled down to something you can build in an interview or a weekend project.

A node might not be eligible for a pod at all, for example it does not have enough free memory, or it has been marked as unavailable for a certain kind of workload. This is the filtering question, does the pod even fit here.

Among the nodes where the pod does fit, some are still better choices than others. Maybe you want to spread pods evenly across machines instead of stacking everything on one box. This is the scoring question, which eligible node is the best choice.

Nodes fail, pods crash, and the world drifts away from what you intended. Something needs to keep checking the actual state of the cluster against the desired state and correct the difference. This is the reconciliation loop, the heartbeat of the whole system.

Sometimes every node is full but a new pod is more important than something already running. In that case the scheduler should be willing to evict a lower priority pod to make room for a higher priority one. This is preemption.

If you can build these four pieces cleanly, you have built the core of Kubernetes.

---

## Breaking the problem into entities

Following the checklist, here are the nouns from the problem statement turned into classes.

A `ResourceRequest` is simply how much cpu and memory something needs. It has no behavior, it is a small value object.

A `Node` represents one machine. It knows its total capacity, how much is currently used, and which pods are running on it. It can answer the question can this pod fit here, and it can allocate or release resources.

A `Pod` represents one unit of work. It knows what it needs, how important it is, and what state it is in, waiting to be scheduled, running, or failed.

A `Predicate` is a single filtering rule. Does this pod fit on this node. You will have more than one of these eventually, so it becomes an interface.

A `PriorityFunction` is a single scoring rule. Given that a pod fits on a node, how good a fit is it. Also an interface, also pluggable.

A `Scheduler` ties predicates and priority functions together. It takes a pod, filters the nodes, scores what survives, and binds the pod to the winner.

A `Controller` is the reconciliation loop. It keeps a queue of pods waiting to be placed and keeps retrying them, because a node that has no room today might have room in five seconds once something else finishes.

Now let us actually write this in Java.

## Building the resource model

Every design starts with the simplest, most boring class. Resist the urge to skip it.

```java
public class ResourceRequest {
    private final int cpu;
    private final int memory;

    public ResourceRequest(int cpu, int memory) {
        this.cpu = cpu;
        this.memory = memory;
    }

    public int getCpu() {
        return cpu;
    }

    public int getMemory() {
        return memory;
    }
}
```

## The Pod class

A pod carries what it needs, how important it is, and its current status. Status matters because a pod is not a fire and forget object. It moves through states as the scheduler works on it.

```java
public class Pod {

    public enum Status {

        RUNNING,
        FAILED
    }

    private final String id;

        return id;
    }

        return request;
    }

    public int getPriority() {
        return priority;
    }

    public Status getStatus() {
        return status;
    }

        this.status = status;

        return nodeId;
```

## The Node class

A node owns capacity and the pods running on it. Keep the allocate and release methods synchronized because multiple scheduling decisions could touch the same node at once in a real system, and this is a cheap way to protect the invariant that used resources never exceed capacity.

```java
import java.util.HashMap;
import java.util.Map;

public class Node {

    private final String id;
    private final int cpuCapacity;
    private final int memoryCapacity;
    private int cpuUsed;
    private int memoryUsed;
    private final Map<String, Pod> runningPods = new HashMap<>();

    public Node(String id, int cpuCapacity, int memoryCapacity) {
        this.id = id;
        this.cpuCapacity = cpuCapacity;
        this.memoryCapacity = memoryCapacity;
    }

    public String getId() {
        return id;
    }

    public synchronized boolean canFit(ResourceRequest request) {
        return cpuUsed + request.getCpu() <= cpuCapacity
                && memoryUsed + request.getMemory() <= memoryCapacity;
    }

    public synchronized void allocate(Pod pod) {
        cpuUsed += pod.getRequest().getCpu();
        memoryUsed += pod.getRequest().getMemory();
        runningPods.put(pod.getId(), pod);
    }

    public synchronized void release(Pod pod) {
        cpuUsed -= pod.getRequest().getCpu();
        memoryUsed -= pod.getRequest().getMemory();
        runningPods.remove(pod.getId());
    }

    public synchronized int freeCpu() {
        return cpuCapacity - cpuUsed;
    }

    public synchronized int freeMemory() {
        return memoryCapacity - memoryUsed;
    }

    public synchronized Map<String, Pod> getRunningPods() {
        return new HashMap<>(runningPods);
    }
}
```

Notice that `Node` never talks to `Scheduler`. It only exposes what it knows about itself. This is what keeps the design clean. The node does not decide anything, it just reports its own state honestly.

## Filtering, the predicate interface

This is the first half of the two phase decision. A predicate answers one yes or no question about whether a pod could possibly run on a node.

```java
public interface SchedulingPredicate {
    boolean test(Node node, Pod pod);
}
```

The most obvious predicate is resource fit.

```java
public class ResourceFitPredicate implements SchedulingPredicate {

    @Override
    public boolean test(Node node, Pod pod) {
        return node.canFit(pod.getRequest());
    }
}
```

You could add more predicates later, for example a node that is marked unschedulable, or a pod that must avoid certain nodes. The point of making this an interface is that adding a new rule never touches the scheduler itself. You just add the rule to a list.

## Scoring, the priority function interface

Once you know which nodes are eligible, you need a way to rank them. A priority function looks at a node and a pod and returns a number, the higher the better.

```java
public interface PriorityFunction {
    int score(Node node, Pod pod);
}
```

A very natural rule is to prefer nodes that have more free capacity relative to their total size, which keeps load spread evenly across the cluster instead of stacking pods onto the first machine that fits.

```java
public class LeastRequestedPriority implements PriorityFunction {

    private static final int MAX_SCORE = 100;

    @Override
    public int score(Node node, Pod pod) {
        double cpuFraction = (double) node.freeCpu() / totalCpu(node);
        double memFraction = (double) node.freeMemory() / totalMemory(node);
        double freeFraction = (cpuFraction + memFraction) / 2.0;
        return (int) (freeFraction * MAX_SCORE);
    }

    private int totalCpu(Node node) {
        return node.freeCpu() + usedCpu(node);
    }

    private int totalMemory(Node node) {
        return node.freeMemory() + usedMemory(node);
    }

    private int usedCpu(Node node) {
        return node.getRunningPods().values().stream()
                .mapToInt(p -> p.getRequest().getCpu())
                .sum();
    }

    private int usedMemory(Node node) {
        return node.getRunningPods().values().stream()
                .mapToInt(p -> p.getRequest().getMemory())
                .sum();
    }
}
```

In a real system you would expose total capacity directly from `Node` instead of recomputing it like this. The version above keeps `Node` minimal on purpose so you can see the two responsibilities staying separate, the node reports facts and the priority function turns facts into a score.

## The scheduler itself

The scheduler owns the two phase decision. Filter first, score second, bind last.

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.Optional;

public class Scheduler {

    private final List<Node> nodes;
    private final List<SchedulingPredicate> predicates;
    private final List<PriorityFunction> priorityFunctions;

    public Scheduler(List<Node> nodes,
                      List<SchedulingPredicate> predicates,
                      List<PriorityFunction> priorityFunctions) {
        this.nodes = nodes;
        this.predicates = predicates;
        this.priorityFunctions = priorityFunctions;
    }

    public Optional<Node> schedule(Pod pod) {
        List<Node> feasible = filter(pod);
        if (feasible.isEmpty()) {
            return Optional.empty();
        }
        Node chosen = pickBest(feasible, pod);
        bind(chosen, pod);
        return Optional.of(chosen);
    }

    private List<Node> filter(Pod pod) {
        List<Node> result = new ArrayList<>();
        for (Node node : nodes) {
            if (passesAllPredicates(node, pod)) {
                result.add(node);
            }
        }
        return result;
    }

    private boolean passesAllPredicates(Node node, Pod pod) {
        for (SchedulingPredicate predicate : predicates) {
            if (!predicate.test(node, pod)) {
                return false;
            }
        }
        return true;
    }

    private Node pickBest(List<Node> feasible, Pod pod) {
        return feasible.stream()
                .max(Comparator.comparingInt(node -> totalScore(node, pod)))
                .orElseThrow();
    }

    private int totalScore(Node node, Pod pod) {
        int total = 0;
        for (PriorityFunction fn : priorityFunctions) {
            total += fn.score(node, pod);
        }
        return total;
    }

    private void bind(Node node, Pod pod) {
        node.allocate(pod);
        pod.setNodeId(node.getId());
        pod.setStatus(Pod.Status.RUNNING);
    }
}
```

Read this class out loud. Filter narrows the field. Score picks a winner. Bind makes it real. Three small private methods, each doing exactly one job, and the public `schedule` method reads like a sentence describing the algorithm. This readability is exactly what an interviewer is scoring you on.

## Adding preemption

Sometimes every node fails the filter step because nothing has enough free room. But if the incoming pod is more important than something already running, we should be willing to evict lower priority pods to make space. This is the part of the problem that separates a toy scheduler from something that resembles Kubernetes.

The idea is simple even though it looks intimidating. For each node, look at the pods running there that are less important than the new pod. Sort them from least important to most important. Start removing them one at a time, in your head, and check after each removal whether there would now be enough room. If yes, that node becomes a valid preemption target and those pods are the victims.

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.Optional;

public class PreemptingScheduler {

    private final Scheduler baseScheduler;
    private final List<Node> nodes;

    public PreemptingScheduler(Scheduler baseScheduler, List<Node> nodes) {
        this.baseScheduler = baseScheduler;
        this.nodes = nodes;
    }

    public Optional<Node> schedule(Pod pod) {
        Optional<Node> placed = baseScheduler.schedule(pod);
        if (placed.isPresent()) {
            return placed;
        }
        return scheduleWithPreemption(pod);
    }

    private Optional<Node> scheduleWithPreemption(Pod pod) {
        for (Node node : nodes) {
            List<Pod> victims = findVictims(node, pod);
            if (victims != null) {
                evict(node, victims);
                node.allocate(pod);
                pod.setNodeId(node.getId());
                pod.setStatus(Pod.Status.RUNNING);
                return Optional.of(node);
            }
        }
        return Optional.empty();
    }

    private List<Pod> findVictims(Node node, Pod pod) {
        List<Pod> candidates = new ArrayList<>();
        for (Pod running : node.getRunningPods().values()) {
            if (running.getPriority() < pod.getPriority()) {
                candidates.add(running);
            }
        }
        candidates.sort(Comparator.comparingInt(Pod::getPriority));

        int freedCpu = node.freeCpu();
        int freedMemory = node.freeMemory();
        List<Pod> victims = new ArrayList<>();

        for (Pod candidate : candidates) {
            if (enough(freedCpu, freedMemory, pod)) {
                break;
            }
            victims.add(candidate);
            freedCpu += candidate.getRequest().getCpu();
            freedMemory += candidate.getRequest().getMemory();
        }

        return enough(freedCpu, freedMemory, pod) ? victims : null;
    }

    private boolean enough(int freeCpu, int freeMemory, Pod pod) {
        return freeCpu >= pod.getRequest().getCpu()
                && freeMemory >= pod.getRequest().getMemory();
    }

    private void evict(Node node, List<Pod> victims) {
        for (Pod victim : victims) {
            node.release(victim);
            victim.setStatus(Pod.Status.PENDING);
            victim.setNodeId(null);
        }
    }
}
```

Notice that eviction does not just delete the victim pods, it sets them back to pending. Somewhere else in the system, the reconciliation loop will pick them up and try to place them again, hopefully on a different node this time. Nothing is lost, it is just displaced. That is the same idea Kubernetes uses, preemption never destroys work, it just reschedules it.

## The reconciliation loop

Real clusters are not static. A node might be full right now and have room a minute later once other pods finish. A pod might fail to schedule the first time and needs to be retried. The controller is the piece that keeps trying, on a timer, forever, comparing what should be running against what is actually running.

```java
import java.util.LinkedList;
import java.util.Optional;
import java.util.Queue;

public class SchedulerController {

    private final PreemptingScheduler scheduler;
    private final Queue<Pod> pendingPods = new LinkedList<>();

    public SchedulerController(PreemptingScheduler scheduler) {
        this.scheduler = scheduler;
    }

    public void submit(Pod pod) {
        pendingPods.add(pod);
    }

    public void reconcile() {
        int attempts = pendingPods.size();
        for (int i = 0; i < attempts; i++) {
            Pod pod = pendingPods.poll();
            if (pod == null) {
                break;
            }
            Optional<Node> result = scheduler.schedule(pod);
            if (result.isEmpty()) {
                pendingPods.add(pod);
            }
        }
    }
}
```

`reconcile` is meant to be called again and again, for example every few seconds by a scheduled executor. Each call takes one pass through the current backlog of pending pods and tries to place each one. Pods that still cannot be placed go back on the queue for the next pass. This is the whole idea of a control loop in one small method, keep nudging the actual state toward the desired state, and be fine with the fact that it might take more than one attempt.

## Wiring it together

```java
import java.util.List;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

public class ClusterDemo {

    public static void main(String[] args) {
        Node nodeA = new Node("node-a", 8, 16);
        Node nodeB = new Node("node-b", 8, 16);

        Scheduler baseScheduler = new Scheduler(
                List.of(nodeA, nodeB),
                List.of(new ResourceFitPredicate()),
                List.of(new LeastRequestedPriority())
        );

        PreemptingScheduler scheduler = new PreemptingScheduler(baseScheduler, List.of(nodeA, nodeB));
        SchedulerController controller = new SchedulerController(scheduler);

        controller.submit(new Pod("pod-1", new ResourceRequest(2, 4), 5));
        controller.submit(new Pod("pod-2", new ResourceRequest(3, 6), 5));
        controller.submit(new Pod("pod-3", new ResourceRequest(9, 4), 9));

        ScheduledExecutorService executor = Executors.newSingleThreadScheduledExecutor();
        executor.scheduleAtFixedRate(controller::reconcile, 0, 2, TimeUnit.SECONDS);
    }
}
```

`pod-3` needs nine units of cpu, which is more than either single node has as total capacity, so this particular example would never place it even with preemption. That is intentional, it shows the honest limit of the design, a scheduler can move work around but it cannot make a machine bigger than it is. In a real interview you would point this out yourself, that is the kind of observation that shows depth.

## Making it safe under multithreading

Everything so far works perfectly as long as only one pod is ever being scheduled at a time. That is a fine place to start, since you always want correctness on a single thread before you touch concurrency at all. But a real cluster is deciding placement for many pods at once, and the queue is being fed by several workload controllers on their own timers. So let us walk through exactly where this design breaks under concurrency and fix it piece by piece.

### Where the race actually lives

Look again at what `schedule` does. It reads the state of every node during filtering, decides on a winner during scoring, and only touches shared state during the final `allocate` call in bind. That gap between reading and writing is exactly where trouble happens.

Picture two pods being scheduled on two different threads at the same moment, pod one and pod two, and only one node in the whole cluster has enough free room for either of them, node x. Thread one filters and finds node x fits pod one, since nothing is allocated yet. Thread two filters at almost the same instant and finds node x also fits pod two, for the same reason. Neither thread has written anything yet, so neither one sees the other coming. Both threads then proceed to bind, both call allocate on node x, and node x now holds more cpu and memory than it physically has. This is a classic check then act race, the check happened on one snapshot of the world and the act happened on a world that had already moved on.

Locking the entire cluster during every single scheduling decision would fix this, but it also means only one pod can ever be placed at a time, which throws away the whole reason you wanted multiple threads.

### Fixing it, make the reservation itself atomic

The real fix is to stop treating checking and reserving as two separate steps. Node already declares its methods synchronized, which means each individual method is safe on its own, but that does not help when the scheduler calls two separate methods, canFit and then allocate, with a gap of scoring logic in between. The fix is to give Node one method that checks and reserves in the same breath, so there is no gap for another thread to slip into.

```java
public synchronized boolean tryAllocate(Pod pod) {
    ResourceRequest request = pod.getRequest();
    if (cpuUsed + request.getCpu() > cpuCapacity
            || memoryUsed + request.getMemory() > memoryCapacity) {
        return false;
    }
    cpuUsed += request.getCpu();
    memoryUsed += request.getMemory();
    runningPods.put(pod.getId(), pod);
    return true;
}
```

`canFit` still earns its keep during the filter phase, where you are just narrowing down a rough list of candidates and a slightly stale answer is harmless. But the moment you actually want to commit a pod to a node, you go through `tryAllocate`, and only through `tryAllocate`, so the check and the write can never be pulled apart by another thread.

This changes how the scheduler behaves when it loses a race. Filtering and scoring can still run freely without any locking, since they only read. But bind now has to be ready for the possibility that its first choice node got taken by somebody else a moment ago, so it falls through to the next best ranked node instead of just failing outright.

```java
public Optional<Node> schedule(Pod pod) {
    List<Node> feasible = filter(pod);
    if (feasible.isEmpty()) {
        return Optional.empty();
    }

    List<Node> ranked = feasible.stream()
            .sorted(Comparator.comparingInt((Node n) -> totalScore(n, pod)).reversed())
            .collect(Collectors.toList());

    for (Node candidate : ranked) {
        if (candidate.tryAllocate(pod)) {
            pod.setNodeId(candidate.getId());
            pod.setStatus(Pod.Status.RUNNING);
            return Optional.of(candidate);
        }
    }
    return Optional.empty();
}
```

Now two threads can filter and score the same pair of pods at the same time with no coordination at all, and whichever one calls `tryAllocate` first simply wins node x. The loser does not corrupt anything, it just moves on to its second choice, exactly the way you would want two people racing for the last seat on a train to fall back to the next carriage instead of both sitting in the same seat.

### Extending the same idea to preemption

Preemption has a similar gap, only wider. `findVictims`, `evict`, and the final `allocate` are three separate steps, and another thread could sneak in and grab the space you just freed before you get to use it yourself. The fix is the same idea as before, wrap the whole sequence in one lock so nobody sees the node in a half evicted state.

Since `Node` already uses `synchronized` instance methods, its intrinsic lock is the node object itself, so `PreemptingScheduler` can reuse that exact same lock with a `synchronized` block instead of inventing a new one.

```java
private Optional<Node> tryPreemptOn(Node node, Pod pod) {
    synchronized (node) {
        List<Pod> victims = findVictims(node, pod);
        if (victims == null) {
            return Optional.empty();
        }
        evict(node, victims);
        if (node.tryAllocate(pod)) {
            pod.setNodeId(node.getId());
            pod.setStatus(Pod.Status.RUNNING);
            return Optional.of(node);
        }
        return Optional.empty();
    }
}
```

Because this block holds the same monitor that every `synchronized` method on `Node` uses, nothing else can call `allocate`, `release`, or `tryAllocate` on this node while we are in the middle of deciding who to evict. The eviction and the new pod's arrival happen as one indivisible step from every other thread's point of view.

### Making the queue and the reconcile loop safe too

`SchedulerController` has two more soft spots. The pending pod queue is a plain `LinkedList`, and workload controllers can call `submit` from their own timers while `reconcile` is draining that same list, which a plain `LinkedList` was never built to survive. And if two reconcile ticks ever overlap, for example one tick runs long and the next one fires before it finishes, both would drain the same queue at once with no coordination.

```java
import java.util.Optional;
import java.util.concurrent.ConcurrentLinkedQueue;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicBoolean;

public class SchedulerController {

    private final PreemptingScheduler scheduler;
    private final ConcurrentLinkedQueue<Pod> pendingPods = new ConcurrentLinkedQueue<>();
    private final ExecutorService schedulingWorkers = Executors.newFixedThreadPool(4);
    private final AtomicBoolean reconciling = new AtomicBoolean(false);

    public SchedulerController(PreemptingScheduler scheduler) {
        this.scheduler = scheduler;
    }

    public void submit(Pod pod) {
        pendingPods.add(pod);
    }

    public void reconcile() {
        if (!reconciling.compareAndSet(false, true)) {
            return;
        }
        try {
            int attempts = pendingPods.size();
            for (int i = 0; i < attempts; i++) {
                Pod pod = pendingPods.poll();
                if (pod == null) {
                    break;
                }
                schedulingWorkers.submit(() -> tryPlace(pod));
            }
        } finally {
            reconciling.set(false);
        }
    }

    private void tryPlace(Pod pod) {
        Optional<Node> result = scheduler.schedule(pod);
        if (result.isEmpty()) {
            pendingPods.add(pod);
        }
    }
}
```

`ConcurrentLinkedQueue` lets `submit` and `reconcile` touch the queue from different threads with no external locking at all. The `AtomicBoolean` guard means if a reconcile tick is still busy handing pods off to the worker pool, the next timer firing simply skips itself instead of draining the same queue twice. And handing each pod to `schedulingWorkers` means the actual filter, score, and bind work for many pods happens in parallel, while each individual node still protects its own capacity through the lock it already owns.

One last easy thing to miss, `Pod` has fields like status and nodeId that get written on one thread and read on another, for example a monitoring thread checking whether a pod is running while a scheduling worker is in the middle of updating it. Java gives no guarantee that a plain field write becomes visible to another thread without some form of synchronization in between. Marking these fields volatile is a small change that closes that gap.

```java
private volatile Status status;
private volatile String nodeId;
```

This is worth saying out loud in an interview because it is easy to get everything else right and still lose points here, correctness under concurrency is not just about avoiding corrupted data, it is also about making sure other threads can actually see the correct data once it is written.

If you want to tie this back to the real thing, this is close to how the actual Kubernetes scheduler behaves. Filtering and scoring for a pod run without touching shared state that other pods care about, so many pods can go through that pipeline in parallel. The actual commit is a single conditional write guarded by a version number the API server tracks for every object, which is the exact same idea as our node level tryAllocate, check the current state and write in one atomic step, and if someone else got there first, just try again.

## Extensibility, new workload types and changing resources

A design is only as good as its ability to absorb requirements nobody mentioned on day one. Two of those requirements come up constantly with a scheduler. First, real clusters do not just run bare pods, they run cron jobs, long running services that need a fixed number of replicas, and one off batch jobs. Second, a running pod's resource needs do not stay fixed forever, someone might bump its memory limit while it is already running. Let us extend the design to handle both without touching a single class we already wrote.

### Separate what to run from where to run

The key insight is that a cron job or a deployment is never actually scheduled onto a node. Only a pod is. A cron job is really just a small piece of logic that says, every so often, create a new pod. A deployment is a small piece of logic that says, keep exactly this many pods alive at all times. Both of them are producers of pods, not something the `Scheduler` needs to know about.

This means the scheduler we already built does not change at all. What we add is a new layer above it, workload controllers, and each one talks to the `SchedulerController` the exact same way our demo code already did, by calling `submit`.

```java
public interface WorkloadController {
    void reconcile();
}
```

A `PodTemplate` describes what a pod for this workload should look like, so each controller can stamp out new pods on demand.

```java
public class PodTemplate {

    private final ResourceRequest request;
    private final int priority;

    public PodTemplate(ResourceRequest request, int priority) {
        this.request = request;
        this.priority = priority;
    }

    public Pod newPod(String id) {
        return new Pod(id, request, priority);
    }
}
```

### Deployments, keep a fixed number of replicas alive

A deployment watches its own pods and tops them up whenever one goes missing.

```java
import java.util.ArrayList;
import java.util.List;

public class DeploymentController implements WorkloadController {

    private final String name;
    private final int desiredReplicas;
    private final PodTemplate template;
    private final SchedulerController schedulerController;
    private final List<Pod> managedPods = new ArrayList<>();
    private int nextIndex = 0;

    public DeploymentController(String name, int desiredReplicas, PodTemplate template,
                                 SchedulerController schedulerController) {
        this.name = name;
        this.desiredReplicas = desiredReplicas;
        this.template = template;
        this.schedulerController = schedulerController;
    }

    @Override
    public void reconcile() {
        managedPods.removeIf(pod -> pod.getStatus() == Pod.Status.FAILED);

        while (managedPods.size() < desiredReplicas) {
            Pod pod = template.newPod(name + "-" + nextIndex++);
            managedPods.add(pod);
            schedulerController.submit(pod);
        }
    }
}
```

Every time `reconcile` runs it compares how many pods it currently owns against how many it wants and creates the difference. If a pod later fails and gets marked `FAILED`, the next reconcile pass notices the gap and quietly replaces it. Nobody had to write a special case for failure recovery, it falls out of comparing desired against actual on every tick.

### Cron jobs, create a pod on a schedule

A cron job barely needs any new machinery, it just needs a clock.

```java
public class CronJobController implements WorkloadController {

    private final String name;
    private final long intervalMillis;
    private final PodTemplate template;
    private final SchedulerController schedulerController;
    private long lastRunAt = 0;
    private int runCount = 0;

    public CronJobController(String name, long intervalMillis, PodTemplate template,
                              SchedulerController schedulerController) {
        this.name = name;
        this.intervalMillis = intervalMillis;
        this.template = template;
        this.schedulerController = schedulerController;
    }

    @Override
    public void reconcile() {
        long now = System.currentTimeMillis();
        if (now - lastRunAt >= intervalMillis) {
            Pod pod = template.newPod(name + "-run-" + runCount++);
            schedulerController.submit(pod);
            lastRunAt = now;
        }
    }
}
```

A one off batch job is the simplest case of all, it is a cron job that runs exactly once and never resets its timer. A daemon style workload that wants exactly one pod per node is also just a controller, one that looks at the current node list instead of a replica count and submits one pod template per node. None of these needed a new field on `Pod`, a new method on `Scheduler`, or a new predicate. They are all just different reconcile loops sitting beside the scheduler, submitting work the same way.

The tick that drives everything simply calls every controller's `reconcile` and then the scheduler controller's own `reconcile`, in that order, on the same timer.

```java
List<WorkloadController> workloadControllers = List.of(deploymentController, cronJobController);

executor.scheduleAtFixedRate(() -> {
    workloadControllers.forEach(WorkloadController::reconcile);
    controller.reconcile();
}, 0, 2, TimeUnit.SECONDS);
```

### Letting resource requests change after a pod is already running

The second requirement is that a pod's cpu or memory request should be changeable after it has already been placed. This is trickier because `Node` is the single source of truth for how much of its capacity is used, and that number must never drift out of sync with what pods actually hold.

The safe way to do this is to make the update go through `Node`, never around it. Give `Node` one new method that adjusts both the old and the new value in a single step.

```java
public synchronized boolean resize(Pod pod, ResourceRequest newRequest) {
    ResourceRequest oldRequest = pod.getRequest();
    int cpuDelta = newRequest.getCpu() - oldRequest.getCpu();
    int memoryDelta = newRequest.getMemory() - oldRequest.getMemory();

    if (cpuUsed + cpuDelta > cpuCapacity || memoryUsed + memoryDelta > memoryCapacity) {
        return false;
    }

    cpuUsed += cpuDelta;
    memoryUsed += memoryDelta;
    pod.setRequest(newRequest);
    return true;
}
```

This only works if `Pod` allows its request to be replaced instead of being fixed forever, so `request` stops being `final` and gets a small setter next to the one it already has.

```java
public void setRequest(ResourceRequest request) {
    this.request = request;
}
```

Now teach the scheduler what to do when a resize does not fit in place. The honest answer is the same one Kubernetes reaches for, try to grow the pod where it already lives first, since that is free and causes no disruption, and only if that fails fall back to evicting and rescheduling it somewhere with more room.

```java
public boolean resize(Pod pod, ResourceRequest newRequest, Node currentNode) {
    boolean fitInPlace = currentNode.resize(pod, newRequest);
    if (fitInPlace) {
        return true;
    }

    currentNode.release(pod);
    pod.setRequest(newRequest);
    pod.setStatus(Pod.Status.PENDING);
    pod.setNodeId(null);
    return schedule(pod).isPresent();
}
```

Nothing about `SchedulingPredicate` or `PriorityFunction` needed to change for this, they already take a `Pod` and read whatever request that pod currently holds, so a resized pod is filtered and scored the exact same way a fresh one would be. And if tomorrow someone adds a third resource dimension, say gpu, the only class that needs a new field is `ResourceRequest` itself, everything downstream keeps working because it was never written against a fixed number of fields, it was written against the request object as a whole.

This is really the payoff of the whole exercise. We spent the earlier sections keeping `Node`, `Scheduler`, `SchedulingPredicate`, and `PriorityFunction` narrow and honest about what each one owns. New workload types and changing resources both turned out to be additions next to the existing classes, not edits inside them.

## Talking through the design in an interview

If you get asked to defend this design here is the story you tell. The predicate list and the priority function list are both interfaces, so new scheduling rules are new classes, not new branches inside an existing method. The node never makes decisions about itself, it only reports facts, which keeps the scheduler as the single place where policy lives. Preemption reuses the exact same allocate and release methods that normal scheduling uses, so there is only one source of truth for what a node's capacity looks like. The reconciliation loop is what turns a one shot function into a system that heals itself, because a single call to schedule is not enough in a world where capacity keeps changing.

If asked how you would make this safe under real concurrency, the answer is the one worked through in the multithreading section, collapse the check and the reservation into one atomic call on the node so two threads can never both believe the same free capacity belongs to them, let filtering and scoring stay lock free since they only read, and fall back to the next ranked node whenever a bind loses a race instead of failing outright. That single change, moving from a two step check then act to one atomic tryAllocate, is usually the difference between a design that sounds right and one that is actually right under load.
