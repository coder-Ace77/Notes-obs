Controllers are the processes that monitor the kubernetes objects and reconcile accordingly. 

### Replication controller

Up till now we have been running single pod and that pod if for some reason goes down entire application will shut. To go around we make controllers which monitors the application and constantly tries to maintain that group of pod. 

Now to create replication controller we define the spec to have `template` of the pod we want to create and a key name replicas. Also note that template here is a key whose value is the dictionary which is corresponding to that pod definition itself. Here we define the metadata and spec of pod created earlier. 

```yml
apiVersion: v1
kind: ReplicationController
metadata:
  name: myapp-rc
  labels:
    app: my-app
    type: front-end

spec:
  template:
    metadata:
      name: nginx
      labels:
        app: nginx
        type: frontend
    spec:
      containers:
        - name: nginx
          image: nginx
  replicas: 3
```

Replicaset is the newer version of replication controller. 

The difference is that Replica set also has a field `selector` to be specified in the spec. Now this selector takes dictionry with property matchLabels which is again a property this should specify the one of the labels present in either earlier template. 

```yaml
  apiVersion: v1
  kind: ReplicaSet
  metadata:
    name: myapp-Replicaset
    labels: 
      app: myapp
      type: frontend

  spec:
    template:
      metadata:
        name: myapp
        labels:
          app: myapp
          type: frontend
      spec:
        containers:
          - name: nginx
            image: nginx
    replicas: 3
    selector:
      matchLabels:
        type: frontend
```


For example here we have mateched using the label type. 

#### Label and selectors

Replica set can be used to monitor the pods and create new pods if not available. Using labels we can quickly identify which pod to use and then select based on that field. As shown in earlier example. Template is actually required because it will tell the kubernetes what pod to start again. Finally we can update other information like replicas to update the pods count. This is possible since the yaml is just the declarative way of stating the config. Also finally we can scale using the scale command

```bash
kubectl scale --replicas=6 -f File-name
```

The command will override the number of replicas from the file def. 

To get the replicasets - 

```bash
kubectl get replicaset # get all
kubectl delete replicaset my-replicaset # delete what we want
```

Now if one tries to make more pods or delete the pods with the label put in the matchSelector then the replicaset process will kill or auto spin new pods. 

### Deployments

Deployment objects come on top of the replica set in hierarchy. They allow us to undo changes give us rolling updates etc. A **Deployment** is a high-level resource object that provides declarative updates for applications.

When you want to update your application (e.g., deploying a new version of a container image), you simply update the Deployment specification. Kubernetes will automatically perform a "Rolling Update," gracefully shutting down old Pods and starting new ones in phases, ensuring zero downtime.

A standard deployment yaml looks like this 

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
```

As evident the definition is similar with the replicaset. Now how to do update 

When you update a Deployment (for example, by changing the container image from `v1` to `v2`), the `podTemplate` hash changes. This is the trigger for a rolling update.

The Deployment Controller detects the new hash and executes the following sequence:

1. **Create New ReplicaSet:** It creates a brand new ReplicaSet configured with the new `v2` pod template. Initially, this ReplicaSet is told to have `0` replicas.
2. **Calculate Limits:** It calculates how to scale based on two critical parameters defined in your Deployment strategy:
    - **`maxUnavailable`:** The maximum number of Pods that can be offline during the update. (Default is 25% of desired replicas).
    - **`maxSurge`:** The maximum number of _extra_ Pods that can be created above the desired replica count during the update. (Default is 25%).

**The Scale Up/Down Dance:** The controller begins a loop:
- It scales _up_ the new ReplicaSet (respecting `maxSurge`).
- Once a new Pod is running and passes its Readiness Probes, it scales _down_ the old ReplicaSet (respecting `maxUnavailable`).
- It repeats this until the new ReplicaSet reaches the target replica count and the old ReplicaSet reaches `0`.

So you just need to do apply to the deployment file

```bash
kubectl apply -f deployment.yaml
```

Finally rollbacks 

Because the Deployment manages state via ReplicaSets, version control is essentially just managing the lifecycle of these ReplicaSet objects.

- **Revision History:** When a rolling update completes, the Deployment Controller does _not_ delete the old ReplicaSet. It simply leaves it scaled to `0`.
    
- **Annotations:** The controller annotates each ReplicaSet with a revision number (e.g., `deployment.kubernetes.io/revision: "1"`).
    
- **`revisionHistoryLimit`:** By default, Kubernetes keeps the last 10 ReplicaSets (controlled by the `revisionHistoryLimit` field in the Deployment spec). This acts as your version control history.
    
- **Executing a Rollback:** When you trigger a rollback (e.g., `kubectl rollout undo deployment/nginx-deployment`), the controller simply looks up the ReplicaSet associated with the previous revision number. It then reverses the rolling update process: it initiates a scale-up on the old ReplicaSet and a scale-down on the currently active one.

```bash
kubectl rollout undo deployment/nginx-deployment # undo deployment
```

Now a generalization , Replicaset , Deployments , StatefulSet , DaemonSet ,  Jobs and CronJobs all have similar templates since all they do is create pods based on different properties. 

Replicaset gurantee that this many pods will be there. Deployments add other functionalities like `rollout`.

### Stateful set

Statefull set solve differnet problem - Deployments are great, but they treat all pods as identical and interchangeable pod names are random hashes, any pod can be swapped for any other, and storage isn't tied to a specific pod. For the distributed databases we need them to have predictable and reporducable names 

But some apps don't work that way. Think of a database cluster (like MySQL, Kafka, or Elasticsearch) where:
- **Each instance needs a stable identity** — node-0, node-1, node-2, not random names — because they need to know and address each other (e.g. node-0 is always the "primary").
- **Each instance needs its own persistent storage** — if pod-1 restarts, it must come back with _its own_ disk, not a random one, and definitely not an empty one.
- **They often need to start up in order** — node-0 first, then node-1, then node-2, because node-1 might need node-0 to already be alive.

A **StatefulSet** solves exactly this: stable network identity (`<name>-0`, `<name>-1`, ...), stable storage per pod (via `volumeClaimTemplates`), and ordered, predictable start/stop. Observe no new field

Its basic template is. See clusterIp = None. It means we are disabling the loadbalancer step and coreDNS will be directly assinging ips to the pods. Not via clusterip mechanism. More on it later in networking section.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: postgres            # the HEADLESS service — required
spec:
  clusterIP: None           # ← this is what makes it headless
  selector:
    app: postgres
  ports:
    - port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres     # must name the headless Service above
  replicas: 3
  podManagementPolicy: OrderedReady
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: postgres
          image: postgres:17
          ports:
            - containerPort: 5432
              name: pg
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:     # ← one PVC per Pod, created automatically
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: gp3
        resources:
          requests:
            storage: 100Gi
```

Two points it has spec which hqs template. And template defines the pods since its always a pod we don't need the `apiVersion` and `kind` we just have `metadata` and `spec` for the containers. Once you know how to write pods it works fine. Second thing is `volumeClainTemplate` to gets same volume everytime asked so that volumes survivev restart and get attached to same pods. 

For the things like `dbs` its pretty necessary to have ordering for example `pod-0` which is primary replica should start first and followed by others. Also this is usefull once db is running as others need to connect to same primary pod everytime. 

Pods are named `<statefulset>-<ordinal>`, starting at 0: These names are **deterministic and permanent**. Delete `postgres-1` and the replacement is also called `postgres-1`. Scale to 5 and you get `postgres-3` and `postgres-4`; scale back to 3 and those two are removed, highest ordinal first.

The ordinal is exposed inside the Pod as the hostname, which is how a container can discover which member it is:

Now this statefull set also provides the stable network identity. For the deployments what happens is that it has one clusterip and that ip is loadbalanced to all the pods at random. Now with dbs we can't do that. We exactly need the primary and secondry pod id. 

A **headless** Service (`clusterIP: None`) has no virtual IP. Instead, CoreDNS creates a DNS record per Pod:

```
postgres-0.postgres.platform.svc.cluster.local  → 10.244.1.5
postgres-1.postgres.platform.svc.cluster.local  → 10.244.2.7
postgres-2.postgres.platform.svc.cluster.local  → 10.244.3.9
```

The pattern is `<pod>.<serviceName>.<namespace>.svc.cluster.local`. Querying the Service name itself returns all the Pod IPs as A records rather than a single ClusterIP.

`volumeClaimTemplates` creates one PVC per Pod, named `<template>-<statefulset>-<ordinal>`:

```yaml
data-postgres-0
data-postgres-1
data-postgres-2
```

**Startup** (`podManagementPolicy: OrderedReady`, the default): Pods are created one at a time, in ordinal order. `postgres-1` is not created until `postgres-0` is **Running and Ready**. If `postgres-0` never becomes ready, nothing else is ever created. **Shutdown**: reverse ordinal order, one at a time, each fully terminated before the next. **Scale down**: highest ordinal first, one at a time.
**Rolling update**: highest ordinal first, downward, one at a time, each fully Ready before the next.

### Daemonset , jobs and cronjobs.

Three controllers for three shapes of work: one Pod per node, work that finishes, and work that finishes on a schedule. A DaemonSet ensures a copy of a Pod runs on every node or every node matching a selector. When a node joins the cluster, it gets one. When a node leaves, its Pod is cleaned up.

```yamlapiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: node-exporter
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 0
  template:
    metadata:
      labels:
        app: node-exporter
    spec:
      hostNetwork: true
      hostPID: true
      tolerations:
        - operator: Exists          # run on EVERY node, including tainted ones
      containers:
        - name: node-exporter
          image: prom/node-exporter:v1.8.2
          args:
            - --path.rootfs=/host
          ports:
            - containerPort: 9100
              hostPort: 9100
          resources:
            requests: {cpu: 50m, memory: 64Mi}
            limits: {memory: 128Mi}
          securityContext:
            readOnlyRootFilesystem: true
            runAsNonRoot: true
            runAsUser: 65534
          volumeMounts:
            - name: rootfs
              mountPath: /host
              readOnly: true
      volumes:
        - name: rootfs
          hostPath:
            path: /

```

A Job runs Pods until a specified number complete successfully, then stops.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: migrate
spec:
  backoffLimit: 4
  activeDeadlineSeconds: 600
  ttlSecondsAfterFinished: 3600
  completions: 1
  parallelism: 1
  template:
    spec:
      restartPolicy: OnFailure        # or Never — NOT Always
      containers:
        - name: migrate
          image: myapp/migrations:v2.3.1
          command: ["./migrate", "up"]

```

Notice again template is common. 

A CronJob creates Jobs on a cron schedule. It is a controller that watches the clock and creates Job objects nothing more.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"                # 02:00 daily
  timeZone: "Europe/London"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  suspend: false
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: backup
              image: myapp/backup:v1
              command: ["./backup.sh"]
```


Without `timeZone`, the schedule is interpreted in the **controller’s** timezone, which is almost always UTC. 

### Requests and limits

Requests buy you a reservation. Limits impose a ceiling.

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 1
    memory: 512Mi
```

**Requests** are used by the **scheduler**. They reserve capacity on a node. Nothing enforces them at runtime — a container requesting 250m CPU can use 4 cores if the node is idle.

**Limits** are enforced by **cgroups** on the node. They are a hard ceiling, always. These are placed on the pods  These can be enforced at pod level or container level. 

Resouce qouta can define the req and limits for all the `namespaces`

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-budget
  namespace: platform
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
    persistentvolumeclaims: "20"
    requests.storage: 500Gi
    count/deployments.apps: "30"
    services.loadbalancers: "2"
```

The forgotten third resource  the container writable layer, `emptyDir`, and logs. 

```yaml
resources:
  requests:
    ephemeral-storage: 1Gi
  limits:
    ephemeral-storage: 4Gi
```

Exceeding the limit gets the Pod **evicted**, not throttled. Without limits, one Pod writing logs to a file fills the node’s disk and triggers `DiskPressure`, evicting unrelated Pods across the node.
