## Vector embeddings

Unstructured data—like a block of text, an image, or an audio clip—has no inherent mathematical structure that a database can easily query for semantic similarity.

Vector embeddings solve this by using neural networks to map this raw data into a high-dimensional continuous space. The output is an array of floating-point numbers. The core principle is **semantic proximity**: data points that share similar meanings or contexts are mapped closer together in this mathematical space.

For example, a model doesn't just look at the string "dog". It processes the context in which "dog" is used and outputs a vector. The vectors for "dog" and "wolf" will have a small mathematical distance between them, while "dog" and "skyscraper" will be far apart.

In high-dimensional space, how do "features" become coordinates?

Think of a simple 2D space where the X-axis is "fluffiness" and the Y-axis is "size". A cat would have high fluffiness and low size `[0.9,0.2]`. A bear would be `[0.8,0.9]`.

Modern embedding models (like OpenAI's `text-embedding-3-small` or BERT) don't just use 2 or 3 dimensions; they typically use anywhere from 384 to 3072 dimensions. 
Unlike the fluffiness example, these features are rarely human-readable. The neural network decides internally what microscopic contextual clues matter perhaps dimension 142 represents a specific mix of sarcasm and urgency, while dimension 650 represents geographical context. Together, these hundreds of coordinates pinpoint the exact semantic concept in the feature space.

### Types of vectors

When designing a system, you have to choose how to represent your embeddings. This fundamentally alters how your retrieval system operates.

**Dense Vectors (e.g., BERT, OpenAI):** * Every dimension usually has a non-zero, floating-point value.

- The dimensionality is fixed and relatively low compared to the vocabulary (e.g., 768 or 1536 dimensions).
- **Strength:** Excellent for capturing implicit, semantic meaning. A search for "shoes" will match "sneakers" because their dense vectors point in the same direction, even if the keywords don't overlap.

**Sparse Vectors (e.g., BM25, SPLADE):**

- Most dimensions are zero.
- The dimensionality is massive—usually equal to the entire size of the vocabulary in a given language (e.g., 30,000+ dimensions).
- Each dimension corresponds to a specific token or word. The value in that coordinate is a weight (like Term Frequency-Inverse Document Frequency) indicating how important that word is to the document.
- **Strength:** Excellent for exact keyword matching. If a user searches for a specific error code or a rare noun, sparse vectors ensure an exact syntactic match.

### Similarity

When you pass a query to a vector database, it calculates the distance between your query vector and the stored vectors. The metric you choose fundamentally changes what the database considers a "match."

#### 1. Eucledian distance

Euclidean distance is the most intuitive metric. It measures the straight-line distance between two points in multidimensional space—exactly how you would measure the distance between two dots on a piece of paper with a ruler.

$d(p,q)=\sum_{i=1}^{n}{(q_i-p_i)}^2$

Use L2​ when the **magnitude** (length) of the vectors is important. If the length of a vector represents the intensity, frequency, or weight of a specific feature.

#### 2. Cosine Similarity

Cosine similarity measures the angle between two vectors, completely ignoring their magnitude (length).

$cos(A,B)=(A.B)/(|A||B|)$

Result ranges from `(-1,1)`. 

This is the gold standard for Natural Language Processing (NLP) and text embeddings. Imagine you have a short tweet about "machine learning" and a 50-page textbook on "machine learning." The textbook will have a much larger vector magnitude because the word frequencies are higher, but mathematically, the vectors will point in the exact same semantic direction. Cosine similarity correctly identifies them as highly similar, whereas Euclidean distance would consider them far apart.

#### 3. Dot product

The dot product is a fast, highly efficient metric that captures a blend of both angle and magnitude. You multiply the corresponding dimensions of each vector and sum the results. There is no normalization (no division by length), meaning vectors with larger magnitudes will yield higher dot products.

If you normalize your vectors before storing them in the database (forcing their length to equal 1), the Dot Product becomes mathematically identical to Cosine Similarity. Because Dot Product skips the complex division step required by Cosine Similarity, computing it is significantly faster. Vector databases love normalized dot products for high-performance querying.

## Vector dbs indexings

This is where vector databases separate themselves from standard databases. In a traditional system, finding an exact match is easy using indexes like B-Trees or Hash Maps. But in high-dimensional space, where we want _approximate_ matches based on distance metrics, we cannot afford to scan every single record. 

To search billions of vectors in milliseconds, we rely on Approximate Nearest Neighbor (ANN) algorithms. These trade a tiny bit of accuracy (recall) for a massive gain in speed.

### Flat indexing 

Flat indexing isn't really an "index" at all—it is a brute-force mathematical scan.

When a query vector arrives, the database calculates its distance against _every single vector_ stored in the system using a metric like Euclidean distance or Cosine similarity. It then sorts the results to return the top k closest vectors.
Flat indexing guarantees **100% recall** (perfect accuracy). It is strictly used for very small datasets (e.g., under 10,000 vectors) where compute time is negligible, or as a ground-truth baseline to test the accuracy of more complex ANN algorithms.

### IVF(inverted file index)

IVF drastically reduces the search space by grouping similar vectors together before the query even happens. During the indexing phase, IVF uses a clustering algorithm (typically K-Means) to divide the vector space into a set of clusters. The space around each cluster's center (the centroid) forms a region called a Voronoi cell. Every vector in the database is assigned to its nearest centroid.

When a query vector comes in, the system first calculates the distance between the query and all the _centroids_. It identifies the closest centroid, and then only performs a flat search against the vectors inside that specific Voronoi cell.

By searching only a fraction of the database, search times drop exponentially. However, if a query falls near the boundary of a Voronoi cell, the true nearest neighbor might actually be in an adjacent cell. To improve accuracy, you can increase a parameter called `nprobe`, which tells the system to search the top x nearest cells instead of just one.

### HNSW(Hierarchical Navigable Small World)

HNSW is currently the industry gold standard for vector search (powering systems like Milvus, Pinecone, and Qdrant). It relies on graph theory rather than clustering.

HNSW builds a multi-layered graph. It is inspired by the "six degrees of separation" concept (Navigable Small World) combined with the logic of a skip-list.

- **Layer 0 (Bottom):** Contains every single vector in the database, linked to its nearest neighbors via short edges.
- **Higher Layers:** Contain exponentially fewer vectors, connected by long-range edges that span across the vector space.

- **The Search Phase:** The search starts at the top layer. It traverses the long edges to rapidly zoom in on the general neighborhood of the query vector. Once it finds a local minimum in that layer, it "drops down" to the layer below and repeats the process. By the time it hits Layer 0, it is already surrounded by the exact closest neighbors.
- **Time Complexity:** O(logn) search time, offering incredibly fast lookups with highly accurate recall, though it consumes significant memory to store the graph edges.

Note that there are other techniques for indexing which aim to solve other problems like space optimization. 

## ChromaDB

ChromaDB is brilliant for prototyping, testing, and learning because it completely removes infrastructure friction. It runs in-memory or persists directly to your local file system, making it incredibly easy to spin up inside a Docker container or a Python environment like FastAPI.

### Arch

It might be surprising, but ChromaDB uses standard SQLite to handle its metadata, collections, and relationship mapping. This gives it ACID transactions for the non-vector parts of your data. For the actual embeddings, Chroma builds a **Hierarchical Navigable Small World (HNSW)** graph. Chroma utilizes a Write-Ahead Log (WAL). Incoming vectors are first appended to the WAL for immediate durability, and then asynchronously compacted into the main HNSW index.

####  Workflow
1. **Text Input:** You give the database a piece of text (e.g., a paragraph from a book).
2. **Embedding:** ChromaDB uses a model (like Sentence Transformers or OpenAI) to turn that text into a list of numbers (a vector).
3. **Storage:** The vector and the original text are stored together.
4. **Query:** When you ask a question, it's converted into a vector, and ChromaDB finds the "nearest" vectors in its collection.

We can install a library in python.

```bash
pip install chromadb
```

A collection in chromadb is like table in sql. 

```python

import chromadb
# Initialize the client (Persistent saves data to a folder)
client = chromadb.PersistentClient(path="./my_vectordb")
# Create a collection
# By default, it uses 'all-MiniLM-L6-v2' to create embeddings automatically
collection = client.get_or_create_collection(name="office_policies")
```

Now we can add the documents to the collections.

```python
collection.add(
    documents=[
        "The office is closed on public holidays.",
        "Remote work is allowed up to 2 days a week.",
        "The annual bonus is distributed in December.",
        "Employees must wear business casual attire."
    ],
    metadatas=[{"category": "HR"}, {"category": "HR"}, {"category": "Finance"}, {"category": "Office"}],
    ids=["id1", "id2", "id3", "id4"]
)
```

Finally we can query the data. 

```python
results = collection.query(
    query_texts=["Can I work from my home?"],
    n_results=1 # Give me the single best match
)

print(f"Top Match: {results['documents'][0][0]}")
# Output: Top Match: Remote work is allowed up to 2 days a week.
```

To use OpenAI embeddings with ChromaDB, you need to swap out the default embedding function (which runs locally) for the `OpenAIEmbeddingFunction`. This tells ChromaDB to send your text to OpenAI’s API to generate the vectors before storing or querying them. We also need to install Openai intergration package for chroma. 

Here is the set up

```python

import chromadb
from chromadb.utils import embedding_functions
import os

# Set your API key
api_key = os.getenv("OPENAI_API_KEY")

# Define the OpenAI embedding function
openai_ef = embedding_functions.OpenAIEmbeddingFunction(
                api_key=api_key,
                model_name="text-embedding-3-small"
            )
            
client = chromadb.PersistentClient(path="./chroma_openai_db")

# Create collection with the OpenAI embedding function
collection = client.get_or_create_collection(
    name="openai_docs", 
    embedding_function=openai_ef
)
```

After this we can continue with the normal workflow.
