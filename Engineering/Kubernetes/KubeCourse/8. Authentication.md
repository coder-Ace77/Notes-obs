Kubernetes api server contacts everyone and will authenticate everything from a human calling cli to pod running or any controller. We can classify them in trwo groups

- Humans and external systems
- Workloads - These are the internal components inside kubernetes. 

Kubernetes stores workload identities (ServiceAccounts are real objects) but **not human identities**. `kubectl get serviceaccounts` works; `kubectl get users` never will. Human identity is always asserted by an external system and merely translated at the edge. 

Every request that hits the Kubernetes API server whether it's `kubectl get pods`, a CI pipeline deploying a Helm chart, or a pod trying to read a Secret passes through the same pipeline before anything happens - api server first authenticates and check if user can perform the required actions. 

Authentication answers exactly one question: **can this request prove an identity?** Nothing more. It does not decide what that identity can do  that's authorization's job entirely. If authentication succeeds, the API server attaches a **username** and a set of **groups** to the request and moves on. If it fails, the request is rejected with a 401 before authorization is even consulted. To do authentication kubernetes does not have built-in user database. So identity needs to come from external to cluster except for the service accounts. 

#### Client authentication

This is how `kubectl` usually authenticates you when you first set up a cluster. Your kubeconfig file contains an X.509 client certificate and private key. When you make a request, your TLS handshake presents that certificate to the API server. When you make a request, your TLS handshake presents that certificate to the API server. Instead, it trusts a **Certificate Authority (CA)**  usually the cluster's own CA that signed the API server's own serving certificate. If your client certificate was signed by that trusted CA, the API server accepts it as proof of identity. The username and group aren't looked up anywhere — they're literally _encoded inside the certificate itself_, in the **Subject** field:

```
Subject: CN=adil, O=platform-team
```

- `CN` (Common Name) becomes the **username** → `adil`
- `O` (Organization) becomes a **group** → `platform-team`

**Worked example:** if you wanted to create a new human user "priya" with read-only access, you would:

1. Generate a private key and a Certificate Signing Request with `CN=priya`.
2. Get the cluster CA to sign it (via the `CertificateSigningRequest` API or manually).
3. Hand priya the signed cert + key, which she puts in her kubeconfig.
4. Separately, grant `priya` permissions via RBAC (covered in section 2) — the certificate alone gets her "known," not "allowed."

Note this cluster `CA` is a pod running inside cluster itself. Its not external one like Keycloak. 

#### Machine authentication

This is a way by which a pod is authenticated inside cluster. Note pod means all the things like controllers , normal pods etc. 

Every pod, unless explicitly opted out, gets a **ServiceAccount** a lightweight identity object that _is_ actually stored inside Kubernetes (this is the exception mentioned earlier). Kubernetes automatically mounts a token for that ServiceAccount into the pod's filesystem at:

```
/var/run/secrets/kubernetes.io/serviceaccount/token
```

That token is a signed JWT. When the pod's process wants to talk to the API server, it sends this token as an `Authorization: Bearer <token>` header. The API server verifies the JWT's signature against its own trusted signing key, extracts the identity from the token's claims, and treats it like:

```
username: system:serviceaccount:<namespace>:<serviceaccount-name>
groups:   system:serviceaccounts, system:serviceaccounts:<namespace>
```

**Worked example:** a monitoring pod in the `observability` namespace running as ServiceAccount `metrics-reader` authenticates as the identity `system:serviceaccount:observability:metrics-reader`. That naming convention (`system:serviceaccount:<ns>:<name>`) is not cosmetic — you'll write RBAC rules that reference this exact string, or bind roles to the ServiceAccount object directly.

This is precisely how your ML platform's controllers/operators (Ray operator, KServe controller, Kubeflow components, etc.) authenticate to the API server to reconcile custom resources — each one runs as a ServiceAccount with a token, and that token is its passport.

### External identity providers

For human users at any real organization, nobody wants to hand-issue X.509 certificates per person. So production clusters typically authenticate humans via **OIDC (OpenID Connect)**.

the API server is configured to trust tokens issued by an external identity provider (Okta, Google, Azure AD, Dex, etc.) — the same way it trusts certificates signed by a CA. You log into your identity provider once it hands you back a signed ID token, and every `kubectl` request includes that token.

### Authorization 

Once the API server knows _who_ you are (username + groups), it asks a second, independent question for every request: given this specific verb (get/list/create/delete/...) on this specific resource (pods/secrets/deployments/...) in this specific namespace, is this identity permitted?

Kubernetes supports several authorization modes, but the one that matters in virtually every real cluster is **RBAC (Role-Based Access Control)**

This is the conceptual leap that makes RBAC click: you never say "adil can delete pods." You always do it in two decoupled steps:

- **Define a bundle of permissions** a reusable, named set of "verb + resource" rules, independent of _who_ gets it. This bundle is called a **Role** (if scoped to a namespace) or a **ClusterRole** (if it applies cluster-wide or to non-namespaced resources).
- **Attach that bundle to an identity** a **RoleBinding** (namespace-scoped) or **ClusterRoleBinding** (cluster-wide) says "this Role applies to this user/group/ServiceAccount."

Say you want the `metrics-reader` ServiceAccount from earlier to be able to `get`, `list`, and `watch` pods — but only in the `observability` namespace, and nothing else (no deleting, no touching Secrets, no access to other namespaces).

**Step 1 — the Role** (the permission bundle, scoped to `observability`):

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: observability
  name: pod-reader
rules:
  - apiGroups: [""]           # "" means the core API group (pods, services, etc.)
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

Read this literally: "within the `observability` namespace, permit `get`/`list`/`watch` on `pods`." Nothing here mentions _who_. This Role, on its own, grants nobody anything.

**Step 2 — the RoleBinding** (attaching it to the identity):

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: metrics-reader-binding
  namespace: observability
subjects:
  - kind: ServiceAccount
    name: metrics-reader
    namespace: observability
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Now the identity `system:serviceaccount:observability:metrics-reader` (from section 1.2) can read pods in `observability`, and only that. If that same pod tried to read pods in the `default` namespace, or tried to delete anything, the request would be authenticated fine (the token is valid) but rejected at authorization with a 403 Forbidden.

A **Role** can only describe rules about resources within a single namespace, and it can only be bound (via a RoleBinding) inside that same namespace.

A **ClusterRole** describes rules that either apply cluster-wide (like `nodes`, which aren't namespaced at all) or _could_ be reused across many namespaces. But a ClusterRole's binding still determines the actual grant:

- Bind it with a **ClusterRoleBinding** → the permission applies everywhere, in every namespace, cluster-wide.
- Bind it with a **RoleBinding** (yes, this is legal) → the _same_ ClusterRole's rules apply only within that one namespace.

**Worked example of the reuse pattern:** imagine you define one ClusterRole called `deployment-editor` that permits `get/list/watch/create/update/patch/delete` on `deployments`. You can then:

- Bind it cluster-wide with a ClusterRoleBinding, if you want someone to manage deployments everywhere.
- Or bind the _exact same_ ClusterRole separately in `team-a` and `team-b` namespaces via two different RoleBindings, giving each team edit rights only in their own namespace — without writing the rule twice.

Two consequences that matter in practice:

- **RBAC is purely additive.** There is no "deny" rule in native RBAC. You cannot write a rule that says "allow get on all pods except in kube-system." Permissions only ever add up; the final decision is "was there at least one matching allow rule anywhere." If you need exceptions, you structure your Roles/bindings so the broad grant simply never includes the excluded case.
- **The most permissive applicable rule wins**, because there's no ordering or precedence — it's a set union. If a ServiceAccount has one RoleBinding granting read-only, and _another_ accidentally grants `*` verbs on `*` resources, it has full access. This is why auditing _all_ bindings touching an identity matters more than looking at any single one.

### Notes

Note that we can do a role binding to either human account or to any service account. 

**RoleBinding** grants permissions **within its own namespace**. It can reference either a Role (same namespace) or a ClusterRole (applied only within the binding’s namespace):

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alice-deploys-platform
  namespace: platform
subjects:
  - kind: User
    name: alice@example.com
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole              # a cluster role...
  name: deployment-manager
  apiGroup: rbac.authorization.k8s.io

```

Here `alice` gets `deployment-manager` permissions **only in `platform`**, even though the role is cluster-wide. The RoleBinding’s namespace scopes it.

**ClusterRoleBinding** grants a ClusterRole across **all namespaces**:

```yaml
kind: ClusterRoleBinding
metadata:
  name: alice-deploys-everywhere
subjects:
  - kind: User
    name: alice@example.com
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: deployment-manager
  apiGroup: rbac.authorization.k8s.io
```

subjects are the people on which we are role bindinfg to and they are three types  

```yaml
subjects:
  - kind: User
    name: alice@example.com
    apiGroup: rbac.authorization.k8s.io
  - kind: Group
    name: platform-team
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: ci-deployer
    namespace: ci
```

The common real case is granting a ServiceAccount exactly the API access its controller needs:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: config-watcher
  namespace: platform
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-watches-config
  namespace: platform
subjects:
  - kind: ServiceAccount
    name: api-server
    namespace: platform
roleRef:
  kind: Role
  name: config-watcher
  apiGroup: rbac.authorization.k8s.io
```

`kubectl auth can-i` is the whole toolkit — it queries the authorizer directly

```
kubectl auth can-i create deployments -n platform
```

### Service Account

A **Service Account** is an identity for processes that run inside Kubernetes pods. Just like user accounts allow humans to authenticate to systems, service accounts allow applications running in pods to authenticate with:

- The Kubernetes API
- External systems (AWS, GCP, Azure, etc.)
- Other services in your cluster

Now one can create the Service acoount simplest example 

```yaml
# ===== 1. KUBERNETES SERVICE ACCOUNT =====
apiVersion: v1
kind: ServiceAccount
metadata:
  name: external-secrets-sa              # Name of the service account
  namespace: default                      # Kubernetes namespace
  annotations:
    # This annotation links the K8s Service Account to an AWS IAM role
    # This enables "IRSA" (IAM Roles for Service Accounts)
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/external-secrets-role
```

Now this will create kubernetes identity kind of a pass. Now any pod can assume this identity or pass and annotation is importnant this annotation links the service account to real iam role. Once that happens any pod can authenticate to aws as this IAM role. Note you might be confused that if anyone can do this is this not a secruity flaw. 

The real thing which happens is this - 

```yaml
Step 1: Pod requests credentials
        ↓
Step 2: Kubernetes OIDC Provider issues JWT token
        (signed with Kubernetes' private key)
        ↓
Step 3: Pod sends JWT to AWS STS
        ↓
Step 4: AWS STS verifies JWT signature
        (using Kubernetes' public key)
        ↓
Step 5: AWS STS validates:
        ✓ JWT signature is valid
        ✓ JWT is from THIS specific cluster
        ✓ Pod identity matches service account
        ✓ Timestamp is fresh
        ↓
Step 6: If all checks pass → Issue AWS credentials
```

So kubernetes has a OIDC provider which issues JWT token signes it using private key and it is this thing which is verified by aws. Now this IAM role has a trust policy that allows 

Now this OIDC provider is something which is runned by the eks control plane and is this EKS which issues the signed JWT from kubernetes. Pod can simply use this JWT to authenticate to `aws` and get req things. Now how will you stop the access. Mainly we create IAM roles which restrict usage and allow the cluster 1 to have access to given IAM. Note that since JWT is signed by the OIDC from a given cluster aws will know req is comming from which cluster. So you can create iam role which only are restricted to a given clusters. 

```
Pod (Cluster 1)
  ↓
Gets JWT signed by Cluster 1's Kubernetes
  ↓
Sends JWT to AWS STS: "I'm from CLUSTER1ID, I'm cluster-1-sa"
  ↓
AWS checks: Is JWT signed by CLUSTER1ID OIDC provider?
  ✅ YES
  ↓
AWS checks: Does cluster-1-role trust CLUSTER1ID?
  ✅ YES
  ↓
AWS issues credentials with cluster-1-role policy
  ↓
Pod accesses S1
  ✅ SUCCESS (allowed by policy)
```

### IRSA

A **Service Account** is a Kubernetes-native identity for pods. 

**What SA does:**

- ✅ Authenticates pod to **Kubernetes API server**
- ✅ Allows pods to read ConfigMaps in the cluster
- ✅ Allows pods to query Kubernetes resources
- ❌ Does NOT authenticate to AWS, Google Cloud, etc.

Pod so can not access the aws or external services or resources. 
IRSA is IAM Roles for Service Accounts. Meaning roles specifically for the service accounts. It extentends the service accounts to authenticate to aws. 

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-sa
  namespace: default
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/my-role
```

**What IRSA does:**

- ✅ Authenticates pod to **Kubernetes API server** (SA feature)
- ✅ Authenticates pod to **AWS services** (NEW!)
- ✅ Pod gets temporary AWS credentials

```
Pod → Uses SA with IRSA → Gets JWT from Kubernetes → 
AWS STS verifies JWT → Issues temporary AWS credentials → 
Access AWS services (S3, SecretsManager, etc.)
```

### Example of pod accessing s3

Example -

```bash
# Get cluster name
CLUSTER_NAME=my-eks-cluster
AWS_REGION=us-east-1
AWS_ACCOUNT_ID=123456789

# Get OIDC provider URL
OIDC_ID=$(aws eks describe-cluster \
  --name $CLUSTER_NAME \
  --region $AWS_REGION \
  --query "cluster.identity.oidc.issuer" \
  --output text | cut -d '/' -f 5)

echo "OIDC ID: $OIDC_ID"
# Output: OIDC ID: EXAMPLEID1234567890

OIDC_PROVIDER="oidc.eks.${AWS_REGION}.amazonaws.com/id/${OIDC_ID}"
echo "OIDC Provider: $OIDC_PROVIDER"
```

#### Create IAM role

IAM role has the federated trust-policies.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789:oidc-provider/oidc.eks.us-east-1.amazonaws.com/id/EXAMPLEID1234567890"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "oidc.eks.us-east-1.amazonaws.com/id/EXAMPLEID1234567890:aud": "sts.amazonaws.com",
          "oidc.eks.us-east-1.amazonaws.com/id/EXAMPLEID1234567890:sub": "system:serviceaccount:default:s3-access-sa"
        }
      }
    }
  ]
}
```

Now create the role -- 

```bash
aws iam create-role \
  --role-name s3-access-role \
  --assume-role-policy-document file://trust-policy.json \
  --region $AWS_REGION

# Output:
# {
#   "Role": {
#     "RoleName": "s3-access-role",
#     "Arn": "arn:aws:iam::123456789:role/s3-access-role",
#     ...
#   }
# }
```

Now we create bucket policy - 

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "S3ListBucket",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket",
        "s3:GetBucketVersioning"
      ],
      "Resource": "arn:aws:s3:::my-app-bucket"
    },
    {
      "Sid": "S3ReadWrite",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::my-app-bucket/*"
    }
  ]
}
```

Now we need to attach this policy to the role and move forward. 

```
aws iam put-role-policy \
  --role-name s3-access-role \
  --policy-name s3-access-policy \
  --policy-document file://s3-policy.json \
  --region $AWS_REGION
```

Once S3 is created we then create `ServiceAccount`

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-access-sa                    # ServiceAccount name
  namespace: default                    # Namespace
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/s3-access-role
    # This annotation links K8s SA to AWS IAM role
```

Now pod will be given this service account.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: s3-access-pod
  namespace: default
spec:
  # CRITICAL: Reference the ServiceAccount with IRSA
  serviceAccountName: s3-access-sa
  
  # Mount the token for IRSA
  automountServiceAccountToken: true
  
  containers:
  - name: s3-app
    image: amazon/aws-cli:latest  # AWS CLI pre-installed
    
    # Environment variables for AWS
    env:
    - name: AWS_ROLE_ARN
      value: arn:aws:iam::123456789:role/s3-access-role
    - name: AWS_WEB_IDENTITY_TOKEN_FILE
      value: /var/run/secrets/eks.amazonaws.com/serviceaccount/token
    - name: AWS_REGION
      value: us-east-1
    
    # Command to run
    command:
    - /bin/bash
    - -c
    - |
      echo "=== Testing S3 Access ==="
      
      # List buckets
      echo "Listing S3 buckets..."
      aws s3 ls
      
      # List bucket contents
      echo "Listing my-app-bucket..."
      aws s3 ls s3://my-app-bucket/
      
      # Download file
      echo "Downloading test.txt..."
      aws s3 cp s3://my-app-bucket/test.txt ./downloaded.txt
      cat ./downloaded.txt
      
      # Upload file
      echo "Uploading new file..."
      echo "Data from pod" > data.txt
      aws s3 cp data.txt s3://my-app-bucket/data-from-pod.txt
      
      # Verify upload
      echo "Verifying upload..."
      aws s3 ls s3://my-app-bucket/
      
      echo "=== S3 Access Successful! ==="
      
      # Keep pod running for inspection
      sleep 3600
    
    # Resource requests (optional but recommended)
    resources:
      requests:
        cpu: 100m
        memory: 128Mi
      limits:
        cpu: 500m
        memory: 512Mi
```
