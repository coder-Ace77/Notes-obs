An **anti-pattern** is not simply "a bad design." It is specifically a design that _looks_ reasonable, that people fall into naturally when solving a real problem, but that reliably causes serious pain once the system grows. Learning to recognize anti-patterns is arguably just as valuable as learning the patterns themselves — in system design interviews and in real architecture reviews, spotting _why_ a design is fragile is often exactly what is being tested.

### 2.1 The Distributed Monolith

This is one of the most common traps teams fall into when adopting microservices. On paper, the system has been split into separate services, each with its own codebase and its own deployment pipeline. But in practice, `ServiceA` cannot be deployed without also deploying `ServiceB` at the exact same time, because they share a rigid, tightly-coupled contract and depend on each other's internal implementation details rather than a stable, well-defined interface.

```
ServiceA (v2) calls a field in ServiceB's response that only exists in ServiceB (v2).
If you deploy ServiceA (v2) before ServiceB (v2) is live, ServiceA breaks immediately.
```

You have paid the full operational cost of microservices — network calls, separate deployments, separate on-call rotations — without gaining their actual benefit, which is the ability to develop, deploy, and scale services _independently_. The fix is disciplined API versioning and backward compatibility: a service should be able to add new fields or new behavior without breaking every existing consumer, and consumers should tolerate unknown new fields gracefully rather than breaking on them.

### 2.2 Chatty Services

This anti-pattern shows up when one logical operation requires a huge number of small, sequential network calls between services, instead of one well-designed call that fetches everything needed at once.

python

```python
# Anti-pattern: "chatty" — five separate network round trips
def get_order_summary(order_id):
    order = order_service.get(order_id)                # network call 1
    user = user_service.get(order.user_id)              # network call 2
    items = []
    for item_id in order.item_ids:                      # network calls 3, 4, 5, ...
        items.append(inventory_service.get(item_id))
    return build_summary(order, user, items)
```

Every network call carries real latency — even a fast internal call might take a few milliseconds — and when you chain five, ten, or twenty of them sequentially just to answer one request, those milliseconds add up into a genuinely slow response, even though each individual service is fast on its own. The fix usually involves batching calls (asking `inventory_service` for all items in one request instead of one call per item), or introducing an aggregation layer — often the API Gateway from Phase 4 — that fetches what it needs in parallel rather than one after another.

### 2.3 The Shared Database Anti-Pattern

This happens when multiple independent services all read from and write to the _same_ underlying database directly, instead of each service owning its own data and exposing it only through its own API.

```
┌───────────────┐     ┌───────────────┐     ┌───────────────┐
│ OrderService  │     │ InventoryService│    │ AnalyticsService│
└───────┬───────┘     └───────┬───────┘     └───────┬───────┘
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                               ▼
                     ┌───────────────────┐
                     │   Shared Database   │
                     └───────────────────┘
```

This looks convenient at first — no need to build APIs between services, just query the shared tables directly — but it quietly destroys the entire point of having separate services. If `InventoryService` decides to rename a column or change how stock counts are calculated, it might silently break `AnalyticsService` and `OrderService`, neither of which had any warning, because they were never going through a stable, intentional interface in the first place. The fix is the principle of **database-per-service**: each service owns its own data exclusively, and every other service must go through that service's actual API to read or affect that data — never by reaching directly into its tables.

### 2.4 The God Object / God Service

A **God Object** in traditional object-oriented code is a single class that has grown to know about, and control, far too much of the system — it does validation, business logic, formatting, and persistence, all in one enormous class that everyone is afraid to touch. The distributed-systems version of this is a **God Service**: one microservice that has slowly absorbed responsibility for order processing, user management, notifications, and payments, all inside "just one more endpoint," until it has effectively become the monolith the team was originally trying to move away from — just now wearing the label "microservice."

python

```python
class OrderService:
    def place_order(self, order): ...
    def send_email(self, user): ...        # this doesn't belong here
    def calculate_tax_for_region(self, order): ...  # neither does this
    def update_user_loyalty_points(self, user): ...  # or this
    def generate_invoice_pdf(self, order): ...       # or this
```

The fix is the same discipline that motivated microservices in the first place: each service should have one clear, well-bounded responsibility — often guided by a concept called a **bounded context**, where a service's boundaries match a specific business capability (like "handling payments" or "sending notifications"), rather than growing organically wherever it was easiest to add the next feature.

### 2.5 The Single Point of Failure (SPOF)

This anti-pattern is about architecture, not code style: it occurs whenever one single, non-redundant component sits in the critical path of your entire system, such that if that one component goes down, the whole system goes down with it — even if every other service is perfectly healthy.

A classic example is a single API Gateway instance from Phase 4 with no backup: if that one gateway process crashes, every client request fails, even though `OrderService`, `PaymentService`, and every other backend service are running perfectly fine behind it. The fix is redundancy at every critical layer — running multiple instances of the gateway behind a load balancer, running multiple replicas of a database with automatic failover, and generally asking, for every component in your architecture, "if this one thing disappeared right now, what happens?" A component surviving that question is resilient; a component that takes down the whole system is a single point of failure waiting to be discovered at the worst possible time.

### 2.6 Ignoring Idempotency

This anti-pattern is subtle and shows up specifically because of the distributed patterns from Phase 4. Since networks are unreliable, clients frequently retry requests that appear to have failed — but sometimes the original request actually succeeded, and only the _response_ got lost on the way back. If an operation like "charge the customer ₹500" is retried blindly, the customer could be charged twice for a single order.

python

```python
# Anti-pattern: not idempotent — retrying this call charges the customer again
def charge_customer(order_id, amount):
    payment_gateway.charge(amount)
```

The fix is designing operations to be **idempotent** — safe to run more than once with the exact same effect as running them once — typically by having the client attach a unique **idempotency key** to each logical operation, and having the server remember which keys it has already processed.

python

```python
def charge_customer(order_id, amount, idempotency_key):
    existing_result = idempotency_store.get(idempotency_key)
    if existing_result:
        return existing_result  # already processed — just return the same result again

    result = payment_gateway.charge(amount)
    idempotency_store.save(idempotency_key, result)
    return result
```

This single pattern quietly underlies almost every reliable distributed system in production — every retry mechanism we discussed conceptually back with Circuit Breakers in Phase 4 is only actually safe to use if the operation being retried is idempotent in the first place.
