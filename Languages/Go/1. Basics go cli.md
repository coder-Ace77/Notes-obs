### Go cli

```bash
go run
go build

go install 

go get

go mod <module name>

go mod tidy

go test
```

`run` compiles and runs the file in a single step. It creates a temporary binary and then deletes. 

`build` Compiles the packages and their dependencies into an executable binary in your current directory

Install Compiles the package and moves the resulting binary to your `$GOBIN` directory (usually `~/go/bin`), making it accessible from anywhere in your terminal.

`get` is used to download package from and adds to the module. 

`test` is used to run any file ending with `_test.go`. 

### Go code 

In go the `module` is the highest level of code organization. Its atually the collection of go packages. Now `go` modules allow the developer to interact with external code. To do that module has a path name eg - `github.com\user\project`. All the details of go modules are kept in the `go.mod` file which contains the module path and go version. It is also the place where the external requirements aka other libraries are listed. 

`go.sum` is a checksum file used to verify if code has not been tampered. go does not forces a certain directory structure but community has settled on the following structure. 

```go
my-app/
├── go.mod                # Module definition
├── go.sum                # Dependency checksums
├── cmd/                  # Entry points for the application
│   └── my-app/
│       └── main.go       # The "main" package
├── internal/             # Private library code (cannot be imported by others)
│   └── auth/
│       └── service.go
├── pkg/                  # Public library code (can be imported by other projects)
│   └── logger/
│       └── logger.go
├── api/                  # API protocols (Swagger, Protocol Buffers)
├── web/                  # Static assets, UI components
└── configs/              # Configuration files
```

**`/cmd`**: Contains the main applications for the project. Each subdirectory here represents a separate executable.

**`/internal`**: This is a special directory name. The Go compiler **prevents** any package outside of your module from importing code inside `internal`. It’s for logic you want to keep private.

**`/pkg`**: Used for code that is safe for other projects to import. _Note: Many modern projects are moving away from `/pkg` in favor of just putting packages in the root or `/internal`._

In Go, **every directory is a package**. All files within a single directory must belong to the same package (usually named after the directory). A package is a single directory containing one or more `.go` files.

- **Rule:** Every file in that directory **must** have the same `package name` at the top.
- **Purpose:** To group related logic (e.g., all database code goes in `package db`)

Go does not have `public`, `private`, or `protected` keywords. Instead, visibility is determined by the **first letter** of the identifier:

- **Upper Case (Exported):** `func DoWork()` is visible outside the package.
- **Lower Case (Unexported):** `func doWork()` is only visible within the same package.

Go imports are based on the module name defined in `go.mod`.

If your module is named `github.com/alex/myapp`, and you have a package in `pkg/auth`, you import it like this:

```go
import "github.com/alex/myapp/pkg/auth"
```

When you run `go build`, the compiler performs **Static Linking**. This means it grabs every library, every dependency, and even the runtime (which handles garbage collection and scheduling) and packs them all into a **single, self-contained binary file**

**Portability:** You can build a binary on your Ubuntu machine and (usually) just copy that one file to a server, and it will run without needing Go installed there

Go is a compiled language, but it feels like an interpreted one because it is incredibly fast.

1. **Scanning/Parsing:** The compiler reads your `.go` files and checks for syntax errors.
2. **Type Checking:** It ensures you aren’t trying to add a string to an integer.
3. **Optimization:** It removes dead code (code that is never called) to keep the binary small.
4. **Code Generation:** It converts your code into machine code (binary) for your specific CPU architecture (e.g., AMD64 or ARM64).

Good thing about go is it can either work to compile a single file or also act as package manager so when you write `go run main.go`. It not only compiler main but all the dependencies it depends on mainly that is dictated by the imports you do. However it will not compile and make the binary for anything not used by main. 

**`go run .` (The Recommended Way)**: The dot represents the "current directory." This tells Go to compile **all** files in the current folder that belong to `package main`. This is almost always what you want to do.

Finally with the module defined we use `go build` to create a permanant binary that is prepared for deployment. Also note that when you use external packages code is actually imported from the external system.
