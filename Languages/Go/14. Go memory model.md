Go tries to allocate memory on the **stack** whenever possible because stack allocation and deallocation require zero CPU overhead (it’s just a pointer increment/decrement).

However, if a variable's lifetime exceeds the scope of the function that created it, or if its size is dynamic/too large, it must be allocated on the **heap**. The Go compiler performs **Escape Analysis** at compile-time to determine where a variable should live.

```go
func createOnStack() int {
    x := 10 // Stays on the stack, dies when function returns
    return x
}

func createOnHeap() *int {
    x := 10 // "Escapes" to the heap because a reference is returned
    return &x
}
```

Heap allocation in Go uses a multi-level hierarchy to prevent lock contention among concurrent goroutines:

- **`mcache` (Per-Thread Cache):** Each logical processor (the `P` in Go's GMP scheduler) gets its own local memory cache. Allocating from `mcache` requires no locks, making it incredibly fast.
    
- **`mcentral`:** When an `mcache` runs out of a specific size class of memory, it fetches a chunk from `mcentral`. This requires a lock, but it is infrequent.
    
- **`mheap`:** The global memory pool. If `mcentral` is empty, it pulls pages of memory directly from the OS into `mheap`.

### Garbage collection

Go uses a **non-generational, concurrent, tri-color mark-and-sweep** garbage collector. Unlike Java or C#, Go does _not_ use a generational GC (splitting objects into "young" and "old" generations). Go can get away with this because its Escape Analysis ensures that most short-lived objects are allocated on the stack (which is cleaned up automatically), significantly reducing the pressure on the heap GC. 

The GC views all objects in memory as a directed graph. During the "Mark" phase, it traverses this graph using three colors:

- **White:** Objects that have not been visited yet. At the end of the GC cycle, any remaining white objects are considered garbage.
    
- **Grey:** Objects that have been visited (they are reachable), but their child pointers have not yet been scanned.
    
- **Black:** Objects that have been visited, and all of their immediate child pointers have also been scanned.

Go's GC prioritizes **low latency** over high throughput. It aims to keep Stop-The-World (STW) pauses under 1 millisecond. It achieves this by doing most of the work concurrently with your application code.

1. **Sweep Termination (STW):** The application is briefly paused. The GC ensures the previous sweep phase is fully complete.
    
2. **Mark Phase (Concurrent):** The GC roots (globals, stack variables) are colored Grey. The GC then concurrently traverses the heap, turning Grey objects Black and their children Grey.
    - _The Write Barrier:_ Because the application is running concurrently, it might mutate pointers while the GC is scanning. Go enables a "write barrier" during this phase. If your code creates a new pointer reference, the write barrier catches it and colors the new object Grey, ensuring it isn't accidentally swept.

- **Mark Termination (STW):** The application is paused again briefly. The GC finishes any remaining work, flushes caches, and disables the write barrier.
    
- **Sweep Phase (Concurrent):** The application resumes. The GC concurrently sweeps the heap, reclaiming memory from all remaining White objects and returning it to the allocator.

Go's GC has historically been tuned with a single environment variable: `GOGC`.

- **`GOGC` (Default 100):** This is the pacing multiplier. A value of 100 means the GC will trigger when the heap size has grown by 100% (doubled) since the last collection. Lowering it makes the GC run more often; raising it uses more memory but saves CPU cycles.
    

Introduced in Go 1.19, `GOMEMLIMIT` offers a soft memory limit:

- **`GOMEMLIMIT`:** Allows you to specify an absolute memory cap (e.g., `GOMEMLIMIT=2GiB`). The GC will respect `GOGC` normally, but if the application approaches the memory limit, the GC will aggressively run more often to prevent an Out-Of-Memory (OOM) crash, effectively overriding `GOGC`.
