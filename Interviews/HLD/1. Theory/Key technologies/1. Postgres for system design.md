Postgres is a relational database. To understand its working in general consider what happens when client wants to connect to db. 
### Client request flow:

In postgres everything needs to connect to it first, be it an application server or a simple interactive client. Before anything else, it helps to be precise about what a "connection" actually is: it's a stateful, authenticated session over TCP between a client and the PostgreSQL server. Each postgres connection is a real OS process(expensive). Because setting one up is real work (a TCP handshake, authentication, and process creation on the server), a connection is a comparatively expensive.

Note that for each connection three steps are done - `tcp+auth+prcoess fork` which can take around 30-40ms while a typical query only takes around 1ms. Also under heavy load postgres has upper limit to total number of opened connection which can exhaust and put more pressure on application.  Any application wanting to talk to Postgres needs a piece of client code to manage this a **postgres driver**.

A request comes into a backend service, and the handler needs data, so it goes through the Postgres driver library. In practice, that driver almost never opens a fresh connection for this one request instead it maintains an **application-level connection pool**: a set of connections that were opened once, authenticated, and are kept alive for reuse. Request comes any idle connection is choosen. This is why pool size also matters too small, and requests start queueing for a free connection under load; too large, and the application ends up forcing the database to sustain far more live connections than it needs to.

Postgres uses the process per connection model this means any isolated request will not corrupt memory of other process and crash of one process will not make entire db down. 
It also means each connection permanently reserves real memory and scheduling overhead on the server, and PostgreSQL's `max_connections` ceiling is consequently only in the low hundreds by default. An application-level pool helps a single service reuse its own connections efficiently, but it doesn't change the fact that *many* service instances, each with its own pool, can still add up to more total connections than PostgreSQL can comfortably sustain which is exactly the problem external poolers solve.
##### PgBouncer

**PgBouncer** is a lightweight, standalone proxy that sits between applications and PostgreSQL, and it exists for precisely that multi-instance problem: across a fleet of application servers, the *combined* connection count from all their individual pools can easily run into the thousands.

![[Pasted image 20261012113816.png]]

PgBouncer solves this by terminating all of those client-side connections itself and funneling the actual work through a much smaller, reused pool of real backend connections to PostgreSQL.

Pgbouncer supports three distinct pooling modes - 
- **session** (a client keeps its backend connection for the lifetime of its session, safest but least efficient),
- **transaction** (the backend is only reserved for the duration of a single transaction and returned to the pool immediately after, the most common production setting), 
- **statement** (returned after every single statement, the most aggressive but breaks multi-statement transactions

PgBouncer itself is single-threaded per pool (though it can run multiple processes for higher throughput), it's not free  it's simply cheaper than a full PostgreSQL backend, so it should be sized and monitored. 

### What happens when request is received?

The very first thing that happens to an incoming query string is that it gets run through the **parser**, which checks the SQL for syntactic correctness and converts the raw text into a **parse tree** a structured, tree-shaped representation of the query that the rest of the system can reason about.

From there the query moves into the **rewrite stage**, where PostgreSQL applies any relevant **rules** for example, expanding a query against a view into a query against its underlying base tables, or applying rules created via `CREATE RULE`. This is a distinct step from planning; it transforms the query itself before any thought is given to *how* to execute it.

Once the rewritten query is ready, it's handed to the **planner/optimizer**. The planner  creates multiple candidate strategies for answering the same query (different join orders, different access paths, different algorithms) and estimates the **cost** of each one using statistics PostgreSQL maintains about the tables (row counts, value distributions, index selectivity, etc.). It then chooses the plan with the lowest estimated cost.

Once a plan is chosen, it moves into the **executor**, which actually walks that plan tree and produces the result rows. This execution model is **pull-based**: the top of the tree (the node closest to the client) asks the node below it for a row. This pull-based, node-by-node approach lets PostgreSQL support **pipelined execution**, meaning it generally doesn't have to materialize the entire result set in memory before returning anything to the client; rows can stream out as they're produced. The exception is when an operation inherently needs to see the whole input before it can produce output a full `ORDER BY` sort or a `DISTINCT` typically has to buffer everything first, since you can't emit the first sorted row until you've seen every candidate row.

Underneath all of this, actually getting at the data is the job of the **buffer manager**. PostgreSQL keeps a cache of recently used data pages in a shared memory region called `shared_buffers`; when the executor needs a row, it first checks whether the containing page is already cached there. If it isn't, PostgreSQL has to perform an actual **disk read** to pull the page in, and pages are typically read and cached in fixed **8KB** units regardless of how much of that page is actually relevant to the query.

On the write path, durability is guaranteed through **write-ahead logging (WAL)**: any change is first written as a log record to the WAL before the corresponding data page is modified, so that if the server crashes mid-write, PostgreSQL can replay the WAL on restart and recover to a consistent state. Concurrently, PostgreSQL enforces ACID guarantees particularly isolation between simultaneous transactions  using **MVCC (Multi-Version Concurrency Control)**, where instead of locking rows for reads, each transaction sees a consistent snapshot of the data as of some point in time, while writers create new row versions rather than overwriting old ones in place; this is what allows readers and writers to avoid blocking each other in the common case.

Finally, once the executor has produced the result rows, PostgreSQL doesn't just hand back raw internal representations  the data is **formatted** according to what the connecting client actually asked for, whether that's plain text, PostgreSQL's binary wire format, or something like JSON, before being sent back over the connection.

### Optimisation which postgres does:

The first is **parallel query execution**. For large scans or aggregations, PostgreSQL can split the work across multiple background worker processes  `Parallel Seq Scan`, `Parallel Hash Join`, or `Parallel Aggregate`. The way this works is that the leader process spins up a handful of parallel workers, each one is handed a slice of the table to scan independently, and the leader gathers their partial results back together. 

![[Pasted image 20261012113600.png]]

The second is the **index-only scan**. Normally, using an index to find a row is a two-step affair look up the entry in the index to get a row's location (a TID), then go fetch the actual row from the table (the heap) to read whichever columns the query needs. If every column the query needs is already present in the index itself, PostgreSQL can in principle skip that second heap fetch entirely and answer the query straight from the index. 
## Indexes
#### Working of indexes

When we store data in a database, it's ultimately written to disk as a collection of files. The main table data is typically stored as a heap file - essentially a collection of rows in no particular order.

Modern databases face an interesting challenge: they need to store and quickly access vast amounts of data. While the data lives on disk (typically SSDs nowadays), we can only process it when it's in memory. This means every query requires loading data from disk into RAM.

When querying without an index, we need to scan through every page of data one by one, loading each into memory to check if it contains what we're looking for. With millions of pages, this means millions of (relatively) slow disk reads just to find a single record. 

But with indexes, we transform our access patterns. Instead of reading through every page of data sequentially, indexes provide a structured path to follow directly to the data we need. They help us minimize the number of pages we need to read from storage by telling us exactly which pages contain our target data. Indexes also need to be stored on disk.

Indexes have two downsights however, first one is that each index requires the disk space. Second every update to main table will also required to update the indexes. Meaning if the table is having more writes than reads we might get hurt. 

Creating one is as simple as:

```sql
CREATE INDEX idx_salary ON employees (salary);
```

 PostgreSQL builds an entirely separate physical structure on disk (tracked via `pg_index` and its own files under the database's data directory), and indexes are never stored inside the table's own file they live alongside it as distinct files. From this point on, PostgreSQL has to keep that structure in sync with every `INSERT`, `UPDATE`, and `DELETE` made against the table.

### B-tree

B-tree indexes are the most common type of database index, providing an efficient way to organize data for fast searches and updates. They achieve this by maintaining a balanced tree structure that minimizes the number of disk reads needed to find any piece of data.

### Structure

A B-tree is a self-balancing tree that maintains sorted data and allows for efficient insertions, deletions, and searches. Unlike binary trees where each node has at most two children, B-tree nodes can have multiple children - typically hundreds in practice. Each node contains an ordered array of keys and pointers, structured to minimize disk reads.

![[Pasted image 20261012114153.png]]

Every node in a B-tree follows strict rules:

- All leaf nodes must be at the same depth
- Each node can contain between m/2 and m keys (where m is the order of the tree)
- A node with k keys must have exactly k+1 children
- Keys within a node are kept in sorted order

This structure is particularly clever because it maps perfectly to how databases store data on disk. Each node is sized to fit in a single disk page (typically 8KB), maximizing our I/O efficiency. When PostgreSQL needs to find a record with id=350, it might only need to read 2-3 pages from disk: the root node, maybe an internal node, and finally a leaf node. It's well suited to equality lookups, range queries (`BETWEEN`, `<`, `>`), sorting operations (`ORDER BY`), and enforcing uniqueness constraints like primary keys. 

B-trees maintain the physical order of keys within their leaf pages, so scanning a range doesn't mean jumping randomly around the index, it can walk sequential, neighboring pages instead, which is far friendlier to disk I/O than random access. Because the tree stays balanced and multi-level no matter how much data goes in, lookups, insertions, and range scans all land at roughly `O(log n)` complexity. 

### Hash index

A **hash index** is a narrower, more specialized structure: essentially a hash table mapping a key directly to a row pointer.

```sql
CREATE INDEX idx_user_hash ON users USING hash (email);
SELECT * FROM users WHERE email = 'john@abc.com';
```

Because hashing deliberately destroys any notion of order  two very similar emails can hash into completely different buckets a hash index is only useful for exact-equality lookups; it can't help with range queries or `ORDER BY` the way a B-tree can. In practice this makes it a niche tool: it's worth reaching for only when you're confident a column is *exclusively* queried via equality, and even then a B-tree is usually competitive enough that many teams just default to B-tree everywhere to keep things simple.
### GIN (Generalized Inverted Index)

It's called inverted because it maps **values to rows** a **GIN** index stores:
```psql
element/value → list of row locations containing that element
```

So suppose we have data as:

|id|description|
|---|---|
|1|"apple orange banana"|
|2|"orange mango"|
|3|"banana apple"|

GIN breaks each row's text apart and indexes every individual word:

```
"apple"  → [1, 3]
"banana" → [1, 3]
"orange" → [1, 2]
"mango"  → [2]
```

so for example with the following query:

```sql
SELECT * FROM products WHERE description @@ to_tsquery('apple & banana');
```

PostgreSQL doesn't need to scan the table at all  it looks up `"apple"` and `"banana"` in the index, intersects their row lists, and only fetches rows `{1, 3}`. Structurally, a GIN index is really made of two parts: the **entries**, which are the distinct lexemes (words/tokens) it has extracted, and each entry's **posting list**  a sorted list of TIDs (tuple identifiers, i.e. row pointers) for every row containing that lexeme. Internally, PostgreSQL stores those entries themselves in an ordinary **B-tree**, but instead of each entry pointing to a single row like a normal B-tree index, each entry points to an entire *set* of rows.

This structure is what makes GIN good for full-text search over `tsvector` columns-
```sql
CREATE INDEX idx_products_desc_gin ON products USING GIN (to_tsvector('english', description));
```

then we can search 
```sql
SELECT * FROM products WHERE to_tsvector('english', description) @@ plainto_tsquery('banana apple');
```

### Trigram search (fuzzy search and substring matching)

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_products_desc_trgm ON products USING GIN (description gin_trgm_ops);

SELECT * FROM products WHERE description ILIKE '%banana%';
SELECT * FROM products WHERE description % 'bananna'; -- fuzzy
```

A **trigram** is simply a sequence of three consecutive characters taken from a string, with a space padded onto the start and end so that the leading and trailing characters get represented too:

```
String:   "apple"
Trigrams: "  a", " ap", "app", "ppl", "ple", "le ", "e  "
```

When you search for a string that's slightly misspelled e.g., `"aple"` as a typo of `"apple"`  PostgreSQL compares the **overlap between the trigram sets** of both strings rather than requiring an exact character match:

```
'apple' trigrams:  { ' ap', 'app', 'ppl', 'ple' }
'aple'  trigrams:  { ' ap', 'apl', 'ple' }
```

Enough of those trigrams overlap that PostgreSQL considers the two strings similar, even though they aren't identical. Without an index, evaluating this kind of similarity (or a leading-wildcard `ILIKE '%banana%'`) means computing trigrams and comparing them row by row across the entire table  it performs very badly at any real scale, because there's no way to jump straight to the relevant rows.

A **GIN (or GiST) trigram index** fixes that by precomputing and indexing the trigrams up front:

```sql
CREATE INDEX idx_products_desc_trgm ON products USING GIN (description gin_trgm_ops);
```

PostgreSQL now stores **trigrams of each `description`** in an inverted index, exactly the same entries-to-posting-lists structure described for GIN above, just with trigrams as the entries instead of whole words:

| Trigram | Rows containing it |
| ------- | ------------------ |
| "app"   | [1, 5, 8, 22]      |
| "ppl"   | [1, 8, 22]         |
| "ple"   | [1, 22]            |
| "ban"   | [3, 9, 12]         |
When you run the search, Postgres retrieves all rows containing trigrams similar to `"apple"` and only checks those avoiding full-table scan.

Result: **massive speedup**, often 100x–1000x faster.

#### Composite index

Composite indexes are the most common optimization pattern you'll encounter in practice. Instead of creating separate indexes for each column, we create a single index that combines multiple columns in a specific order. This matches how we typically query data in real applications.

For an example Consider a typical social media feed query:

```sql
SELECT * FROM posts 
WHERE user_id = 123 
AND created_at > '2024-01-01'
ORDER BY created_at DESC;
```

One way is to create two indexes however that way is inefficient because first index will be used to get the candidates pertaining to first set of rules and then second query will filter out from another time. Instead composite index will give all we need in a one shot by combining columns.

```sql
CREATE INDEX idx_user_time ON posts(user_id, created_at);
```

When we create a composite index, we're really creating a B-tree where each node's key is a concatenation of our indexed columns. For our (user_id, created_at) index, each key in the B-tree is effectively a tuple of both values. The B-tree maintains these keys in sorted order based on user_id first, then created_at. Conceptually, the keys might look like:

Now when we execute our query, the database can traverse the B-tree to find the first entry for user_id=123, then scan sequentially through the index entries for that user until it finds entries beyond our date range. Because the entries are already sorted by created_at within each user_id group, we get both our filtering and sorting for free.

![[Pasted image 20261012120856.png]]

The order of columns in a composite index is crucial. Our index on (user_id, created_at) is great for queries that filter on user_id first, but it's not helpful for queries that only filter on created_at.

This is why you'll often hear database experts say "order columns from most selective to least selective."

Consider common interview scenarios like:

- Order history lookups: (customer_id, order_date)
- Event processing: (status, priority, created_at)
- Activity feeds: (user_id, type, timestamp)

### Covering Index

When PostgreSQL uses an index to find a row, it typically needs to do two things:

1. Look up the value in the index to find the row's location
2. Fetch the actual row from the table to get other columns you need

But what if we could store all the data we need right in the index itself? That's what covering indexes do:

```sql
-- Let's say this is a common query in our social media app:
SELECT title, created_at 
FROM posts 
WHERE user_id = 123 
ORDER BY created_at DESC;

-- A covering index that includes all needed columns
CREATE INDEX idx_posts_user_include 
ON posts(user_id) INCLUDE (title, created_at);
```

The trade-off is the same one indexes always carry, just amplified: the index itself grows larger since it's now storing whole extra columns, not just the indexed key, and every write that touches `title` or `created_at` now has more index data to update, so writes get slightly slower in exchange for the read-side win.

### Partial index

Sometimes you don't need to index *all* of your data  only a subset of it is ever actually queried. In a social media platform, for instance, the overwhelming majority of queries are probably looking for active users, not deleted ones, so indexing deleted users at all is close to pure waste:

```sql
-- Standard index indexes everything
CREATE INDEX idx_users_email ON users(email);  -- Indexes ALL users

-- Partial index only indexes active users
CREATE INDEX idx_active_users 
ON users(email) WHERE status = 'active';  -- Smaller, faster index
```

Because the `WHERE status = 'active'` clause is baked into the index definition itself, PostgreSQL simply never adds an entry for rows that don't match it  the index only ever needs to store, scan, and maintain the active subset, not the whole table. This pays off in a few compounding ways: the index is physically smaller, which means it's more likely to stay resident in memory (`shared_buffers`) rather than requiring disk reads; every `INSERT`/`UPDATE`/`DELETE` against an *inactive* row skips updating this index entirely, since it was never eligible in the first place; and PostgreSQL can only use this index for queries whose `WHERE` clause is compatible with (i.e., logically implies) the index's own condition a query with no `status` filter, or one explicitly asking for `status = 'deleted'`, won't be able to use it at all. Partial indexes are consequently most valuable whenever there's a persistent, lopsided split in your data active vs. deleted, unprocessed vs. processed, current vs. archived where the bulk of real traffic only ever cares about one side of that split.

### Geospecial index

Geospatial indexes are specialized data structures designed to efficiently store and query data representing objects in geometric space (points, lines, polygons). Unlike standard B-trees, which are optimized for one-dimensional, linear data (like numbers or strings), geospatial indexes must handle multidimensional coordinates simultaneously.

In a standard B-tree, data is sorted in a single order. If you try to query a 2D range (e.g., "find all points within 5km of my location"), a standard index can only optimize for one dimension (Latitude **OR** Longitude) at a time. This results in a "scan" of massive amounts of irrelevant data.

Geospatial indexes solve this by mapping 2D or 3D coordinates into a format that preserves **spatial locality** meaning objects close together in the physical world remain close together in the index structure.

#### Indexing techniques

##### Grid based 

The simplest approach divides the world into a uniform grid of cells. Each cell is assigned a unique identifier. An object's coordinates are mapped to a specific cell ID. To find nearby objects, the database only looks at the current cell and its immediate neighbors. "Fixed" grids suffer from the **"Goldilocks Problem"**: if cells are too large, they contain too much data; if they are too small, a single object might span many cells. 

#### Quadtrees

A Quadtree is a tree data structure in which each internal node has exactly four children. It is primarily used to partition a two-dimensional space by recursively subdividing it into four quadrants (Northwest, Northeast, Southwest, Southeast).

It has max allowed entities inside any square limit. So if any square has more than `k` elements square is again recursively divided. 
It is good for handling non-uniform distributions as the indexing is density aware. 
Now with this it forms a tree with each node having `4` children. A proxity query will work like of the segment tree query Basically a traversal of quad tree. Which means Proximy search is really fast `O(logn)`. 

However quadtrees are expensive to rebuild consider the case when some person moves out of the boundry and moves into new one. Then entire tree needs to get rebuild. 

Most quadtrees require a predefined "bounding box" for the entire space. If an object moves outside this initial boundary, the tree may need to be entirely rebuilt or significantly restructured.

While searching is fast, keeping the tree updated as objects move can be computationally expensive, especially if frequent re-balancing or subdivision/merging of nodes is required.

Every internal node must store pointers to its four children. In very sparse datasets, the memory used by the tree structure (pointers and node metadata) can sometimes exceed the memory saved by the spatial partitioning.

If all data points are clustered very closely together, the tree can become extremely deep (unbalanced), leading to performance that degrades toward O(N) in the worst case.

```python
class Point:
    def __init__(self, x, y, data=None):
        self.x = x
        self.y = y
        self.data = data  # Optional: store object references

class Rect:
    def __init__(self, x, y, w, h):
        self.x = x  # Center X
        self.y = y  # Center Y
        self.w = w  # Half-width
        self.h = h  # Half-height

    def contains(self, point):
        return (self.x - self.w <= point.x <= self.x + self.w and
                self.y - self.h <= point.y <= self.y + self.h)

    def intersects(self, other):
        return not (other.x - other.w > self.x + self.w or
                    other.x + other.w < self.x - self.w or
                    other.y - other.h > self.y + self.h or
                    other.y + other.h < self.y - self.h)

class QuadTree:
    def __init__(self, boundary, capacity):
        self.boundary = boundary
        self.capacity = capacity
        self.points = []
        self.divided = False

    def subdivide(self):
        x, y, w, h = self.boundary.x, self.boundary.y, self.boundary.w, self.boundary.h
        
        # Create four quadrants
        nw = Rect(x - w/2, y + h/2, w/2, h/2)
        ne = Rect(x + w/2, y + h/2, w/2, h/2)
        sw = Rect(x - w/2, y - h/2, w/2, h/2)
        se = Rect(x + w/2, y - h/2, w/2, h/2)

        self.northwest = QuadTree(nw, self.capacity)
        self.northeast = QuadTree(ne, self.capacity)
        self.southwest = QuadTree(sw, self.capacity)
        self.southeast = QuadTree(se, self.capacity)
        
        self.divided = True

    def insert(self, point):
        if not self.boundary.contains(point):
            return False

        if len(self.points) < self.capacity:
            self.points.append(point)
            return True
        
        if not self.divided:
            self.subdivide()

        # Try to insert into children
        return (self.northwest.insert(point) or 
                self.northeast.insert(point) or 
                self.southwest.insert(point) or 
                self.southeast.insert(point))

    def query(self, range_rect, found_points=None):
        if found_points is None:
            found_points = []

        if not self.boundary.intersects(range_rect):
            return found_points

        # Check points in this node
        for p in self.points:
            if range_rect.contains(p):
                found_points.append(p)

        # Recurse into children
        if self.divided:
            self.northwest.query(range_rect, found_points)
            self.northeast.query(range_rect, found_points)
            self.southwest.query(range_rect, found_points)
            self.southeast.query(range_rect, found_points)

        return found_points
```

### Geohashing

Geohashing is a hierarchical spatial data structure that encodes a geographic location (latitude and longitude) into a short string of letters and digits. It effectively divides the Earth into a grid and assigns a unique identifier to each cell. You can think of geohashing as a way to flatten 2D spatial data into a 1D string while maintaining **spatial locality**. 

Geohashing uses a process called **Interleaving** or **Z-order curves**. First the world is divided into longitude of range `[-180,180]` and latitude `[-90,90]`. For longitude, if the point is in the right half `([0,180])`, the first bit is **1**. If it's in the left `([−180,0])`, it's **0**.
This continues recursively, narrowing the range with each bit.

- The bits from the longitude and latitude are "interleaved."
- Example: If Longitude bits are L1​L2​L3​ and Latitude bits are A1​A2​A3​, the combined bit string is L1​A1​L2​A2​L3​A3​

The resulting binary string is grouped into chunks of 5 bits. Each chunk is converted into a character using a specific Base32 alphabet (excluding confusing characters like 'a', 'i', 'l', 'o').
The length of the geohash string determines the size of the grid cell. A longer string means a smaller, more precise area.
Because geohashes are just strings, you can store them in a standard B-Tree index (like in **PostgreSQL** or **MongoDB**). A prefix search (e.g., `WHERE geohash LIKE 'tdr12%'`) instantly finds all points in that general vicinity.  
It’s easy to cache results for a specific geohash cell (e.g., "Top restaurants in geohash `wtw3s`").
Since nearby locations often share the same prefix, finding "nearby" points becomes a simple string comparison.

Geohashing follows a **Z-order curve**. While it generally keeps nearby points together, it suffers from **discontinuities at boundaries**. **The Problem:** Two points can be centimeters apart but on opposite sides of a major grid line. Their geohashes might look completely different (e.g., one starts with `s` and the other with `u`). **The Solution:** To perform a proper "nearby" search, developers typically query the target geohash **plus its 8 neighbors** (North, South, East, West, and diagonals) to ensure no points are missed at the edges.

Library exists in python which can do these stuffs. 

```python
import pygeohash as gh

# Latitude, Longitude for a spot in Delhi
lat, lon = 28.6139, 77.2090

# Encode to precision 7
hash_value = gh.encode(lat, lon, precision=7)
print(f"Geohash: {hash_value}") # Output: ttnfphv

# Decoding back
decoded_lat, decoded_lon = gh.decode(hash_value)
```

Update usually is `O(logn)` since when object changes its location we only need to calc new geohash and update `Btrees`.  Note that to save the location indexing must be used. Additonally redis supports geohash natively. 

Geohash are very fast for updates but they suffer from problem of uneven data distributions for example if there too many ppl at same geolocation then many ppl will will have same geostrings.
