Spring Boot simplifies data access by providing integration with various data sources like
relational databases (via JPA and JDBC) and NoSQL databases (e.g., MongoDB). It also
supports robust transaction management.
To access with data we define the entities which are analogoes to table schema and then define the queries in the `repository`. 

JPA defines how Java objects should be mapped to relational databases. It doesn't _do_ anything on its own; it’s just a set of interfaces.
Hibernate is the actual implementation It’s the engine under the hood that actually executes the SQL and manages the database connection. Spring data JPA is build on top of hibernate which provides repositories.  It makes using Hibernate even easier by providing repositories, so you don't even have to write "Save" or "Update" logic—you just define an interface.


### `@Entity`

`@Entity` marks a Java class as a table in the database. Example

```java
@Entity
public class User{
	@Id
	@GeneratedValue
	private Long id;
	private String name;
}
```

Other annotations are

| **Annotation**    | **Purpose**                                                                           |
| ----------------- | ------------------------------------------------------------------------------------- |
| `@Entity`         | Tells JPA that this class should be mapped to a database table.                       |
| `@Id`             | Marks the primary key of the entity.                                                  |
| `@GeneratedValue` | Defines the strategy for ID generation (e.g., `IDENTITY` for auto-increment).         |
| `@Column`         | Optional. Used to customize the column name or constraints (like `nullable = false`). |
| `@Table`          | Optional. Used to specify a custom name for the table.                                |
### Relational mapping

Every entity needs a unique identity and a way to be identified by the JPA provider.

```java
@Entity
@Table(name = "users") // Good practice: pluralize table names
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 50)
    private String username;

    @Column(name = "email_address") // Map Java field to specific SQL column
    private String email;

    @Transient
    private String sessionToken; // This field will NOT be saved to the DB
    
    // Standard Getters/Setters/Constructors
}
```

Relationships are defined by "Ownership." One side usually holds the Foreign Key in the database.

Imagine a `Post` that has many `Comments`. The "Many" side (Comment) is almost always the **Owner** because it holds the `post_id` foreign key.

Now both sides of realationships has to be annotated for jpa to know which column will be used for joining. The owner side side `Many` contains the annotation `ManyToOne`  and also join column. Note that we keep the one side object refernece as well. 

Similarly one side gets an list of array and is mapped by annotation like `@OneToMany` inside it may be mapped by `post` 

```java
@Entity
public class Post {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    // 'mappedBy' indicates that 'Post' is NOT the owner of the relationship.
    // It refers to the field name in the Comment class.
    @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Comment> comments = new ArrayList<>();
}

@Entity
public class Comment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String content;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "post_id") // This creates the Foreign Key column
    private Post post;
}
```

#### Many to many 

Think of `Student` and `Course`. A student has many courses, and a course has many students. This requires a **Join Table**.

```java
@ManyToMany
@JoinTable(
  name = "student_course", 
  joinColumns = @JoinColumn(name = "student_id"), 
  inverseJoinColumns = @JoinColumn(name = "course_id")
)
private Set<Course> enrolledCourses = new HashSet<>();
```

When defining these annotations, two parameters are critical for performance and data integrity:

**FetchType:**

- `EAGER`: Load the relationship immediately (default for `@ManyToOne`). Use with caution; it can kill performance.
- `LAZY`: Load the relationship only when you call the getter (default for `@OneToMany`). This is generally preferred.

**CascadeType:**
- `PERSIST`: When you save the parent, save the children.
- `REMOVE`: When you delete the parent, delete the children.
- `ALL`: Covers all operations.

If you use Lombok, **never** use `@Data` or `@ToString` on entities with relationships. It will cause a circular reference (Post calls Comment, which calls Post...), leading to a `StackOverflowError`. Always write your own `toString()` or exclude the relationship fields. 

### Repository pattern

JPA repository is actually the combination of two - 
- CrudRepository - Basic Create, Read, Update, Delete.
- PagingAndSorting - Adds methods to retrieve entities using pagination and sorting.

```java
@Repository
public interface ProductRepository extends JpaRepository<Product, Long> {
    // Basic CRUD methods are inherited automatically!
}
```

When the standard `findById` isn't enough, Spring gives you four main levels of "custom" querying.

Level 1: Derived Query Methods (The "Naming Convention")
Spring parses the method name to generate the SQL. This is best for simple queries.

```java
// SQL: SELECT * FROM products WHERE name = ? AND price < ?
List<Product> findByNameAndPriceLessThan(String name, Double price);

// SQL: SELECT * FROM products WHERE category IN (?, ?, ?)
List<Product> findByCategoryIn(List<String> categories);
```

Level 2: JPQL (Java Persistence Query Language)

When names get too long (e.g., `findByNameAndCategoryAndPriceLessThanAndStatusOrderByCreatedAtDesc`), use `@Query`. **JPQL works with Java Objects/Fields, not SQL Table/Column names.**

Note the names field as well as table names in `JPQL` are defined that of entities not of database table or column names. 

Unlike SQL, you almost always need an alias (e.g., `SELECT u FROM User u`).

```java
@Query("SELECT p FROM Product p WHERE p.price > :minPrice AND p.active = true")
List<Product> findExpensiveActiveProducts(@Param("minPrice") Double minPrice);
```

|**Operation**|**JPQL Syntax**|
|---|---|
|**Select All**|`SELECT p FROM Product p`|
|**Filtering**|`SELECT p FROM Product p WHERE p.price > 100`|
|**Ordering**|`SELECT p FROM Product p ORDER BY p.name DESC`|
|**Joins**|`SELECT p FROM Post p JOIN p.comments c WHERE c.approved = true`|
|**Aggregates**|`SELECT COUNT(u), u.department FROM User u GROUP BY u.department`|
```java
SELECT [Alias/Field] 
FROM [EntityName] [Alias]
JOIN [Alias.relationshipField] [JoinAlias]
WHERE [Conditions]
GROUP BY [Fields]
HAVING [Conditions]
ORDER BY [Fields] [ASC/DESC]
```

There are two ways to pass parameters: **Positional** and **Named**.

Named is the cleanest method because it’s readable and order doesn't matter. You use the `:variableName` syntax. 

```java
@Query("SELECT u FROM User u WHERE u.email = :email AND u.status = :status")
User findActiveUserByEmail(
    @Param("email") String email, 
    @Param("status") String status
);
```

Parameters are matched by their index. You use `?1`, `?2`, etc.

```java
@Query("SELECT u FROM User u WHERE u.email = ?1 AND u.status = ?2")
User findByEmailAndStatus(String email, String status);
```

Native sql

Use this for database-specific features (like PostgreSQL JSONB) that JPQL doesn't support.

```java
@Query(value = "SELECT * FROM products WHERE stock_count > 0", nativeQuery = true)
List<Product> findAvailableProductsNative();
```

The syntax is almost identical to JPQL, but remember: you must use the actual **Database Column Names**.

```java
@Query(value = "SELECT * FROM users_table WHERE email_addr = :email AND is_active = true", 
       nativeQuery = true)
User findByNativeEmail(@Param("email") String email);
```

Fetching an entire `@Entity` is expensive. **Projections** allow you to fetch only the data you need (e.g., just the Name and Price) into a lightweight interface or DTO.

Projections. 

```java
public interface ProductSummary {
    String getName();
    Double getPrice();
}

// In Repository:
List<ProductSummary> findAllByStatus(String status);
```



Spring Data provides interfaces for CRUD operations without boilerplate code. This is where Spring Boot really shines. Instead of writing complex DAO (Data Access Object) classes, you create an interface that extends `JpaRepository`.

```java
public interface UserRepository extends JpaRespository<User,Long>{
	List<User> findByName(String name);
}
```

Define complex queries using JPQL or native SQL.

```java
@Query("SELECT u FROM User u WHERE u.name LIKE %:name%")
List<User> searchByName(@Param("name") String name);
```

Built-in support via Pageable and Sort.

`Page<User> page = userRepository.findAll(PageRequest.of(0, 10, Sort.by("name")));`

One thing that trips people up is the **Persistence Context**. When you fetch an object, Hibernate keeps track of it. If you change a value on that object within a `@Transactional` method, Hibernate will automatically "flush" those changes to the database when the method finishes. You don't even have to call `save()`!

#### Database configurations

In Spring Boot, database configuration is handled primarily through the `application.properties` (or `.yml`) file. By default, Spring Boot uses **HikariCP** (Hikari Connection Pool) as the engine to manage these connections. 

Creating a new database connection for every request is **expensive**. It requires a TCP handshake, authentication, and resource allocation on the database server.

A **Connection Pool** maintains a "cache" of live connections. When your application needs to talk to the DB, it "borrows" an existing connection from the pool and "returns" it when finished. This makes the application significantly faster.

To connect to a database, you only need four core properties. Spring Boot will see these and automatically set up the Hikari Connection Pool for you.

```java
# 1. The Database URL (specific to your DB type)
spring.datasource.url=jdbc:postgresql://localhost:5432/my_database

# 2. Credentials
spring.datasource.username=admin
spring.datasource.password=secret_pass

# 3. The Driver (usually optional, Spring Boot guesses it from the URL)
spring.datasource.driver-class-name=org.postgresql.Driver

# 4. Hibernate Dialect (Tells Hibernate to write Postgres-flavored SQL) spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect

# 5. Hibernate Strategy (create, update, validate, or none)
spring.jpa.hibernate.ddl-auto=update
```

Hikari is famous for being the fastest and most lightweight connection pool. While the defaults (like a **maximum pool size of 10**) work for most, you can customize it using the `spring.datasource.hikari.*` prefix.

| **Property**         | **Default** | **Description**                                            |
| -------------------- | ----------- | ---------------------------------------------------------- |
| `maximum-pool-size`  | 10          | The absolute max number of connections.                    |
| `minimum-idle`       | 10          | Minimum number of connections kept "warm" and ready.       |
| `connection-timeout` | 30s         | How long you'll wait for a connection before failing.      |
| `idle-timeout`       | 10m         | How long a connection can sit unused before being retired. |
| `max-lifetime`       | 30m         | Max age of a connection (prevents "stale" connections).    |

```java
# Small pool for a microservice
spring.datasource.hikari.maximum-pool-size=5
spring.datasource.hikari.connection-timeout=20000 
spring.datasource.hikari.pool-name=MySpringBootHikariPool
```

Creator of hikari suggests using pool size using this formula. 

```
connections = 2*core_count+ effective_spindle_count
```

### H2

H2 is a lightweight, open-source **relational database**. It is used in springboot for testing and development. 

- **In-Memory Mode:** Data is stored in RAM. It’s incredibly fast but volatile (restarting the app wipes the data).
- **Embedded Mode:** Data is saved to a local file on your hard drive (persistent across restarts).
- **Browser Console:** It comes with a built-in GUI to run SQL queries while your app is running.
- **Compatibility:** It can "mimic" other databases like PostgreSQL, Oracle, or MySQL to ensure your code works similarly to production.

In springboot you just need to add dependency

```java
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>
```

```
# Basic Connection
spring.datasource.url=jdbc:h2:mem:testdb
spring.datasource.driverClassName=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=password

# Enable the H2 Console (Access via http://localhost:8080/h2-console)
spring.h2.console.enabled=true
spring.h2.console.path=/h2-console

# Keeps the database alive even if no connections are active
spring.datasource.url=jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1
```

Note there is another file based variation of h2.`jdbc:h2:file:./data/sample`

Since H2 starts empty every time in memory-mode, you can use two special files in your `src/main/resources` folder to prep the DB:

1. **`schema.sql`**: To define your tables manually.
2. **`data.sql`**: To insert seed data (users, products, etc.) automatically on startup.

Alternatively, if you use `spring.jpa.hibernate.ddl-auto=update`, Hibernate will generate the tables for you based on your `@Entity` classes.
