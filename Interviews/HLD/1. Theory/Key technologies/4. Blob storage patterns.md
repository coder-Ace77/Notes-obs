Sometimes you'll need to store large, unstructured blobs of data. This could be images, videos, or other files. Storing these large blobs in a traditional database is both expensive and inefficient and should be avoided when possible. Instead, you should use a blob storage service like Amazon S3 or Google Cloud Storage. These platforms are specifically designed for handling large blobs of data, and are much more cost-effective than a traditional database.

Blob storage services are simple. You can upload a blob of data and that data is stored and get back a URL. You can then use this URL to download the blob of data. Often times blob storage services work in conjunction with CDNs, so you can get fast downloads from anywhere in the world. Upload a file/blob to blob storage which will act as your origin, and then use a CDN to cache the file/blob in edge locations around the world.

- When clients want to upload a file, they request a presigned URL from the server.
- The server returns a presigned URL to the client, recording it in the database.
- The client uploads the file to the presigned URL.
- The blob storage triggers a notification to the server that the upload is complete and the status is updated.

To download:

- The client requests a specific file from the server and are returned a presigned URL.
- The client uses the presigned URL to download the file via the CDN, which proxies the request to the underlying blob storage.

#### Multipart upload:

For large files (think multi-GB videos) you don't upload in a single request - a network blip halfway through would mean starting over. Instead the file is split into chunks (e.g. 5-10MB each) and uploaded as separate parts, each getting its own presigned URL:

- Client asks server to initiate a multipart upload, server asks blob storage for an upload id and returns presigned URLs per part (or a way to fetch them part by part).
- Client uploads each chunk in parallel, retrying only the failed chunks instead of the whole file.
- Once all parts are uploaded, client (or server) calls a "complete multipart upload" request, blob storage stitches the parts together into one object.
- This also enables resumable uploads - if the client crashes/loses connection it can query which parts already succeeded and only re-upload the missing ones.

#### Upload validation:

Since the client is uploading directly to blob storage, you need to make sure it can't be abused:

- Presigned URLs should be scoped tightly - max file size, allowed content-type, and a short expiry time so the link can't be reused later.
- Even so, don't trust the upload blindly. After upload completes, validate the actual object (real size, real content-type/magic bytes match what's expected) before marking it usable.
- Run a virus/malware scan on uploaded files before they're served to other users.
- Presigned URLs that are issued but never used leave behind "pending" DB rows - run a periodic cleanup job (TTL based) to garbage collect these orphaned records/objects.

#### Post-upload processing & notification:

The raw uploaded blob usually isn't what gets served - e.g. YouTube needs to transcode a video into multiple resolutions/formats and generate a thumbnail before it's watchable.

- Blob storage emits an event when the upload completes (e.g. S3 event notification), which is pushed to a queue (SQS/SNS, Kafka, etc.) instead of the server polling for completion.
- A worker/consumer picks up the event, runs the processing pipeline (transcoding, thumbnailing, virus scan, etc.), and writes the results (new derived blobs + metadata) back to storage/db.
- Only once processing succeeds does the server flip the DB record's status from "pending" to "ready", at which point the content becomes visible/servable to other users.
- This decouples slow processing work from the upload request itself - the client gets a fast ack on upload, processing happens async, and the client can poll or get notified (websocket/push) when it's ready.
