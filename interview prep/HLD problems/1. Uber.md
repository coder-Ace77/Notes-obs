### Geospecial index

Geospatial indexes are specialized data structures designed to efficiently store and query data representing objects in geometric space (points, lines, polygons). Unlike standard B-trees, which are optimized for one-dimensional, linear data (like numbers or strings), geospatial indexes must handle multidimensional coordinates simultaneously.

In a standard B-tree, data is sorted in a single order. If you try to query a 2D range (e.g., "find all points within 5km of my location"), a standard index can only optimize for one dimension (Latitude **OR** Longitude) at a time. This results in a "scan" of massive amounts of irrelevant data.

Geospatial indexes solve this by mapping 2D or 3D coordinates into a format that preserves **spatial locality**—meaning objects close together in the physical world remain close together in the index structure.

#### Indexing techniques

##### Grid based 

The simplest approach divides the world into a uniform grid of cells. Each cell is assigned a unique identifier. An object's coordinates are mapped to a specific cell ID. To find nearby objects, the database only looks at the current cell and its immediate neighbors. "Fixed" grids suffer from the **"Goldilocks Problem"**: if cells are too large, they contain too much data; if they are too small, a single object might span many cells. 

#### Quadtrees

A Quadtree is a tree data structure in which each internal node has exactly four children. It is primarily used to partition a two-dimensional space by recursively subdividing it into four quadrants (Northwest, Northeast, Southwest, Southeast).

It has max allowed entities inside any square limit. So if any square has more than `k` elements square is again recursively divided. 
It is good for handling non-uniform distributions as the indexing is density aware. 
Now with this it forms a tree with each node having `4` children. A proxity query will work like of the segment tree query Basically a traversal of quad tree. Which means Proximy search is really fast `O(logn)`. 

However quadtrees are expensive to rebuild consider the case when some person moves out of the boundry and moves into new one. Then entire tree needs to get rebuild. 

Most quadtrees require a predefined "bounding box" for the entire space. If an object moves outside this initial boundary, the tree may need to be entirely rebuilt or significantly restructured.

While searching is fast, keeping the tree updated as objects move can be computationally expensive, especially if frequent re-balancing or subdivision/merging of nodes is required.

Every internal node must store pointers to its four children. In very sparse datasets, the memory used by the tree structure (pointers and node metadata) can sometimes exceed the memory saved by the spatial partitioning.

If all data points are clustered very closely together, the tree can become extremely deep (unbalanced), leading to performance that degrades toward O(N) in the worst case.

```python
class Point:
    def __init__(self, x, y, data=None):
        self.x = x
        self.y = y
        self.data = data  # Optional: store object references

class Rect:
    def __init__(self, x, y, w, h):
        self.x = x  # Center X
        self.y = y  # Center Y
        self.w = w  # Half-width
        self.h = h  # Half-height

    def contains(self, point):
        return (self.x - self.w <= point.x <= self.x + self.w and
                self.y - self.h <= point.y <= self.y + self.h)

    def intersects(self, other):
        return not (other.x - other.w > self.x + self.w or
                    other.x + other.w < self.x - self.w or
                    other.y - other.h > self.y + self.h or
                    other.y + other.h < self.y - self.h)

class QuadTree:
    def __init__(self, boundary, capacity):
        self.boundary = boundary
        self.capacity = capacity
        self.points = []
        self.divided = False

    def subdivide(self):
        x, y, w, h = self.boundary.x, self.boundary.y, self.boundary.w, self.boundary.h
        
        # Create four quadrants
        nw = Rect(x - w/2, y + h/2, w/2, h/2)
        ne = Rect(x + w/2, y + h/2, w/2, h/2)
        sw = Rect(x - w/2, y - h/2, w/2, h/2)
        se = Rect(x + w/2, y - h/2, w/2, h/2)

        self.northwest = QuadTree(nw, self.capacity)
        self.northeast = QuadTree(ne, self.capacity)
        self.southwest = QuadTree(sw, self.capacity)
        self.southeast = QuadTree(se, self.capacity)
        
        self.divided = True

    def insert(self, point):
        if not self.boundary.contains(point):
            return False

        if len(self.points) < self.capacity:
            self.points.append(point)
            return True
        
        if not self.divided:
            self.subdivide()

        # Try to insert into children
        return (self.northwest.insert(point) or 
                self.northeast.insert(point) or 
                self.southwest.insert(point) or 
                self.southeast.insert(point))

    def query(self, range_rect, found_points=None):
        if found_points is None:
            found_points = []

        if not self.boundary.intersects(range_rect):
            return found_points

        # Check points in this node
        for p in self.points:
            if range_rect.contains(p):
                found_points.append(p)

        # Recurse into children
        if self.divided:
            self.northwest.query(range_rect, found_points)
            self.northeast.query(range_rect, found_points)
            self.southwest.query(range_rect, found_points)
            self.southeast.query(range_rect, found_points)

        return found_points
```

### Geohashing

Geohashing is a hierarchical spatial data structure that encodes a geographic location (latitude and longitude) into a short string of letters and digits. It effectively divides the Earth into a grid and assigns a unique identifier to each cell. You can think of geohashing as a way to flatten 2D spatial data into a 1D string while maintaining **spatial locality**. 

Geohashing uses a process called **Interleaving** or **Z-order curves**. First the world is divided into longitude of range `[-180,180]` and latitude `[-90,90]`. For longitude, if the point is in the right half `([0,180])`, the first bit is **1**. If it's in the left `([−180,0])`, it's **0**.
This continues recursively, narrowing the range with each bit.

- The bits from the longitude and latitude are "interleaved."
- Example: If Longitude bits are L1​L2​L3​ and Latitude bits are A1​A2​A3​, the combined bit string is L1​A1​L2​A2​L3​A3​

The resulting binary string is grouped into chunks of 5 bits. Each chunk is converted into a character using a specific Base32 alphabet (excluding confusing characters like 'a', 'i', 'l', 'o').
The length of the geohash string determines the size of the grid cell. A longer string means a smaller, more precise area.
Because geohashes are just strings, you can store them in a standard B-Tree index (like in **PostgreSQL** or **MongoDB**). A prefix search (e.g., `WHERE geohash LIKE 'tdr12%'`) instantly finds all points in that general vicinity.  
It’s easy to cache results for a specific geohash cell (e.g., "Top restaurants in geohash `wtw3s`").
Since nearby locations often share the same prefix, finding "nearby" points becomes a simple string comparison.

Geohashing follows a **Z-order curve**. While it generally keeps nearby points together, it suffers from **discontinuities at boundaries**. **The Problem:** Two points can be centimeters apart but on opposite sides of a major grid line. Their geohashes might look completely different (e.g., one starts with `s` and the other with `u`). **The Solution:** To perform a proper "nearby" search, developers typically query the target geohash **plus its 8 neighbors** (North, South, East, West, and diagonals) to ensure no points are missed at the edges.
