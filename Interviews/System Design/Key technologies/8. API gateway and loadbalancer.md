## API Gateway

Especially in a microservice architecture, an API gateway sits in front of your system and is responsible for routing incoming requests to the appropriate backend service. The gateway is also typically responsible for handling cross-cutting concerns like authentication, rate limiting, and logging.

![[Pasted image 20251013114410.png]]

Most common API gateways are AWS API Gateway or NGINX (also Kong, Envoy, Apigee).

## Load Balancer

Most system design problems will require you to design a system that can handle a large amount of traffic. When you have a large amount of traffic, you will need to distribute that traffic across multiple machines (called horizontal scaling) to avoid overloading any single machine or creating a hotspot. This is where a load balancer comes in. For the purposes of an interview, you can assume that your load balancer is a black box that will distribute work across your system.

The reality is that you need a load balancer wherever you have multiple machines capable of handling the same request.

![[Pasted image 20251013114953.png]]

Note that sometimes you'll need to have specific features from your load balancer, like sticky sessions or persistent connections. The most common decision to make is whether to use an L4 (layer 4) or L7 (layer 7) load balancer.

### L4 vs L7

- **L4 (transport layer)**  operates on raw TCP/UDP. It looks only at IP address + port and forwards packets without inspecting the payload; it doesn't fully terminate the connection, it just routes it. This makes it very fast and protocol-agnostic (works for HTTP, gRPC, WebSockets, raw TCP), but it can't route based on URL path, headers, or cookies.

- **L7 (application layer)** terminates the client connection, parses the actual HTTP request (headers, path, cookies, body), then opens a **new** connection to the chosen backend. This enables smart routing (path/header-based), SSL termination, request rewriting, and caching but costs more CPU per request since it has to parse and buffer the protocol.

You can somewhat shortcut this decision with a simple rule of thumb: if you have persistent connections like websockets, you'll likely want to use an L4 load balancer (avoids repeatedly re-parsing a long-lived connection). Otherwise, an L7 load balancer offers great flexibility in routing traffic to different services while minimizing the connection load downstream.

The most common load balancers are AWS Elastic Load Balancer (NLB = L4, ALB = L7), NGINX (an open-source webserver frequently used as a load balancer), and HAProxy (a popular open-source load balancer).

- The **load balancer** decides **which gateway or backend instance** gets the request.
- The **API gateway** decides **which microservice endpoint** should handle it, and **how** (auth, rate limits, etc.).

### Load balancing algorithms & health checks

Load balancers maintain a list of instances and pick one using an algorithm:

- **Round robin** — cycle through instances in order.
- **Weighted round robin** — same, but bigger/faster instances get proportionally more traffic.
- **Least connections** — send to the instance with the fewest active connections; good when request durations vary a lot.
- **Least response time** — factors in observed latency as well as active connections.
- **IP hash / consistent hashing** — same client (or key) always maps to the same instance; useful for cache locality or sticky sessions without the LB storing session state.

To know which instances to send traffic to, the LB runs **health checks**:

- **Active checks** — the LB periodically pings a `/health` endpoint on each instance.
- **Passive checks** — the LB observes real traffic (timeouts, 5xxs) and marks an instance unhealthy without extra probe traffic.

An unhealthy instance is pulled out of rotation until it recovers.

### Request flow

Suppose we have a microservice architecture and a request comes in. It's first resolved by DNS and reaches the API gateway. The gateway performs auth, validation, etc., and routes it to the **load balancer** in front of the target microservice. The load balancer then decides which instance gets the request.

In Kubernetes, each microservice has a **Kubernetes Service** object that acts as an internal **load balancer + service discovery**. The API Gateway (Ingress Controller) routes external requests into the cluster.

## What can an API gateway do?

### Request validation

This validation includes checking that the request URL is valid, required headers are present, and the request body (if any) matches the expected format.

This early validation is important because it helps catch obvious issues before they reach your backend services. For example, if a mobile app sends a malformed JSON payload or forgets to include a required API key, there's no point in routing that request further into your system.

### Middleware task

API gateway can handle many middleware tasks like

- Authenticate requests using JWT tokens
- Limit request rates to prevent abuse (typically via **token bucket**, **leaky bucket**, or **sliding-window counter** algorithms)
- Terminate SSL connections
- Log and monitor traffic
- Compress responses
- Handle CORS headers
- Whitelist/blacklist IPs
- Validate request sizes
- Handle response timeouts
- Version APIs
- Throttle traffic
- Integrate with service discovery

### Routing

The gateway maintains a routing table that maps incoming requests to backend services. This mapping is typically based on a combination of:

- URL paths (e.g., /users/* routes to the user service)
- HTTP methods (e.g., GET, POST, etc.)
- Query parameters
- Request headers

### Backend communication

While most services communicate via HTTP, in some cases your backend services might use a different protocol like gRPC for internal communication. When this happens, the API Gateway can handle translating between protocols, though this is relatively uncommon in practice.

The gateway would, thus, transform the request into the appropriate protocol before sending it to the backend service. This is nice because it allows your services to use whatever protocol or format is most efficient without clients needing to know about it.

### Caching

Before sending the response back to the client, the gateway can optionally cache the response. This is useful for frequently accessed data that doesn't change often and, importantly, is not user specific. If your expectation is that a given API request will return the same result for a given input, caching it makes sense.

## Scaling the API gateway

When discussing API Gateway scaling in interviews, there are two main dimensions to consider: handling increased load and managing global distribution.

### Horizontal scaling

The most straightforward approach to handling increased load is horizontal scaling. API Gateways are typically stateless, making them ideal candidates for horizontal scaling. You can add more gateway instances behind a load balancer to distribute incoming requests.

### Global distribution

Another option that works well particularly for large applications with users spread across the globe is to deploy API Gateways closer to your users, similar to how you would deploy a CDN. This typically involves:

1. **Regional Deployments**: Deploy gateway instances in multiple geographic regions
2. **DNS-based Routing**: Use GeoDNS to route users to the nearest gateway
3. **Configuration Synchronization**: Ensure routing rules and policies are consistent across regions

With a microservices architecture, an API Gateway becomes almost essential. Without one, clients would need to know about and communicate with multiple services directly, leading to tighter coupling and more complex client code. The gateway provides a clean separation between your internal service architecture and your external API surface.

### Gateway load balancing is two different things

While API Gateways are primarily known for routing and middleware functionality, they often include load balancing capabilities. It's important to understand the distinction:

1. **Client-to-Gateway Load Balancing**  typically handled by a dedicated load balancer in front of your API Gateway instances (like AWS ELB or NGINX).
2. **Gateway-to-Service Load Balancing** the API Gateway itself performs load balancing across multiple instances of backend services.

This can typically be abstracted away during an interview. Drawing a single box to handle "API Gateway and Load Balancer" is usually sufficient. You don't want to get bogged down in the details of your entry points as they're more likely to be a distraction from the core functionality of your system.

## Why are gateways/load balancers so fast, and how do they handle such huge throughput?

This is really a question about hot-path design — these components are built so that the "expensive" parts of serving a request never happen on them. A few things stack together:

1. **They do almost no "work" per request.** No business logic, no DB writes. A routing decision is a hash-map/trie lookup plus an algorithm step (round-robin counter, least-connections heap) — O(1) or O(log n) in-memory operations. Compare that to a backend request, which might run several DB queries.
2. **Event-driven, non-blocking I/O.** NGINX, HAProxy, and Envoy use an event-loop (epoll/kqueue) reactor model instead of one OS thread per connection. A single worker process can hold tens of thousands of open connections because it isn't blocked waiting on any one of them  it just reacts to readiness events. This avoids the memory footprint and context-switch overhead of thread-per-connection servers (like older Apache).
3. **Multi-core scaling via `SO_REUSEPORT`.** Modern LBs run one event loop per CPU core, each with its own listening socket, so the kernel spreads incoming connections across cores with no lock contention between workers.
4. **Kernel-level / zero-copy tricks.** L4 load balancers (e.g., IPVS/LVS, which underlies many cloud LBs) can forward packets **inside the kernel**, never copying data up into user space at all. Even L7 proxies use `sendfile`/`splice`-style zero-copy where possible. The highest-throughput setups (Envoy + eBPF/XDP, DPDK-based LBs) bypass large parts of the kernel networking stack entirely.
5. **Connection reuse & multiplexing.** The TCP + TLS handshake is the expensive part of a request, not the byte-shuffling. Gateways keep persistent keep-alive connection pools to backends and reuse them across many client requests, so the handshake cost is paid once, not per-request. HTTP/2 multiplexing lets many logical requests share a single TCP connection.
6. **Stateless → horizontally scalable.** Gateways/LBs don't hold per-request state (beyond maybe a routing/session table), so you can run N identical instances behind DNS/anycast and add throughput near-linearly. The "black box" single LB in a diagram is usually a fleet behind an anycast IP.
7. **Implementation language & low-level engineering.** NGINX/HAProxy/Envoy are written in C/C++ (no GC pauses, no VM overhead), with years of micro-optimization around buffer reuse and avoiding allocations on the hot path.
8. **Hardware acceleration at the very top end.** Cloud load balancers (AWS NLB, Google's Maglev) and hardware appliances (F5) are purpose-built to push packets at line rate, combined with anycast IP + ECMP routing so traffic is spread across many physical LB nodes before it even reaches a single one.
