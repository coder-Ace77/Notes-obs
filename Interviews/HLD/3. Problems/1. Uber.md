Uber is ride sharing platform that connects passengers with drivers. 

### Requirements(Functional and Non functional requirements)

#### Function requirements
- User should be able to input the start and end location and get the price estimate. 
- User should be able to request a ride based on estimate.
- Drivers should be able to accept/deny a request and navigation to pickup/dropoff. (Consistency)

Out of scope 
- Multiple car types (out of scope)
- Ratings
- Schedule ride in advance

#### Non functional requriements
- Low lantency matching < 1 min to failure
- CAP theorum - Consistency of matching is important - meaning one user should only be mapped to only one driver. This also means as soon as driver picks up one req it should not be accpetable by others. 
- Highly avalable outside matching. 
- Handle high throughput - surges high on special events - Order - 100K in a specific region in a specific period. 

Out of scope

- User privacy 
- Resilience
- Monitoring , alerting
- CI/CD

### Core entities

- RIder
- Drivers
- Location
- Ride

#### API

Lets satisfy the functional requirments. 

User will want a fare estimate that will create a ide object for that location and when users want to start the ride we can use that same ride_id to move on the matching process. 

- POST - `/ride/fare-estimate`  - `Partial<Ride>`
BODY
```
{
	src,
	dest
}
```

- POST - `/ride/request` -> `returns 200`
BODY - `{rideid}`

- POST - `/location/update`
- Multiple car types (out of scope)
`{lat,long}` - End point run by the drivers updating their locations. 

Dirvers need to be able to accept the users

- PATCH `/ride/driver/accept`
`{rideId,true,false}`

- PATCH `/ride/driver/update` - `{lat,long}` or `null`
`{rideId,status:'Pickup'|'DROPOFF'}`

Identity ids will be stored in secured jwt tokens.

Flow -

Once Choosen It will call and request will go to ride service which will first do the estd time and distance using third party like google maps. Once done it will create an object onto the db. ### Location update

Uber has `6M` users and say drivers work in the shift of 8hrs on average so about `2M` will be actiave at a time. However with peak 2/3 at the same time so `3-4M`  online. Now for the `5s` interval updates its about `1M` writes to DB. 

Note that two operations are being done each time. `Lat/Long` update and a range query which can return the ids of nearby drivers in some radius. While update can e handled by db like postgres. The query of nearby drivers can not be done efficinetly in niave manner.  2d range queries can not handled efficently. Also postgres can only give out `2-4k writes per second`.

#### More optimization on location

Now even though we can use the geohash we still have around `1M` `req/s` to handle a database postgres cluster can not do it. First upgrade can be to add  a queue in between which will hold the data adn batch them into 1. So instead of hitting `1M` in one go we will make batches and say every `200ms` send a batch this although can add some latency but reduces the number of operations on the db.

#### Consistency of matching 

- We don't send more than one req at a time for a given ride. 
- We don't send any driver more than one req at a time.  

So first one we can add the logic in matching to send the accpetance to only one driver wait for 10s and move to the next driver. It means at a time only one dirver will be able to accept. So for a given user its req goes to one driver only. 

Second is to have one driver have only one rider req at a time and that is difficult since the Ride matching service is horizontally scaled. So a given driver who can be nearby to multiple users can get multiple push notifications for multiple  users. To make it correct we can have a redis store having a driver status - `is_req_send` and if `yes` we will not send out the request again. We can do it with ttl say of `10s`. Also if the dirver accpts we can have this driver not send another req say by again updating status for estd `ttl`. This needs to be atomic.
