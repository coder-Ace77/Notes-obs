Two issues -

- We want to have cluster running in different enviornments
- We want to ship our application so other people can install our cluster resouces in just one command. 

Issues is that you will be neededing different resource limits, a different image tag, and different environment variables per environment.

Both Kustomize and Helm exist to let you define something _once_ and vary it _per environment_ they just take opposite philosophies on how to do that variation.

### Kustomize

Kustomize is is build in tool which provides users to maintain multiple environments by putting patches on the default configuration. So first we have base yaml files. Then we apply something called as patches which tell which thing to change and how. 

Basic project stores everything first as base files all of which are valid `yaml` files. Now For an example a simple `pod.yaml` is also a valid file.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-pod
  labels:
    app: web
spec:
  containers:
    - name: web
      image: nginx
      resources:
        requests:
          cpu: 10
          memory: 50Mi
        limits:
          cpu: 20
          memory: 200Mi
```

Kustomise will treat this as base but to do that we need to tell kustomize file first. Its name should be `kustomization.yaml` and placed in folder we are wanting to kustomize. 

For an instance say we have `prod` folder and inside we have base files all of which are referenece by `kustomization.yaml`

```yaml
resources:
  - pod.yaml
patches:
  - target:
      kind: Pod
      name: web-pod
    patch: |-
      - op: replace
        path: /spec/containers/0/resources/limits/memory
        value: 400Mi
```

A basic customization will always have `resources` which can list a directory or it may be a file. Now there are many ways to change this file simplest is to patching which we have done here. 

Now conceptually to do changes to a configuration we need to specify which objects to change and then what to change that object and finally new value.

`patches` is an array of changes. `target` defines what object to change here we define the kind and name. Then we define what to change and how. path specifies the absoulute path of a field in the object. `op = replace` means we want to just update and replace value at that path with our value. Note that value does not needs to be valid here and `kustomize` will don't check that. 

Now here is the thing `kubectl apply -k .` is two steps in one first 
- kustomize - which is where it takes all the base files and spits out the final new file. 
- apply 

Note this kustomization step happens recursively so a resource can again be a full kustomize folder. What will happen is that firrst this inner folder `yaml` will be calcualted and then patches will be applied on top. So its like a tree in that sense. 

Now we could also selected the objects to patch by `kind+name` we could have also matched by the `labelSelector` , `namespace` or `regex` name. `name: web-pod` had to match the **final** name of the object, i.e. after any earlier transformers (like `namePrefix`) had already run. 

Patch is actual patch and is written in the form of called **JSON 6902**. 

There are multiple op types - 

- add - insert new field , array item
- remove - remove field , array item
- replace - override existing value - you will get error if path does not exist.

Path - a **JSON Pointer**, i.e. a slash-separated address into the object, exactly mirroring the YAML/JSON structure. 

Quick examples - 

```yaml
# add a new label
- op: add
  path: /metadata/labels/env
  value: staging

# remove the memory limit entirely
- op: remove
  path: /spec/containers/0/resources/limits/memory

# append to an array (special index)
- op: add
  path: /spec/containers/0/env/-
  value:
    name: LOG_LEVEL
    value: debug
```
The at the end of an array path is a JSON Pointer convention meaning "append to the end of this array"

Now there are big weakness with json path patching. Look at the path we mention array element `0` which can be reordered by a person inside. So we have `strategic merge` which matches by identity. 

### Anatomy of kustomization file

Every kustomize directory revolves around one required file:

```yaml
kustomization.yaml
```

This is the entry point kustomize reads _this_ file, not your regular YAMLs directly, to know what to assemble.

#### `resource` - what raw yaml to include

```yaml
resources:
  - deployment.yaml
  - service.yaml
  - configmap.yaml
```

Just points to your existing plain Kubernetes YAML files. This is the base layer, unmodified.
The real power shows up when you introduce a second folder, an **overlay**, that references the base and layers changes on top of it:

```yaml
app/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    ├── staging/
    │   └── kustomization.yaml
    └── production/
        └── kustomization.yaml
```

- **base** — the common, environment-agnostic manifests
- **overlays** — one folder per environment, each referencing the base and applying differences on top

An overlay's `kustomization.yaml` looks like:

```yaml
resources:
  - ../../base
patches:
  - path: replica-patch.yaml
```

Instead of maintaining full duplicate YAML per environment, you write small patches that modify only what changes.

For example 

```yaml
# replica-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 5
```

### Managing two environments

```yaml
myapp/
├── base/
│   ├── pod.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── prod/
        └── kustomization.yaml
```

Now say base/kustomization.yaml is what you already have. 

```yaml
resources:
  - pod.yaml
```

Now we define `overlay/dev/kustomization.yaml` 

```yaml
resources:
  - ../../base
patches:
  - target:
      kind: Pod
      name: web-pod
    patch: |-
      - op: replace
        path: /spec/containers/0/resources/limits/memory
        value: 200Mi
```

Now prod can maintain some different version of it. 

```yaml
resources:
  - ../../base
patches:
  - target:
      kind: Pod
      name: web-pod
    patch: |-
      - op: replace
        path: /spec/containers/0/resources/limits/memory
        value: 800Mi
```

Notice: `../../base` isn't a typo — from `overlays/dev/`, you go up two levels to reach `myapp/`, then down into `base/`. This line is what triggers the "build the base fully, then apply my patches on top" behavior we talked about earlier. 

#### Strategic merging 

Its the preferred way of merging. Here we write a partial YAML document containing the fields you want to change. Field although needs to be from full path from root. Not just some sub path. Here we can either point to a file or we can put file inside using this `|-` after patch 

```yaml
patches:
  - target:
      kind: Pod
      name: web-pod
    patch: |-
      apiVersion: v1
      kind: Pod
      metadata:
        name: web-pod
      spec:
        containers:
        - name: web
          resources:
            limits:
              memory: 400Mi
```

Or we can do this 

```yaml
patches:
  - target:
      kind: Pod
      name: web-pod
    patch: pod-patch.yaml
    
--- 
# pod-patch.yaml
apiVersion: v1
kind: Pod
metadata:
name: web-pod
spec:
containers:
- name: web
  resources:
	limits:
	  memory: 400Mi
```

Note the shorthand: kustomize also lets you skip the `apiVersion`/`kind`/full `metadata` boilerplate and write only the `spec:` fragment when using `patches:` with an inline patch but writing the identifying fields (as above) is the safer/clearer habit, especially once you have multiple resources of the same kind. Note first example was of inline patch and second one is of file patching. 


Notice `containers: - name: web` is present in the patch, even though you're not changing the container's name. **You have to include it** because for lists, Kubernetes doesn't merge by position (like JSON patch's `/0/`), it merges by a declared **merge key**. For the `containers` array, that key is `name`. So this patch reads as: find the container named `web` in the list wherever it is and merge these fields into it.

Ok now what merge does. It depends on value and type of field observe there was no `op` field here. 

- scalers (string , numbers)- patch overrides , its replace
- Maps get merge field by field recursively. If same field is mentioned with new value it will be replaced however if new field is mentioned it will be added.
- For the list there is a concept of key if list items have key we can replace items of the list by the key they match however if no key for example bare list entire list will be replaced. For example in containers the merge key is name. That's why in the example above, the patch's container entry (`name: app`) matched the base's container entry (`name: app`) and merged into it _instead of_ appending a second container or replacing the whole list.

If you'd patched with a container `name: sidecar` that doesn't exist in the base, SMP would **append** it to the list rather than merging.

```yaml
# base
containers:
- name: app
  args: ["--verbose", "--port=8080"]

# patch
containers:
- name: app
  args: ["--debug"]
```

To remove an item from a merge-keyed list, or remove a field entirely, SMP has special directives:
```yaml
# remove a specific container by name
containers:
- name: sidecar
  $patch: delete

# remove an entire field/map
resources:
  $patch: delete

# replace a list wholesale even if it normally merges (force replace instead of merge)
containers:
  $patch: replace
  ...
```


> [!NOTE] | - 
> | is the block literal means read the entire thing below me as a string block. - is different operator means remove the end daggling line. 

```yaml
literal_keep: |
  line one
  line two
# value: "line one\nline two\n"

literal_strip: |-
  line one
  line two
# value: "line one\nline two"   (no trailing \n)

folded: >
  line one
  line two
# value: "line one line two\n"  (newlines become spaces — "folded")
```

## 4. Common footguns

1. **Forgetting `metadata.name` in the patch file** → Kustomize won't know which resource to target (error: unable to find target).
2. **Expecting `args`/`command`/plain lists to merge** → they replace. If you only want to _add_ a flag, you must repeat the full desired list in the patch.
3. **Trying to patch a field that doesn't exist yet without realizing SMP will happily add it** → this is usually desired, but can silently mask a typo (e.g. `spec.templete` creates a new sibling field instead of erroring).
4. **Multiple containers, forgetting the merge key match** → if your patch's container `name` doesn't exactly match the base's, you get a _new_ container appended, not a merge, and now you have two containers.
5. **Using SMP for CRDs without a defined merge key** → Custom Resources generally don't have the Go struct-tag metadata that native K8s types have, so Kustomize treats their lists as **plain YAML merge**, which for lists usually still means replace-by-default unless Kustomize's fallback (openapi schema or `# +patchMergeKey`/`# +patchStrategy` comments) is present. This is a common surprise when patching CRDs like Argo Workflows or KServe `InferenceService` — worth remembering given the KServe work you're doing on Bodhi.

One more thing since kustomization is native to kubernetes we don't need to install anything. Second note that a single kustomization file can enclude multiple yaml files as resources and even entire folders. What it means is that we can setup entire application using just one command. 
### Helm 

Helm takes the opposite approach: instead of patching complete YAML, you write **templates** YAML files with placeholders and a separate file of **values** that fill those placeholders in. Helm can also provide the versioning of the applications. Meaning you have multiple files and we are keeping them as together unders one version. 

#### Components

- **Chart** a chart is just a packaged bundle of Kubernetes YAML templates plus metadata. It's the "package." If you `helm install` KServe, you're installing the KServe chart, which contains templates for its Deployments, Services, RBAC rules, CRDs, etc.
- **Values** charts don't hardcode things like image tag or replica count. Instead, the YAML files are _templates_ with placeholders, and a separate `values.yaml` file supplies the actual values. This is the mechanism that lets the same chart deploy differently to dev vs prod — you just swap the values file, not the templates.
- **Release**  when you install a chart with a specific set of values, Helm doesn't just fire-and-forget the YAML at the cluster. It records that installation as a "release" a named, versioned snapshot of exactly what was deployed and with what config. This is the part that makes upgrades and rollbacks possible, and it's the biggest conceptual jump from plain `kubectl`.

So the relationship is: **Chart (template) + Values (config) → rendered YAML → applied to cluster → tracked as a Release.**

Now how does it works - a person will have templates of all the yamls written in a folder called template/ and then we will have `Chart.yaml` which will define the project. Then we have values which are the fillers for the placeholders in the templates `yamls`. Now helm takes the chart templates which are yaml files but have go template syntax. `{{.Values.replicaCount}}` and your values files and does the string substitution to produce the plain final YAML. This happens entirely on your machine. 

**Helm then talks to the Kubernetes API directly**, the same way `kubectl` does, to create/update those resources. 

**The release record itself is stored _inside the cluster_ as a Kubernetes Secret** (one per release revision), in the namespace you deployed to. This is the trick that makes rollback possible — Helm isn't keeping some external database of "what I deployed"; it literally stores a compressed copy of the rendered manifest for each revision as a Secret object. When you rollback, Helm just re-applies the manifest from an older revision's Secret.

Ok so lets say you create a new helm repo mychart. To push them to server what you need to do is 

```yaml
helm install myrelease ./mychart -f values-dev.yaml
```


on the client side. Renders the chart with your values, applies it, creates release "myrelease" at revision 1. Helm client api can talk to kubernetes server. But helm needs to be configured. 

Now suppose you change something on your repo. 

```
helm upgrade myrelease ./mychart -f values-dev.yaml
```

And finally we can rollback

```yaml
helm rollback myrelease 1
```

Other commands

```yaml
helm list
helm status myrelease
helm history myrelease
```

See what's installed, its current state, and its revision history.

```yaml
helm uninstall myrelease
```

Finally we can install which someone else created. 

For **discovering and using someone else's charts** (like when you'd install KServe or Prometheus):

```yaml
helm repo add <name> <url>
helm repo update
helm install my-kserve kserve/kserve -f my-values.yaml
```

Finally note that helm is just a client binary that runs where you want to run it , ci runner or maybe laptop. It uses `kubeconfig` and renderes the templates locally and makes calls to the api server. Only trace it leaves is secrets it creates in the cluster to store the versioning.

### Installing multiple compoenents

In the reality there are two versions of this kind. First one is each component is having a single chart. 

```yaml
charts/
  frontend/
    Chart.yaml
    values.yaml
    templates/
  backend/
    Chart.yaml
    values.yaml
    templates/
  service-a/
  service-b/
  service-c/
```

Here each chart is installed separately. Each is a fully independent, installable chart. You install each as its own **release**:

```bash
helm install frontend ./charts/frontend -f charts/frontend/values-prod.yaml -n myapp
helm install backend  ./charts/backend  -f charts/backend/values-prod.yaml  -n myapp
helm install service-a ./charts/service-a -n myapp
helm install service-b ./charts/service-b -n myapp
helm install service-c ./charts/service-c -n myapp
```

Each shows up separately in `helm list -n myapp`, gets its own revision history, and can be upgraded/rolled back independently which matters a lot in practice, because you almost never want to redeploy your frontend just because service-b changed.

#### Umbrella 

If services are tightly coupled and you want "install the whole app" as one atomic action, Helm supports a parent chart that declares the others as **dependencies** - 

```
myapp-chart/
  Chart.yaml          # lists frontend, backend, service-a/b/c as dependencies
  values.yaml          # can override each subchart's values under its name
  charts/               # actual subcharts get pulled/copied in here
    frontend/
    backend/
    service-a/
    ...
```

`Chart.yaml` for the parent looks like:

```yaml
apiVersion: v2
name: myapp
version: 1.0.0
dependencies:
  - name: frontend
    version: "1.0.0"
    repository: "file://../frontend"
  - name: backend
    version: "1.0.0"
    repository: "file://../backend"
  # ... etc
```

```bash
helm dependency update ./myapp-chart   # pulls/links subcharts into charts/
helm install myapp ./myapp-chart -n myapp
```

Note this dependency update will pull the internal charts into one and then we will be good to go. 

### Anatomy of helm charts

```yaml
mychart/
  Chart.yaml          # metadata about the chart
  values.yaml          # default config values
  values.schema.json   # (optional) JSON schema to validate values
  charts/               # subcharts live here (dependencies)
  templates/            # your actual K8s manifest templates
    deployment.yaml
    service.yaml
    ingress.yaml
    _helpers.tpl         # reusable template snippets/functions
    NOTES.txt             # printed after install/upgrade
  .helmignore            # files to exclude when packaging
```

Each helm chart project will have `Chart.yaml` and `values.yaml` in root dir and templates in subdirs. Only `Chart.yaml`, `values.yaml`, and `templates/` are truly required. Everything else is convention/optional.

Chart.yaml is pure metadata about the porject and no templating happens here. 

```yaml
apiVersion: v2
name: backend
description: Backend microservice
type: application
version: 0.1.0          # chart version — bump this when the chart itself changes
appVersion: "1.4.2"      # version of the actual app/image being deployed — informational only
dependencies:             # only if using subcharts
  - name: redis
    version: "17.x.x"
    repository: "https://charts.bitnami.com/bitnami"
    condition: redis.enabled
```

Two version fields trip people up: `version` is the chart's own version (bump on template changes), `appVersion` is just a label reflecting the app image version — Helm doesn't act on it, it's informational.

Now values.yaml is simply the values we provide as key value pairs. Note that some keys have entire path listed for example `resource.requests.cpu`.

```yaml
replicaCount: 2

image:
  repository: myrepo/backend
  tag: "1.4.2"
  pullPolicy: IfNotPresent

resources:
  limits:
    cpu: 500m
    memory: 512Mi

service:
  type: ClusterIP
  port: 8080

env: []
```

You override this at install time with `-f values-prod.yaml` or inline `--set image.tag=1.5.0`.

Templates live under `templates/` and are just Kubernetes YAML with **Go template actions** wrapped in `{{ }}`. Let's go through the syntax pieces one at a time using a real deployment.yaml.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-backend
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: backend
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

`.Values.replicaCount` pulls from `values.yaml`. `.Release.Name` is a **built-in object** Helm injects automatically — the name you gave with `helm install <name>`.

- Values - Everything from values.yaml (merged with `--set`/`-f` overrides)
- .Release - `.Release.Name`, `.Release.Namespace`, `.Release.IsInstall`, `.Release.IsUpgrade`, `.Release.Revision`
- .Chart - `.Chart.Name`, `.Chart.Version` — from Chart.yaml

Conditionals -

`if`

```yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Release.Name }}-ingress
spec:
  rules:
    - host: {{ .Values.ingress.host }}
{{- end }}
```

The whole Ingress block only renders if `ingress.enabled: true` in values. This is how one chart can conditionally include/exclude resources — very common for things like Ingress, HPA, ServiceMonitor.

`{{-` strips preceding whitespace/newline, `-}}` strips trailing. Templates without these produce YAML with extra blank lines that can sometimes still be valid, but gets messy fast. Rule of thumb: use `{{-` at the start of control statements (`if`, `range`, `end`) so they don't leave stray blank lines in your rendered YAML.

For rendering environment variables, multiple ports, etc.:

```yaml
env:
{{- range .Values.env }}
  - name: {{ .name }}
    value: {{ .value | quote }}
{{- end }}
```

So note that inside `{{}}` any string or key can come however only variables are replaced which start from `.Values`. paired with values.yaml:

```yaml
env:
  - name: LOG_LEVEL
    value: debug
  - name: DB_HOST
    value: postgres.default.svc
```

Go templates support Unix-style piping of a value through functions:

```yaml
value: {{ .Values.someString | quote }}
name: {{ .Values.appName | lower | trunc 63 }}
```

`quote` wraps in quotes, `lower` lowercases, `trunc 63` truncates — common because K8s names have length limits. This piping style is everywhere in real charts.

`with` — scoping into a nested value

```yaml
{{- with .Values.resources }}
resources:
  limits:
    cpu: {{ .limits.cpu }}
    memory: {{ .limits.memory }}
{{- end }}
```

`with` changes what `.` refers to inside the block — saves you repeating `.Values.resources.` on every line. Only use it when the value is guaranteed non-empty, since it also skips the block entirely if the value is empty/nil.

We can also put required so that values file need to have that. 

```yaml
image: "{{ required "image.repository is required!" .Values.image.repository }}"
```
We can keep default values using `{{ .Values.x | default "fallback" }}`
