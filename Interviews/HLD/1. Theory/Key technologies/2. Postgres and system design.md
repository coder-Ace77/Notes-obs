### Client request flow:

In postgres everything needs to connect to it first, be it an application server or a simple interactive client. Before anything else, it helps to be precise about what a "connection" actually is: it's a stateful, authenticated session over TCP between a client and the PostgreSQL server, and  as we'll see in a moment  the server's side of that session isn't just a socket, it's an entire dedicated OS process kept alive for as long as the connection lasts. Because setting one up is real work (a TCP handshake, authentication, and process creation on the server), a connection is a comparatively expensive, stateful resource, not something you casually open and close per request.Note that for each three step process - `tcp+auth+prcoess fork` can take around 30-40ms while a typical query only takes around 1ms. Also under heavy load postgres has upper limit to total number of opened connection which can exhaust and put more pressure on application.  Any application wanting to talk to Postgres needs a piece of client code to manage this a **postgres driver**.

So how does an actual request get from application code down to the database? A request comes into a backend service, and the handler needs data, so it goes through the Postgres driver library (things like `pg`/node-postgres for Node, `psycopg` for Python, JDBC + HikariCP for Java, `pgx` for Go, etc.). In practice, that driver almost never opens a fresh connection for this one request instead it maintains an **application-level connection pool**: a set of connections that were opened once, authenticated, and are kept alive for reuse. The request handler simply **borrows** an idle connection from this pool, runs its query or transaction on it, and **returns** it to the pool when done rather than closing it, so the same underlying connection and the backend process behind it serves request after request. This is purely an amortization move: since opening a connection is expensive (as noted above), paying that cost once and reusing it thousands of times is far cheaper than paying it on every request. It's also why pool size is a real tuning knob — too small, and requests start queueing for a free connection under load; too large, and the application ends up forcing the database to sustain far more live connections than it needs to.

Now zoom in on what "opening a connection" actually costs the *server*, which is what makes pooling worth doing in the first place. Unlike MySQL, which handles connections with lightweight threads, PostgreSQL uses a **process-per-connection model**: every single connection whether it comes straight from an app's pool or anywhere else is handed off to its own dedicated OS-level **backend process** (a `postgres` process forked from the postmaster), and that process sticks around for the connection's entire lifetime. This is a deliberate architectural choice process isolation means a crash in one backend can't easily corrupt the memory of another, which makes PostgreSQL more robust but it also means each connection permanently reserves real memory and scheduling overhead on the server, and PostgreSQL's `max_connections` ceiling is consequently only in the low hundreds by default. An application-level pool helps a single service reuse its own connections efficiently, but it doesn't change the fact that *many* service instances, each with its own pool, can still add up to more total connections than PostgreSQL can comfortably sustain which is exactly the problem external poolers solve.

##### PgBouncer

**PgBouncer** is a lightweight, standalone proxy that sits between applications and PostgreSQL, and it exists for precisely that multi-instance problem: across a fleet of application servers, the *combined* connection count from all their individual pools can easily run into the thousands, far past what `max_connections` allows, since every one of those still maps to a full, memory-heavy backend process if it reaches Postgres directly. PgBouncer solves this by terminating all of those client-side connections itself and funneling the actual work through a much smaller, reused pool of real backend connections to PostgreSQL, so the database only ever sees a manageable, roughly-constant number of connections no matter how many clients are talking to PgBouncer. Before reaching for it, though, there are a few things worth knowing: it supports three distinct pooling modes  **session** (a client keeps its backend connection for the lifetime of its session, safest but least efficient), **transaction** (the backend is only reserved for the duration of a single transaction and returned to the pool immediately after, the most common production setting), and **statement** (returned after every single statement, the most aggressive but breaks multi-statement transactions); anything beyond session pooling means session-level state `SET` variables, prepared statements, temp tables, advisory locks, `LISTEN/NOTIFY`  can no longer be relied upon to persist or behave predictably, since a given client may get a *different* underlying backend connection for its next query; and because PgBouncer itself is single-threaded per pool (though it can run multiple processes for higher throughput), it's not free  it's simply cheaper than a full PostgreSQL backend, so it should be sized and monitored like any other piece of infrastructure rather than treated as an unlimited buffer in front of the database.

Whichever path got us here  a connection borrowed straight from an app's own pool, brokered through PgBouncer, or opened directly once it's established and authenticated, the client can start sending SQL statements or transactions down that same backend process. The very first thing that happens to an incoming query string is that it gets run through the **parser**, which checks the SQL for syntactic correctness and converts the raw text into a **parse tree** a structured, tree-shaped representation of the query that the rest of the system can reason about instead of dealing with raw text. From there the query moves into the **rewrite stage**, where PostgreSQL applies any relevant **rules** for example, expanding a query against a view into a query against its underlying base tables, or applying rules created via `CREATE RULE`. This is a distinct step from planning; it transforms the query itself before any thought is given to *how* to execute it.

Once the rewritten query is ready, it's handed to the **planner/optimizer**. The planner  creates multiple candidate strategies for answering the same query (different join orders, different access paths, different algorithms) and estimates the **cost** of each one using statistics PostgreSQL maintains about the tables (row counts, value distributions, index selectivity, etc.). It then chooses the plan with the lowest estimated cost. Every one of these plans is represented internally as a **tree of nodes**, and each node type represents a distinct operation: **scan nodes** like `SeqScan` or `IndexScan` decide how rows are physically read off a table or index; **join nodes** like `Nested Loop` or `Hash Join` decide how two row sets get combined; **aggregate nodes** implement things like `SUM`, `COUNT`, and `AVG`; and **sort nodes** implement `ORDER BY`. Because the plan is a tree, complex queries end up as a composition of these simpler node types stacked on top of one another.

Once a plan is chosen, it moves into the **executor**, which actually walks that plan tree and produces the result rows. This execution model is **pull-based**: the top of the tree (the node closest to the client) asks the node below it for a row, which in turn asks the node below *it*, and so on down to the leaves data doesn't get pushed upward proactively. This pull-based, node-by-node approach lets PostgreSQL support **pipelined execution**, meaning it generally doesn't have to materialize the entire result set in memory before returning anything to the client; rows can stream out as they're produced. The exception is when an operation inherently needs to see the whole input before it can produce output a full `ORDER BY` sort or a `DISTINCT` typically has to buffer everything first, since you can't emit the first sorted row until you've seen every candidate row.

Underneath all of this, actually getting at the data is the job of the **buffer manager**. PostgreSQL keeps a cache of recently used data pages in a shared memory region called `shared_buffers`; when the executor needs a row, it first checks whether the containing page is already cached there. If it isn't, PostgreSQL has to perform an actual **disk read** to pull the page in, and pages are typically read and cached in fixed **8KB** units regardless of how much of that page is actually relevant to the query. On the write path, durability is guaranteed through **write-ahead logging (WAL)**: any change is first written as a log record to the WAL before the corresponding data page is modified, so that if the server crashes mid-write, PostgreSQL can replay the WAL on restart and recover to a consistent state. Concurrently, PostgreSQL enforces ACID guarantees particularly isolation between simultaneous transactions  using **MVCC (Multi-Version Concurrency Control)**, where instead of locking rows for reads, each transaction sees a consistent snapshot of the data as of some point in time, while writers create new row versions rather than overwriting old ones in place; this is what allows readers and writers to avoid blocking each other in the common case.

Finally, once the executor has produced the result rows, PostgreSQL doesn't just hand back raw internal representations  the data is **formatted** according to what the connecting client actually asked for, whether that's plain text, PostgreSQL's binary wire format, or something like JSON, before being sent back over the connection.
#### Optimisation which postgres does:

Beyond just picking the cheapest single-process plan, PostgreSQL has a handful of optimizations that kick in either during planning or execution to squeeze more performance out of a query, and it's worth understanding what each one actually buys you and when it applies.

The first is **parallel query execution**. For large scans or aggregations, PostgreSQL can split the work across multiple background worker processes instead of running it all in one backend — this is what shows up in `EXPLAIN` output as a `Gather` node feeding from things like `Parallel Seq Scan`, `Parallel Hash Join`, or `Parallel Aggregate`. The way this works is that the leader process spins up a handful of parallel workers (bounded by `max_parallel_workers_per_gather`), each one is handed a slice of the table to scan independently, and the leader gathers their partial results back together  for an aggregate, each worker computes a partial `SUM`/`COUNT` over its slice and the leader combines them, rather than one process walking every row serially. This isn't automatic for every query, though: the planner only considers going parallel when it estimates the table is large enough that the parallelism gain outweighs the fixed overhead of starting workers (`parallel_setup_cost`, `parallel_tuple_cost`), which is why parallel plans typically only show up for scans over sizeable tables, not small ones  for a tiny table the overhead of coordinating workers costs more than just scanning it directly. It's also worth knowing that not everything can be parallelized: certain operations (like scans with certain kinds of triggers, or writes, in earlier Postgres versions) are excluded because correctness under multiple concurrent workers is either unsafe or unsupported.

The second is the **index-only scan**. Normally, using an index to find a row is a two-step affair look up the entry in the index to get a row's location (a TID), then go fetch the actual row from the table (the heap) to read whichever columns the query needs. If every column the query needs is already present in the index itself, PostgreSQL can in principle skip that second heap fetch entirely and answer the query straight from the index. 

## Indexes

At its core, an **index** is a separate data structure that lets PostgreSQL locate rows without scanning the entire table, in exchange for the overhead of maintaining that extra structure. Without one, satisfying a `WHERE` clause means a **sequential scan**: PostgreSQL reads every row in the table, front to back, and evaluates the condition against each one. With an index built on the relevant column, PostgreSQL can instead **jump directly** to the matching rows using a tree or hash lookup, turning what would otherwise be a linear walk through the whole table into something far closer to logarithmic or constant time depending on the index type.

Creating one is as simple as:

```sql
CREATE INDEX idx_salary ON employees (salary);
```

 PostgreSQL builds an entirely separate physical structure on disk (tracked via `pg_index` and its own files under the database's data directory), and indexes are never stored inside the table's own file they live alongside it as distinct files. From this point on, PostgreSQL has to keep that structure in sync with every `INSERT`, `UPDATE`, and `DELETE` made against the table. That sync cost is the fundamental trade-off behind every index you create: reads get faster, but every write now has to update the table *and* every index built on it, so writes get slower and disk usage grows.

### B-tree (the default)

If you don't specify an index type, you get a **B-tree** a balanced, multi-level tree structure, and the general-purpose workhorse of PostgreSQL indexing. It's well suited to equality lookups, range queries (`BETWEEN`, `<`, `>`), sorting operations (`ORDER BY`), and enforcing uniqueness constraints like primary keys. 

B-trees maintain the physical order of keys within their leaf pages, so scanning a range doesn't mean jumping randomly around the index, it can walk sequential, neighboring pages instead, which is far friendlier to disk I/O than random access. Because the tree stays balanced and multi-level no matter how much data goes in, lookups, insertions, and range scans all land at roughly `O(log n)` complexity. 

### Hash index

A **hash index** is a narrower, more specialized structure: essentially a hash table mapping a key directly to a row pointer.

```sql
CREATE INDEX idx_user_hash ON users USING hash (email);
SELECT * FROM users WHERE email = 'john@abc.com';
```

Because hashing deliberately destroys any notion of order  two very similar emails can hash into completely different buckets a hash index is only useful for exact-equality lookups; it can't help with range queries or `ORDER BY` the way a B-tree can. In practice this makes it a niche tool: it's worth reaching for only when you're confident a column is *exclusively* queried via equality, and even then a B-tree is usually competitive enough that many teams just default to B-tree everywhere to keep things simple.
### GIN (Generalized Inverted Index)

It's called "inverted" because it maps **values → rows**, the inverse of a B-tree, which effectively maps rows → values. So while a **B-tree** stores sorted key-value pairs like:

```psql
key → row location
```

a **GIN** index stores:
```psql
element/value → list of row locations containing that element
```

So suppose we have data as:

|id|description|
|---|---|
|1|"apple orange banana"|
|2|"orange mango"|
|3|"banana apple"|

GIN breaks each row's text apart and indexes every individual word:

```
"apple"  → [1, 3]
"banana" → [1, 3]
"orange" → [1, 2]
"mango"  → [2]
```

so for example with the following query:

```sql
SELECT * FROM products WHERE description @@ to_tsquery('apple & banana');
```

PostgreSQL doesn't need to scan the table at all  it looks up `"apple"` and `"banana"` in the index, intersects their row lists, and only fetches rows `{1, 3}`. Structurally, a GIN index is really made of two parts: the **entries**, which are the distinct lexemes (words/tokens) it has extracted, and each entry's **posting list**  a sorted list of TIDs (tuple identifiers, i.e. row pointers) for every row containing that lexeme. Internally, PostgreSQL stores those entries themselves in an ordinary **B-tree**, but instead of each entry pointing to a single row like a normal B-tree index, each entry points to an entire *set* of rows.

This structure is what makes GIN good for full-text search over `tsvector` columns, containment queries on arrays (`@>`, `<@`, `&&`), and JSONB containment queries — anything where a single row logically contains *many* searchable values, and you need to go from one of those values back to all the rows containing it. To use it for full-text search, first create the index:
```sql
CREATE INDEX idx_products_desc_gin ON products USING GIN (to_tsvector('english', description));
```

then we can search 

```sql
SELECT * FROM products WHERE to_tsvector('english', description) @@ plainto_tsquery('banana apple');
```

### Trigram search (fuzzy search and substring matching)

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_products_desc_trgm ON products USING GIN (description gin_trgm_ops);

SELECT * FROM products WHERE description ILIKE '%banana%';
SELECT * FROM products WHERE description % 'bananna'; -- fuzzy
```

A **trigram** is simply a sequence of three consecutive characters taken from a string, with a space padded onto the start and end so that the leading and trailing characters get represented too:

```
String:   "apple"
Trigrams: "  a", " ap", "app", "ppl", "ple", "le ", "e  "
```

When you search for a string that's slightly misspelled e.g., `"aple"` as a typo of `"apple"`  PostgreSQL compares the **overlap between the trigram sets** of both strings rather than requiring an exact character match:

```
'apple' trigrams:  { ' ap', 'app', 'ppl', 'ple' }
'aple'  trigrams:  { ' ap', 'apl', 'ple' }
```

Enough of those trigrams overlap that PostgreSQL considers the two strings similar, even though they aren't identical. Without an index, evaluating this kind of similarity (or a leading-wildcard `ILIKE '%banana%'`) means computing trigrams and comparing them row by row across the entire table  it performs very badly at any real scale, because there's no way to jump straight to the relevant rows.

A **GIN (or GiST) trigram index** fixes that by precomputing and indexing the trigrams up front:

```sql
CREATE INDEX idx_products_desc_trgm ON products USING GIN (description gin_trgm_ops);
```

PostgreSQL now stores **trigrams of each `description`** in an inverted index, exactly the same entries-to-posting-lists structure described for GIN above, just with trigrams as the entries instead of whole words:

|Trigram|Rows containing it|
|---|---|
|"app"|[1, 5, 8, 22]|
|"ppl"|[1, 8, 22]|
|"ple"|[1, 22]|
|"ban"|[3, 9, 12]|
When you run the search, Postgres retrieves all rows containing trigrams similar to `"apple"` and only checks those avoiding full-table scan.

Result: **massive speedup**, often 100x–1000x faster.

### Categorical data handling

Categorical columns are trickier to index well than most others, because the number of *distinct* values is limited while the number of *rows* sharing each value can be huge  a `status` column with only three possible values on a hundred-million-row table means an index on it has terrible selectivity: any single lookup still matches millions of rows, so the index barely narrows anything down. This same low-cardinality problem shows up directly in pagination. The naive approach, `LIMIT`/`OFFSET`, works fine for the first few pages, but it degrades as users page deeper, because `OFFSET` doesn't know how to skip rows for free PostgreSQL still has to walk through and discard every row up to the offset before it can return your requested slice. The deeper the page, the more rows get read and thrown away internally, so query time grows roughly linearly with how far into the dataset you're paging, even with a perfectly good index backing the query.

The better approach for this is **keyset pagination**, where instead of an absolute page number, you keep a pointer the last row you saw  and move it forward or backward. Concretely, `WHERE order_id > last_seen AND category = 1 ORDER BY order_id` lets PostgreSQL use an index on `(category, order_id)` to jump directly to the first row after `last_seen` within that category and return the next batch, reading only the rows actually needed. That makes query time nearly constant no matter how deep into the dataset you are — keyset pagination is `O(1)` per page, versus `OFFSET`'s `O(n)` in how far you've paged. The trade-off is flexibility: `OFFSET` lets you jump to an arbitrary page directly (`OFFSET 20000 LIMIT 10` for page 2001), while keyset pagination has no such shortcut, since each page's starting point is only known once you've seen the previous one. In return, keyset pagination is also more robust to concurrent writes because `OFFSET` counts rows by position, inserts or deletes happening between page loads can shift what "row 20000" even means, causing rows to be skipped or repeated, whereas keyset's cursor-based approach (anchored to a real `order_id`, not a row count) isn't affected by rows changing before that cursor.

In reality, most real products lean into this trade-off rather than fight it: websites often don't let you jump to an arbitrary page at all Amazon, for instance, won't let you skip straight to the last page of results and only expose forward/backward navigation, with "forward" being the easy, common case.

```sql
SELECT * 
FROM products 
WHERE category = 1 
  AND order_id > :last_seen
ORDER BY order_id ASC
LIMIT 10;
```

Backward

```sql
SELECT *
FROM products
WHERE category = 1
  AND order_id < :first_seen  -- note: "<" instead of ">"
ORDER BY order_id DESC          -- reverse order
LIMIT 10;
```

One more thing worth noting about paginated listings: sites usually don't compute the *exact* total row count either, for the same reason `OFFSET` is expensive  a real `COUNT(*)` means scanning (or index-scanning) every matching row. Instead, they lean on PostgreSQL's own table statistics to produce a cheap approximation:

```sql
SELECT CEIL(reltuples / 20.0) AS estimated_pages
FROM pg_class
WHERE relname = 'products';
```

`reltuples` is a planner-maintained estimate of the table's row count (updated by `ANALYZE`/autovacuum, not computed on the spot), so this is effectively free compared to actually counting — at the cost of being an estimate rather than an exact number, which is a trade-off most UIs ("About 2,400 results") are happy to make.

Making keyset pagination actually fast, as in the `category` example above, depends on having the right index shape which brings in one more technique: **compound (multi-column) indexing**.

```sql
CREATE INDEX idx_products_category_id
ON products (category, id);
```

PostgreSQL B-tree indexes are ordered **left-to-right**, meaning the index is sorted by the first column, and *within* each value of the first column, sorted by the second  much like a phone book sorted by last name, then first name. That ordering is exactly what lets a compound index on `(category, id)` efficiently serve a query that filters on `category` and then orders or range-scans by `id`, since all the rows for a given category already sit together in the index, sorted by `id`:

```sql
SELECT * FROM products WHERE category = 'electronics' ORDER BY id LIMIT 20;
```

Because of that left-to-right ordering, column order in the index definition isn't interchangeable — an index can efficiently skip over its leading column(s) to narrow down a range, but it can't do the same for a column buried after one it isn't filtering on. So swapping the order actually changes what the index is good for entirely:

```sql
CREATE INDEX idx_products_id_category ON products (id, category);
```

This index would efficiently serve a query filtering by `id` and then `category`, but it's of little help for `WHERE category = 'electronics' ORDER BY id` — PostgreSQL can't use it to jump straight to the `electronics` rows, since `category` isn't the leading column. As a rule of thumb, the columns you filter on with equality should generally come first in a compound index, followed by the column you range-scan or sort on.

So far we've covered the different types of indexes PostgreSQL offers, but there's more to query optimization than just picking the right index type.

### Covering Index

When PostgreSQL uses an index to find a row, it typically needs to do two things:

1. Look up the value in the index to find the row's location
2. Fetch the actual row from the table to get other columns you need

But what if we could store all the data we need right in the index itself? That's what covering indexes do:

```sql
-- Let's say this is a common query in our social media app:
SELECT title, created_at 
FROM posts 
WHERE user_id = 123 
ORDER BY created_at DESC;

-- A covering index that includes all needed columns
CREATE INDEX idx_posts_user_include 
ON posts(user_id) INCLUDE (title, created_at);
```

Covering indexes are the practical way you *get* the index-only scans described earlier: by including `title` and `created_at` as extra, non-key payload columns via `INCLUDE`, the index carries everything the query needs, so as long as the visibility map cooperates PostgreSQL can satisfy the entire query straight from the index without ever touching the table. The trade-off is the same one indexes always carry, just amplified: the index itself grows larger since it's now storing whole extra columns, not just the indexed key, and every write that touches `title` or `created_at` now has more index data to update, so writes get slightly slower in exchange for the read-side win.

### Partial index

Sometimes you don't need to index *all* of your data  only a subset of it is ever actually queried. In a social media platform, for instance, the overwhelming majority of queries are probably looking for active users, not deleted ones, so indexing deleted users at all is close to pure waste:

```sql
-- Standard index indexes everything
CREATE INDEX idx_users_email ON users(email);  -- Indexes ALL users

-- Partial index only indexes active users
CREATE INDEX idx_active_users 
ON users(email) WHERE status = 'active';  -- Smaller, faster index
```

Because the `WHERE status = 'active'` clause is baked into the index definition itself, PostgreSQL simply never adds an entry for rows that don't match it  the index only ever needs to store, scan, and maintain the active subset, not the whole table. This pays off in a few compounding ways: the index is physically smaller, which means it's more likely to stay resident in memory (`shared_buffers`) rather than requiring disk reads; every `INSERT`/`UPDATE`/`DELETE` against an *inactive* row skips updating this index entirely, since it was never eligible in the first place; and PostgreSQL can only use this index for queries whose `WHERE` clause is compatible with (i.e., logically implies) the index's own condition a query with no `status` filter, or one explicitly asking for `status = 'deleted'`, won't be able to use it at all. Partial indexes are consequently most valuable whenever there's a persistent, lopsided split in your data active vs. deleted, unprocessed vs. processed, current vs. archived where the bulk of real traffic only ever cares about one side of that split.

## Practical performance

As a rough set of numbers to calibrate against: a single PostgreSQL core can typically sustain on the order of 10,000 simple, well-indexed queries per second, complex multi-table joins drop that down to roughly 1,000 per second, and a single table tends to stay comfortably manageable up to around 100 million rows. None of these are hard ceilings PostgreSQL can be pushed well past them with the right optimization but they're useful rules of thumb for when to start seriously considering partitioning, sharding, or other scaling strategies rather than continuing to tune a single instance.

Keep in mind, memory is king when it comes to performance: queries that can be satisfied entirely from memory are orders of magnitude faster than those requiring disk access, so as a rule of thumb you should try to keep your working set the data actually accessed frequently resident in RAM.

### Write performance

When a write occurs in PostgreSQL, several distinct steps happen to balance performance against durability. First, the change is written to the **Write-Ahead Log (WAL)** on disk a purely sequential write, which is relatively fast and this is the point at which the transaction becomes durable, because even if the server crashes immediately afterward, PostgreSQL can replay the WAL on restart to recover the change. Second, the actual data pages affected by the change are updated in memory, inside PostgreSQL's shared buffer cache where the live tables and indexes are cached; a modified page is simply marked "dirty" to flag that it still needs to be written to disk eventually. 

Third, those dirty pages aren't flushed immediately the **background writer** periodically writes them out to the real data files asynchronously, whether because memory pressure is building, a checkpoint has occurred, or simply on its own schedule, and this delayed-write strategy is what lets PostgreSQL batch many logical changes into fewer physical disk writes. 

Finally, every index on the table also has to be updated to reflect the change, and just like table data index changes are themselves protected by the WAL, which is exactly why adding more indexes to a table slows down writes: each one means additional WAL entries and additional in-memory pages to maintain per write. Altogether, this architecture is why PostgreSQL writes can be fast despite being fully durable: most of the actual work happens in memory, with the WAL providing the durability guarantee up front, while the slower job of getting data pages onto disk happens later, batched, and off the critical path.

One consequence of MVCC that this write path doesn't mention directly, but that follows straight from it, is that neither an `UPDATE` nor a `DELETE` actually removes a row in place MVCC means the old row version is simply left behind as a **dead tuple** while a new version is written (or nothing, for a delete). Left unchecked, this steadily bloats both tables and indexes and drags down performance over time, which is exactly what **VACUUM** exists to clean up: it scans for dead tuples no longer visible to any active transaction and reclaims that space for reuse, and it's also what keeps the visibility map (used by index-only scans) up to date. In practice you rarely run `VACUUM` by hand  **autovacuum** is a background process that does this automatically once a table's dead-tuple count crosses a threshold but it's worth knowing it exists, because a table writing much faster than autovacuum can keep up with is a classic, easy-to-miss cause of gradually degrading performance.
### Throughput

Now that we know what happens during a write, it's worth talking about the practical limits of write throughput, since that's what tells you whether PostgreSQL is even the right fit for a given system. A well-tuned instance on decent (not exceptional) hardware can typically sustain roughly 5,000 simple inserts per second per core, 1,000–2,000 updates per second per core once index maintenance is involved, only hundreds per second for complex transactions that touch multiple tables and indexes, and tens of thousands of rows per second for genuinely bulk operations — and these numbers all assume PostgreSQL's default Read Committed isolation level. Crucially, this is a *single-node* figure: if your system needs sustained write throughput well beyond, say, 5,000 writes/second, that doesn't mean PostgreSQL is off the table — it means you're going to need to shard across multiple instances rather than expect a single node to keep up.

A handful of factors determine where you actually land within that range: write throughput is very often bottlenecked by disk I/O for the WAL before anything else; every additional index reduces write throughput, since each one is extra WAL and memory work per write; synchronous replication, if configured, adds latency because the primary has to wait on replica acknowledgment before confirming the write; and simply touching more tables and indexes within a single transaction makes it proportionally slower.

### Optimisation for write performance

The simplest lever is vertical scaling more cores, faster disks, more memory which buys headroom without any application changes. Beyond that, **batch processing** is usually the next highest-leverage change: instead of committing each write as its own transaction, you collect multiple operations and execute them together in a single transaction, so instead of inserting 1,000 likes one at a time, you insert all 1,000 in one shot, amortizing per-transaction overhead across many rows. Where strict per-write durability isn't actually required, `synchronous_commit = off` is another lever worth knowing about it lets PostgreSQL acknowledge a write to the client before its WAL record has actually been flushed to disk, trading a small, bounded window of potential data loss on crash for meaningfully higher write throughput.

Not every write needs to happen synchronously at all, though. Analytics data, activity logs, and aggregated metrics are frequently fine to process asynchronously: instead of writing directly to PostgreSQL, you send the write to a message queue like Kafka, have background workers consume and batch those queued writes, and optionally land them in a separate analytics database entirely keeping this lower-priority write traffic off the primary path completely.

For large tables, **partitioning** can improve both read and write performance by splitting one logical table into multiple physical ones, most commonly by time range.

```sql
CREATE TABLE posts (
    id SERIAL,
    user_id INT,
    content TEXT,
    created_at TIMESTAMP
) PARTITION BY RANGE (created_at);

-- Create partitions by month
CREATE TABLE posts_2024_01 PARTITION OF posts
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

This helps writes in a few compounding ways: different sessions can write to different partitions concurrently, increasing effective concurrency; index maintenance on insert only has to touch the relevant partition's indexes rather than one enormous index over the whole table; and bulk loads can proceed partition by partition. It conveniently helps reads too  when users view recent posts, PostgreSQL only has to scan the recent partitions (a technique called partition pruning), with no need to wade through years of historical data it already knows can't match.

When a single node genuinely isn't enough, **sharding**  the most common answer in interviews distributes writes across multiple PostgreSQL instances entirely. The key design decision is the shard key: for example, sharding posts by `user_id` keeps all of a given user's data on one shard, which matters because it avoids cross-shard queries that would otherwise require scatter-gathering data from multiple shards at read time so you generally want to shard on whatever column you query by most often. It's worth being upfront, though, that sharding isn't free: it's usually the *last* resort precisely because of what it costs operationally resharding to rebalance data is a genuinely hard, often online-migration-style problem; anything that needs to join or transact across shards becomes significantly more complex or simply unsupported; and the shard key is expensive to change your mind about later, since it's baked into how every row's location is determined. It's the right tool once a single node's throughput ceiling is a real constraint, but it trades away a lot of what makes a single PostgreSQL instance simple to reason about.

## Replication

Replication is the process of copying data from one database to one or more others. It's worth separating two axes that are easy to conflate: *what* gets replicated, and *when* the primary considers a write safely replicated.

On the "what" axis, PostgreSQL supports two structurally different kinds of replication. **Physical replication** (streaming replication) ships the raw WAL itself to replicas, which replay it to stay byte-for-byte identical to the primary this is the classic way to build a read replica or a hot standby, and it replicates the entire cluster, not individual tables. **Logical replication**, by contrast, decodes the WAL into row-level changes (inserts/updates/deletes) and streams those through a publish/subscribe model, which allows replicating a subset of tables, replicating into a different schema, or even into a different major PostgreSQL version and it's the same underlying mechanism, logical decoding, that powers CDC, covered below.

On the "when" axis  orthogonal to physical vs. logical PostgreSQL supports synchronous and asynchronous replication. With synchronous replication, the primary waits for acknowledgment from a replica before confirming the write to the client, giving stronger consistency at the cost of higher write latency. With asynchronous replication, the primary confirms the write immediately and replicates in the background, favoring lower latency at the cost of replicas potentially lagging behind, and thus being momentarily inconsistent with the primary.

Replication across nodes buys you a couple of distinct benefits, worth separating clearly.

### Scaling reads

The most common use for replication is scaling read throughput: by creating read replicas, you can distribute read queries across multiple instances while routing all writes to the primary, which is especially effective since most applications are read-heavy to begin with.

There's one key caveat: **replication lag**. If a user writes data and then immediately tries to read it back, they might not see their own change if that read happens to land on a replica that hasn't caught up yet — a violation of what's called "read-your-writes" consistency. The usual mitigations are to route a user's own immediate post-write reads back to the primary rather than a replica (often for some short window after the write), to pin a user's session to whichever replica served their prior reads, or to use a synchronous replica specifically for reads where staleness genuinely isn't acceptable.

### High availability

The second major benefit is high availability: by maintaining copies of the data across multiple nodes, you can survive a hardware failure without downtime — if the primary fails, a replica can be promoted to take its place. It's worth knowing PostgreSQL doesn't do this promotion automatically out of the box; production setups typically layer on external tooling (like Patroni or repmgr) to detect a primary failure and orchestrate a safe promotion, since a naive automatic failover risks a split-brain scenario where two nodes both believe they're the primary.

In your interview, emphasize that replication isn't just about scaling - it's about reliability. You might say: "We'll use replication not just for distributing read load, but also to ensure our service stays available even if we lose a database node."

### Data consistency

If you've chosen to prioritize consistency over availability in your non-functional requirements, then PostgreSQL is a strong choice. It's built from the ground up to provide strong consistency guarantees through ACID transactions.

One of the most common points of discussion in interviews ends up being around transactions. A transaction is a set of operations that are executed together and must either all succeed or all fail together. This is the foundation for ensuring consistency in PostgreSQL.

Consider a simple auction-bidding operation: read the current max bid, place a new bid if it's higher, then update the max bid.

```sql
BEGIN;
-- Get current max bid for item 123
SELECT maxBid from Auction where id = 123;

-- Place new bid if it's higher
INSERT INTO bids (item_id, user_id, amount) 
VALUES (123, 456, 100);

-- Update the max bid
UPDATE Auction SET maxBid = 100 WHERE id = 123;
COMMIT;
```

Even though this is in a transaction, with PostgreSQL's default isolation level (Read Committed), we could still have consistency problems if two users bid simultaneously. Both transactions could read the same max bid before either commits.

Here's how this could lead to an inconsistent state:

1. User A's transaction reads current max bid: $90
2. User B's transaction reads current max bid: $90
3. User A places bid for $100
4. User A commits
5. User B places bid for $95
6. User B commits

Note that in this case bid $95 will be placed as the final max bid — lower than the $100 bid that was already placed. To solve this we have two options.

The first is **row-level locking**: a lock is acquired on the row and won't be released until the transaction is done, so a second transaction touching the same row simply blocks until the first finishes and sees the up-to-date value. 

```sql
BEGIN;
-- Lock the item and get current max bid
SELECT maxBid FROM Auction WHERE id = 123 FOR UPDATE;

-- Place new bid if it's higher
INSERT INTO bids (item_id, user_id, amount) 
VALUES (123, 456, 100);

-- Update the max bid
UPDATE Auction SET maxBid = 100 WHERE id = 123;
COMMIT;
```

Explicit locking introduces deadlocks. If two transactions each lock rows in opposite order say, transaction A locks item 123 then tries to lock item 456, while transaction B has already locked item 456 and now wants item 123 neither can proceed. PostgreSQL detects this automatically and resolves it by aborting one of the two transactions with an error, leaving the application responsible for retrying it. An alternative to locking altogether is **optimistic concurrency control**: instead of locking the row up front, you read a version number alongside the row, and on write you condition the update on that version not having changed — `UPDATE Auction SET maxBid = 100, version = version + 1 WHERE id = 123 AND version = :expected_version` and if zero rows are affected, you know someone else won the race and can retry. This avoids holding a lock for the duration of the transaction, at the cost of needing the same kind of retry logic that higher isolation levels below also require.

The second option is **higher isolation levels**. PostgreSQL predominantly has three practically distinct levels: Read Committed, Repeatable Read, and Serializable. **Repeatable Read** in PostgreSQL provides stronger guarantees than the SQL standard requires: it takes a consistent snapshot of the data as of the start of the transaction, and unlike many other databases, PostgreSQL's implementation prevents both non-repeatable reads AND phantom reads. This means not only will the same query return the same results within a transaction, but no new rows will appear that match your query conditions either, even if other transactions commit such rows.

**Serializable** is the strongest isolation level, making transactions behave as if they were executed one after another in sequence rather than concurrently — in practice PostgreSQL implements this via Serializable Snapshot Isolation (SSI), detecting when concurrent transactions' behavior couldn't be explained by any serial ordering and aborting one of them rather than truly executing everything one at a time. This prevents all types of concurrency anomalies but comes with the trade-off of requiring retry logic in your application to handle the resulting serialization failures.

## When not to use postgres

PostgreSQL is a strong general-purpose default, but it's not the right tool for every workload, and it's worth being able to name the cases where reaching for something else or extending Postgres rather than leaving it makes more sense.

The clearest case is **extreme, horizontally-distributed write throughput**: workloads with write volumes far beyond what sharding a relational database comfortably handles, especially across multiple regions with an active-active requirement. Wide-column stores like **Apache Cassandra** are purpose-built for this  they trade away strong consistency and rich querying for near-linear write scalability across nodes with no single coordinating primary.

Similarly, **very simple access patterns at massive scale**  pure key-value lookups with no real need for joins, complex queries, or transactions are often better served by a purpose-built key-value store like **DynamoDB** or an in-memory store like **Redis**, both of which can be simpler to operate and cheaper to scale for that specific shape of workload than a relational database carrying features you're not using.

**Highly flexible or frequently-changing schemas**, especially where different records legitimately have very different shapes, can be a better fit for a document store like **MongoDB** PostgreSQL's JSONB support handles a reasonable amount of schema flexibility, but a workload that's predominantly schema-less end to end plays more to a document database's strengths.

That said, it's worth being cautious before writing Postgres off for some of the other classic "wrong tool" cases  time-series data, geospatial data, even distributed horizontal scaling because Postgres's extension ecosystem often lets you keep the operational simplicity of a single relational database while still getting purpose-built performance: **TimescaleDB** brings time-series-optimized storage and querying, **PostGIS** brings full geospatial indexing and querying, and **Citus** brings distributed, sharded Postgres behind a single logical interface. In an interview, it's often stronger to name these extensions as the reason you're staying on Postgres rather than assuming any specialized workload automatically forces a migration to a different database entirely.

### Change data capture

**Change Data Capture (CDC)** is a pattern for determining and tracking data that has changed in a database. Instead of copying an entire database every time you want to update a data warehouse or a search index, CDC lets you stream only the "deltas" the specific inserts, updates, and deletes in real time.

Most modern CDC systems follow the same basic pipeline: a **capture** stage monitors the database for any DML changes, an **extract** stage captures the specific change (e.g., "User 5 updated their email") in a structured format like JSON or Avro, a **transport** stage sends that change to a message broker such as Kafka or straight to a destination system, and a **load** stage applies the change at the destination a data warehouse like Snowflake, a search index like Elasticsearch, or a downstream microservice.
