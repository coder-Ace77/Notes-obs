The Complete Search technique, also known as brute force or (recursive) backtracking, is
a method for solving a problem by traversing the entire (or part of the) search space to
obtain the required solution.

There are primarilty two kinds of these searches  - 
- iterative
- recursive

Recursive being more powerfull as every iterative search can be converted to an iterative one in some way or another. 

Simple iterative searches are mostly multiple nested loops one on top of another. Sometimes we can make clever observations and cut down the number of operations which is mostly in adhock manner. 

Complete search is mde powerfully by one fact a bug free solution will always guaranteed to give out correct answer but may not get completed in the time. 

### Josephus problem 

The Josephus problem is a classic problem where initially there are n person numbered from 1, 2, . . . , n, standing in a circle. Starting from person no 1, every k-1 person are skipped and the k-the person is going to be executed and then removed from the circle. This count-then- execute process is repeated until there is only one person left and this person will be saved (history said that he was the person named Josephus). For example, n = 6 and k = 3, then the order of exex is: 3, 6, 4, 2, and 5, leaving person 1 as the sole survivor (draw a small circular array of size n = 6 and simulate this process). 

A general problem will ask the question `F(n,k) = Index of survivor when n people and kth one is exectued.`

Complete search solution is to simulate the solution. What we do is put all persons in the vector and then delete the kth person one by one. One thing to note is these circle based questions are more easily solvable on the `0` based indexing not `1 based` keep that in mind. So in complete search ---

```cpp
int josephus_brute(int n, int k) {
    vector<int> alive(n);
    iota(alive.begin(), alive.end(), 0);   // [0, 1, ..., n-1]
    int idx = 0;                            // current counting position
    while (alive.size() > 1) {
        // move k-1 more steps from current person, wrapping around
        idx = (idx + k - 1) % alive.size();
        alive.erase(alive.begin() + idx);   // this person dies
        // after erase, alive[idx] is automatically the *next* living person,
        // so counting naturally continues from there
    }
    return alive[0];                        // 0-indexed survivor
}
```

Here `idx` is the index where we are starting from now each iteration of while loop simulates the each round of killing first we update `idx` to go to the next killing spot. Modulus operation allows us to not go out of bound. Note that we shift by `k-1` spots. Now we erase that person and repeat.

This solution is `O(n^2)` however it allows us to find the ith kill.  

However we can do better for the `F(n,k)` part. Note that when we kill the first element it is at index `k-1`. Now say we have access to `F(n-1,k)` what can be said about the `F(n,k)`. If we start from the `n-1` people and start from `0` index note that this and situation when we killed just one person is that both have offset difference of `k` spots. So 

```
F(n,k) = (F(n-1,k)+k)%n
```

This recurrence can be solved both recursively and iteratively as well. Base case `n==1` `F(1,k)=0`. Index `0` is the lone survivor. 

```cpp
int josephus(int n, int k) {
    return n == 1 ? 0 : (josephus(n - 1, k) + k) % n;
}
```

Iterative
```cpp
int josephus(int n, int k) {
    int res = 0;                     // J(1, k) = 0
    for (int i = 2; i <= n; i++)
        res = (res + k) % i;         // build J(i,k) from J(i-1,k)
    return res;                      // 0-indexed survivor; add 1 if 1-indexed
}
```

Now in some problems k is small and n is larger `~O(10^12)`. In such problems above will fail. Now to solve this we remind us that once we start for a given round of elimination k is small so we can potentially remove a batch of people at once. 

```cpp
long long josephus_fast(long long n, long long k) {   // 0-indexed
    if (n == 1) return 0;
    if (k == 1) return n - 1;
    if (k > n)  return (josephus_fast(n - 1, k) + k) % n;  // fall back to O(n) step
    long long cnt = n / k;                    // people killed in this pass
    long long res = josephus_fast(n - cnt, k);
    res -= n % k;
    if (res < 0) res += n;                     // wrapped past the start
    else res += res / (k - 1);                 // account for skipped-over dead
    return res;
}
```

The insight of the fast version is that when `k` is small relative to `n`, you can peel off an **entire pass around the circle in one recursive step**, because in one lap you kill a predictable batch of `⌊n/k⌋` people at once.

Everything is 0-indexed, counting starts at position 0, and the first victim is at index `k-1`.

In the first sweep through `n` people you eliminate everyone at indices `k-1, 2k-1, 3k-1, …`. The number of such kills before you run off the end is

```cpp
cnt = n / k          // = floor(n/k), people killed this lap
```

After those `cnt` kills, `n - cnt` people remain, and there's a **tail** of leftover people you counted past but didn't kill:

```cpp
tail = n % k         // survivors sitting after the last kill, before wrapping to index 0
```

So instead of recursing on `n-1`, you recurse on `n' = n - cnt` — a much bigger jump. That single line

```cpp
long long res = josephus_fast(n - cnt, k);
```

gives you the survivor's index **in the reduced circle's own numbering**. All the remaining work is translating that reduced index back to an original index.

When you form the reduced circle, you renumber it so that reduced-index `0` is the person where counting resumes after the lap that's the first person of the **tail**. So the reduced circle, walked in order, looks like:

```
reduced idx:  0        1     ...  (tail-1) | tail          tail+1   ...
original:     cnt·k   cnt·k+1 ...  n-1      | 0, then survivors of [0..cnt·k), skipping the dead
              └──────── the tail ──────────┘└──── wrap-around region ────┘
```

That split is exactly the two branches in the code. The line `res -= n % k` (i.e. `res -= tail`) checks which region the reduced survivor fell into:

**Case A — the survivor is in the tail** (`res < tail`, so `res` goes negative):

```cpp
if (res < 0) res += n;      // original = cnt·k + old_res
```

The tail is a clean contiguous block `[cnt·k, n-1]` with no dead people mixed in, so the mapping is a plain shift. Adding `n` after subtracting `tail` lands you at `cnt·k + res`, which is that contiguous block. Nothing tricky here.

```cpp
else res += res / (k - 1);  // account for the dead we skip over
```

This is the clever line. After `res -= tail`, `res` is now `r` — the rank of the survivor **among the living people in `[0, cnt·k)`**, counted in order. But the _original_ positions in that range aren't contiguous: they come in blocks of `k-1` survivors, each block followed by one corpse (at `k-1, 2k-1, …`). To convert a "living rank" `r` into an original index, you have to add back one position for every full block of `k-1` you've passed — and the number of such blocks is `r / (k-1)`. That's the whole meaning of `res += res / (k-1)`.

Each recursive step replaces `n` with `n - ⌊n/k⌋ ≈ n·(k-1)/k`. So `n` decays geometrically with ratio `(k-1)/k`, and the number of levels until it collapses to a constant is about `log_{k/(k-1)} n ≈ k · ln n`. Hence **`O(k log n)`**.

## Tips

Programs that examine lots of (if not all) candidate solutions and choose the ones that are
correct (or remove the incorrect ones) are called ‘filters’. Programs that gradually build the solutions and immediately prune invalid partial solutions are called ‘generators’

Usually, ‘generator’ programs are easier to implement when written recursively as it gives us greater flexibility for pruning the search space. Do the math (complexity analysis) to see if a filter is good enough or if you need to create a generator.

When generating solutions using recursive backtracking (see tip above), we may encounter
a partial solution that will never lead to a full solution. We can prune the search there
and explore other parts of the search space.

Some problems have symmetries and we should try to exploit symmetries to reduce execu-
tion time! In the 8-Queens problem, there are 92 solutions but there are only 12 unique (or
fundamental/canonical) solutions as there are rotational and line symmetries. 

Sometimes it is helpful to generate tables or other data structures that accelerate the lookup
of a result prior to the execution of the program itself. This is called Pre-Computation, in
which one trades memory/space for time.

Some contest problems look far easier when they are solved ‘backwards’ (from a less obvious angle) than when they are solved using a frontal attack (from the more obvious angle as described in the problem description). Be prepared to attempt unconventional approaches
to problems.

The input constraint in some creative problems where the problem author’s expected solution
is Complete Search may be ‘disguised’ to look too big for a normal Complete Search solution
to work within time limit. But upon more careful inspection, some–usually subtle–remarks
in the problem description actually reduce the search space (significantly) which then makes
a Complete Search solution feasible. 

Given a multiset S of M = 100K integers, we want to know how many di↵erent integers
that we can form if we pick two (not necessarily distinct) integers from S and sum them.
The content of multiset S is prime numbers not more than 20K. If we directly try all possible O(M 2 ) pairs of integers and insert their sums into a hashtable (O(1) per insertion), we will get Time Limit Exceeded as M = 100K integers. However, observe that multiset S contains only prime numbers under 20K. Later in Book 2, we will find out that ⇡(20 000) = 2262, i.e., there are only 2262 distinct prime numbers under 20K despite the size of multiset S can be up to M = 100K. So, we do one O(M ) data compression pass to ensure that each integer only has at most two copies, i.e., N  2 ⇥ 2262. Afterwards, we perform O(N 2 ) complete search check as before.
