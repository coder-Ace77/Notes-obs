Kubernetes uses yaml files to create the objects for deployments such as pods , replicas etc. A kubernetes definition file has 4 fields -

```yaml
apiVersion:
kind:
metadata:

spec:
```

`apiVersion` - eg - v1 `type - string`
`kind` - Type of object we are trying to create. can be - `Pod/ReplicaSet/Service` - `type -string`

Metadata - Data about the object - It should be dictionary. Now we should have exactly one mandatory field here - 

- name - type string - unique identifier for the object within its namespace

We also have multiple optional fields -

- `namespace` (optional — defaults to `default`)
- `labels` (optional — key/value pairs used for identifying/selecting/grouping objects) It is basically a dictionary. 
- `annotations` (optional — arbitrary non-identifying metadata)
- `uid`, `resourceVersion`, `creationTimestamp` etc. are also present but these are auto-generated by Kubernetes, not something you set yourself. 

`spec` - `type-dictionary` -  This is the specification field where we provide information to kubernetes. This is different for different objects.

For a pod we should provide a key - `containers` which is a list since our pod can have multiple containers. Each item of the list is essentially a dictionary difining the specification of container. For an instance we can define name and image name. 

For each item in a list for pod  - we give our container name and image 

```yaml
apiVersion: v1
kind: Pod
metadata: 
	name: myapp-pod
	labels:
		app: myapp
		type: front-end

spec:
	containers:
		- name: nginx-container
		  image: nginx #Specify full path if not using 
```

now we can simply create the pod using - or by `apply`

```bash
kubectl create -f pod-definition.yaml // file name
```

To get the pods

```bash
kubectl get pods # basic info

kubectl describe pod myapp-pod # detaild data
```

Finally the given container can also have a field called env whose value has to be a list of items where each item will have a name and value defining the key and value of environment variables. 

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: postgres
  labels:
    tier: db-tier
spec:
  containers:
    - name: postgres
      image: postgres
      env: 
        - name: POSTGRES_PASSWORD
          value: mysecretpassword

```

We can also create the pod using cmd 

```bash
kubectl run nginx --image=nginx
```

#### apiVersion

First of all what is meaning of `api` here. When people say "the Kubernetes API," they are talking about the **kube-apiserver** a component that runs on the control plane of every Kubernetes cluster.

So when you run `kubectl apply -f pod.yaml`, here's what's actually happening:

1. kubectl reads your YAML file.
2. kubectl converts it to JSON (Kubernetes' API is JSON under the hood; YAML is just a friendlier format for humans).
3. kubectl sends an HTTP request a POST or PATCH to the API server's REST endpoint.
4. The API server authenticates you, checks authorization (RBAC), runs admission controllers (validation/mutation), validates the object against a schema, and then persists it into etcd.
5. Once it's in etcd, other components — like the scheduler or the relevant controller — notice the new object (via a "watch" mechanism) and start acting on it.

Every object type in Kubernetes Pod, Deployment, Service, Job is exposed as a **resource** at a specific URL path on the API server.

```
GET /api/v1/namespaces/default/pods
GET /apis/apps/v1/namespaces/default/deployments
GET /apis/batch/v1/namespaces/default/jobs
```

There are actually **two kinds of root paths**- 

- `/api/v1/...` this is the **core** (also called "legacy") API group. It has no group name, and it's where the oldest, most fundamental resources live: Pod, Service, ConfigMap, Secret, Namespace, Node, PersistentVolume, etc.
- `/apis/<group>/<version>/...`  this is for **named API groups**. Everything that isn't "core" belongs to some group: `apps`, `batch`, `networking.k8s.io`, `rbac.authorization.k8s.io`, `storage.k8s.io`, and so on.

When you write `apiVersion: apps/v1` in your YAML, you are literally telling the API server "route this object to the endpoint under `/apis/apps/v1/`." When you write `apiVersion: v1`, you're saying "route this to `/api/v1/`, the core group." That's it `apiVersion` is a routing and schema-selection instruction, not just a label.

Grouping this way also enables a really important feature: **API extensibility**. Anyone can define their own group via **CustomResourceDefinitions (CRDs)** this is how tools like Istio, cert-manager, and Argo CD add their own object kinds (like `Certificate` or `VirtualService`) into your cluster's API, complete with their own `apiVersion` like `cert-manager.io/v1`.

The second half of `apiVersion` the `v1`, `v1beta1`, `v1alpha1` part tracks the **maturity and stability** of that particular resource's schema, independently per group.

Kubernetes' convention:

- **alpha** (e.g. `v1alpha1`)  brand new, may be buggy, disabled by default on many clusters, fields can change or disappear entirely between Kubernetes releases without warning. Not for production.
- **beta** (e.g. `v1beta1`)  more stable, enabled by default, well-tested, but the schema might still receive small breaking changes before graduating to stable. Usable, with some caution.
- **stable / GA** (e.g. `v1`)  locked in. Kubernetes guarantees backward compatibility for stable APIs for a long, defined support window. This is what production workloads should be built on.

A resource can literally travel through this pipeline over the project's lifetime. `Deployment`, for instance, historically existed as `extensions/v1beta1`, then `apps/v1beta2`, before finally settling at `apps/v1`. 

Gps --

- Core - This has no group name - Pod, Service, ConfigMap, Secret, Namespace `v1`
- apps - Deployment, StatefulSet, DaemonSet, ReplicaSet `apps/v1`
- batch - Job, CronJob `batch/v1`
- networking.k8s.io - Ingress, NetworkPolicy ``networking.k8s.io/v1``
- autoscaling - HorizontalPodAutoscaler - `autoscaling/v2`

Not only this we can simply write our own resources and act on it. That mechanism is the **CustomResourceDefinition**, or **CRD**. A CRD is, itself, a Kubernetes object. You `kubectl apply` it just like anything else. But what it _does_ is register a brand-new `kind` — with its own schema, its own `apiVersion`, its own group — into the API server's vocabulary. Once a CRD is installed, the API server treats your new custom object exactly like it treats a Pod or a Deployment: it accepts it via REST, validates it against the schema you defined, stores it in etcd, and lets you watch/list/get/delete it with `kubectl`.

Here's the conceptual trick that makes this so powerful: **the API server doesn't know or care what your custom object _means_**. It just stores structured data and exposes it via a consistent API. All the actual _behavior_ — the part that makes your custom object do something — comes from a separate program called a **controller** (or **operator**), which watches for these custom objects and takes real action based on what it sees, using the exact same watch-and-reconcile pattern the built-in controllers use for Pods and Deployments.

This is the **CRD + Controller** pattern, and it's the foundation of nearly the entire Kubernetes ecosystem — cert-manager, Argo CD, Prometheus Operator, and yes, Istio, are all built this way.

### Example of Istio

Istio is a **service mesh** it manages traffic, security (mTLS), and observability between your microservices, without you having to change application code. It does this by injecting a sidecar proxy (Envoy) next to every Pod, and then controlling those proxies centrally.

But "controlling traffic between services" isn't something `Deployment` or `Service` objects were ever designed to express. There's no native Kubernetes field for "route 90% of traffic to v1 of this service and 10% to v2" or "only allow calls to this service if they present a valid mTLS certificate." So Istio doesn't try to bend built-in objects into doing this — instead, it defines its **own API group** via CRDs, with object kinds purpose-built for mesh configuration.

When you install Istio, part of that installation is a set of CRD manifests that register new kinds like:

- **`VirtualService`**  defines routing rules: which requests go to which version of a service, retries, timeouts, traffic splitting for canary releases.
- **`DestinationRule`**  defines policies applied _after_ routing: load balancing strategy, connection pool settings, mTLS/TLS behavior toward a destination.
- **`Gateway`**  configures an ingress/egress load balancer at the edge of the mesh, describing which ports/protocols/hosts are exposed.
- **`ServiceEntry`** lets you register services _external_ to the mesh (like an outside API) so mesh traffic rules can apply to them too.
- **`PeerAuthentication`** and **`AuthorizationPolicy`**  control mTLS requirements and fine-grained access control between services.

These all live under Istio's own API group, `networking.istio.io` (and `security.istio.io` for the auth-related ones), so a YAML file for one of these looks like:

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews-route
spec:
  hosts:
    - reviews
  http:
    - match:
        - headers:
            end-user:
              exact: adil
      route:
        - destination:
            host: reviews
            subset: v2
    - route:
        - destination:
            host: reviews
            subset: v1
```


Run `kubectl apply -f istio-crds.yaml` _before_ installing Istio's control plane, and only then does the API server even understand what a `VirtualService` is. Now how does this routing rules take place in `istio` . 

Registering the CRD only gets you storage and validation — a place to put your `VirtualService` object in etcd, and a guarantee it matches the expected schema. Nothing traffic-related actually happens just because the object exists.

The real work is done by **istiod**, Istio's control plane component, which acts as the controller/operator for all these custom resources. istiod continuously watches the API server for `VirtualService`, `DestinationRule`, `Gateway`, etc.  using the same watch mechanism the built-in Kubernetes controllers use and whenever it sees one created or changed, it:

1. Translates your high-level routing/security intent into low-level **Envoy proxy configuration**.
2. Pushes that configuration out to every Envoy sidecar in the mesh via a gRPC API (the **xDS protocol**).
3. The sidecars then enforce that routing/security behavior on real network traffic, transparently, without your application code knowing anything happened.

### More about pods 

Unlike many people beleive a pod can restart if it crashes given stated in its restartPolicy. 

```yml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  restartPolicy: Always   # this is the default
  containers:
    - name: my-app
      image: my-app:v1
```

There are three possible values:
- **`Always`** (the default) — the container is restarted no matter how it exited, whether it crashed with an error or exited cleanly with code 0. This is why long-running services (web servers, APIs) almost always use this.
- **`OnFailure`** — only restart if the container exited with a non-zero (error) exit code. If it exits cleanly (code 0), it's left stopped. Common for batch-style workloads.
- **`Never`** — the container is never restarted by the kubelet, regardless of how it exits. Used when you genuinely want a one-shot run-once container.

However this will only happen if the pod or more importantly a container inside it is dying. In the case that `node` on which it is scheduled it will not start nor it will start if pod was deleted or removed if under resource pressure. 

If a container keeps crashing repeatedly, the kubelet doesn't hammer it with instant restarts forever it applies an **exponential backoff**: 10s, 20s, 40s... up to a cap (5 minutes), so a genuinely broken container doesn't spin infinitely fast and burn CPU/log space. This is the state you see as `CrashLoopBackOff` when you run `kubectl get pods` it's not an error state exactly, it's the kubelet saying "this keeps crashing, so I'm slowing down how often I retry."

To have a proper active pod or set of pods which are maintained and remain active we need to move to controllers.
