A _goroutine_ is a lightweight thread managed by the Go runtime. `go func()` starts a new goroutine running. 

Goroutines run in the same address space, so access to shared memory must be synchronized.

In most languages, when you want to do two things at once, you create a thread. The problem? OS threads are "expensive" they consume a lot of memory (often 1MB or more) and take time for the CPU to swap between them. Go flips the script. A Goroutine starts with a tiny stack (about **2KB**) that grows and shrinks as needed. You can easily run hundreds of thousands of them on a modest laptop without breaking a sweat.

Writing just `go` in front of function call creates a new go thread. 

### Go coroutines modelling

Go uses an **M:N scheduler**, which means it maps **M** Goroutines onto **N** OS threads.

- **The Go Runtime** sits between your code and the OS.
- If one Goroutine blocks (like waiting for a file to read), the scheduler is smart enough to move the other Goroutines to a different OS thread so they can keep working. This is called **work stealing**.

Unlike OS threads, which have a fixed-size guard page of memory, Goroutines are incredibly memory-efficient. Intially starting with small stack of size `2kb`. 

In Go, all Goroutines share the same **address space**. This is both a superpower and a massive responsibility. 

Each goroutine has its own stack meaning the data declared inside a goroutine can not be accessed by another go routine. However heap data and global data is shared. 

When you have multiple Goroutines reading and writing to global variables, you enter the "Danger Zone." Because Goroutines run truly in parallel (on different CPU cores via different **P**s), two Goroutines might try to update a global counter at the exact same microsecond.

### Channels

Channels are typed conduits which are essentially the pipes which can transport the data from one coroutine to another coroutine. You can send a value into a channel from one Goroutine and receive it in another. So there is a `sender channel` and `receiver channel`. There are two kinds of channels in general - 

- **Unbuffered Channels:** The "hand-off." The sender blocks until a receiver is ready. It’s a synchronous event.
- **Buffered Channels:** The "mailbox." The sender only blocks when the buffer is full. It allows for asynchronous communication up to a certain capacity.

Channel always has a `type` like - int, string etc and is always one directional not bidirectional. Creating a channel is easy just using `make`.

```go
ch:= make(chan int,optional_buffer_size)
```

If not optioanal_buffer_size is given then it will become unbuffered channel. While providing it with the size means channel is now buffered. 

In both the cases above the receiver is blocked untill the data is not available. 
### Internal working

In Go, a channel is not a magical primitive; it is a **struct** named `hchan` defined in the Go runtime. When you call `make(chan int, 10)`, Go allocates this struct on the heap.

The anatomy of `hchan`

Inside the `hchan` struct we have - 

 - **`buf` (The Buffer):** A pointer to a circular array. This is only used for buffered channels to store data.
 - **`lock`:** A light mutex. **Yes, channels use a lock internally!** Every send or receive operation requires acquiring this lock to ensure thread safety.
 - **`sendq` and `recvq` (Wait Queues):** These are linked lists of "sudog" structures. A `sudog` represents a Goroutine that is currently blocked, waiting to send to or receive from the channel.
 - **`dataqsiz`:** The size of the circular buffer.
 - **`closed`:** A flag indicating if the channel has been closed.

### Sending and receives

Now there are various schenarios here - 

 - In the case if receiver is already waiting in `recq` then the scheduler removes the receiver from the `recq` and runtime copies the data directly from sender's stack to `receiver's` stack. Reciever is marked as runnable. _No buffer is used here, making it extremely fast._
 - If Goroutine A sends to a buffered channel that isn't full , then the data is started to get copied into the buffer array untill either buffer is full or sender is done with sending. In case buffer is full and data is still there receiver will be put into `sendq` meaning it will be blocked. Now at some other time reviever `B` will start with the revieving part. And will get blocked untill buffer is full. 
 - If Goroutine A tries to send to a full buffered channel (or an unbuffered one with no receiver), then it puts itself into `sendq` list and parks itself. 

So with this key points to remember are-  

 - **Sending to a nil channel:** Blocks forever.
 - **Receiving from a nil channel:** Blocks forever.
 - **Sending to a closed channel:** Panics immediately.
 - **Receiving from a closed channel:** Returns the "zero value" of the type (and `false` if using the comma-ok idiom).

When you send data through a channel, Go **copies** the value.

- If you send an `int`, the 8 bytes are copied.
- If you send a **pointer**, only the memory address (8 bytes) is copied.
- If you send a large `struct` (e.g., 1KB), the entire 1KB is copied into the channel's buffer or the other Goroutine's stack.

For high-performance Go, send pointers through channels if the data structure is large, but be careful—once you send a pointer, you must ensure the sending Goroutine doesn't touch that memory anymore to avoid race conditions.

Meaning is that you need not to worry about the data getting corrupted due to race conditions. 

### Tutorial on channels

To create channel 

```go
ch : = make(chan string)
```

To send/recieve some value across channel we use `<-` syntax. Where receiving side should be on left and sending on right. We can also send multiple values one by one. 

```go 
// sending 

c <- "value"
c <- "value2"

// recieving
s string
s <- c
```

In the unbuffered, sends and receives block until the other side is ready. This allows goroutines to synchronize without explicit locks or condition variables.

While in buffered case , sender to a buffered channel is block only when the buffer is full. Receiver is blocked when the buffer is empty.

A sender can `close` a channel to indicate that no more values will be sent. Receivers can test whether a channel has been closed by assigning a second parameter to the receive expression: 

When you receive from a channel, it actually returns a second boolean value: `v, ok := <-ch`.

- If `ok` is `true`, you received a valid value.
- If `ok` is `false`, the channel is closed and empty.

```go
// receiver side
val , ok <- ch
```

Now close can be called from the receiver side. It does not means channel will be stopped but the `receiver` will get the `ok` value as false and so it can know that channel is closed from sender side. 

1. **Only the sender should close:** If a receiver closes the channel, the sender will **panic** when they try to send the next item.
2. **Don't close twice:** Closing an already closed channel causes a **panic**.
3. **Sending to a closed channel:** This also causes a **panic**.
4. **Receiving from a closed channel is safe:** You will get the "zero value" of the channel's type (e.g., `0` for `int`, `""` for `string`) infinitely.

Manually checking `v, ok := <-ch` in a loop is tedious. The `range` keyword provides a clean way to "drain" a channel.

- **Syntax:** `for value := range ch { ... }`
- **Behavior:** The loop will pull every item off the conveyor belt as it arrives.
- **The Catch:** This loop is **blocking**. It will sit and wait forever for the next item unless the channel is **closed**.

**Crucial Logic:** The `range` loop only terminates when the channel is closed. If you forget to call `close(ch)`, the `range` loop will wait for data that never comes, eventually causing a **deadlock** error.

example 

```go 
func main() {
    jobs := make(chan int, 5)

    // Producer (Goroutine)
    go func() {
        for i := 1; i <= 3; i++ {
            jobs <- i // Sending data
        }
        close(jobs) // "I'm done sending!"
    }()

    // Consumer (Main)
    // range will block until data arrives, and stop when close() is called
    for j := range jobs {
        fmt.Println("Processed job", j)
    }
    
    fmt.Println("All jobs finished.")
}
```

This pattern—where multiple Goroutines (workers) all listen to the same channel—is often called the **Worker Pool** or **Fan-Out** pattern. It is one of the most powerful ways to scale a Go application.

When multiple workers are ranging over the same channel:

- **No Duplication:** Each piece of data is delivered to exactly **one** worker. Go handles the coordination internally so that workers don't "fight" or grab the same item twice.
    
- **Load Balancing:** If Worker A is busy processing a heavy task, Worker B will naturally pick up the next item. This ensures that work is distributed based on who is actually available.

When you call `close(ch)`, every single worker ranging over that channel receives the "stop" signal.

1. Each worker finishes the item they are currently holding.
2. The next time they reach for the channel, they see it is closed.
3. Their `range` loop terminates immediately.

```go
func worker(id int, jobs <-chan int) {
    for j := range jobs {
        fmt.Printf("Worker %d started job %d\n", id, j)
        // Simulate work
        time.Sleep(time.Millisecond * 500)
    }
    fmt.Printf("Worker %d is going home.\n", id)
}

func main() {
    jobs := make(chan int, 10)
    // Spin up 3 workers
    for w := 1; w <= 3; w++ {
        go worker(w, jobs)
    }
    // Send 5 jobs
    for j := 1; j <= 5; j++ {
        jobs <- j
    }
    close(jobs) // All 3 workers will stop once jobs is empty
    // Give them time to finish
    time.Sleep(time.Second * 2)
}
```

### Directional channels 

When passing channels into functions, you can specify if the function should only **send** or only **receive**. This prevents bugs where a function accidentally closes a channel it shouldn't. To do that just specify the direction `chan<-` function is producer. `<-chan` receiver only. 

```go
// This function ONLY produces data
func producer(out chan<- int) {
    for i := 0; i < 5; i++ {
        out <- i
    }
    close(out)
}

// This function ONLY consumes data
func consumer(in <-chan int) {
    for val := range in {
        fmt.Println(val)
    }
}

func main() {
    ch := make(chan int)
    go producer(ch)
    consumer(ch)
}
```

Channels aren't like files; you don't usually need to close them. Closing is only necessary when the receiver must be told there are no more values coming, such as to terminate a `range` loop.

### Select statement

What if you are waiting on _multiple_ channels? The `select` statement lets a Goroutine wait on multiple communication operations. It’s like a `switch` statement but for channels.

```go
func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)

    go func() { ch1 <- "Fast" }()
    go func() { ch2 <- "Slow" }()

    // select picks whichever channel is ready first
    select {
    case msg1 := <-ch1:
        fmt.Println("Received from ch1:", msg1)
    case msg2 := <-ch2:
        fmt.Println("Received from ch2:", msg2)
    case <-time.After(time.Second):
        fmt.Println("Timed out!")
    }
}
```

A `select` blocks until one of its cases can run, then it executes that case. It chooses one at random if multiple are ready. Note select will run only one case not all. 

If you don't want your code to sit and wait (block) at all, you can add a `default` case.
- If any channel is ready, it executes that channel's case.
- If **no** channel is ready, it executes the `default` block immediately instead of waiting.

### Mutex

Mutex locks are used to provide the mutual exclusion in the certain part of code. 

```go
import "sync"

func main(){
	var mu sync.Mutex
	// locking
	mu.Lock()
	
	// unlocking
	mu.Unlock()
}
```

Now we can make them global variables or pass as the struct.

```go
package main

import (
    "sync"
    "fmt"
)

// Global variables (shared across the whole package)
var (
    counter int
    mu      sync.Mutex
    wg      sync.WaitGroup
)

func worker() {
    defer wg.Done()
    
    mu.Lock()         // Start of the "Critical Section"
    counter++         // Only one goroutine can be here
    mu.Unlock()       // End of the "Critical Section"
}

func main() {
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go worker()
    }
    wg.Wait()
    fmt.Println("Final Counter:", counter)
}
```

If you decide to pass a Mutex into a function instead of using a global one, you **must** pass it by **pointer** (`*sync.Mutex`).

```go
// GOOD: This points to the same Mutex in memory.
func update(m *sync.Mutex) { 
    m.Lock()
    defer m.Unlock()
    // ...
}
```

A Mutex tracks its own state (whether it is locked or not). If you pass it by value, Go creates a brand new Mutex in a different memory address. Goroutine A will lock its copy, and Goroutine B will lock its _own_ separate copy. They won't actually be blocking each other, and you'll still get a race condition.

We sometimes include them in the piece of data and pass around as `structs`

```go
type SafeCounter struct {
    mu    sync.Mutex
    value int
}

func (c *SafeCounter) Increment() {
    c.mu.Lock()         // Acquire the lock
    defer c.mu.Unlock() // Ensure it's released even if the function panics
    c.value++
}
```


If you have a piece of data that is **read often** but **written rarely** (like a configuration map), a standard Mutex is inefficient because it prevents multiple readers from working at the same time.

```go
type Config struct {
    mu   sync.RWMutex
    data map[string]string
}

func (c *Config) Get(key string) string {
    c.mu.RLock()         // Read Lock
    defer c.mu.RUnlock()
    return c.data[key]
}
```

A RWMutex allows multiple readers to read at same time and **Only One Writer** to hold the lock (and no readers are allowed while the writer is working).

### Waitgroups

A `sync.WaitGroup` operates like a simple counter:
- **`Add(int)`**: Increments the counter by the number of workers you're starting.
- **`Done()`**: Decrements the counter by 1. (Usually called when a worker finishes).
- **`Wait()`**: Blocks the code right where it is until the counter hits **zero**.

Waitgroups are used as the coordination tools waiting for the things. 

```go
package main

import (
    "fmt"
    "sync"
    "time"
)

func worker(id int, wg *sync.WaitGroup) {
    // 2. Signal "Done" when the function finishes
    defer wg.Done()

    fmt.Printf("Worker %d starting...\n", id)
    time.Sleep(time.Second) // Simulate work
    fmt.Printf("Worker %d finished!\n", id)
}

func main() {
    var wg sync.WaitGroup

    for i := 1; i <= 3; i++ {
        // 1. Tell the leader: "We are starting 1 more task"
        wg.Add(1)
        go worker(i, &wg)
    }

    // 3. Block main until the counter hits zero
    fmt.Println("Main: Waiting for workers...")
    wg.Wait()
    fmt.Println("Main: All workers are done. Cleaning up.")
}
```

Note waitgroup must be passed as functions. Always call `wg.Add(1)` **outside** the Goroutine (in the parent). 

In complex functions (especially in backend logic like your `DocDB` internals), a worker might exit early because of an error. Using `defer wg.Done()` ensures the counter always decrements, even if the worker crashes or returns early.

#### Once

Sometimes you have an initialization task (like connecting to a database) that must happen **exactly once**, even if 1,000 Goroutines try to trigger it at the same time.

```go
var dbConn *sql.DB
var once sync.Once

func GetConnection() *sql.DB {
    once.Do(func() {
        fmt.Println("Connecting to DB...")
        dbConn = setupDatabase()
    })
    return dbConn
}
```


Atomic operations are handled at the CPU level. They are much faster than Mutexes because they don't involve the scheduler "parking" Goroutines. However, they only work on simple types like `int32`, `int64`, and `uint64`.

```go
var count int64

func increment() {
    atomic.AddInt64(&count, 1) // Thread-safe without a Mutex!
}
```

### Semaphores

Go does not have a semaphore while mutex can be used as the binary semaphores. Go encourages you to use the buffered channels as counting semaphores. 

**Acquire:** Send a value into the channel. If the buffer is full, the Goroutine blocks.
**Release:** Receive a value from the channel. This opens up a slot for someone else.

```go
// Capacity of 5 (5 "permits" available)
sem := make(chan struct{}, 5)

func worker() {
    sem <- struct{}{}        // Acquire: take a slot
    defer func() { <-sem }() // Release: give back the slot
    
    // Do heavy database I/O or network call here
}
```

An empty struct `struct{}` occupies **0 bytes** of memory. It’s the most efficient way to signal "I am taking a slot" without actually allocating data.

### Defer

`defer` is used to schedule a function call to run **immediately before** the surrounding function returns. It is Go's way of ensuring that cleanup happens no matter how the function exits (even if it panics). Example 


```go
func processFile(filename string) error {
    f, err := os.Open(filename)
    if err != nil {
        return err
    }
    // This will run at the VERY end, even if the code below fails
    defer f.Close() 

    // ... process the file ...
    return nil
}
```

**Common Use Cases:**
1. **Closing Resources:** Files, network sockets, or database connections.
2. **Unlocking Mutexes:** Ensuring a `mu.Unlock()` always happens.
3. **Timing:** Measuring how long a function took to run.
