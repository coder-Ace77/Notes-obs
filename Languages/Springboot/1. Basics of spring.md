Spring is a lightweight java library for managing the lifecycle of java objects which spring calls beans. Note that earlier java used to have lot of boilerplate code in production systems. Spring main task is to manage the life cycle of the objects which it calls bean. Now since the code itself does not manage the lifecycle of objects which is usual naive code.  Spring works on top of java reflection api. 

We need someone to manage the dependencies for us. Spring is build on top of two important principles - 

### Inversion of control

**Inversion of Control** is a broad design principle where the custom-written portions of a computer program receive the flow of control from a generic framework. In traditional Java programming, your code is the "boss" it decides when to create an object, how to configure it, and when to call its methods. With IoC, the "control" is inverted: the framework (Spring) becomes the boss. It manages the lifecycle and flow of the application, and your code simply sits there waiting to be called or utilized. This removes the burden of "wiring" the application together from the developer and hands it to the system.

### IOC container

The **IoC Container** is the actual specialized engine within Spring (specifically the `ApplicationContext`) that implements this philosophy. When your application starts, the Container reads your configuration (metadata), finds your classes, and instantiates them as "Beans.". It holds these objects in a central registry. It doesn't just store them; it manages their entire existence—from the moment they are born (instantiation), through their configuration and any functional "decoration" (like adding security), until they are eventually destroyed when the application shuts down.

### Dependency injection

**Dependency Injection** is the specific pattern used to implement IoC. It is the physical act of "plugging" one object into another. If `Class A` requires `Class B` to function, `Class A` does not go out and find or create `Class B`. Instead, it simply declares, "I need an object of type B." At runtime, the IoC Container looks at its registry, finds an instance of `Class B`, and "injects" it into `Class A` (usually through a constructor or a setter method). This process ensures that `Class A` remains independent of how `Class B` is created or what specific version of `Class B` is being used, making the system incredibly modular and easy to test.

### Why this?

Well without ioc we will be needed to manage the dependency of any class. Secondly we would be hardwiring a dependency `B` or some version of it into another class. This creates big hassle when needed to be replaced. Finally if the wawy the obejcts are created changed we will be required to change that in every place leading to large code change.

Before the spring era all the objects wee created by the code manually so say you have external jar `EmailSender`. public class UserRegistrationService {

With the advent of spring framework was capable of creating beans aka managed objects which can injected as dependencies into objects. But we still needed to define which objects map to which bean and which bean will get injected. 

In this era we will not create object but will allow any email client to be taken here. 

```java
public class UserRegistrationService {
    private ExternalEmailClient emailClient;
    
    public void setEmailClient(ExternalEmailClient client) {
```

Now spring will inject the dependency by looking at the xml file `application.xml`

```xml
<bean id="myEmailClient" class="com.thirdparty.ExternalEmailClient">

    <constructor-arg value="587" />

```

Here observe that we define a bean of type `myEmailClient` and refer to it by its global class name. Also we give all the constructors arguments as part fo bean definition. This xml based technique allows for the separation of concerns of bussiness logic and infra meaning actual object used. 

Note that `UserRegistrationService` is the class in which we needed a dependency so bean of `myEmailClient` is acutally created. 

Note in earlier example we just made the bean of external client. But we need to maybe inject it as well. In xml era there was no auto injection. We needed to made both the object and its dependencies as been and then  inject them via property. For example

```java
public class NotificationService {

    // The class doesn't care WHAT MessageService is; it just waits for one
```

Now we define the xml based configuration. 

```xml
<beans>
    <bean id="myMessageService" class="com.example.EmailMessageService" />
    <bean id="notificationService" class="com.example.NotificationService">
        <property name="messageService" ref="myMessageService" />
    </bean>

```

With xml based configuration since xml file is an text file it does not do type check and programmers often had to deal with large files. 

To solve these problems modern Annotation based configuration was propoesed which is used currently. The solution was to move the "instructions" **inside the Java class itself** using Metadata (Annotations). This was made possible by Java 5 and fully embraced by Spring 2.5 and 3.0.

First thing which changed was self discovery. Instead of listing every bean in an XML file, Spring introduced **Component Scanning**. You simply put a `@Component` (or `@Service`, `@Repository`) tag on top of your class. When the app starts, Spring "scans" your packages. If it sees the annotation, it automatically creates the bean. You never have to touch a configuration file to register a new class.

Secondly to solve which bean will be injected at which dependency. Instead of manually linking beans in XML using `<property ref="..." />`, you use the `@Autowired` annotation. Spring looks at the variable type and automatically finds the matching bean in its container to "plug" it in. The "wiring" logic is now right next to the variable it affects.

While annotations like `@Component` or `@Service` are great for classes you own, you cannot open a `.jar` file from Google, Amazon, or a database driver and "type" an annotation into their source code.  This is where `@Configuration` annotations are used they allow you to make the bean of third party libraryies and get them injected into your code. 

```java
@Configuration
public class AppConfig {
    @Bean
    public ExternalEmailClient emailClient() {
        // This is pure Java. If you mistype 'ExternalEmailClient', 
        // the IDE turns red and the code won't compile!
        return new ExternalEmailClient("smtp.server.com", 587);
    }
}
```

Now when any bean will be wanted the object of type `ExternalEmailClient` spring will return this bean automatically. 

Another example

```java
@Configuration
public class CloudConfig {

    public S3Client s3Client() {

        return S3Client.builder()
                       .region(Region.US_EAST_1)
                       .credentialsProvider(StaticCredentialsProvider.create(myCreds))
                       .build();
    }
}
```

### Little on java xml 

In xml based cinfiguration Spring **IoC Container** reads at startup to build the application's object graph. In the XML era, the file (usually named `applicationContext.xml`) was the "brain" of the application, sitting entirely outside the Java source code.

A Spring XML file is wrapped in a `<beans>` root element. Each class you want Spring to manage is defined as a `<bean>`.

```java
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans 
       http://www.springframework.org/schema/beans/spring-beans.xsd">

    <bean id="myDataSource" class="org.apache.commons.dbcp.BasicDataSource">
        <property name="driverClassName" value="com.mysql.jdbc.Driver" />
        <property name="url" value="jdbc:mysql://localhost:3306/mydb" />
    </bean>

    <bean id="userRepository" class="com.example.repo.JdbcUserRepository">
        <property name="dataSource" ref="myDataSource" />
    </bean>

    <bean id="userService" class="com.example.service.UserService">
        <constructor-arg ref="userRepository" />
    </bean>

</beans>
```

- `id` - This is the unique name of a bean. 
- `class` - This is the fully quantifiable name
- When you use the `<property>` tag, Spring uses **Java Reflection** to call a setter method. Now the requirement is that java should have a matching setting constructor. 
- **`value` vs `ref`**: This is a crucial distinction. `value` is for literal data (strings, numbers), while `ref` is for connecting to another bean defined in the XML.
- Constructor injection -  This tells Spring to pass the dependencies through the class constructor. If your class has multiple constructors, you often have to use `index="0"` or `type="int"` attributes to help Spring figure out which constructor to call. XML makes this very verbose compared to modern Java.
- By default, all beans in an XML file are **Singletons** and are **Eagerly Initialized**. The moment the Spring container starts, it creates _every_ object defined in the XML. You have to explicitly add `lazy-init="true"` if you want an object to be created only when it's actually needed.

### Annotation era 

In the XML era, you had to manually "label" every bean with a String ID and then "point" to that ID from other beans. This is what is often reffered to as the string-based matching. Modern spring uses `Type based matching` meaning java class itself is an identity. 

Secondly in annotation java spring goes through what is called discovery of classes and what does it means is instead of processing the xml file now the spring will itself start and will start scanning all the files for the annotations and will track all the objects desired to be beans.  Spring defaults the "ID" to the class name (with a lowercase first letter), but you almost never need to know it because Spring finds it by its **Type**.

In XML, you had to explicitly tell Spring: "Take Bean A and plug it into Bean B" using the `ref` attribute. This required you to keep track of every ID in your head. 

When Spring sees `@Autowired` above a variable (like `private UserRepository repo;`), it doesn't look for a String ID. It looks into its container and says: _"Do I have an object that is an instance of `UserRepository`?"_ * **The Nuance:** If it finds exactly one, it "plugs" it in automatically. This is called **Autowiring by Type**. You no longer need to write a single line of configuration code to connect two objects.

In XML, if you had two different database repositories (one for MySQL and one for Oracle), you had to manually pick the correct `id` in the `ref` tag.

If Spring finds two beans of the same type, it doesn't know which one to pick. You solve this with:
- **`@Primary`**: Mark one class as the "Default" choice.
- **`@Qualifier("name")`**: Explicitly ask for a specific one at the injection point.

## Spring annotations

Spring annotations are the metadata-driven mechanism that replaced the traditional XML-based configuration, allowing developers to define bean lifecycles, dependency relationships, and infrastructure behaviors directly within the Java source code. 

The core of this system lies in **Stereotype Annotations** like `@Component`, `@Service`, `@Repository`, and `@Controller`.  

When the application starts, Spring searches specified packages for classes bearing these markers; it then generates a `BeanDefinition` for each, effectively "registering" the class as a managed object within the ApplicationContext. This eliminates the need for manual bean registration, as the framework assumes responsibility for the object’s instantiation and management based solely on the presence of the annotation.

In Spring, **Stereotype Annotations** are specialized markers that define the "role" of a class within the overall application architecture. Technically, these annotations are all "aliases" for the base `@Component` annotation. By using these specific names instead of just a generic `@Component`, you provide metadata that Spring uses to apply specialized behaviors like automatic exception translation or web-routing logic to the class.

#### `@Component`

This is the "root" stereotype. Any class marked with `@Component` is picked up by Spring and turned into a managed object. It is used for general-purpose components that don't fit into the specific categories of data, logic, or web handling.

**Example:** A utility class that performs file conversions or encryption.

#### `@Service`

The `@Service` annotation is applied to classes that house the **Business Logic** of the application. While it functions exactly like `@Component` technically, it is used to signify that the class contains the core calculations, data processing, and coordination of the app.

A `PaymentService` that calculates taxes, validates a credit card, and then calls a database to save the transaction.

#### `@Repository`

This is used for classes that interact directly with the database (the Data Access Layer). Beyond just marking the class for the IoC container, it adds a crucial "nuance": **Automatic Exception Translation**.
- **Example:** A `UserRepository` class that writes SQL queries or uses an ORM to fetch user data.

#### `@Controller` and `@RestController`

 They are responsible for receiving HTTP requests (from a browser or mobile app) and returning a response.
- **`@Controller`**: Usually returns a "View" (like an HTML page).
- **`@RestController`**: A specialized version for APIs. It combines `@Controller` and `@ResponseBody`, meaning the data returned (like a `User` object) is automatically converted into **JSON** format.

#### External assembly `@Configuration` and `@Bean`

While the annotations above are for **classes you wrote**, `@Configuration` is used when you need to manage **third-party classes** or perform complex setup logic that a simple `@Component` cannot handle. A class marked with `@Configuration` acts as a "factory" for beans.

Inside a `@Configuration` class, you define methods marked with **`@Bean`**. Spring calls these methods at startup and takes the returned object to store it in the container.

Example: Suppose you are using an external library for **JSON Parsing** (like Jackson's `ObjectMapper`). Since you didn't write the `ObjectMapper` class, you can't go inside its code and add `@Component`. Instead, you do this:

```java
@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper customMapper() {
        ObjectMapper mapper = new ObjectMapper();
        // Explicit setup: Tell the mapper to ignore unknown properties
        mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
        return mapper;
    }
}
```

It allows you to "bring in" external objects into the Spring ecosystem. It also ensures that the objects are **Singletons**; if five different classes ask for the `ObjectMapper`, Spring's `@Configuration` proxy ensures they all get the exact same instance, saving memory and ensuring consistent settings.

### Workflow

When the application starts, Spring doesn't know your classes exist. It uses a process called **Classpath Scanning** (triggered by `@ComponentScan`). Spring looks through every folder in your project (the packages). It inspects the bytecode of every class looking for "Stereotype Annotations" like `@Component`, `@Service`, or `@Configuration`. It doesn't create objects yet. Instead, it creates a **BeanDefinition**—a "blueprint" or "recipe".

Once Spring has a map of all the "recipes" (BeanDefinitions), it begins creating the actual Java objects (Beans) using the **Java Reflection API**. It doesn't just create them in any order. It looks at the dependencies. If `Service A` needs `Service B`, Spring will try to create `Service B` first. 

It calls the constructor of your class. If you have a constructor annotated with `@Autowired`, it uses that; otherwise, it uses the default no-argument constructor. 
Note that java spring will put the dependency by type matching meaning if a field is wanting a type of `A` and springboot gets type of `A`. It will inject it. Since types are defined by classname it is important that you have unique classpath. 

In Spring, when you have multiple beans of the same type, the framework gets "confused" because it doesn't know which one to inject—a situation known as the **NoUniqueBeanDefinitionException**. To manage this, Spring provides three primary tools: `@Primary`, `@Qualifier`, and `@Resource`.

```java
public interface MessageService {
    void sendMessage(String msg);
}

@Component
public class EmailService implements MessageService {
    public void sendMessage(String msg) { System.out.println("Email: " + msg); }
}

@Component
public class SMSService implements MessageService {
    public void sendMessage(String msg) { System.out.println("SMS: " + msg); }
}
```

The `@Primary` annotation tells Spring to use a specific bean by default when multiple options are available. Think of it as the "tie-breaker."

```java
@Component
@Primary // This will be chosen by default
public class EmailService implements MessageService { ... }
```

The `@Qualifier` annotation allows you to name your beans and specify exactly which name you want to inject at the point of use.

```java
@Component("emailBean")
public class EmailService implements MessageService { ... }

@Component("smsBean")
public class SMSService implements MessageService { ... }

@Component
public class NotificationController {

    private final MessageService messageService;

    // We specify exactly which bean we want here
    public NotificationController(@Qualifier("emailBean") MessageService messageService) {
        this.messageService = messageService;
    }
}
```

Unlike `@Autowired` (which matches primarily by **type**), `@Resource` (from `jakarta.annotation`) matches primarily by **name**. It’s a cleaner way to handle multiple beans if you already know the bean name.

```java
@Resource(name = "smsBean")
private MessageService messageService;
```

Note that this can also happen with the external libraries. 

```java
@Configuration
public class AppConfig {

    @Bean
    @Primary // Default choice if no qualifier is specified
    public MessageService emailService() {
        return new EmailService();
    }

    @Bean
    public MessageService smsService() {
        return new SMSService();
    }
}
```

If you need the non-primary bean (the `smsService`), you must use the `@Qualifier` and match it to the **method name** from your configuration class.

```java
@Service
public class AlertService {

    private final MessageService messageService;

    // Matches the method name 'smsService' in AppConfig
    public AlertService(@Qualifier("smsService") MessageService messageService) {
        this.messageService = messageService;
    }
}
```

#### How will spring inject values to beans - 

There are two ways for this - 

- First one is using using property source like `application.properties`.. If you have a field like `@Value("${server.port}") private int port;`, Spring:

1. Reads the properties file.
2. Finds the key `server.port`.
3. Converts the string "8080" into an integer.
4. Uses **Reflection** to "force" that value into the private field, even if there is no setter method.

The `@Value` annotation in Spring is used to inject values into fields in Spring-managed beans. These values can come from property files (like `application.properties`), system environment variables, or even expressions.

The most common use case is pulling a value from your `application.properties` or `application.yml` file.

```properties
app.display.name=My Cool App
app.timeout=5000
```

Now the value will be injected while creation. 

```java
@Component
public class AppSettings {

    @Value("${app.display.name}")
    private String appName;

    @Value("${app.timeout}")
    private int timeout;

    public void printConfig() {
        System.out.println("App: " + appName + " (Timeout: " + timeout + "ms)");
    }
}
```

We can also define default values here.

```java
// If 'app.color' is missing, it defaults to 'Blue'
@Value("${app.color:Blue}")
private String themeColor;
```

Second is from `IOC` container where the field is mostly complex object. Spring:

1. Looks at the **Type** of the field (e.g., `UserRepository`).
2. Searches its internal "Registry" (a Map of already-created beans) to find an instance of that type.
3. Injects that instance into the field.

### Constructor vs field injection

In spring dependency injection is the process of providing the class with its dependencies there are two important ways to do it. Constructor and field injection. 

### Field injection

You simply put the `@Autowired` annotation directly on the private field. 

```java
@Service
public class ReportService {

    @Autowired
    private EmailService emailService; // Injected directly into the field

    public void generateReport() {
        emailService.sendMessage("Report is ready!");
    }
}
```

In this model, Spring first creates the object using a default (no-argument) constructor and then "reaches back in" to populate the fields. Spring calls `new MyClass()` (default constructor) → The object exists but all `@Autowired` fields are `null` → Spring uses **Java Reflection** to bypass `private` modifiers → Spring "injects" the values into the fields.

Because the object is created _before_ the fields are populated, there is a tiny window of time (or specific lifecycle methods like the constructor itself) where the dependencies are `null`. If you try to use a field inside your constructor, the app will crash with a `NullPointerException`.

It makes it easy to add 20 dependencies to a class without noticing, whereas a constructor with 20 arguments would immediately look like a "code smell" that needs refactoring.

You cannot easily test this class in a plain JUnit test without starting the entire Spring Container or using a specialized "Reflection Test Utility," because you can't pass the dependencies in manually.  Reason being the field is private and has no setter. 

If you _insist_ on using field injection, you are forced to use `@SpringBootTest` or `@ExtendWith(MockitoExtension.class)` with `@InjectMocks`. This tells the testing framework to use **Reflection** to forcibly open the private field and insert the mock. While this works, it hides the fact that your class has a "hidden" dependency that isn't obvious from its public API. 

Finally if using field injection one can not make the field final for obvious reason that it needs to get set. 

### Setter injection 

This is used when the setter methods are declared so that instead of field injection. The values of any bean are injected via setter methods. 

### Constructor injection

You define the dependencies as parameters in the constructor. This method does not uses reflection api to bypass the private fields. 

```java
@Service
public class ReportService {

    private final EmailService emailService; // Can be marked 'final'

    // Spring 4.3+ automatically autowires if there is only one constructor
    public ReportService(EmailService emailService) {
        this.emailService = emailService;
    }

    public void generateReport() {
        emailService.sendMessage("Report is ready!");
    }
}
```

 Using `final` ensures the dependency cannot be changed after the bean is initialized. You can simply call `new ReportService(mockEmailService)` in a plain JUnit test. No Spring required.
 The compiler ensures that you cannot create the object without providing its dependencies (prevents `NullPointerException`).

In constructor injection, the dependencies are provided at the moment the object is instantiated. Spring calculates the dependency graph, finds the required beans, and passes them as arguments to the class constructor.

Spring uses standard Java constructor calls. It doesn't need to "hack" into your private fields after the object exists.

If Class A needs Class B, and Class B needs Class A, Spring will throw a `BeanCurrentlyInCreationException` immediately at startup. This forces you to fix bad architectural design early.

**Modern Spring Best Practice is Constructor Injection.** It is more "explicit." It guarantees that your object is never in an inconsistent state, and it allows you to write code that is decoupled from the framework. Field injection is often discouraged today because it hides complexity and makes unit testing significantly more difficult.

## Application context

The Application Context is the **brain** of your Spring app. Without it, your `@Autowired` annotations are just empty comments, and your `@Value` properties are just strings that never get read. While we often call it a "container," it is technically an advanced interface that manages the entire lifecycle of your objects (Beans).

The Application Context performs four major roles that keep your app running:

- **Bean Factory:** It creates and assembles objects (Beans) based on your configurations.
- **Dependency Injection (DI):** it "wires" objects together so you don't have to use the `new` keyword.
- **Resource Loading:** It provides a unified way to read files (like `application.properties` or XML files) from the classpath or the web.
- **Event Publication:** It allows beans to talk to each other using an "Event/Listener" model (e.g., "UserRegisteredEvent").

The Application Context maintains a **Bean Definition Registry**. When Spring starts, it doesn't just create objects randomly; it follows a precise recipe:

1. **Scanning:** It looks for `@Component`, `@Service`, or `@Bean` annotations.
2. **Metadata Creation:** It creates a `BeanDefinition` for each class (noting its scope, lazy/eager loading, and dependencies).
3. **The Singleton Cache:** By default, Spring creates **one instance** of each bean and stores it in a internal `Map<String, Object>`. When you `@Autowire` a service, Spring just looks up the instance in this map and hands it to you.


We can also work with applicationContext 

```java
@SpringBootApplication
public class MyMainApp {
    public static void main(String[] args) {
        // 'context' represents the fully initialized ApplicationContext
        ApplicationContext context = SpringApplication.run(MyMainApp.class, args);

        // Manually grabbing a bean by its type
        MyService service = context.getBean(MyService.class);
        service.doSomething();
        
        // Checking if a bean exists
        boolean exists = context.containsBean("emailService");
    }
}
```

Every Spring Boot app starts with a standard Java `public static void main` method. This is the only part of the code that behaves like a "normal" Java program.

```java
@SpringBootApplication // This is the "Magic Switch"
public class MyStoreApplication {
    public static void main(String[] args) {
        // This line hands control over to the Spring Framework
        SpringApplication.run(MyStoreApplication.class, args);
    }
}
```

When `SpringApplication.run()` is called, the following happens in order:

1. **Stopwatch Starts:** Spring starts a timer to tell you how fast it booted.
2. **Environment Setup:** It looks for your `application.properties` or `yml` files and system environment variables.
3. **The Banner:** It prints that famous "Spring" ASCII art in your console.
4. **Context Creation:** It creates the **Application Context** (the "Bucket" we discussed earlier).
5. **The Component Scan:** This is the most important part. Spring looks at the package where your `main` class is located and "scans" all sub-packages for classes marked with `@Component`, `@Service`, `@RestController`, etc.
