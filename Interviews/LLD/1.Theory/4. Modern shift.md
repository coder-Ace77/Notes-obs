Design patterns came in 1990s and were meant to be solving the general problems faced by developers at that time. However now the software design has shifted since languages now provide multiple of these features by default. 

#### Solving creational design pattern

A normal solution for the payment gateway problem can look like this. Here we are uisng simple factory. 

```java
interface PaymentGateway {
    void charge(double amount);
}

class StripeGateway implements PaymentGateway {
    public void charge(double amount) {
        System.out.println("Charging via Stripe: " + amount);
    }
}

class RazorpayGateway implements PaymentGateway {
    public void charge(double amount) {
        System.out.println("Charging via Razorpay: " + amount);
    }
}

class PaymentGatewayFactory {
    public static PaymentGateway create(String type) {
        if (type.equals("stripe")) {
            return new StripeGateway();
        } else if (type.equals("razorpay")) {
            return new RazorpayGateway();
        }
        throw new IllegalArgumentException("Unknown gateway: " + type);
    }
}
```

However note that factory  has lots of if/else. To solve this we developed `Registry pattern`. where implementations register themselves at startup, and the factory just looks them up.

```java
class PaymentGatewayRegistry {
    private static Map<String, Supplier<PaymentGateway>> registry = new HashMap<>();

    public static void register(String type, Supplier<PaymentGateway> supplier) {
        registry.put(type, supplier);
    }

    public static PaymentGateway create(String type) {
        Supplier<PaymentGateway> supplier = registry.get(type);
        if (supplier == null) {
            throw new IllegalArgumentException("Unknown gateway: " + type);
        }
        return supplier.get();
    }
}

// Somewhere during application startup:
PaymentGatewayRegistry.register("stripe", StripeGateway::new);
PaymentGatewayRegistry.register("razorpay", RazorpayGateway::new);
```

And then registry can be used to call to get actual objects. This solves problem elegantly but if we have hundred of objects to manage we can not register manually since it will be a hassle to first corretly register then in the some format. Also don't forget the some objects need other objects to get created so ordering is important. Modern soluution is dependency injection frameworks. 

**Dependency Injection** flips the responsibility of "who creates the object" outward. Instead of a class creating its own dependencies (`new StripeGateway()` inside itself), the dependencies are handed to it from the outside — usually through the constructor.

```java
class PaymentService {
    private final PaymentGateway gateway;

    // The gateway is "injected" through the constructor.
    // PaymentService no longer decides which gateway to use.
    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }

    public void process(double amount) {
        gateway.charge(amount);
    }
}
```

This alone is called **manual dependency injection**, and it is already a big win — `PaymentService` is now completely decoupled from any specific gateway implementation. But someone, somewhere, still has to build the object graph: create the `StripeGateway`, pass it into `PaymentService`, pass that into whatever needs `PaymentService`, and so on, all the way up. In a large application, this wiring code — often called the "composition root" — becomes enormous and fragile.

This is exactly the gap that **DI containers** fill. A DI container is a piece of framework infrastructure that automatically builds the entire object graph for you, based on some configuration or, more commonly today, based on annotations placed directly on your classes.

Here is the same example using Spring, the most widely used DI framework in the Java ecosystem:

```java
@Component
class StripeGateway implements PaymentGateway {
    public void charge(double amount) {
        System.out.println("Charging via Stripe: " + amount);
    }
}

@Service
class PaymentService {

    private final PaymentGateway gateway;

    @Autowired
    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }

    public void process(double amount) {
        gateway.charge(amount);
    }
}
```

Notice what disappeared: there is no factory class, no registry, and no manual `new PaymentService(new StripeGateway())` anywhere. The `@Component` annotation tells Spring, "this class is a candidate object you can create and hand out." The `@Autowired` annotation tells Spring, "whenever something needs a `PaymentService`, first find or create a `PaymentGateway` and pass it in automatically." Spring scans your codebase at startup, figures out the dependency graph, and constructs everything in the correct order — this whole mechanism is often called **Inversion of Control (IoC)**, because the control over object creation has been inverted from your code to the framework.

The Factory pattern is not "wrong" — in fact, DI containers use factory-like logic _internally_ to actually construct objects. What changed is that this factory logic used to be something **you** wrote by hand, and now it is something the **framework** provides as infrastructure. The creational pattern did not vanish; it moved from your application code into the platform underneath your application code.

#### The Structural Shift

Consider older decorator pattern. 

```java 
interface Coffee {
    double cost();
    String description();
}

class SimpleCoffee implements Coffee {
    public double cost() { return 2.0; }
    public String description() { return "Coffee"; }
}

// Abstract decorator: it "wraps" a Coffee and also IS a Coffee.
abstract class CoffeeDecorator implements Coffee {
    protected Coffee wrapped;
    public CoffeeDecorator(Coffee wrapped) {
        this.wrapped = wrapped;
    }
}

class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee wrapped) { super(wrapped); }
    public double cost() { return wrapped.cost() + 0.5; }
    public String description() { return wrapped.description() + " + Milk"; }
}

class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee wrapped) { super(wrapped); }
    public double cost() { return wrapped.cost() + 0.2; }
    public String description() { return wrapped.description() + " + Sugar"; }
}
```

To get "coffee with milk and sugar," you wrap one object inside another, inside another:

```java
Coffee order = new SugarDecorator(new MilkDecorator(new SimpleCoffee()));
System.out.println(order.description() + " = " + order.cost());
// Output: Coffee + Milk + Sugar = 2.7
```

This works, and it is elegant _in theory_, but look at the sheer number of classes we needed: an interface, a base decorator class, and one full class per behavior. If you wanted five optional add-ons — milk, sugar, whipped cream, extra shot, caramel — you would need five separate decorator classes, each repeating almost the same boilerplate of a constructor and two overridden methods.

Modern languages treat functions as **first-class citizens** — meaning a function can be stored in a variable, passed as an argument, and returned from another function, exactly like any other value such as a number or a string.

Here is the exact same coffee problem solved in JavaScript, using plain functions:

```js 
function simpleCoffee() {
  return { cost: 2.0, description: "Coffee" };
}

function withMilk(coffeeFn) {
  return function () {
    const coffee = coffeeFn();
    return { cost: coffee.cost + 0.5, description: coffee.description + " + Milk" };
  };
}

function withSugar(coffeeFn) {
  return function () {
    const coffee = coffeeFn();
    return { cost: coffee.cost + 0.2, description: coffee.description + " + Sugar" };
  };
}

const order = withSugar(withMilk(simpleCoffee))();
console.log(`${order.description} = ${order.cost}`);
// Output: Coffee + Milk + Sugar = 2.7
```

There is no interface, no abstract class, and no inheritance hierarchy anywhere. `withMilk` and `withSugar` are just functions that take a function and return a new function — this idea is called a **higher-order function**, and it is the functional-programming equivalent of the Decorator pattern. Adding a sixth add-on means writing one small function, not one entire class.

**Python takes this even further with its `@decorator` syntax**, which is language-level sugar built exactly for this use case:

```python
def with_logging(func):
    def wrapper(*args, **kwargs):
        print(f"Calling {func.__name__} with {args}")
        result = func(*args, **kwargs)
        print(f"{func.__name__} returned {result}")
        return result
    return wrapper

@with_logging
def add(a, b):
    return a + b

add(3, 4)
# Output:
# Calling add with (3, 4)
# add returned 7
```

Similar kind of thing happened with the `strategy pattern`. 

#### The Behavioral Shift

The **Observer pattern** solves a very common need: "When something happens in one part of my system, I want other parts to be notified automatically, without those parts being tightly coupled to each other."

classical observer pattern 

```java 
interface Observer {
    void update(float temperature);
}

class WeatherStation {
    private List<Observer> observers = new ArrayList<>();
    private float temperature;

    public void addObserver(Observer o) {
        observers.add(o);
    }

    public void setTemperature(float temp) {
        this.temperature = temp;
        notifyObservers();
    }

    private void notifyObservers() {
        for (Observer o : observers) {
            o.update(temperature);
        }
    }
}

class PhoneDisplay implements Observer {
    public void update(float temperature) {
        System.out.println("Phone display: " + temperature + "°C");
    }
}

WeatherStation station = new WeatherStation();
station.addObserver(new PhoneDisplay());
station.setTemperature(25.0f);
// Output: Phone display: 25.0°C
```

This works fine for a single, simple event like "temperature changed." But real-world systems rarely deal with just one event stream in isolation — they deal with sequences of asynchronous operations. Consider fetching a user from a database, then fetching their orders, then calculating a total, where each step depends on the previous one finishing, and each step might fail. Using plain callback-based Observers for this kind of chained, asynchronous work quickly leads to deeply nested callbacks, sometimes called **"callback hell"**:

```java
getUser(userId, function (user) {
  getOrders(user.id, function (orders) {
    calculateTotal(orders, function (total) {
      console.log("Total: " + total);
      // If any of these three steps can fail, you now need
      // an error-handling callback at every single level too.
    });
  });
});
```

**Promises** were introduced specifically to flatten this nested structure. A `Promise` represents "a value that will exist eventually" — either successfully (resolved) or with an error (rejected). Instead of passing callbacks deeper and deeper, you chain `.then()` calls at the same nesting level

```js
getUser(userId)
  .then(user => getOrders(user.id))
  .then(orders => calculateTotal(orders))
  .then(total => console.log("Total: " + total))
  .catch(error => console.error("Something failed:", error));
```

Modern JavaScript goes one step further with `async`/`await`, which lets asynchronous code _read_ almost exactly like ordinary, synchronous code:

```js
async function showTotal(userId) {
  try {
    const user = await getUser(userId);
    const orders = await getOrders(user.id);
    const total = await calculateTotal(orders);
    console.log("Total: " + total);
  } catch (error) {
    console.error("Something failed:", error);
  }
}
```

The `await` keyword tells the JavaScript engine, "pause this function here until the promise resolves, but don't block anything else in the program while waiting." This "don't block anything else" part is powered by something called the **Event Loop** — the mechanism that lets a single-threaded language like JavaScript handle thousands of pending operations (network calls, timers, file reads) at once without needing separate threads for each one. Instead of a thread sitting idle while waiting for a database response, the event loop parks that particular task, goes and does other useful work, and comes back to resume the paused task the moment its result is ready. This is fundamentally the same underlying idea as the Observer pattern — "notify me when something is ready" — just built directly into the language runtime instead of being hand-coded with Subject and Observer classes.

Promises and async/await are great for a _single_ eventual value. But what about a continuous _stream_ of values over time — like mouse movements, keystrokes, WebSocket messages, or stock price ticks? This is where **Reactive Streams**, popularized by libraries like **RxJS** (JavaScript) and **Project Reactor** (Java), come in. Their core building block is the **Observable** — conceptually a supercharged version of the classic Subject, but designed specifically to represent an ongoing sequence of values, with built-in tools to transform, filter, and combine those values.

```js
import { fromEvent } from 'rxjs';
import { map, filter, debounceTime } from 'rxjs/operators';

const searchBox = document.getElementById('search');

fromEvent(searchBox, 'input').pipe(
  map(event => event.target.value),      // extract just the text typed
  filter(text => text.length > 2),        // ignore very short queries
  debounceTime(300)                       // wait for typing to pause
).subscribe(text => {
  console.log("Searching for:", text);
});
```

Compare this to what the classic Observer pattern would have required: you would need to manually track "has enough time passed since the last keystroke," manually check the string length before notifying anyone, and manually extract the text from the raw event — all as extra `if` statements sitting inside your `notifyObservers()` method. RxJS instead gives you `.pipe()`, which lets you chain small, reusable **operators** (`map`, `filter`, `debounceTime`, and dozens of others) directly onto the stream of events. Each operator does one clear thing, and you assemble a whole pipeline out of small building blocks — very similar in spirit to how we chained decorator functions in Part 2, but applied to _events over time_ instead of _values right now_.

## Cloud and distributed patterns 

Everything we have covered so far — design patterns, dependency injection, decorators, reactive streams — assumes your application lives inside one process, running on one machine, talking to itself. Cloud systems break that assumption completely. A single "checkout button" click on an e-commerce site might travel through a load balancer, hit an authentication service, call an inventory service, call a payment service, call a shipping service, and write to three different databases — all running on different machines, possibly in different data centers, possibly failing independently of one another at any moment.

This is the world of **distributed systems**, and it introduces problems that simply do not exist in a single-process application. What happens if the payment service is slow to respond — do you wait forever? What happens if a request needs to be routed to one of fifty different microservices — does every client need to know all fifty addresses? What happens if a multi-step transaction succeeds on the first three services but fails on the fourth — how do you undo the first three, since there is no single database transaction spanning all of them? And what happens when one service needs to tell twenty other services "something happened," without directly calling all twenty of them one by one?

#### Resilience and routing

##### Circuit breaker 

Picture an e-commerce backend with three microservices: `OrderService`, `InventoryService`, and `PaymentService`. `OrderService` calls `PaymentService` for every single checkout request. Now imagine `PaymentService` starts running slowly — maybe its database is overloaded — and every call to it now takes 30 seconds to time out instead of the usual 200 milliseconds. 

Here is where it gets dangerous. `OrderService` keeps sending requests to `PaymentService`, because from `OrderService`'s point of view, nothing has technically failed yet it is just waiting. But now every incoming checkout request to `OrderService` is also stuck waiting 30 seconds. `OrderService`'s own thread pool or connection pool fills up with requests that are all just sitting there, waiting on a service that is not going to respond in time. Eventually, `OrderService` itself becomes unresponsive not because anything is wrong with `OrderService`'s own code, but because it kept faithfully calling a broken dependency. This is called a **cascading failure**: one slow or broken service drags down every service that depends on it, like dominoes falling.

The Circuit Breaker pattern borrows its name directly from electrical circuit breakers in your house. If too much current flows through a wire, the physical circuit breaker "trips" and cuts off the flow entirely, protecting the rest of the house from damage — instead of letting the fault keep spreading. A software Circuit Breaker does the same thing for service calls: if a downstream service keeps failing, the circuit breaker stops sending it requests entirely, for a while, and immediately returns a fast failure or a fallback response instead.

A circuit breaker has three distinct states, and understanding these three states is the entire key to understanding the pattern:

- **Closed** — the normal state. Requests flow through to the downstream service as usual. The circuit breaker is quietly counting failures and successes in the background.
- **Open** — the tripped state. Once failures cross a defined threshold (for example, "5 failures within the last 10 seconds"), the circuit breaker "opens." While open, it does **not** call the downstream service at all — it fails immediately, or returns a fallback value, saving both services from wasted effort.
- **Half-Open** — after a cooldown period, the circuit breaker cautiously allows a small number of test requests through, to check whether the downstream service has recovered. If those test requests succeed, the breaker moves back to **Closed**. If they fail again, it goes straight back to **Open** and waits longer before trying again.

Here is a simplified circuit breaker implemented from scratch in Python

```python
import time

class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=10):
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.failure_count = 0
        self.state = "CLOSED"
        self.opened_at = None

    def call(self, func, *args, **kwargs):
        if self.state == "OPEN":
            if time.time() - self.opened_at > self.recovery_timeout:
                self.state = "HALF_OPEN"
            else:
                raise Exception("Circuit is OPEN — failing fast, not calling downstream service")

        try:
            result = func(*args, **kwargs)
        except Exception as e:
            self.failure_count += 1
            if self.failure_count >= self.failure_threshold:
                self.state = "OPEN"
                self.opened_at = time.time()
            raise e
        else:
            # A successful call resets everything — the service has proven it's healthy.
            self.failure_count = 0
            self.state = "CLOSED"
            return result


def call_payment_service():
    # Imagine this sometimes raises an exception when PaymentService is struggling.
    raise Exception("Payment service timeout")

breaker = CircuitBreaker(failure_threshold=3, recovery_timeout=10)

for i in range(5):
    try:
        breaker.call(call_payment_service)
    except Exception as e:
        print(f"Attempt {i+1} failed: {e}")
```

In real production systems, you rarely write this from scratch — you use a battle-tested library. Java developers commonly use **Resilience4j**. 

### API gateway pattern 

In microservice architecture there is no one unified backend rather there are lots of them. Instead of client application knowing all the backends we have api gateway. 

An **API Gateway** sits in front of all your microservices as a single, unified entry point. Every client — mobile app, web app, third-party integration — talks only to the gateway. The gateway then handles the messy work of figuring out which internal service should actually handle the request, and routes it there.

Beyond simple routing, an API Gateway commonly takes on several other cross-cutting responsibilities that would otherwise have to be duplicated inside every single microservice:

- **Authentication and authorization** — checking the user's token once, at the gateway, instead of every downstream service re-implementing token validation.
- **Rate limiting** — preventing a single client from overwhelming the system with too many requests per second.
- **Request routing** — sending `/orders/*` requests to `OrderService`, `/users/*` requests to `UserService`, and so on.
- **Response aggregation** — combining data from multiple services into one response, so the client does not need to make five separate calls just to render one screen.
- **Protocol translation** — a client might speak plain HTTP/JSON, while an internal service speaks gRPC; the gateway can translate between them.

### SAGA pattern 

#### The problem: transactions across multiple databases

In a single-database application, if you need to do multiple related writes together say, deduct money from one account and add it to another you wrap them in a **database transaction**.

Distributed systems break this guarantee completely. Consider booking a trip that involves three separate microservices, each with its own separate database:

1. `FlightService` — books a flight seat.
2. `HotelService` — books a hotel room.
3. `PaymentService` — charges the customer's card.

There is no single database transaction that can span all three of these services, because they are entirely separate systems, sometimes running on entirely separate database technologies. So what happens if the flight booking succeeds, the hotel booking succeeds, but the payment fails?

The solution: the Saga pattern

A **Saga** breaks a large, multi-service transaction into a sequence of smaller, local transactions, where each local transaction happens inside a single service and updates only that service's own database. Crucially, every step in the saga also has a matching **compensating transaction** — an action that undoes the effect of that step, in case a later step in the sequence fails. So in case of booking a flight compensation action is cancelling flight. So if payment fails it does not stop there we also do compensating actions more importantntly in the reverse direction. 

There are two ways to go with saga. 

**1. Choreography-based Saga** - There is no central coordinator. Each service listens for events from the previous service and reacts on its own, publishing its own event when it finishes, which triggers the next service in line.

```
FlightService  ──"FlightBooked" event──▶  HotelService
HotelService   ──"HotelBooked" event───▶  PaymentService
PaymentService ──"PaymentFailed" event─▶  HotelService (compensate)
HotelService   ──"HotelCancelled" event▶  FlightService (compensate)
```

This is simple to set up initially, but it can become hard to follow as the number of services grows, because the overall "story" of the saga is scattered across many services instead of living in one place.

2. **Orchestration-based Saga** — a central **orchestrator** (a different service all together) explicitly tells each service what to do, step by step, and explicitly decides when to trigger compensating actions. In this case our orchestrator code will be living inside order service which orchestrates all the down services. 

```python 
class TripBookingSaga:
    def __init__(self, flight_service, hotel_service, payment_service):
        self.flight_service = flight_service
        self.hotel_service = hotel_service
        self.payment_service = payment_service
        self.completed_steps = []

    def execute(self, trip_request):
        try:
            self.flight_service.book(trip_request.flight)
            self.completed_steps.append("flight")

            self.hotel_service.book(trip_request.hotel)
            self.completed_steps.append("hotel")

            self.payment_service.charge(trip_request.payment)
            self.completed_steps.append("payment")

            print("Trip booked successfully!")

        except Exception as e:
            print(f"Saga failed at step after: {self.completed_steps}. Rolling back...")
            self._compensate(trip_request)

    def _compensate(self, trip_request):
        # Undo whatever succeeded, in reverse order.
        if "payment" in self.completed_steps:
            self.payment_service.refund(trip_request.payment)
        if "hotel" in self.completed_steps:
            self.hotel_service.cancel(trip_request.hotel)
        if "flight" in self.completed_steps:
            self.flight_service.cancel(trip_request.flight)
```

The orchestrator service holds the saga state (`completed_steps`) — in production this is usually persisted (DB row, not just an in-memory list) so that if the orchestrator process itself crashes mid-saga, it can resume or compensate on restart. Compensating actions (`cancel`, `refund`) should be idempotent, and the calls to the services should have retry logic, since network calls fail.

### Event driven pipelines 

The problem: tight coupling through direct service calls

Suppose `OrderService` needs to tell several other parts of the system when a new order is placed: `InventoryService` needs to reduce stock, `NotificationService` needs to email the customer, `AnalyticsService` needs to log the sale, and `RecommendationService` needs to update the user's purchase history for future recommendations.

The naive approach is for `OrderService` to directly call all four of these services, one after another, every time an order is placed:

```python
def place_order(order):
    save_order(order)
    inventory_service.reduce_stock(order.items)
    notification_service.send_confirmation_email(order.user)
    analytics_service.log_sale(order)
    recommendation_service.update_history(order.user, order.items)
```

Two issues first tight coupling and then if we want to add something new we need to add the code in this `place_order` as well. 

In an event-driven architecture, `OrderService` does not call anyone directly. Instead, it simply publishes an event a small message describing "what happened" to a **message broker** (common examples include Apache Kafka, RabbitMQ, and AWS SQS/SNS). Any service that cares about that event can independently **subscribe** to it and react on its own schedule, without `OrderService` ever knowing they exist.

Example in kafka 

```python
from kafka import KafkaProducer
import json

producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)

def place_order(order):
    save_order(order)
    producer.send('order-events', {
        'event_type': 'OrderPlaced',
        'order_id': order.id,
        'user_id': order.user_id,
        'items': order.items,
    })
    print(f"Published OrderPlaced event for order {order.id}")
```

And here is what a completely independent service — say, `NotificationService` — looks like when consuming that same event. Notice that this code lives in a totally separate application, possibly written in a different programming language altogether, and `OrderService` has no idea it exists:

```python 
from kafka import KafkaConsumer
import json

consumer = KafkaConsumer(
    'order-events',
    bootstrap_servers='localhost:9092',
    value_deserializer=lambda v: json.loads(v.decode('utf-8'))
)

for message in consumer:
    event = message.value
    if event['event_type'] == 'OrderPlaced':
        send_confirmation_email(event['user_id'], event['order_id'])
```

Istio is wave 1 because it installs the CRDs that almost everything later uses — the comment on the parent Application says exactly that. oauth2-proxy is wave 2 because the Istio gateway configuration references it. Profiles are wave 6 because the profile controller creates user namespaces that wave-7 components then populate. PodDefaults are wave 8 because they inject configuration into notebook pods and must exist before a notebook is ever created. The ingress is wave 9, last, because exposing the platform before its backends are healthy produces a public URL that returns errors.

### CQRS (Command Query Responsibility Segregation)

In almost every application you have built so far, you probably used the same class, the same database table, and the same ORM model for both writing data and reading it back. 

Example 

```python
class Product:
    def __init__(self, id, name, price, stock_count, category):
        self.id = id
        self.name = name
        self.price = price
        self.stock_count = stock_count
        self.category = category

def update_stock(product_id, quantity_sold):
    product = db.query(Product).get(product_id)
    product.stock_count -= quantity_sold
    db.commit()

def get_product_page(product_id):
    product = db.query(Product).get(product_id)
    return render_page(product)
```

This looks completely reasonable, and for a small application, it is. But as the system grows, the **write side** and the **read side** of this same data start to pull in genuinely opposite directions. Writing data (a "command," like "reduce stock by 3 units") usually cares about **correctness and validation**: you must check that stock never goes negative, that the price change is authorized, that business rules are respected.

Reading data (a "query," like "show me the product listing page with price, reviews, stock badge, and related products") usually cares about **speed and shape**: you want a single, fast response that already has all the information laid out exactly how the UI needs it, often by pulling data from _multiple_ different sources the product table, a reviews table, a recommendations service, a currently-viewing counter. Trying to satisfy both needs with one single `Product` class and one single database table means you constantly have to compromise. Either your write model gets bloated with denormalized fields it does not actually need just to make reads faster, or your reads stay slow and require expensive joins across many tables every single time a page loads.

This mismatch gets much worse at scale. Read traffic on something like a product page is often a hundred or a thousand times higher than write traffic — thousands of people browse a product for every one person who actually buys it or a warehouse worker who actually updates stock. If reads and writes share the exact same database and the exact same model, you cannot scale them independently: you are forced to scale your entire database up just to handle read traffic, even though your actual write logic barely needs any extra capacity at all.

**CQRS** stands for **Command Query Responsibility Segregation**. The core idea, stripped down to one sentence, is this: _use a completely separate model for writing data (a "Command" model) than the one you use for reading data (a "Query" model), instead of forcing one model to do both jobs._

"Command" here just means "an instruction to change something" think `PlaceOrder`, `ReduceStock`, `UpdatePrice` as opposed to a "Query," which just means "a request to read something without changing it" think `GetProductDetails`, `GetOrderHistory`.

Here is the same product example, now split using CQRS. Notice there are now two separate models, two separate code paths, and — in a fully realized version of this pattern — even two separate databases.

**The Command side** — focused purely on correctness, validation, and business rules:

```python
class ReduceStockCommand:
    def __init__(self, product_id, quantity):
        self.product_id = product_id
        self.quantity = quantity

class ProductCommandHandler:
    def handle(self, command: ReduceStockCommand):
        product = write_db.query(ProductWriteModel).get(command.product_id)

        if product.stock_count < command.quantity:
            raise Exception("Not enough stock available")

        product.stock_count -= command.quantity
        write_db.commit()

        # Publish an event so the read side can update itself later.
        event_bus.publish("StockReduced", {
            "product_id": command.product_id,
            "new_stock_count": product.stock_count,
        })
```

**The Query side** — a completely separate, denormalized model built purely for fast reading, shaped exactly like the UI needs it, often stored in a different kind of database entirely (for example, a document store or a cache, instead of a relational database)

```python
class ProductPageReadModel:
    """
    This is deliberately denormalized — it already contains everything
    the product page needs in one place, so reading it never requires a join.
    """
    def __init__(self, product_id, name, price, stock_badge, average_rating, related_product_ids):
        self.product_id = product_id
        self.name = name
        self.price = price
        self.stock_badge = stock_badge          # e.g. "In Stock", "Only 2 left", "Out of Stock"
        self.average_rating = average_rating
        self.related_product_ids = related_product_ids

def get_product_page(product_id):
    # This single, fast lookup replaces what would otherwise be several joins.
    return read_db.query(ProductPageReadModel).get(product_id)
```

The two sides are synced through events using event driven architecture. When the command side successfully reduces stock, it publishes a `StockReduced` event, and a separate listener updates the read model in the background. 

```python
def on_stock_reduced(event):
    read_model = read_db.query(ProductPageReadModel).get(event["product_id"])
    new_count = event["new_stock_count"]

    if new_count == 0:
        read_model.stock_badge = "Out of Stock"
    elif new_count <= 5:
        read_model.stock_badge = "Only a few left"
    else:
        read_model.stock_badge = "In Stock"

    read_db.commit()

event_bus.subscribe("StockReduced", on_stock_reduced)
```

The gains here are substantial once a system grows past a certain size:

- **Independent scaling.** Since read traffic is usually far higher than write traffic, you can run many more copies of the read-side database (or use a fast cache) without touching the write-side database at all.
- **Optimized shapes for each job.** The write model can stay simple, normalized, and focused on validation. The read model can be as denormalized and pre-computed as it needs to be, since it exists purely to be read quickly.
- **Different technology per side.** It is very common to use a strongly consistent relational database (like PostgreSQL) for the write side, and a fast document store or search index (like Elasticsearch or a Redis-backed cache) for the read side, since reads and writes genuinely have different technical needs.

Cons of using it are - 
- **Eventual consistency between the two sides.** There is a small window of time between when a command updates the write model and when the corresponding event finishes updating the read model. A customer could, in theory, reduce stock to zero and then immediately view a product page that briefly still says "In Stock," until the read model catches up.
- **More moving parts.** You now have two models, an event bus connecting them, and two things that can each go wrong independently, instead of one simple model.

### Event sourcing 

Idea is simple instead of storing current state as most of the databases do what we instead do is to store the events. The current state is not stored at all it is derived from the events and it becomes the source of truth. Now it can happen that lots of events are processed to get to the current state so what we do is to take the snapshot upto a certain event. 

```python
class BankAccount:
    def __init__(self):
        self.balance = 0
        self.account_id = None

    def apply(self, event):
        """
        Each event knows how to modify the account's state.
        This is the only place state is ever changed — always by replaying an event.
        """
        if event["event_type"] == "AccountOpened":
            self.account_id = event["account_id"]
        elif event["event_type"] == "MoneyDeposited":
            self.balance += event["amount"]
        elif event["event_type"] == "MoneyWithdrawn":
            self.balance -= event["amount"]

def rebuild_account(account_id):
    events = event_store.get_events_for(account_id)  # fetched in chronological order
    account = BankAccount()
    for event in events:
        account.apply(event)
    return account

account = rebuild_account(101)
print(account.balance)  # 4500 — derived, not stored directly
```

Writing new data works by simply appending a new event to the end of the log you never update or delete an existing event, only add new ones. 

Once you store data as events instead of current state, you immediately run into the exact problem CQRS was designed to solve: an event log is a _terrible_ format to query directly. Asking "show me all accounts with a balance over ₹10,000" against a raw event log would require rebuilding every single account from scratch, just to answer one simple query that is obviously impractical.

The natural pairing is to use Event Sourcing for the **write side** (the event log is your true, permanent source of truth), and to use CQRS to maintain a separate, fast, queryable **read model** that gets updated every time a new event is appended exactly the same "listen to an event, update a read-optimized copy" mechanism we already built for the product page example in Part 1.
