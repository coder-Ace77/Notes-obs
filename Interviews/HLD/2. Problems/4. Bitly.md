We need to design a url shortner service like bitly. 

## Functional requirements

- Users should be able to submit a long URL and receive a shortened version.
- Users should be able to access the original URL by using the shortened URL.
- Optional - Expireation time and custom alias.
- Out of scope - Analytics and auth
### Non functional requirements

- The system should ensure uniqueness for the short codes (each short code maps to exactly one long URL)
- The redirection should occur with minimal delay (< 100ms)
- The system should be reliable and available 99.99% of the time (availability > consistency)
- The system should scale to support 1B shortened URLs and 100M DAU

### Entities

- Original url
- Short url 
- User

## API

- Creating short urls 
```js
POST /urls

REQ_BODY = {
	"original_url":"https://...",
	"custom_alias":"...",
	"expiration_time":"..."
}

RES = {
	"shortened_url":"..."
}
```

- Go to end point
```js
GET /url/{short_code}

-- http - 302 redirect for the original url
```

### High level design

We will start with creating the short url. The way it will work is by generating a random shortcode of alphanumeric string. There are 52 diff alpha and 10 digits - 62 so we need approx - 8 chars. 

Secondly we need to be able to define the alias and we might need to look for it quickly to do that we can add indexing on the alias if present or not. 

For the redirect part is straight forward we can make checks for ttl and then we will send redirect codes - `301/302` to the browser along with orginal url. Browser will automatically make a request to that site. 

Now `301/302` differ-
- 302 is temporary redirect meaning dns/browser won't cache it. So each req will hit the shortner service.
- 301 is permanent redirect meaning it will be cached at dns level or browser.

In our case we may want to use `302` if we want every req to hit our servers and `301` is good if we want  to have the better cache.

### Deep dives

#### Creating short url

Now if alias is not proided how do we generate short code. Many different approaches can be made - 

- Use prefix of original url. May not work with same page
- Hash of original url and then prefix. -- better then do the base62 encoding
- Counter - Problem is the determines that we have seq nature and people may guess next or prev urls. Now people can know all the `original_code`. The solution is to use bijective function of current counter and return that code. This code is mapped to some other random base 62 encoded number so no way to predict next character.

Lets go over with the second hash based approach and use that. Howeer downside is that we need to check before updating. So write is going to be req may be two reads and one write. 
### Low latency redirect

Note that we have already added index on the alias part. Now this will mean constant time lookup. But still we will be hitting the disk which is much slower. So we need to introduce the inmemory cache we can simple work with read through lru cache. With this our design is complete. 

## Scale

`1B` urls and `100DAU`. Assuming each user to be going upto 1-2 req per day. Calculation says that `10^8/10^5` = `1000` req per second or `10k` say for peak. This kind of traffic can easily be beared by single server with good vertial server. We see that horizontal scaling is prob not required. As good server in amazon can prob handle this. 

Or if we want we may go ahead with microservice architecture as well. When doing so we can create two services as one needs to scale (read) and another write which does not scales. 

Now for scaling we can use application loadbalancer which can be configured on some threshold and move from there. 

Finally for the counter(if used) it needs to be consistent if write service is horizontally scaled. To do that we will be using redis counter. Which is inhernetly single threaded and works fine with atomic operations.
