### Functional requirement

- user should be able to view events
- Users should be able to search for events
- Users should be able to book tickets to events

### NFR

- Consistency in booking tickets No double booking
- The system should be scalable and able to handle high throughput in the form of popular events (10 million users, one event)
- The system should have low latency search (< 500ms)
- The system is read heavy, and thus needs to be able to support high read throughput (100:1)

### Core entities

 - Event
 - User
 - Performer
 - Venue
 - Ticket
 - Booking

#### API

```
GET /events/:eventId -> Event & Venue & Performer & Ticket[]

- tickets are to render the seat map on the Client
  // for the event seatmap
  
  
GET /events/search?keyword={keyword}&start={start_date}&end={end_date}&pageSize={page_size}&page={page_number} -> Event[] // showing search results


POST /bookings/:eventId -> bookingId
 {
   "ticketIds": string[], 
   "paymentDetails": ...
 } // booking a ticket
```

Now Flow of search - 

We will use simple search query wildcard matching for the search `select .. from event where description like %keyword%`

Event crud service will give back to us the events with seat map.

Finally we need booking so once a booking end point is hit we make that entry in db translate request to the third party and come back. 

Now booking flow will be a two phase process where we book the ticket this locks the ticket seat in a distributed lock redis this will be hold only for 10mins ttl. So if user books well and good however if not booked we will be able to make this seat available again after say 10 min as ttl will not be there. If booking is confirmed we will update status to booked and will be done. 

![[Pasted image 20260305215628.png]]

As for the search optimisation we can use the elastic search db which is optimised for the sarch , filter and other queries. We will populate the elastic search using cdc. 

![[Pasted image 20260305220430.png]]

Now how do we handle the popular events if we allow all the users to book and view a given event we might have so many users so that it will be quickly full and users will have very bad user experience. One thing may be we can do it is queue for the given event we will create a virtual waiting queue where the users will wait. We can allow the users to have the queue either at the view event or when booking on a given event. 

Finally since we have read to write ratio `100:1` we can simply cache the venue and performer.
