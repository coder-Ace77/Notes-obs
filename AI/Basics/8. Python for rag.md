Production-grade RAG pipelines live and die by two metrics: **Latency** (how fast can we fetch information?) and **Reliability** (is the data structured exactly as we expect?).

 - `asyncio` drastically reduces latency by fetching from multiple sources concurrently.
 - `Pydantic` guarantees reliability by validating external data and forcing LLMs to output strict, predictable JSON.

In a RAG system, the "Retrieval" phase is almost entirely I/O bound. You are waiting on network requests to Vector Databases (like Pinecone, Qdrant), web search APIs, or SQL databases. Doing this sequentially is a massive bottleneck.

If you query three different databases and each takes 1 second to respond, a synchronous pipeline takes 3 seconds. By using `asyncio.gather`, you fire all requests simultaneously, reducing the total time to just ~1 second.

## asyncio

Think of `asyncio` as a way to write "single-threaded concurrent code." It’s designed to handle I/O-bound tasks (like web requests or database queries) efficiently by allowing the program to do other things while waiting for data to return.

We  can start multiple i/o processes and run them and simultaneiusly get the results using asyncio package. 

```python
import asyncio
import time

# Simulated async database clients
async def fetch_from_vector_db(query: str) -> dict:
    await asyncio.sleep(1.2)  # Simulate network latency
    return {"source": "vector_db", "text": "Company Q3 revenue grew by 15%.", "score": 0.92}

async def fetch_from_web_search(query: str) -> dict:
    await asyncio.sleep(0.8)  # Simulate API latency
    return {"source": "web", "text": "Recent news shows a 15% bump in Q3.", "score": 0.88}

async def fetch_from_internal_wiki(query: str) -> dict:
    await asyncio.sleep(1.0)  # Simulate database latency
    return {"source": "wiki", "text": "Internal targets for Q3 were exceeded.", "score": 0.75}

async def high_throughput_retrieval(query: str) -> list[dict]:
    print(f"Starting concurrent retrieval for: '{query}'...")
    start_time = time.time()
    
    # Schedule all I/O bound tasks to run concurrently
    tasks = [
        fetch_from_vector_db(query),
        fetch_from_web_search(query),
        fetch_from_internal_wiki(query)
    ]
    
    # await asyncio.gather executes them in parallel and waits for all to finish
    results = await asyncio.gather(*tasks)
    
    print(f"Retrieval completed in {time.time() - start_time:.2f} seconds.")
    return results

# To run the async function in a standard Python script:
# results = asyncio.run(high_throughput_retrieval("Q3 revenue"))
```

### Basics

**Coroutines:** Functions defined with `async def`. They don't run immediately when called; they return a coroutine object that needs to be scheduled to run.

**The Event Loop:** The "manager" that schedules and runs your asynchronous tasks.

**Await:** The keyword used to pause a coroutine until the awaited task is finished, yielding control back to the event loop.

```python
import asyncio

async def say_hello():
    print("Starting...")
    await asyncio.sleep(1) # Simulates an I/O operation
    print("...Hello!")

# The entry point to run the top-level coroutine
asyncio.run(say_hello())
```

We can also run multiple tasks at the same time. 

```python
import asyncio

async def fetch_data(id, delay):
    await asyncio.sleep(delay)
    return f"Data {id}"

async def main():

    # Schedule multiple tasks simultaneously
    results = await asyncio.gather(
        fetch_data(1, 3),
        fetch_data(2, 1),
        fetch_data(3, 2)
    )

asyncio.run(main())
```

The results will be returned in the finish first order. The operation to finish first's will have the result. Usually result is a list of outputs. 

Notes - 

- Calling the `asyncio.run()` stops the current run untill inside function does not stops.
- `asyncio.fetch()` is strictly await reason being it is strcitly scheduled using event loop. 

### Details - 

- `Asyncio.run()` creates the event loop. Without this call event loop does not  exists. It takes one top-level function (usually called `main()`) and runs it until it finishes. Once that main function is done, `run()` shuts down the loop, closes any remaining "background" connections. 
- `gather` call on the other hand is used to run and orchestrate multiple tasks. It will run all the background tasks and wait for the results. 
- await - It is used to handle the async tasks in the event loop. Once statement prefixed with await is reached the call is scheduled in the event loop. However event loop will not pause the evecution entirely. Although the current function will stop event loop can schedule some other tasks in the mean time. 

## Pydrantic

Pydantic is the most widely used data validation library for Python. Instead of writing custom error-checking code to ensure your data is in the correct format, Pydantic allows you to use standard Python type hints to define how your data should look.

### Core - BaseModel

At the heart of Pydantic is the `BaseModel` class.To create a data schema, you simply create a new class that inherits from `BaseModel` and define your fields as class attributes with type hints.

When you create an instance of this model, Pydantic automatically validates the data you pass in against the types you defined.

Example - 

```python
from pydantic import BaseModel

class User(BaseModel):
    id: int
    username: str
    email: str

# Creating an instance with valid data
user = User(id=1, username="johndoe", email="john@example.com")

print(user.model_dump())
# Output: {'id': 1, 'username': 'johndoe', 'email': 'john@example.com'}
```

A crucial concept to understand is that Pydantic is primarily a **parsing** library, not just a validation library. This means Pydantic guarantees the types and constraints of the output model, not necessarily the input data.

If you pass data of the wrong type, Pydantic will attempt to convert (coerce) it into the correct type before throwing an error.

```python
from pydantic import BaseModel

class Product(BaseModel):
    id: int
    price: float
    in_stock: bool

# Notice the input types: string, integer, and string
# Pydantic will convert these to int, float, and bool respectively.
item = Product(id="123", price=19, in_stock="yes")

print(item.id)       # Output: 123 (converted from string to int)
print(item.price)    # Output: 19.0 (converted from int to float)
print(item.in_stock) # Output: True (converted from "yes" to bool)
```


Pydantic determines whether a field is required or optional entirely based on whether you provide a **default value**.

If you define a type hint without a default value, Pydantic treats that field as required. If the field is missing when the model is instantiated, a `ValidationError` is raised.

```python
class Profile(BaseModel):
    name: str  # Required! No default value is provided.
    age: int = 25 # default provided optional
```

We can also provide the Null using following syntax. 

```python
class Profile(BaseModel):
    name: str
    bio: str | None = None
```

### Fields

While basic type hints are great, they have limits. You can't use a standard type hint to say "this integer must be greater than 10" or "this list must have at least 3 items." This is where the `Field` function comes in.

It allows you to configure specific validation rules, default behaviors, and metadata for a single attribute.

Common `Field` Arguments:
 - **Constraints:** `gt` (greater than), `ge` (greater than or equal to), `lt`, `le`, `min_length`, `max_length`.
- **Default Factories:** `default_factory` is a function called to generate a default value dynamically (crucial for things like generating UUIDs or current timestamps).
- **Metadata:** `description`, `title`, or `examples` (useful if you are generating OpenAPI documentation from your models).

example

```python
from pydantic import BaseModel, Field
from datetime import datetime
import uuid

class Product(BaseModel):
    # Dynamically generate a unique ID if none is provided
    id: str = Field(default_factory=lambda: str(uuid.uuid4()))
    
    # Must be at least 3 characters, max 50
    name: str = Field(min_length=3, max_length=50, description="The product's display name")
    
    # Price must be strictly greater than 0
    price: float = Field(gt=0.0)
    
    # Sets the exact time the model was created
    created_at: datetime = Field(default_factory=datetime.now)

# Validation in action
valid_product = Product(name="Wireless Mouse", price=29.99)
print(valid_product.id) # Output: e.g., 'a3b5c...'
```

Real-world JSON data is rarely flat; it is usually nested. Because Pydantic models are just Python classes, you can use one `BaseModel` as a type hint inside another. Pydantic will automatically traverse the nested dictionaries and validate the entire tree.

```python
from pydantic import BaseModel

# 1. Define the "child" model first
class Address(BaseModel):
    street: str
    city: str
    zip_code: str = Field(min_length=5, max_length=10)

# 2. Use it as a type hint in the "parent" model
class User(BaseModel):
    id: int
    username: str
    # A single user has one address
    shipping_address: Address 
    # A list of nested models is also perfectly fine
    billing_addresses: list[Address] = [] 

# Input data as a nested dictionary
raw_data = {
    "id": 101,
    "username": "tech_guru",
    "shipping_address": {
        "street": "123 Main St",
        "city": "Seattle",
        "zip_code": "98101"
    }
}

# Pydantic recursively parses the dictionary into objects
user = User(**raw_data)
print(user.shipping_address.city)  # Output: Seattle
```

Once your data is safely validated inside a Pydantic object, you usually need to send it somewhere else (like an API response or a database). This requires converting the objects back into standard formats, a process called **serialization**.

```python
model_dump() # convert to standard python dictionary
model_dump_json() # convert the data to the json data
```

Both functions are part of model object and can accept the arguments - 

- exclude
- include

```python
class Account(BaseModel):
    id: int
    password_hash: str
    is_active: bool = True

account = Account(id=1, password_hash="hashed_abc123")

# Basic dictionary export
print(account.model_dump()) 
# {'id': 1, 'password_hash': 'hashed_abc123', 'is_active': True}

# JSON string export, securely hiding the password hash
print(account.model_dump_json(exclude={'password_hash'}))
# {"id":1,"is_active":true}
```


### Custom validators

When type hints and `Field` constraints aren't enough, you write custom Python logic to validate the data.

`@field_validator` (Validating a single field)
Use this to check or format the data of a single attribute.


```python
from pydantic import BaseModel, field_validator
import re

class UserSignUp(BaseModel):
    username: str
    password: str

    @field_validator('password')
    @classmethod
    def password_must_contain_symbol(cls, value: str) -> str:
        # Check for at least one special character
        if not re.search(r'[!@#$%^&*(),.?":{}|<>]', value):
            raise ValueError('Password must contain at least one special symbol')
        return value
```

Sometimes validation needs to check multiple fields at once. 

```python
from pydantic import BaseModel, model_validator

class PasswordChange(BaseModel):
    new_password: str
    confirm_password: str

    @model_validator(mode='after')
    def check_passwords_match(self) -> 'PasswordChange':
        # 'self' is the fully parsed model instance here
        if self.new_password != self.confirm_password:
            raise ValueError('Passwords do not match')
        return self
```


**Note:** Always return the value (in `field_validator`) or self (in model_validator(mode='after')) at the end of your custom validator functions, otherwise Pydantic will overwrite the field with `None`
